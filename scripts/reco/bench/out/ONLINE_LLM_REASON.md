# 온라인 LLM 사유 생성 — 실측 기록 (2026-08-31)

환경: M4 Pro 24GB (GPU 가용 16GB) · `gemma4:12b-it-qat` · ollama 0.33.0
모델 VRAM 7.64GB · context 4096 · Apache 2.0

| 항목 | 실측 | 스크립트 |
|---|---|---|
| 생성 처리량 | **27.0 tok/s** | `gemma4_korean_probe.py` |
| 프리필 처리량 | **136.8 tok/s** | 〃 |

## 🔴 동시 처리량 상한 — 이것이 결정적이다

| 동시 | p50 | p95 | 처리량 |
|---|---|---|---|
| 1 | 2.05s | 1.17s | 0.68 req/s |
| 2 | 3.32s | 4.14s | 0.70 req/s |
| 4 | 5.95s | 10.06s | 0.71 req/s |
| 8 | 10.85s | 19.52s | **0.75 req/s** |

**동시성을 8배로 올려도 처리량이 0.68→0.75 로 평평하다.** 지연만 5.3배 늘어난다.

설정 결함이 아님을 확인했다 — `OLLAMA_NUM_PARALLEL=4` + flash attention + KV q8_0 로
재측정해도 처리량 0.72 로 동일했고, 단건 지연은 2.05→4.72s 로 **오히려 나빠졌다**
(병렬 슬롯이 KV 캐시를 쪼개고 VRAM 이 7.64→8.72GB 로 증가). **GPU 포화다.**

## 환각

금칙어(건강·영양·제철·인기 등) 기준 **0/10**. 그러나 금칙어로 안 잡히는 것이 있다:

- 🔴 **인과 날조**: "김치 소비기한이 3일 남았으**므로** 보유 재료로 바로 조리할 수 있어요"
  — 두 사실 사이에 없는 인과를 만든다. 템플릿의 `~고`(중립 접속)는 이 오류가 불가능하다.
- 🔴 **문체 이탈**: "당면 1개를 추가해 잡채를 만드**세요**" — 사유가 명령문으로 변질.

## 대안 (f) "템플릿이 사실 확정 + LLM 은 문장만 다듬기" 검증

`reason_polish.py` — 실제 `build_reason()` 출력을 다듬게 하고 슬롯값을 기계 검증.

```
사실 보존 10/10   p50 1.67s   p95 2.06s
```

**그러나 검증기가 못 잡는 오류가 나왔다:**

```
"많이 만드는 레시피예요"  →  "양이 많은 레시피예요"     # 인기도 → 분량. 의미 반전
```

슬롯이 없는 템플릿이라 검증할 값이 없다. 집중 측정 (`reason_polish_slotless.py`):

| 템플릿 | 변경 |
|---|---|
| `f_coverage` | 5/5 (경어체 변경, 무해) |
| `f_popularity` | 4/5 — `자주 만드는`(개선) / 앞선 시행에서 `양이 많은`(**반전**) |
| `f_season` | 5/5 (`딱 제철`, 무해) |
| `f_quality` | **0/5** (유일하게 불변) |
| `f_skill_fit` | 5/5 (무해) |
| `f_content` | 5/5 (`결이` 탈락, 경미) |

**슬롯 없는 문구의 80% 가 재작성된다.** 대부분 무해하거나 개선이지만,
의미를 뒤집는 변형이 같은 확률 공간에 있고 **기계적으로 구분할 수 없다.**

### 🔑 여기서 나오는 구조적 결론

슬롯 없는 문구를 **원문 그대로 포함하도록 강제**하면 검증이 완전해진다.
그러나 그러면 LLM 이 바꿀 것이 없어져 다듬는 의미가 사라진다.

> **이득과 위험이 같은 행위(재작성)에서 나온다.**
> 안전할 만큼 조이면 무의미해지고, 유용할 만큼 풀면 검증이 뚫린다.

## 캐시로 구제되는가 — 키 공간 실측 (`reason_cache_space.py`)

파이프라인의 실제 `top_reasons()` 로 요청 400 × 후보 500 → 노출 4,000건 시뮬.

> ⚠️ 1차 시뮬은 레시피를 4.4만에서 **균등추출**해 히트율 0% 가 나왔다 — 겹칠 수가 없으니
> 당연한 결과였고 시뮬 결함이다. 실제 Retrieval 은 냉장고 재료로 거르고 한국 가정의
> 재료는 크게 겹치므로 노출이 편중된다. **Zipf(a=1.0) · 풀 20,000** 으로 고쳐 재측정했다.

| 키 설계 | 고유 키 | 결과 |
|---|---|---|
| A. 피처조합만 | **80개** | 작다. 그러나 슬롯값이 빠져 단독 키로 못 쓴다 |
| B. (레시피 × 피처조합) | 3,130 / 4,000 | **히트율 상한 21.8%** |

노출 집중도: 고유 레시피 1,709개, **상위 100개가 노출의 50.2%**.

**21.8% 는 낙관적 상한이다.** 슬롯값(유저별 소비기한 재료명·D-N·선호재료)을 키에 넣으면
더 내려가고, D-N 은 매일 바뀌므로 TTL 이 24시간을 못 넘는다.

> **결론: 캐시는 0.7 req/s 를 0.9 req/s 로 올릴 뿐이다.** 필요한 배수와 자릿수가 다르다.

다만 **상위 100개가 노출 절반**이라는 사실은 다른 쓸모가 있다 —
유저 비의존 피처조합(`f_coverage`+`f_popularity`, `f_time_fit`, `f_quality`, `f_season`)에
한해 **오프라인 사전생성**이 가능하다. 유저별 값(`f_expiring` 재료명)이 낀 조합은 불가.

## 🔴 처리량 판단 정정 — 병목은 처리량이 아니라 **지연**이다

초기에 "유저 100명이면 16.7 사유/s 가 필요한데 0.7 뿐이라 24배 부족"이라고 적었다.
**이 계산은 틀렸다.** 유저가 분당 1회 요청한다고 가정했는데, 레시피 앱에서 비현실적이다.

### 사유 1건당 토큰 (n=8 실측)

| | 평균 | 범위 |
|---|---|---|
| 입력(프리필) | **104 tok** | 100~106 |
| 출력(생성) | **25 tok** | 20~30 |

### 현실적 사용량으로 재계산

| 시나리오 | 사유/일 | 필요 req/s (피크 5배) | 로컬 0.7 대비 |
|---|---|---|---|
| 유저 100 · 3회/일 | 3,000 | **0.17** | ✅ 여유 4배 |
| 유저 100 · 10회/일 | 10,000 | **0.58** | 🟡 빠듯 |
| 유저 1,000 · 3회/일 | 30,000 | 1.74 | ❌ 2.5배 부족 |
| 유저 10,000 · 3회/일 | 300,000 | 17.4 | ❌ 25배 부족 |

**유저 100명 규모에서는 로컬 GPU 처리량이 충분하다.** 캐시(21.8%)도 필요 없다.

### 그러면 진짜 병목은?

**지연이다.** 사유 10건 배치 = **8.2초**. 온라인 목표 p95 **300ms** 대비 **27배 초과**.
처리량은 남는데 한 요청을 끝내는 데 걸리는 시간이 예산을 넘는다.

> 따라서 설계 과제는 "GPU 를 늘리는 것"이 아니라
> **"8.2초를 응답 경로 밖으로 빼내는 것"** 이다.

## 더 작은 모델로 300ms 에 들어갈 수 있는가 — 물리 한계

사유 1건 = 25 tok. 300ms 안에 내려면 **83 tok/s**, 10건이면 **833 tok/s** 가 필요하다.

| 모델 | 크기 | 생성 | p50 (1건) | 10건 소요 |
|---|---|---|---|---|
| Gemma 4 **E2B** QAT | 4.3GB | **90.9 tok/s** | 0.45s | **2.8s** |
| Gemma 4 **12B** QAT | 6.66GB | 27.0 tok/s | 1.65s | 9.3s |

E2B 가 3.4배 빠르다. **그래도 1건조차 300ms 를 1.5배 넘고, 10건은 2.8초다.**

### 🔴 그리고 E2B 는 우리가 필요한 성질을 정확히 내준다

| 입력 사실 | 12B 출력 | E2B 출력 |
|---|---|---|
| 김치 소비기한 D-3 | "김치 소비기한이 **3일 남았습니다**" | "소비기한이 **임박하여 신선하게** 즐기실 수 있습니다" |
| 많이 만드는 레시피 | "많이 만드는 레시피입니다" | "**대량 조리가 편리합니다**" |

- **숫자 소실**: `D-3` 이 "임박"으로 뭉개진다 → 슬롯값 검증 실패
- **자기모순**: "소비기한 임박"인데 "신선하게"
- **의미 반전 재발**: `많이 만드는`(인기) → `대량 조리`(분량). 12B 에서도 나온 그 오류다

> **속도를 얻는 대가로 사실 충실도를 잃는다.** 작은 모델은 해법이 아니다.

### 결론 — 하드 바운드

**어떤 로컬 모델도 사유 10건을 300ms 에 못 낸다.** 833 tok/s 는 단일 스트림 생성으로
도달 불가능한 수치다. 따라서 선택지는 셋뿐이다:

1. 응답 경로 밖으로 뺀다 (비동기 2단계 / 사전생성)
2. 온라인 예산을 올린다 (1-4 절대원칙과 충돌)
3. 하지 않는다

## 모델 로드 시간 — 상주 vs 배치 창에만 올리기 (2026-08-31)

```
콜드(언로드 직후)  총 6.04s   그중 모델 로드 5.46s
웜(연속)          총 0.44s   그중 모델 로드 0.00s
```

**5.46초는 30분 배치에서 0.3% 다.** 트랙1 배치는 시작할 때 한 번 올리고 끝나면 내리면 된다.

> **결론: LLM 을 상시 상주시킬 이유가 없다.**
> 온라인 경로는 LLM 을 쓰지 않으므로(트랙2 = 템플릿), 7.64GB 는 **평시 RAM 이 아니라
> 새벽 배치 창의 피크**다. 다만 신청값은 피크로 잡아야 한다.
>
> 🔴 **ko-SBERT(torch) 배치와 겹치면 피크가 합산된다.** cron 에서 순서를 갈라야 한다.

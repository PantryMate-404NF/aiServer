# 클라우드에 데이터베이스 세우기

**무엇을 다루는가**: 빈 PostgreSQL 에 이 서비스가 쓸 구조와 사전을 넣는 절차

**적용 대상**: 클라우드 인프라를 맡은 인원

**버전**: 1.0.0 · **최종 수정**: 2026-09-18 · **작성자**: 파트 A (데이터)

---

## 1. 먼저 알아 둘 것

앱 컨테이너 안에는 **데이터베이스를 채우는 도구가 없습니다.** 이미지는 서빙만 합니다. 아래 절차는 저장소를 클론한 곳(개발 머신 또는 배포 잡)에서 돌립니다.

데이터베이스는 세 겹으로 채워집니다.

```text
① 구조     테이블·인덱스·함수          아래 2절
② 사전     재료 696종 · 별칭 671개      아래 3절
③ 레시피   46,353건                    아래 5절. 별도 협의가 필요합니다
```

①②까지만 해도 **서비스는 뜹니다.** 다만 추천할 레시피가 없습니다.

---

## 2. 구조 만들기

### 준비물

| | |
|---|---|
| PostgreSQL | **16 이상** |
| 확장 | `vector` · `intarray` · `pg_trgm` · `ltree` |
| 권한 | 대상 데이터베이스에 스키마·확장을 만들 수 있을 것 |

확장 넷은 DB 관리자가 미리 설치해야 할 수 있습니다. 관리형 서비스(RDS·Cloud SQL)는 대개 목록에서 켜는 방식입니다. 하나라도 없으면 스크립트가 **그 이름을 찍고 멈춥니다.**

### 실행

```bash
./deploy/apply_schema.sh "postgresql://사용자:비밀번호@호스트:5432/디비이름"
```

자동화(CI·배포 잡)에서는 확인 질문을 건너뜁니다.

```bash
ASSUME_YES=1 ./deploy/apply_schema.sh "$DATABASE_URL"
```

로컬에 `psql` 이 없어도 됩니다. 스크립트가 일회용 컨테이너로 실행합니다.

### 무엇이 만들어지나

```text
01_extensions.sql   확장 4종 · 스키마 reco · 시간대 Asia/Seoul
02_schema.sql       테이블 29개
03_indexes.sql      인덱스
04_functions.sql    조회 함수 6개
```

**데이터베이스 이름은 무엇이든 됩니다.** 스크립트가 접속한 데이터베이스를 그대로 씁니다.

### 일부러 빼는 것 둘

**`00_databases.sql`** — 데이터베이스를 만드는 권한이 없을 수 있어 뺍니다. MLflow 용 데이터베이스가 따로 필요하면 관리자에게 요청하십시오. 안 하면 MLflow 가 테이블 15개를 우리 스키마에 만듭니다.

**`05_roles.sql`** — 계정과 비밀번호는 클라우드 정책에 맞춰 관리자가 만듭니다.

### 시간대가 왜 중요한가

`01_extensions.sql` 이 데이터베이스 수준으로 한국 시간을 박습니다. **컨테이너 환경변수만으로는 부족합니다** — 그건 컨테이너 안에서만 유효하고, 밖에서 붙는 연결에는 적용되지 않습니다.

UTC 로 돌면 자정부터 오전 9시 사이에 **"오늘"이 하루 어긋나서** 소비기한 임박 판정이 틀립니다. 에러는 나지 않습니다.

## 3. 사전 넣기

```bash
DATABASE_URL="postgresql://..." make seed
```

재료 696종 · 다른 이름 671개 · 분류 66종 · 단위 환산표가 들어갑니다. **여러 번 돌려도 같은 결과**입니다.

넣기 전에 사전이 성한지 스스로 검사합니다. 깨져 있으면 거기서 멈춥니다.

---

## 4. 확인

```bash
psql "$DATABASE_URL" -c "
  SELECT count(*) FROM reco.ingredient;          -- 696
  SELECT count(*) FROM reco.ingredient_alias;    -- 671
  SELECT current_setting('TimeZone');            -- Asia/Seoul
"
```

앱 컨테이너를 띄우면 `/health` 가 데이터베이스 접속 상태를 알려 줍니다.

## 5. 레시피 데이터 — 별도 협의

여기까지 하면 **구조와 사전은 완성이지만 레시피가 0건**입니다. 추천 API 는 뜨지만 돌려줄 것이 없습니다.

레시피 46,353건은 저장소에 없습니다. 원본 파일이 219MB 라 GitHub 한도를 넘고, **후기 작성자 닉네임이 그대로 들어 있어** 공개 저장소에 올릴 수 없습니다.

옮기는 방법은 둘입니다.

| 방법 | 내용 | 비고 |
|---|---|---|
| 복사본 전달 | 데이터베이스 사본을 떠서 넘김 | 가장 빠릅니다 |
| 원본에서 다시 생성 | 크롤 원본을 받아 배치를 돌림 | 약 15분. 원본 전달 협의 필요 |

**어느 쪽이든 데이터 파트와 먼저 이야기해 주십시오.** 특히 원본에서 다시 만드는 경우, 후기 작성자 식별값을 만드는 열쇠가 바뀌면 **기존 데이터와 어긋나고 되돌릴 수 없습니다.**

---

### 열쇠 하나는 절대 새로 만들지 마십시오

후기 작성자를 식별하는 값(`REVIEW_SALT`)이 있습니다. 닉네임을 그대로 저장하지 않고
이 값으로 섞어서 넣기 때문에, **값이 바뀌면 기존 624,422건과 전혀 다른 결과가 나옵니다.**

없다고 새로 만들면 안 됩니다. 데이터 파트에 요청하십시오. 한 번 어긋나면 되돌릴 수
없습니다.

이 값은 **앱 컨테이너에 넣지 않습니다.** 레시피를 넣을 때만 쓰는 값이고, 서빙에는
필요 없습니다.

---

## 6. 컨테이너 테스트만 할 경우

배포·확장·헬스체크만 보시려면 **2절과 3절까지만 하면 됩니다.**

추천 API 는 현재 목업 응답을 돌려줍니다. 데이터베이스가 비어 있어도 200 을 반환하므로, **그 200 을 추천 엔진이 정상 동작하는 근거로 읽지 마십시오.** 실제 엔진 연결은 추천 코어 파트의 남은 작업입니다.

---

## 7. 막혔을 때

| 증상 | 원인 |
|---|---|
| 확장 이름을 찍고 멈춤 | 확장이 설치돼 있지 않음. 관리자에게 요청 |
| 스크립트가 입력을 기다림 | 자동화면 `ASSUME_YES=1` 을 붙이십시오 |
| 사전 넣기가 멈춤 | 사전 파일이 깨진 것. 메시지에 어느 줄인지 나옵니다 |
| 추천이 빈 목록 | 레시피가 0건. 5절 참조 |
| 날짜가 하루 어긋남 | 시간대가 안 붙은 것. 4절로 확인 |

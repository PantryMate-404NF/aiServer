# 01 · DEVELOPMENT_RULES

**정하는 것**: 일하는 방식. 브랜치, 커밋, 검증, 리뷰, PR, 테스트, 배포.

**적용 대상**: 이 저장소에 커밋하는 모든 인원 및 AI 코딩 에이전트

**버전**: 1.0.0 · **최종 수정**: 2026-09-04 · **작성자**: 김민경

---

## 0. 규범 용어

| 용어 | 의미 | 위반 시 |
|---|---|---|
| **MUST / MUST NOT** | 절대적 요구·금지 | 3.2의 검증 명령 또는 리뷰어가 차단합니다. 병합 불가 |
| **SHOULD** | 강력 권고 | 이탈하려면 PR 본문에 사유를 씁니다. 사유 없이는 승인하지 않습니다 |
| **MAY** | 선택 | 리뷰에서 논쟁하지 않습니다 |

검증되지 않은 정량 기준에는 `(예시값, 실제 데이터로 대체 필요)` 를 붙입니다. 2개 스프린트 뒤 8절의 실측 데이터로 재산정합니다.

## 1. 팀 표준화 원칙

3인 팀에서 규칙이 무너지는 지점은 언제나 같습니다. **아무도 확인하지 않는 규칙**입니다.

| 원칙 | 내용 |
|---|---|
| A. 도구는 범주당 하나 | 같은 일을 하는 도구를 둘 이상 두지 않습니다. 도구 논쟁이 가장 비싼 커뮤니케이션 비용입니다 |
| B. 검증 명령은 하나 | 팀원 전원이 3.2의 같은 명령을 실행하고, 판정 기준은 `pyproject.toml` 하나에서 나옵니다 |
| C. 규칙에는 확인 방법이 따라붙습니다 | 누가 언제 무엇으로 확인하는지 없는 규칙은 채택하지 않습니다(MUST NOT) |
| D. 위반은 경고가 아니라 실패 | linter의 warning 등급을 쓰지 않습니다. 통과 아니면 실패입니다 |

### 표준 도구

| 범주 | 표준 | 금지 대안 | 확인 지점 |
|---|---|---|---|
| 패키지·가상환경 | `uv` | `pip`, `poetry`, `conda`, 수동 `venv` | `uv sync --frozen` |
| Lint · Format | `ruff` | `flake8`, `black`, `isort`, `pylint` | 3.2 |
| 타입 검사 | `mypy` | `pyright`, `pyre` | 3.2 |
| 테스트 · 커버리지 | `pytest` + `pytest-cov` | `unittest` 직접 실행 | 3.2 |

신규 도구 도입은 Tech Lead 승인과 이 표의 갱신을 동반해야 합니다(MUST).

## 2. Git

### 2.1 브랜치 — 간소화 Trunk-based

3인 팀에서 Git-flow의 `develop`·`release` 계층은 병합 비용이 격리 이득을 넘습니다. **단일 트렁크 + 단기 작업 브랜치**만 씁니다.

1. `main` 은 보호 브랜치입니다. 직접 push와 force push를 금지합니다(MUST NOT).
2. `main` 은 항상 배포 가능한 상태를 유지합니다(MUST). 3.2가 실패하는 커밋이 `main` 에 있어서는 안 됩니다(MUST NOT).
3. 작업 브랜치 수명은 최대 3영업일입니다(예시값, 실제 데이터로 대체 필요). 초과가 예상되면 작업을 분할합니다(MUST).
4. 작업 브랜치는 `main` 에서 분기하고 `main` 으로만 병합합니다(MUST). 브랜치 간 상호 병합을 금지합니다(MUST NOT).
5. `main` 을 따라잡을 때는 rebase를 씁니다(SHOULD). **타인이 이미 체크아웃한 브랜치는 rebase하지 않습니다**(MUST NOT).
6. 병합된 브랜치는 즉시 삭제합니다(MUST).

**브랜치 이름**

```regex
^(feat|fix|refactor|perf|test|docs|chore|hotfix)\/[a-z0-9]+(-[a-z0-9]+)*$
```

| 통과 | `feat/receipt-ocr-pipeline`, `fix/date-parsing`, `hotfix/db-pool-leak` |
|---|---|
| **차단** | `feature/OCR`, `김민수-작업`, `feat_receipt`, `fix/Bug#12` |

영문 소문자·숫자·하이픈만 허용합니다(MUST). 원격 저장소의 브랜치 이름 규칙에 위 정규식을 등록합니다(MUST).

### 2.2 커밋 메시지

**언어** — 헤더는 영어로 씁니다(MUST). 정규식이 `[a-z]` 로 시작을 강제하므로 한국어 헤더는 차단됩니다. body와 footer는 한국어를 허용합니다(MAY).

```regex
^(build|chore|ci|docs|feat|fix|perf|refactor|revert|test)(\([a-z0-9._-]+\))?(!)?: [a-z].{0,59}[^.\s]$
```

```text
<type>(<scope>)<!>: <subject>

<body — 왜 그렇게 했는지. 무엇을 했는지는 diff가 말합니다>

<footer — Closes #12 / BREAKING CHANGE: ...>
```

| type | 사용 조건 |
|---|---|
| `feat` | 사용자가 체감하는 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 외부 동작 변경 없는 구조 변경 |
| `perf` | 외부 동작 변경 없는 성능 개선 |
| `test` | 테스트 코드 |
| `docs` | 문서만 |
| `build` | 의존성·패키징·`pyproject.toml` |
| `ci` | CI 설정 |
| `chore` | 위 어디에도 속하지 않는 잡무 |
| `revert` | 이전 커밋 되돌리기 |

- subject는 소문자로 시작하는 명령형 현재시제이며 마침표로 끝내지 않습니다(MUST).
- `!` 는 하위 호환을 깨는 변경에만 붙이고, footer에 `BREAKING CHANGE:` 를 씁니다(MUST).
- 의존성을 바꾼 `build` 커밋의 body에는 **추가 사유 한 줄이 필수**입니다(MUST).

```text
feat(receipt): add confidence threshold to ocr line filter

프린터 기종에 따라 인식 신뢰도 분포가 달라 고정 임계값으로는
저품질 영수증에서 누락이 발생했다. 임계값을 config로 분리해
재튜닝 시 코드 수정이 필요 없게 했다.

Closes #42
```

### 2.3 커밋 단위

1. **1 커밋 = 1 논리적 변경**입니다(MUST). 리팩터링과 기능 추가를 섞지 않습니다(MUST NOT).
2. `git revert` 1회로 복구되지 않으면 커밋이 과도합니다. 분할합니다(MUST).
3. 3.2가 통과하지 않는 상태로 PR을 생성하지 않습니다(MUST NOT).
4. 구조 변경 PR과 기능 구현 PR을 분리합니다(MUST). 구조 변경을 먼저 병합한 뒤 기능에 착수합니다.

### 2.4 커밋 금지 대상

작성자가 PR 생성 전에, 리뷰어가 승인 전에 확인합니다(MUST).

| 대상 | 이유 |
|---|---|
| `.env`, API 키, 토큰, 인증서 | 유출 시 복구 불가 |
| 모델 가중치, 데이터 산출물, 빌드 결과물 | 용량 과다, 재생성 가능 |
| 개인정보가 포함된 샘플 데이터 | 개인정보보호법 위반 소지 |
| 에디터·OS 설정 파일 | 개인 환경은 전역 gitignore로 처리 |
| 주석 처리된 코드 블록 | 히스토리에 이미 있습니다 |

**비밀값이 커밋됐다면** 자격증명을 **즉시 폐기하고 재발급합니다**(MUST). 히스토리 정리보다 이것이 먼저입니다. 클론된 사본에 값이 남으므로 커밋 제거만으로 유출은 취소되지 않습니다. 팀 채널에 폐기 완료 시각을 공유하고, 재발 방지 조치를 `docs/decisions/` 에 남깁니다(MUST).

### 2.5 병합

- `main` 으로는 **Squash merge만** 허용합니다(MUST). PR 제목이 커밋 메시지가 되므로 **PR 제목도 2.2의 정규식을 만족해야 합니다**(MUST).
- 병합은 **작성자가 직접** 수행합니다(MUST). 작성자만 아는 후속 조치가 있습니다.

## 3. 코드 스타일과 검증

### 3.1 설정 단일화

모든 도구 설정은 `pyproject.toml` 하나에 둡니다(MUST). `.flake8`, `setup.cfg`, `mypy.ini`, `pytest.ini` 를 만들지 않습니다(MUST NOT).

```toml
[tool.ruff]
target-version = "py312"
line-length = 100                  # (예시값, 실제 데이터로 대체 필요)
src = ["src", "tests"]

[tool.ruff.lint]
select = ["E", "W", "F", "I", "N", "UP", "B", "S", "T20", "ANN", "RUF"]

[tool.ruff.lint.per-file-ignores]
"tests/**" = ["S101"]

[tool.ruff.lint.flake8-tidy-imports]
ban-relative-imports = "all"

[tool.mypy]
python_version = "3.12"
strict = true
disallow_untyped_defs = true

[tool.pytest.ini_options]
addopts = "-q --strict-markers --cov=src --cov-report=term-missing --cov-fail-under=80"
testpaths = ["tests"]
```

### 3.2 검증 명령과 통과 기준

PR 생성 전에 로컬에서 실행합니다(MUST). 하나라도 실패한 상태로 PR을 생성하지 않습니다(MUST NOT).

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy src && uv run pytest tests/unit
```

| # | 통과 조건 | 검증 수단 |
|---|---|---|
| 1 | Lint 위반 0건 | `uv run ruff check .` |
| 2 | 포맷 미적용 0건 | `uv run ruff format --check .` |
| 3 | 타입 오류 0건 | `uv run mypy src` |
| 4 | 단위 테스트 실패 0건 | `uv run pytest tests/unit` |
| 5 | 라인 커버리지 80% 이상 (예시값, 실제 데이터로 대체 필요) | `--cov-fail-under=80` |
| 6 | `uv.lock` 과 `pyproject.toml` 일치 | `uv sync --frozen` |
| 7 | PR 변경 300라인 이하 (예시값, 실제 데이터로 대체 필요) | 5.1 |
| 8 | 비밀값·개인정보 미포함 | 2.4 |

**책임 소재.** 판정은 도구가 하되 **실행과 확인의 책임은 작성자에게** 있습니다(MUST). PR 본문에 통과 출력을 첨부합니다(MUST). **리뷰어는 통과 출력이 없는 PR을 승인하지 않습니다**(MUST NOT).

### 3.3 린트 예외

`# noqa`, `# type: ignore` 는 아래 셋을 모두 충족할 때만 허용합니다(MUST).

1. 규칙 코드를 명시합니다. `# noqa` 단독 사용을 금지합니다(MUST NOT).
2. 같은 줄에 사유를 씁니다. `# noqa: S608  # 정적 문자열만 사용, 사용자 입력 없음`
3. PR 본문에 사유를 쓰고 Tech Lead를 태그해 승인받습니다. 승인 코멘트가 없으면 병합할 수 없습니다(MUST NOT).

전역 ignore 추가는 Tech Lead 승인과 3.1의 갱신을 동반합니다(MUST).

## 4. AI 생성 코드

**AI가 생성한 코드는 PR 생성 전에 작성자가 한 줄씩 읽고 검증해야 합니다**(MUST). 커밋 시점부터 책임 주체는 AI가 아니라 커밋한 사람입니다. 리뷰에서 "AI가 만든 부분이라 모른다"는 답변을 허용하지 않습니다(MUST NOT).

**검증 항목**

- 존재하지 않는 라이브러리·함수·인자를 쓰지 않았는가
- `02_DIRECTORY_STRUCTURE.md` 의 배치와 의존 방향을 지켰는가
- 예외를 삼키는 코드가 없는가
- 하드코딩된 URL·경로·자격증명·매직 넘버가 없는가
- 요청하지 않은 추상화·설정 옵션·미사용 코드가 없는가

**표기** — 생성 코드가 변경분의 30% 이상이면(예시값, 실제 데이터로 대체 필요) 커밋 footer에 `Assisted-by: <도구명>` 을 남기고 PR 본문에 사용 범위를 씁니다(MUST). 리뷰어가 환각 위험 구간에 집중하기 위한 것이며 AI 사용을 제한하려는 조항이 아닙니다.

**금지** — 검증 없이 대량 생성된 코드의 단일 커밋 포함, API 키·고객 데이터를 외부 AI 프롬프트에 입력, 검증하지 않은 생성 테스트로 커버리지 채우기(MUST NOT).

## 5. 코드 리뷰와 PR

### 5.1 정량 기준

| 항목 | 기준값 |
|---|---|
| PR 변경 라인 수 상한 | 300라인 (예시값, 실제 데이터로 대체 필요) |
| 최소 승인자 수 | 1명 (예시값, 실제 데이터로 대체 필요) |
| 리뷰 첫 응답 SLA | 24시간 이내, 영업일 기준 (예시값, 실제 데이터로 대체 필요) |
| PR 최대 수명 | 5영업일 (예시값, 실제 데이터로 대체 필요) |

- 라인 수는 `추가 + 삭제` 이며 `uv.lock` 은 제외합니다. 그 밖에 자동 생성된 파일을 제외하려면 PR 본문에 무엇을 왜 제외했는지 씁니다(MUST).
- 상한 초과가 불가피하면 PR 본문 최상단에 분할 불가 사유를 쓰고 **Tech Lead의 사전 승인**을 받습니다(MUST). 사후 승인은 인정하지 않습니다(MUST NOT).
- SLA 초과 시 작성자가 팀 채널에 리마인드를 게시합니다(MUST).
- 최대 수명 초과 시 분할하거나 폐기합니다(MUST). 장기 미병합 PR은 충돌 비용만 쌓습니다.

### 5.2 작성자 확인 (PR 생성 전)

- [ ] diff 전체 통독
- [ ] 3.2 검증 명령 실행 및 통과 출력 확보
- [ ] 디버그 출력·임시 코드·미해결 TODO 제거
- [ ] AI 생성 코드를 4절 기준으로 한 줄씩 검증
- [ ] 변경 라인 수 300라인 이하 (예시값, 실제 데이터로 대체 필요)

### 5.3 PR 본문 템플릿

PR 본문은 아래 다섯 항목을 이 순서로 담습니다(MUST). 항목을 빼지 않습니다(MUST NOT).

```markdown
## 무엇을
한 문단.

## 왜
어떤 문제를 해결하는가. Closes #<이슈번호>

## 어떻게 검증했는가
3.2 검증 명령의 실행 출력을 붙여넣습니다.

## AI 사용 여부
미사용 / 사용 (도구명, 적용 범위, 검증 완료 여부)

## 리뷰어가 중점적으로 볼 부분
자신 없는 구간을 작성자가 먼저 지목합니다.
```

### 5.4 리뷰 규칙

모든 코멘트에 등급 접두어를 붙입니다(MUST). 등급이 없으면 작성자가 우선순위를 판단할 수 없습니다.

| 접두어 | 의미 | 작성자 의무 |
|---|---|---|
| `blocker:` | 결함·보안·데이터 손실 위험 | 수정 없이 병합 불가(MUST) |
| `major:` | 설계·유지보수성 문제 | 수정하거나 반박 근거를 제시(MUST) |
| `nit:` | 취향·사소한 개선 | 재량(MAY). 리뷰어는 이를 근거로 승인을 보류하지 않습니다(MUST NOT) |

**리뷰어**

- 지적에 근거를 함께 제시합니다(MUST). "이건 별로다"가 아니라 "이 경로로 들어오면 `None` 이 반환되어 다음 줄에서 실패한다".
- **스타일·포맷·import 순서를 지적하지 않습니다**(MUST NOT). 도구가 이미 결정했습니다.
- 3.2의 통과 출력이 없는 PR을 승인하지 않습니다(MUST NOT).

**작성자**

- 반영한 스레드는 커밋 링크를 남기고 닫습니다(MUST).
- 논의가 3왕복을 넘으면 동기 대화로 전환합니다(MUST).
- 승인 뒤 **로직 변경·의존성 변경·스키마 변경**을 push하면 승인은 무효이며 재승인이 필요합니다(MUST). 오탈자와 리뷰 반영만 포함된 push는 제외합니다(MAY).

# 03 · IMPLEMENTATION_RULES

**정하는 것**: 코드를 어떻게 쓰는가. 파일 내부 순서, 설정과 비밀값, 예외와 로깅, 외부 자원, 데이터베이스, 테스트.

**적용 대상**: `src/` 아래의 모든 파이썬 코드

**버전**: 1.0.0 · **최종 수정**: 2026-09-04 · **작성자**: 김민경

---

## 1. 파일 내부 순서

```python
"""모듈이 무엇을 하는지 한 줄."""

from __future__ import annotations

# 1. 표준 라이브러리
import logging
from pathlib import Path

# 2. 서드파티
import httpx

# 3. 내부 절대 경로
from config import settings
from features.<도메인>.schema import ParsedItem

logger = logging.getLogger(__name__)

# 4. 상수
MIN_CONFIDENCE = 0.6

# 5. 공개 함수·클래스

# 6. 내부 함수 (_ 접두)
```

- 타입 힌트는 모든 공개 함수의 인자와 반환에 붙입니다. 3.12 문법을 씁니다. `list[str]`, `str | None` 이며 `List`, `Optional` 을 쓰지 않습니다.
- import 정렬은 ruff가 강제합니다. 손으로 맞추지 않습니다.
- `logger` 는 모듈마다 `logging.getLogger(__name__)` 로 만듭니다. `print` 를 쓰지 않습니다.

## 2. 설정과 비밀값

- **`config.py` 하나가 환경변수를 읽습니다.** 다른 파일에서 `os.environ` 을 호출하지 않습니다.
- pydantic-settings로 타입과 필수 여부를 강제합니다. 없는 키는 **실행 시작 시점에** 터져야 합니다. 처리 중간에 터지면 어느 입력에서 실패했는지 추적이 어려워집니다.
- API 키는 환경변수에서만 옵니다. 코드·로그·에러 메시지·커밋 어디에도 값이 남지 않습니다.
- 외부 서비스 식별자(모델명, 엔드포인트, 리전)는 `config.py` 에 둡니다. 교체가 한 줄 수정이어야 합니다.
- 새 환경변수를 추가하면 **같은 커밋에서** `.env.example` 을 갱신합니다.

**튜닝 상수를 코드에 박지 않습니다.** 임계값, 가중치, 타임아웃, 재시도 횟수, 상위 N처럼 **데이터와 환경에 따라 다시 맞춰야 하는 값**은 전부 `config.py` 로 뺍니다. 물리적 입력을 다루는 경로일수록 이 값들은 반드시 재조정됩니다. 리터럴로 박으면 조정 자체를 막습니다.

## 3. 예외와 로깅

- 최상위 기반 예외 하나(`AppError`)를 두고 모든 커스텀 예외가 상속합니다. 위치는 `utils/errors.py` 입니다.
- **실패 지점을 구분합니다.** 계층이나 자원별로 하위 예외를 둡니다. 호출부가 무엇이 실패했는지 알아야 재시도 여부를 판단합니다.
- `except Exception: pass` 를 금지합니다. 빈 except를 금지합니다.
- **예외를 삼키고 기본값을 반환하지 않습니다.** 무엇이 왜 실패했는지 남아야 재처리할 수 있습니다.
- 로그에 처리 대상 식별자와 사용자 식별자를 항상 포함합니다. "처리 실패"만으로는 아무것도 할 수 없습니다.
- **원문 데이터 전체와 자격증명을 로그에 남기지 않습니다.** 사용자 입력에는 개인정보가 섞여 들어옵니다.

## 4. 외부 자원과 외부 호출

- **무거운 자원의 생성 위치는 한 파일뿐입니다.** 모델, 커넥션 풀, HTTP·SDK 클라이언트가 해당합니다. 함수 안에서 매번 만들면 메모리와 지연시간으로 즉시 드러납니다. 모듈 수준 지연 초기화나 `functools.lru_cache` 로 하나를 재사용합니다.
- 자원 설정은 `config.py` 에서 받습니다. 생성 파일에 하드코딩하지 않습니다.
- **라이브러리의 원시 반환값을 생성 모듈 밖으로 내보내지 않습니다.** 자체 스키마로 변환한 뒤 넘깁니다. 원시 형식은 버전에 따라 바뀝니다.
- **외부 응답을 신뢰하지 않습니다.** pydantic 모델로 검증한 뒤 다음 단계로 넘깁니다. 검증 실패는 전용 예외로 올리고 원문을 로그에 남깁니다.
- 외부 호출에는 **타임아웃과 재시도 횟수를 명시합니다.** 라이브러리 기본값에 맡기지 않습니다.
- **입력 해시를 키로 캐시할 수 있게 만듭니다.** 유료 API나 느린 처리를 개발 중에 수십 번 반복하게 됩니다.
- **텍스트 자산을 코드에 박지 않습니다.** 프롬프트, 템플릿, 쿼리문 같은 긴 문자열은 `.md` 나 `.sql` 파일로 분리합니다. 자산만 고친 커밋이 코드 변경과 섞이지 않습니다.

**규칙으로 되는 것을 외부 서비스에 보내지 않습니다.** 정형 패턴은 코드로 처리하고, 규칙이 서지 않는 것만 외부에 맡깁니다. 비용과 지연시간이 여기서 갈립니다.

**판단과 순위를 외부 서비스에 맡기지 않습니다.** 재현이 안 되고 디버깅이 불가능해집니다. 판단 규칙은 순수 함수로 코드에 둡니다.

## 5. 데이터베이스

- **테이블은 소유한 기능이 정의합니다.** `features/<도메인>/tables.py` 입니다.
- `infra/metadata.py` 가 각 기능의 `tables.py` 를 import해 하나의 `MetaData` 로 모읍니다. **이 파일이 유일한 수집 지점입니다.**
- **SQL은 각 기능의 `repository.py` 밖으로 나가지 않습니다.** `service.py` 나 `router.py` 에 쿼리가 보이면 잘못된 것입니다.
- **다른 기능의 테이블을 직접 조인하지 않습니다.** 남의 스키마에 의존하면 그 스키마를 못 고치게 됩니다. 성능 때문에 필요하면 소유 기능이 읽기 전용 조회 함수를 공개하고, 그 결정을 `docs/decisions/` 에 남깁니다.
- **스키마를 바꾸면 운영 반영 방법과 되돌리는 방법을 PR 본문에 함께 씁니다**(MUST). `tables.py` 만 고치고 끝낸 PR은 승인하지 않습니다(MUST NOT).
- 마이그레이션 도구는 아직 도입하지 않았습니다. 도입은 `01_DEVELOPMENT_RULES.md` 1절의 신규 도구 승인 절차를 따릅니다.
- 접속 정보는 `config.py` 가 조립한 DSN 하나로만 받습니다.
- 세션은 컨텍스트 매니저로만 엽니다. 함수가 세션을 반환하게 만들지 않습니다.

**원본과 가공 결과를 다른 테이블에 저장합니다.** 처리 규칙을 바꿔 재처리할 때 원본이 있어야 이전 결과와 비교할 수 있습니다. 원본 입력의 해시를 함께 저장하면 중복 처리를 막을 수 있습니다.

## 6. 테스트 구현

배치는 `02_DIRECTORY_STRUCTURE.md` 2.3, 커버리지 기준은 `01_DEVELOPMENT_RULES.md` 6절이 정합니다. 여기서는 구현 방식만 정합니다.

- **단위 테스트에서 외부 네트워크·실제 DB·유료 API를 호출하지 않습니다.** 저장된 픽스처를 씁니다. 느리고, 비용이 들고, 결과가 비결정적입니다.
- 통합 테스트는 **트랜잭션 롤백으로 격리합니다.** 테이블을 삭제 후 재생성하지 않습니다.
- 테스트 간 실행 순서 의존성을 만들지 않습니다.
- **순수 함수에는 단위 테스트를 반드시 붙입니다.** 알고리즘이나 계산 규칙을 바꿀 때 이 테스트가 유일한 안전망입니다.
- **규칙을 하나 추가하면 그 규칙이 깨질 때 실패하는 테스트를 하나 남깁니다.** 입력 형식은 출처마다 다르고, 규칙 하나를 고치면 다른 형식이 깨집니다.

## 7. 금지 목록

- 함수나 루프 안에서 무거운 자원(모델, 커넥션 풀, 클라이언트) 생성
- 생성 모듈 밖으로 나가는 라이브러리 원시 반환값
- 코드에 인라인으로 박힌 프롬프트·템플릿·긴 쿼리 문자열
- 검증 없이 그대로 저장되는 외부 API 응답
- 외부 서비스가 정하는 판단과 순위
- `repository.py` 밖의 SQL
- 다른 기능의 테이블을 직접 조인하는 코드
- `config.py` 밖의 `os.environ`
- 로그에 남는 자격증명과 원문 데이터 전체
- 타임아웃이 없는 외부 호출

## 구성 근거

무거운 자원의 생성 위치를 한 파일로 못박은 규칙에 서비스의 응답 시간이 걸려 있습니다. 모델이나 커넥션 풀은 생성 비용이 크고, 생성 지점이 흩어지면 성능 문제가 발생한 뒤에도 원인을 찾기 어렵습니다.

판단과 순위를 외부 서비스에 맡기지 않고 순수 함수로 두는 규칙에 유지보수성이 걸려 있습니다. 판단 규칙은 반드시 여러 번 바뀌는데, DB 호출이 섞이거나 결과가 외부에서 나오면 교체할 때마다 테스트를 새로 써야 하고 재현이 불가능해집니다.

튜닝 상수를 전부 `config.py` 로 뺀 것은 물리적 입력을 다루기 때문입니다. 장비와 환경에 따라 결과가 달라지므로 임계값은 반드시 현장 데이터로 다시 맞춰야 합니다. 코드에 박힌 숫자는 그 조정 자체를 막습니다.

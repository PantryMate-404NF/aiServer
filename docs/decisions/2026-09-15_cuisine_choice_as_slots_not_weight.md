# 온보딩 음식 유형은 가중치가 아니라 자리로 반영한다

**정하는 것**: 온보딩에서 받은 "좋아하는 음식 유형"을 맛 취향과 어떻게 나누고, 추천 목록에 어떤 방식으로 얼마나 반영하며, 값을 어떤 어휘로 저장하는가

**적용 대상**: `src/features/recommend/` 의 페르소나·재정렬·계약을 고치는 인원과 AI 코딩 에이전트. 파트 A(데이터)는 1절과 5절, 프론트·백엔드는 1절과 2절을 봅니다

**버전**: 1.0.0 · **최종 수정**: 2026-09-15 · **작성자**: 유재현

---

## 1. 결정

2026-09-15 에 정했습니다. 온보딩 문항이 셋(고른 음식 · 3축 척도 · **음식 유형**)으로 늘었습니다.

| 항목 | 결정 | 파트 B 의 구현 |
|---|---|---|
| 선택지 | 한식 · 중식 · 일식 · 양식 · 아시안 다섯 가지. 여러 개 고를 수 있습니다 | `enums.ONBOARDING_CUISINES`. 정본은 `seeds/cuisine_taxonomy.yaml` 의 `family` 축이고 검사가 둘의 일치를 대조합니다 |
| 저장하는 값 | 화면 이름이 아니라 **`cuisine_family` 코드**(`korean` · `chinese` · `japanese` · `western` · `asian_other`). 한글 라벨로 와도 코드로 바꿔 저장합니다 | `enums.normalize_cuisine()`. 저장 위치는 `user_preference.pref_cuisines`, 실 DB 전까지는 취향 원본 JSON 의 `cuisines` |
| 모르는 값 | 가까운 유형으로 **추측하지 않고 거부**합니다 | `OnboardingIn` 의 검증과 `service._normalized_cuisines()` 둘 다에서 거부하고 셉니다 |
| 맛 취향과의 관계 | **섞지 않습니다.** 유형은 맛 6축에 들어가지 않고 별도 축으로 흐릅니다 | `TasteProfile.cuisines` → `Persona.cuisines` → `UserContext.preferred_cuisines`. `derive_persona()` 의 `vec` 계산에 관여하지 않습니다 |
| 목록 반영 | 점수 가중치를 올리지 않고, **고른 유형이 목록에 한 건도 없을 때만** 몇 칸을 그 유형 몫으로 뗍니다. 유형마다 한 칸, Top-20 에서 최대 두 칸입니다 | `engine/cuisine.py`. 손잡이는 `RankingPolicy.cuisine_slot_ratio`(0.1) · `cuisine_slot_max`(2) |
| 고르는 기준 | 그 유형 안에서 **맛 페르소나에 가장 가까운 것** | 유형별로 `(−f_taste, −score, recipe_id)` 정렬 후 첫 건 |
| 켜는 구간 | 행동(조리·클릭)이 쌓이기 전까지. `behavior` 사용자는 0칸입니다 | `cuisine_spec()` 이 `persona.mode is WARM` 이면 0을 돌려줍니다 |
| 로그 | 유형 칸은 탐색 칸과 **다른 칸**으로 기록합니다 | `RankedItem.is_cuisine_slot`, 추적에 `n_cuisine` · `preferred_cuisines` · `cuisine_unmet` |

## 2. 배경

값을 받을 자리는 이미 있었습니다. DDL 의 `user_preference.pref_cuisines`, 랭킹 피처 `f_cuisine`(w=0.04), 문맥의 `UserContext.preferred_cuisines` 가 그것입니다. 없던 것은 세 가지였습니다.

- 계약에 문항이 없어 백엔드가 보내도 서버가 버렸습니다(`OnboardingIn`).
- 유형의 어휘가 세 곳에서 달랐습니다 — DDL 은 영문 코드, 목업 생성기는 한글 라벨과 "분식", 온보딩 제시 목록은 "기타". 어느 조합도 `recipe.cuisine_family` 와 만나지 못했습니다.
- 가중치만으로는 고른 유형이 목록에 한 번도 안 나올 수 있었습니다.

요청은 "목록의 주 기준이 아니라, 맛 페르소나 기준 좋아할 만한 음식을 몇 개 포함" 이었습니다.

## 3. 왜 이렇게 만드는가

### 3.1 맛 축에 섞지 않는 이유

고른 유형의 평균 맛을 취향에 더하면 "한식을 좋아함" 이 "짜고 매운 것을 좋아함" 으로 번역됩니다. 담백한 한식만 좋아하는 사람에게 문항 하나가 맛 취향 전체를 옮기고, 값이 전부 0~1 이라 어떤 수치 검사에도 걸리지 않습니다. 유형은 맛과 다른 질문이므로 다른 자리에서 씁니다.

### 3.2 가중치가 아니라 자리인 이유

Σw 의 0.44 가 A군(재료 매칭)이고 유형이 뒤집을 수 있는 것은 `f_cuisine` 0.04 뿐입니다. 고른 유형의 레시피가 냉장고 재료와 덜 겹치면 Top-K 에 한 건도 안 들어옵니다 — 가상 사용자 1,600명에서 460명이 그랬습니다. 그렇다고 가중치를 올리면 반대 방향으로 무너집니다.

```text
가중치를 올린다   고른 유형이 목록 전체를 물들인다. 하나만 고른 사람은 20칸이 한 색이다.
자리를 뗀다       18칸은 그대로고 2칸이 유형 몫이다. 무엇이 왜 바뀌었는지 한 줄로 설명된다.
```

자리를 떼면 그 칸의 사유도 유형으로 적힙니다("즐겨 드시는 중식이고, 많이 만드는 레시피예요"). 가중치는 목록 전체를 조금씩 흔들 뿐이라 사용자에게 설명되지 않습니다.

### 3.3 "이미 있으면 떼지 않는다" 와 "뺄 자리를 고른다"

목적은 **고른 유형이 목록에 보이는 것**이지 더 넣는 것이 아닙니다. 조건 없이 매번 떼면 20위 밖 레시피가 이미 있던 같은 유형의 상위 레시피를 밀어냅니다.

같은 이유로 뺄 자리도 아무 데나 고르지 않습니다. 꼬리를 그냥 자르면 하필 그 자리에 있던 **다른 유형의 유일한 한 건**이 사라져, 한 유형을 넣으려고 다른 유형을 지우게 됩니다. 실제로 중식이 20위, 일식이 20위 밖에만 있는 후보에서 일식 칸을 떼자 중식이 통째로 사라지는 것을 확인했습니다(검증 기록 F-91). 그래서 한 유형에서 두 개째를 가져오지 않고, 뺄 자리에서 고른 유형의 마지막 한 건은 건너뜁니다.

### 3.4 코드로 저장하는 이유

레시피 쪽 축이 `recipe.cuisine_family` 코드입니다. 라벨로 저장하면 두 축이 영영 안 만나는데, 둘 다 문자열이라 에러가 나지 않고 그저 `f_cuisine` 이 항상 0 이 됩니다. 모르는 값을 가까운 유형으로 바꾸지 않는 이유도 같습니다 — 사용자가 고르지 않은 유형의 음식이 목록에 오르는데 응답은 200 입니다.

## 4. 되돌릴 조건

- 실데이터에서 유형이 실제 반응(클릭·조리)을 끌면, 슬롯 대신 가중치로 옮깁니다. 그때는 W3 쌍대비교 학습에서 `f_cuisine` 과 `f_taste` 의 절충을 함께 정합니다(회의 안건 N-04, N-17).
- 유형과 맛의 상관이 실데이터에서 충분히 높으면 3.1 의 분리를 재검토합니다.
- 손잡이 두 개(`cuisine_slot_ratio` · `cuisine_slot_max`)로 세기를 조절하며, 0 이면 기능이 꺼집니다. 값을 바꾸면 정책 지문이 달라져 이전 로그와 섞이지 않습니다.

## 5. 다른 파트가 알아야 할 것

- **파트 A**: 이 기능은 실 DB 에서 아직 돌지 않습니다. `recipe.cuisine_family` 가 46,353건 전수 비어 있어 대상 후보를 찾지 못합니다(회의 안건 G-30). 사용자 쪽은 채워졌고 레시피 쪽만 남았습니다. 계약이 바뀌어 A 소유 파일 넷(`enums.py` · `schema.py` · `stage.py` · `tests/unit/recommend/test_contract.py`)을 손댔습니다.
- **백엔드·프론트**: `POST /v1/onboarding/{user_id}` 가 `preferred_cuisines` 를 받습니다(최대 5). 코드와 한글 라벨을 둘 다 받지만 응답은 코드로 돌려주며, 모르는 값은 422 로 거부합니다.
- **파트 C(평가)**: 유형 칸은 탐색 칸과 다른 칸입니다. 노출 확률이 1.0 인 결정적 슬롯이라 IPS 보정의 근거가 되지 않습니다. `is_cuisine_slot` 으로 갈라서 보고, 추적의 `cuisine_unmet` 이 계속 차 있으면 후보 쪽 문제입니다.

# 취향 페르소나는 고른 음식에서 만들고 시간에 따라 감쇠한다

**정하는 것**: 추천 엔진이 사용자의 맛 취향(페르소나)을 무엇으로부터 어떤 순서로 만들고, 시간이 지나면 어떻게 잊으며, 어디에 저장하는가

**적용 대상**: `src/features/recommend/` 의 페르소나·문맥·저장소를 고치는 인원과 AI 코딩 에이전트. 파트 A(데이터)·C(평가)는 1절과 5절만 봅니다

**버전**: 1.1.0 · **최종 수정**: 2026-09-12 · **작성자**: 유재현

## 2. 배경

지금까지 엔진은 온보딩 3축을 취향으로 쓰고, 행동은 지수이동평균(EMA)으로 갱신하며, 이벤트 수가 스무 건이 되면 온보딩에서 행동으로 선형 전이했습니다(작업 기록 D-19, 계획서 3.4). 그 사이 온보딩 문항이 확정됐습니다 — 사용자는 3축 척도와 함께 **제시된 음식 20개 중 3개 이상**을 고릅니다. 데이터 파트는 이미 계약에 그것을 넣어 두었습니다(`OnboardingIn.picks`·`scales`, `user_vector.onboarding_picks`).

고른 음식은 6축 전부를 알려 주고, 3축 척도는 사용자의 자기 보고입니다. 둘이 어긋날 수 있고 어긋나면 고른 음식 쪽이 맞습니다. 그래서 우선순위를 정했습니다.

EMA 는 이벤트 순서만 보고 시각을 보지 않습니다. 1년 전에 몰아서 고른 스무 건과 지난주의 스무 건을 구분하지 못합니다. 시각이 있는 이벤트를 그대로 저장하고 계산 시점에 무게를 매기는 쪽으로 바꿨습니다.

## 3. 왜 이렇게 만드는가

### 3.1 사전 취향과 행동을 합치는 식

축마다 다음과 같이 합칩니다. `p` 는 사전 취향(고른 음식의 평균 또는 3축 척도), `k` 는 그 사전 취향을 조리 몇 건과 같은 무게로 볼지, `b` 는 이벤트의 가중 평균, `S` 는 그 축의 이벤트 무게 합입니다.

```text
persona = (k · p + S · b) / (k + S)
```

이벤트가 없으면 `S = 0` 이라 사전 취향 그대로이고, 이벤트가 쌓일수록 행동 쪽으로 옮겨 갑니다. 오래된 이벤트가 감쇠해 `S` 가 줄면 다시 사전 취향 쪽으로 돌아옵니다. 즉 **잊는 것이 자연스럽게 됩니다.** 사전 취향이 없는 축(3축 척도로는 뒤 3축을 모릅니다)은 행동만으로 채우고, 둘 다 없는 축은 비워 둡니다 — 0 으로 채우지 않는 규칙은 그대로입니다(D-19).

고른 음식으로 만든 사전 취향은 자기 보고 3축보다 무겁게 둡니다(`picks_prior_weight` > `scales_prior_weight`). 실제로 고른 것이 말로 적은 것보다 믿을 만하기 때문입니다.

### 3.2 이벤트 하나의 무게

```text
w = (이벤트 종류 무게) x (시간 감쇠) x (연 주기 친화도) x (주 주기 친화도) x (일 주기 친화도)
```

- **종류 무게**는 데이터 파트의 `LABEL_WEIGHT` 를 씁니다(조리 1.0, 저장 0.6, 클릭 0.3). 음의 값(무시·저장 취소)은 0 으로 두어 페르소나를 만들지 않습니다 — "싫어하는 맛" 은 다른 모델이 다룰 일입니다. 별점은 `rating_to_label` 을 0 아래와 1 위에서 자르고, 1~5 밖의 값은 무게가 아니라 잘못된 이벤트로 세어 저장하지 않습니다 - 상한이 없으면 별점 180 하나가 온보딩 전체를 덮습니다.
- **시간 감쇠**는 `0.5 ^ (경과일 / 반감기)` 입니다. 반감기 90일이면 석 달 전 이벤트는 절반, 반년 전 이벤트는 1/4 입니다. 반감기를 0 이하로 두면 끕니다.
- **주기 친화도**는 `1 − s · (1 − cos(2π·Δ)) / 2` 입니다. `Δ` 는 이벤트와 지금의 주기 위상 차이(0~1), `s` 는 세기입니다. 같은 시기면 1, 정반대 시기면 `1 − s` 입니다. 연 주기의 위상은 연중 경과 비율, 주 주기는 요일, 일 주기는 시각입니다.

세 값을 곱하므로 어느 하나가 0 이면 그 이벤트는 사라집니다. 반대 계절의 이벤트가 전부 사라져 `S = 0` 이 되면 사전 취향으로 돌아갑니다. 그래서 세기 1.0 은 권하지 않고 기본값을 연 주기 0.5 로 둡니다(예시값, 실제 데이터로 대체 필요).

### 3.3 저장소

사용자마다 파일 하나입니다. 파일 안에는 고른 음식의 원본 인덱스와 그 시점의 6축 스냅숏, 3축 척도 원본, 이벤트 목록(레시피, 종류, 시각, 6축 스냅숏)이 있습니다.

- **왜 원본을 두는가**: 데이터 파트가 계약에 적은 그대로입니다 — 평균만 남기면 시드가 바뀌었을 때 다시 계산할 수 없습니다.
- **왜 스냅숏도 두는가**: 페르소나 계산이 이 파일 하나로 끝나야 DB 없이도 돌고 검사할 수 있습니다. 시드가 바뀌면 원본 인덱스로 다시 채웁니다.
- **왜 사용자당 파일인가**: 파일 하나에 전부 넣으면 사용자가 늘수록 쓰기 한 번이 전체를 다시 씁니다. 사용자당 파일이면 쓰기 비용이 그 사용자 것에 그칩니다. 폴더는 사용자 ID 로 256개로 나눠 한 폴더에 파일이 쌓이지 않게 합니다.
- **왜 잘라내는가**: 이벤트는 `persona_max_event_age_days` 보다 오래된 것과 `persona_max_events` 를 넘는 것을 저장할 때 버립니다. 기본값(반감기 90일)에서 2년 전 이벤트의 무게는 0.4% 라 결과에 영향이 없습니다. 반감기를 상한 근처로 늘리면 결과에도 닿습니다. 잘라내기는 서비스가 저장 전에 하며 온보딩 저장과 이벤트 저장 두 경로가 같습니다.
- **원자적 쓰기**: 호출마다 다른 이름의 임시 파일에 쓰고 이름을 바꿉니다. 쓰다가 죽어도 이전 파일이 남고 동시에 써도 서로의 임시 파일을 밟지 않습니다.
- **사용자 대조**: 파일 안의 사용자와 요청한 사용자가 다르면 읽기를 거부합니다. 넘기면 한 사용자의 이벤트가 다른 사용자의 파일로 들어갑니다.
- **읽기 실패는 한 종류**: JSON 으로는 멀쩡해도 객체가 아니거나 축이 모자라거나 NaN 이거나 범위 밖이면 전부 ValueError 로 실패하고, 서빙은 그것을 받아 취향 없는 사용자로 다루며 셉니다.
- **동시 쓰기**: 서비스가 사용자 파일의 읽고-합치고-쓰기를 프로세스 안에서 잠금으로 직렬화합니다. 프로세스가 여럿이면 나중 쓰기가 이깁니다 - 실 DB 로 옮기면 사라지는 제약입니다.

이 저장소는 실 DB 가 붙기 전까지의 정본입니다. 붙은 뒤에는 같은 내용을 `user_vector` 와 `event_log` 에서 읽는 것이 DB 전환 점검표의 항목입니다.

### 3.4 취향이 전혀 없는 사용자

고른 음식도 3축 척도도 없으면 맛 피처가 비고(Zero-Drop), 탐색 슬롯 비율을 `cold_exploration_ratio` 로 올려 목록을 다양하게 만듭니다. "완전 임의값" 을 페르소나에 넣지는 않습니다 — 임의의 취향을 넣으면 **일관되게 엉뚱한** 추천이 되고, 취향을 비우면 다양성 장치가 대신 일합니다.

탐색 칸이 설계대로 채워지려면 후보가 충분해야 합니다. 완화 조회의 종료 기준(`candidate.needed`)은 탐색 비율을 받아 취향 없는 사용자에게 더 많은 후보를 요구하고(20건 목록에 52건, 보통은 36건), 그래도 채우지 못한 칸 수는 추적의 `dropped.explore_shortfall` 에 남습니다. 후보에 군집이 없으면 탐색을 전부 균등으로 채우고 추적에 `explore_fallback: uniform` 을 남깁니다 - `Candidate.cluster_id` 계약이 정한 폴백을 A 의 `mixed_exploration` 이 구현하지 않기 때문입니다(G-27).

## 4. 되돌릴 조건

- 우선순위(고른 음식 > 3축 척도)는 기획이 "고른 음식" 을 필수로 만들면 2단계가 사라질 뿐 식은 그대로입니다.
- 반감기·주기 세기·사전 취향 무게는 전부 예시값입니다(실제 데이터로 대체 필요). W3 가중치 학습에서 다시 정합니다. 값이 바뀌어도 `RankingPolicy.fingerprint()` 가 달라져 이전 로그와 섞이지 않습니다.
- 3축 척도의 범위가 계약(0~4)과 회의 기록(1~5)에서 다릅니다. 엔진은 0~1 로 정규화된 값만 받으므로 범위는 서비스 층 한 곳에서 바꿉니다. 어느 쪽이 맞는지는 회의 안건입니다.
- 실 DB 가 붙으면 JSON 저장소는 읽기 전용 이전 도구가 됩니다. 이전이 끝나면 지웁니다.
- 회의의 "월별 주기" 는 연 주기의 위상으로 해석했습니다. 월내 주기가 필요하다고 확인되면 `cycle_affinity` 위에 손잡이 하나를 더하면 됩니다(G-25).
- "3개 이상" 은 서버가 거부하지 않고 셉니다(`MIN_PICKS`). 계약이 개수를 프론트의 일로 두었기 때문이며, 서버 몫으로 바뀌면 거부로 전환합니다.
- 이벤트 시각은 서버 수신 시각입니다. `EventIn` 에 발생 시각이 없어 오프라인 동기화 배치는 전부 같은 시각을 받습니다. 주·일 주기를 켜려면 시각 필드가 먼저 필요합니다(G-26).

## 5. 다른 파트가 알아야 할 것

- **A(데이터)**: 온보딩 제시 목록(`seeds/onboarding_recipes.yaml`)의 `flavor` 가 곧 측정 도구입니다. 시드를 바꾸면 B 가 원본 인덱스로 스냅숏을 다시 채워야 합니다. 이벤트는 `EventIn` 그대로 받고 시각은 서버 수신 시각입니다. `EventIn` 에 발생 시각 필드가 없어 오프라인 동기화 배치는 전부 같은 시각을 받습니다(G-26).
- **C(평가)**: 추천 로그의 `params` 에 `persona_source`(picks·scales·none)와 `persona_mode`(onboarding·blended·behavior)가 실립니다. 취향이 없는 사용자의 추천은 탐색 비율이 다르므로 평가에서 갈라 봐야 합니다. `persona_mode` 는 행동 무게의 비중(onboarding·blended·behavior)이고 취향의 유무는 `persona_source` 로 봅니다. 추적에 `explore_fallback` 이 있으면 그 요청의 실효 균등 비율은 1.0 이고, `dropped.explore_shortfall` 은 채우지 못한 탐색 칸 수입니다.

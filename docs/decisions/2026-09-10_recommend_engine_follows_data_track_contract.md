# 추천 엔진은 데이터 파트의 계약을 정본으로 따른다

**정하는 것**: 파트 B 추천 엔진이 쓰는 맛 벡터의 축 수, 피처 체계, 노출확률의 의미, 그리고 어느 파일을 정본으로 삼는가

**적용 대상**: `src/features/recommend/` 를 고치는 인원과 AI 코딩 에이전트

**버전**: 1.0.0 · **최종 수정**: 2026-09-10 · **작성자**: 유재현

---

## 1. 결정

A(데이터)·B(추천)·C(평가) 세 파트의 1차 통합 회의에서 정했습니다. 넷 다 같은 방향입니다 — **먼저 구현되어 이미 다른 것들이 그 위에서 도는 쪽이 정본입니다.**

| 항목 | 결정 | 파트 B 의 변경 |
|---|---|---|
| 맛 벡터 | 6축(매움, 짠맛, 단맛, 신맛, 감칠맛, 기름짐). 사용자에게 지금 받는 것은 앞 3축뿐이며 뒤 3축은 값이 없는 채로 들어옵니다 | 3축 계산을 6축으로 넓히고, **값이 없는 축을 분자와 분모에서 함께 뺍니다.** 0 으로 채우지 않습니다 |
| 피처 체계 | `enums.FEATURE_KEYS` 의 17종 | 5블록 가중합을 버리고 17 키를 채웁니다. 못 재는 것은 `None` 입니다 |
| 노출확률 | 확률(0 < p <= 1). `enums.PROPENSITY_SEMANTICS` = "item" | 역수를 싣던 것을 확률로 바꿉니다 |
| 파일 정본 | `enums.py`, `stage.py`, `engine/{rank,reason,explore,serendipity}.py` 는 A | B 는 그 위에서 점수 계산만 채우고 자기 `schema.py`·`explain`·`penalty`·`feedback` 을 지웁니다 |

## 2. 배경

두 파트가 서로의 코드를 보지 못한 채 `src/features/recommend/` 를 각자 만들었습니다. 합치려는 시점에 같은 경로에 다른 구현이 있고, 같은 이름의 모델이 다른 모양이었습니다.

특히 맛 벡터의 축 **순서**가 어긋나 있던 것을 먼저 발견했습니다. 값이 전부 0~1 이고 길이도 같아 어떤 검사에도 걸리지 않으면서 단맛 선호를 짠맛으로 읽는 종류의 오류였습니다. 순서를 맞추고 나니 축의 **개수**도 달랐습니다.

## 3. 왜 A 가 정본인가

A 가 먼저 구현했고, 그 위에서 이미 도는 것이 있습니다. 계약 검증 98건, DB 스키마의 CHECK 제약, 그리고 평가 파트가 읽을 로그의 칸 정의입니다. B 의 모델을 정본으로 하면 그 셋을 전부 다시 맞춰야 합니다.

노출확률은 더 좁은 이유가 있습니다. 값이 하나뿐인 칸에 두 파트가 다른 뜻을 넣으면 **로그를 나중에 나눌 수 없습니다.** 확률과 그 역수는 겉보기에 둘 다 양수라 섞여도 에러가 나지 않고, 사후 평가에서 분모가 조용히 틀립니다.

엔진 조각을 가져온 것도 같은 성질입니다. B 가 사유 선택과 탐색 슬롯을 다시 구현하면 두 벌이 되고, 두 벌의 확률 정의가 갈리는 순간 off-policy 평가가 못 쓰게 됩니다.

## 4. 값이 없는 축을 빼는 이유

0 은 "그 맛이 없다"이고 값이 없는 것은 "모른다"입니다. 채우면 신맛을 물어본 적 없는 사람이 신맛을 싫어하는 사람이 됩니다.

이 처리는 A 가 피처에 이미 쓰고 있는 것과 같습니다. 정규화가 `Σwᵢfᵢ / Σwᵢ` 이고 값이 없는 것은 분자와 분모에서 함께 빠지므로, 남은 가중치를 비례 재분배한 것과 수학적으로 같습니다. 그래서 데이터가 없는 축이나 피처의 가중치를 0 으로 내릴 필요가 없고, **데이터가 오면 코드를 고치지 않아도 켜집니다.**

## 5. 되돌릴 조건

- 6축 전부를 실제로 쓸지는 W3 쌍대비교 학습에서 정합니다(A 트랙 결정 D-11). 학습이 앞 3축만 쓰기로 하면 뒤 3축은 저장만 하고 계산에서 빠집니다. 그때도 이 결정을 되돌릴 필요는 없습니다 — 값이 없는 축을 빼는 처리가 그대로 그 동작이기 때문입니다.
- 17 피처 중 수단이 없는 3종(`f_ing_cf`, `f_group_pref`, `f_content`)의 계산 수단이 생기면 그때 켭니다. 계약은 그대로입니다.
- A 가 자기 계약을 바꾸면 B 가 따라갑니다. 반대 방향은 세 파트가 다시 모여 정합니다.

## 6. 가져온 파일에 손댄 곳

A 원본에서 26곳을 고쳤습니다. 의미를 바꾸지 않으므로 A 가 그대로 받을 수 있습니다.

- 저장소 린트가 헷갈리는 문자로 지적하는 수학 기호 21곳을 뜻이 같은 ASCII 로. 전역 ignore 로 덮는 방법도 있지만 `01_DEVELOPMENT_RULES` 의 3.3 이 Tech Lead 승인을 요구해 쓰지 않았습니다.
- import 순서 2곳.
- 코드 3곳. 재현용 시드 난수에 규칙이 요구하는 형식의 `noqa` 와 사유를 달았고, 항상 참인 멤버십 검사를 같은 뜻의 길이 비교로 바꿨고, 인자 하나에 타입을 붙였습니다.
- 타입 검사가 지적한 16곳은 표기만 손봤습니다.

# 통과는 종료 코드로만 보고한다

**정하는 것**: 검증 결과를 보고할 때 무엇을 근거로 삼는가. 01의 3.4 를 추가한 사례와 근거

**적용 대상**: 이 저장소에 검증 결과를 적는 모든 인원 및 AI 코딩 에이전트

**버전**: 1.0.0 · **최종 수정**: 2026-09-11 · **작성자**: 유재현

---

## 1. 결정

01에 3.4 를 넣었습니다. 요지는 셋입니다.

- 통과 판정은 **종료 코드**로 합니다. 화면의 마지막 줄로 하지 않습니다.
- **돌리지 않은 명령의 결과를 적지 않습니다.** 못 돌렸으면 못 돌렸다고 적습니다.
- 남이 적어 둔 건수를 **자기가 잰 것처럼 인용하지 않습니다.**

이 문서는 01의 9절 2번이 요구하는 "구체적 사례" 입니다. 추상적 제안이 아니라 실제로
일어난 세 건이 근거입니다.

## 2. 사례

### 2.1 마지막 줄이 통과 표시라 통과로 읽었습니다

2026-09-10 병합에서 데이터 파트의 계약 검증(`make contract`)을 "통과" 로 기록했습니다.
확인한 것은 `... | tail -4` 의 출력이었고 거기에는 통과 표시가 찍혀 있었습니다.

실제로는 `.env` 의 빈 값 때문에 `create_app()` 이 `ValidationError` 를 냈고, 그 예외를
`try` 가 잡지 않아 **스크립트가 59번째 체크에서 죽어 있었습니다.** 뒤쪽 계약은 실행조차
되지 않았습니다. 종료 코드는 1 이었고 아무도 그것을 보지 않았습니다.

이 오기는 작업 기록 9.6 과 그 커밋 메시지에 그대로 실려 하루 동안 사실로 남았습니다.
설정값을 채워 다시 재니 98건 전부 통과·종료 코드 0 이었습니다. 결과는 같았지만
**같은 결과를 우연히 맞힌 것과 확인한 것은 다릅니다.**

### 2.2 돌리지 않은 검사를 통과로 적었습니다

같은 날 결정 기록에 "데이터 파트의 검사 242건은 실제로 존재하고 전부 통과합니다" 라고
썼습니다. 실제로 돌린 것은 실 DB 가 필요 없는 125건뿐이고, 242 는 데이터 파트가
`tests/conftest.py` 주석에 적어 둔 수였습니다. 나머지는 확인한 적이 없습니다.

### 2.3 앞선 실행의 수치를 그대로 옮겼습니다

`ruff format --check` 의 대상 파일 수를 128 로 적었는데, 그 뒤 결정 기록 파일이 하나
늘어 실제로는 129 였습니다. 변경 규모도 193 파일·60,887줄로 적었으나 측정 직후 파일이
늘어 194 파일·60,961줄이 됐습니다. 둘 다 옮겨 적은 숫자가 조용히 낡은 경우입니다.

## 3. 왜 규칙이 필요한가

01의 3.2 는 이미 "통과한 출력을 근거로만 보고합니다" 와 "실행과 확인의 책임은
작성자에게" 를 정하고 있었습니다. 세 건 모두 그 조항을 어기려던 것이 아니라,
**출력을 봤는데도 틀렸습니다.**

빠진 것은 "무엇을 봐야 출력을 본 것인가" 였습니다. 검사 스크립트는 실패해도 그때까지의
통과 줄을 이미 화면에 남깁니다. 사람과 에이전트 모두 마지막 줄을 결론으로 읽습니다.
종료 코드를 명시적으로 요구하지 않으면 같은 일이 반복됩니다.

## 4. 함께 한 일

- `tests/unit/recommend/test_contract.py` 의 종단 블록이 `ImportError` 만 잡던 것을 넓혀,
  설정 오류로 멈추면 **실패로 세도록** 고쳤습니다. 이제 `.env` 가 비어 있으면
  92통과·2실패로 끝까지 돌고 종료 코드 1 을 냅니다. 조용히 죽지 않습니다.
- 01의 3.4 5번이 이것을 일반화한 조항입니다 — 검사 스크립트는 실패가 종료 코드로
  드러나게 만듭니다.

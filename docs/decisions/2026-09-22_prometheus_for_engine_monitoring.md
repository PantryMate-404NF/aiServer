# 추천 엔진의 관측을 Prometheus 와 Grafana 로 하기로 한 결정

**정하는 것**: 트랙 C(평가와 모니터링)를 파트 B 담당이 이어받으면서 관측 수단을 무엇으로 정했는지, 앞선 설계(Grafana 가 PostgreSQL 을 직접 읽고 Prometheus 는 쓰지 않는다)와 왜 달라졌는지, 되돌리거나 합칠 조건

**적용 대상**: 추천 엔진을 운영하는 사람과 데이터 파트(A). 클라우드 팀은 3절의 새 컨테이너만 보면 됩니다

**버전**: 1.0.0 · **최종 수정**: 2026-09-22 · **작성자**: 유재현

## 2. 앞선 설계와 왜 달라졌는가

`deploy/grafana/provisioning/datasources/postgres.yml` 은 이렇게 적고 있습니다 — 레이턴시와 처리량이 이미 `recommendation_log.total_latency_ms` 에 적재되므로 Prometheus 를 쓰지 않고 PostgreSQL 을 직접 쿼리한다(설계 1-3). 그 판단은 두 전제 위에 있었고 둘 다 달라졌습니다.

| 전제 | 지금 |
|---|---|
| 서빙 로그가 DB 에 쌓인다 | 로그 적재가 서빙에 연결되지 않았습니다(DB 전환 M-05). 한 행도 쌓이지 않습니다 |
| AI 서버가 자기 DB 로 운영 데이터를 본다 | 운영 데이터는 백엔드 API 로만 옵니다(2026-09-21). DB 없이도 서버는 떠야 합니다 |

DB 를 기다리면 관측이 서빙보다 늦게 옵니다. 그런데 관측이 가장 필요한 때는 실엔진을 처음 연결하는 순간입니다. 그래서 DB 없이 도는 수단을 골랐습니다.

둘은 겹치지 않습니다. PostgreSQL 은 "무엇이 서빙됐는가" 를 행 단위로 답하고(어느 사용자에게 어느 레시피가 몇 위로), Prometheus 는 "서빙이 어떻게 돌고 있는가" 를 시간 축으로 답합니다(지연, 꺼진 신호, 탐색 비율). 로그 적재가 연결되면 기존 데이터소스로 행 단위 분석을 그대로 할 수 있습니다.

| DB 전환 M-07 | 처리했습니다. 서비스의 내부 카운터(삼킨 예외)가 `reco_internal_events_total` 로 나갑니다 |

## 4. 고르지 않은 것

**Streamlit 대시보드**(`pyproject.toml` 의 `dash` 묶음). 앞선 계획이었습니다. 별도 프로세스와 의존성이 필요하고 시간 축의 보관이 없습니다. 관리자 페이지에 필요한 것은 "지금 상태와 할 일" 한 장이라 정적 HTML 로 충분했습니다. 묶음은 지우지 않았습니다.

**오프라인 평가 파이프라인**(추정기 · 통계 · 보고서). 2026-09-18 에 들어왔다가 2026-09-21 에 되돌려졌습니다. 라벨(클릭 · 조리)이 아직 한 건도 없어 돌릴 입력이 없습니다. 이번에는 그 재료가 빠짐없이 쌓이는지만 봅니다 — 노출확률, 순위별 반응, 칸별 반응.

**Alertmanager**. 경보 규칙은 두었지만 알림을 보내는 곳은 두지 않았습니다. 받을 채널이 정해지지 않았습니다. 경보는 Prometheus 와 Grafana 화면에서 봅니다.

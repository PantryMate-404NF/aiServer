# 평가 파트의 요청에 대한 데이터 파트의 답

**정하는 것**: 파트 C 의 `docs/recommend/evaluation/04_recommend_evaluation_requests.md` 2절(파트 A 요청 4건)에 대한 답과, 5절 3인 합의 3건에 대한 데이터 파트의 의견

**적용 대상**: 파트 C(평가). 파트 B 는 5절(`threshold.py`)만 보면 됩니다 — 요청 2.4 의 수신자에 파트 B 도 들어 있습니다

**버전**: 1.1.0 · **최종 수정**: 2026-09-21 · **작성자**: 파트 A (데이터)

---

## 0. 이 문서를 쓴 뒤에 바뀐 것

답을 쓴 날 저녁에 **평가 파이프라인이 통째로 되돌려졌습니다**(PR #14). 요청 문서
`docs/recommend/evaluation/04_recommend_evaluation_requests.md` 와 평가 코드 전부가
저장소에서 사라졌습니다.

그래도 이 문서를 지우지 않습니다. 답의 근거는 **우리 쪽 데이터를 실측한 것**이라
평가가 다시 올라와도 그대로 쓸 수 있습니다. 다만 **5절(`threshold.py`)만 상황이
달라져 아래에 고쳐 적었습니다.**

## 2. 읽기 범위와 IDF 정의 (요청 2.1)

**읽기는 허용입니다.** `recipe_feature.all_ids`, `recipe_ingredient` 의 재료별 집계, `app_user.is_simulated`, `recipe_feature` 건수 모두 읽으셔도 됩니다. 쓰지 않으므로 배치와 충돌하지 않습니다.

### IDF 는 같은 값입니다

두 계산이 다른 SQL 을 쓰는데 결과가 같습니다.

```text
파트 A (서빙)   log(N / ingredient.freq_count)
파트 C (평가)   log(N / count(*) FROM recipe_ingredient GROUP BY ingredient_id)
```

`recipe_ingredient` 의 기본키가 `(recipe_id, ingredient_id)` 라서, `count(*)` 와 `count(DISTINCT recipe_id)` 가 **같을 수밖에 없습니다.** 우연이 아니라 스키마가 막고 있습니다.

실측으로도 확인했습니다 — `freq_count` 가 0 이 아닌 **664종 전부 두 값이 일치**하고, 같은 레시피에 같은 재료가 두 번 든 경우는 0건입니다.

`metrics.py` 가 `jaccard_idf` 를 엔진에서 그대로 가져다 쓰신 것도 맞습니다. 유사도 계산이 두 벌이 될 뻔했습니다.

### 두 가지만 맞춰 주십시오

**N 값.** 저희는 `feature_stats.n_recipes` 를 씁니다. 현재 `stats_version = 7`, 값은 **46,353** 입니다. 실행 시점의 `recipe_feature` 건수와 같으므로 어느 쪽을 쓰셔도 되지만, 리포트에 어느 것을 썼는지 남겨 주시면 나중에 갈릴 때 찾기 쉽습니다.

**한 번도 안 쓰인 재료.** 저희는 `freq_count` 가 0 인 **32종**을 IDF 사전에서 아예 빼서 `DEFAULT_IDF = 1.0` 을 받게 둡니다. 넣으면 `log(N/0)` 이 되기 때문입니다. 평가 쪽도 같게 하지 않으면 희소 재료가 든 목록의 ILD 가 갈립니다.

## 3. 카탈로그 커버리지의 분모 (요청 2.2)

**46,353 입니다.**

```text
recipe_feature   46,353      추천 후보가 될 수 있는 레시피
recipe           46,353      같은 수
원본 jsonl       46,552      199줄 더 많음
```

**46,552 는 쓰지 마십시오.** 그 199줄은 제목이나 원본 id 가 없어 적재 자체가 실패한 것입니다. 추천 후보가 될 수 없으므로 분모에 넣으면 커버리지가 구조적으로 낮게 나옵니다.

`(a)` 와 `(c)` 는 오늘 같은 값입니다. **제안하신 `(c)` 실행 시점의 `recipe_feature` 건수를 권합니다** — 레시피가 늘면 따라가고, 출처를 `stamp.catalog_size_source` 에 찍는 방식도 맞습니다.

## 4. 맛 벡터가 전부 0 인 레시피 (요청 2.3)

**배치는 46,353건 전부 돌았습니다.** 미처리가 아니라 계산 결과입니다.

다만 971건(2.09%) 안에 **성격이 다른 두 종류**가 섞여 있습니다.

| | 건수 | 무엇 | 구분법 |
|---|---|---|---|
| 재료가 하나도 안 붙음 | 945 | 계산할 재료가 없어 0 | `n_total = 0` · `recipe.status = 'raw'` |
| 재료는 있는데 맛이 없음 | 26 | `물`·`생수`·`전분` 만 든 레시피 | `n_total > 0` |

`recipe.status = 'raw'` 인 행이 정확히 945건이라 배치 실행 기록까지 가지 않아도 가를 수 있습니다.

### 945건을 한 번 더 나눠야 합니다

| | 건수 | 고칠 수 있나 |
|---|---|---|
| 원본에 재료가 0개 | 859 | **아니오.** 크롤이 재료를 못 가져온 것입니다 |
| 원본에 재료가 있는데 못 붙임 | 86 | 예. 사전 보강 대상입니다 |

**859건은 영구적인 바닥값입니다.** 비율로 **1.85%**(859 / 46,353)이고, 저희가 사전을 아무리 키워도 내려가지 않습니다. 경보 기준을 잡으실 때 이 값을 바닥으로 두시면 됩니다.

86건은 디저트·베이킹 쪽이 많습니다(`황치즈`·`사브레`·`참깨튀일`·`쌀브라우니`). 사전이 한식 재료 위주라 안 잡힙니다. 저희가 보강하겠습니다.

### 경보 문구 제안

```text
n_total = 0 인 비율     "재료 정규화 실패" — 1.85% 아래로는 안 내려갑니다
n_total > 0 인 비율     정상. 맛이 없는 재료만 든 레시피입니다
```

## 5. `threshold.py` 는 `ingest/` 로 옮겼습니다 (회의 안건 G-17)

답을 쓸 때는 "옮기는 작업은 파트 C 가 해 주시면 된다" 고 적었는데, 그 뒤 평가
파이프라인이 롤백되면서 **파트 C 가 붙였던 검사 4건도 함께 사라졌습니다.** 파일만
남고 검사가 없는 원래 상태로 돌아간 것이라 파트 A 가 처리했습니다.

### 원래 파트 A 의 파일이었습니다

회의 안건 G-17 이 "평가 파트가 쓸 유틸로 보인다" 고 적었는데 폴더 위치만 보고 한
추정이었습니다. 이력을 보면 파트 A 가 만들었고, 파이프라인을 저장소 배치로 옮길 때
`evaluation/` 으로 들어갔습니다.

```text
7d0d74a  2026-09-08  파이프라인을 aiserver 배치로 옮기며 들어옴
```

### 지금 설계의 근거가 이 파일입니다

퍼지 매칭을 자동 확정에 쓰지 않기로 한 결정이 이 도구로 계산한 결과입니다. 우리
인제스트 코드 두 곳이 그 결론을 인용합니다.

```text
ingest/match.py   trgm 임계값 0.6 에서 재현율 0%. 정탐 중앙값 0.143 vs 오탐 0.118 로
                  분포가 겹쳐 어떤 임계값도 정밀도 99% 를 만들지 못한다
ingest/head.py    퍼지 매칭은 오탈자에만 남기고, 임계값은 캘리브레이션으로 정한다
```

그래서 삭제하지 않았습니다. 설계에 아직 손으로 고른 숫자가 여럿 남아 있고
(`MMR λ=0.7` · `N_WARM=20` · 캡 `3/4/2`), 그것들을 실측으로 정할 때 쓰는 도구입니다.

### 한 것

```text
src/features/recommend/evaluation/threshold.py -> src/features/recommend/ingest/threshold.py
tests/unit/recommend/test_eval_threshold.py    -> tests/unit/recommend/test_threshold.py
```

검사는 파트 C 가 만든 것을 롤백 직전 판에서 되살렸습니다. **내용은 그대로이고
import 경로만 맞췄습니다.** 인제스트 주석 두 곳의 경로도 고쳤습니다.

### 커버리지에서는 빠집니다

`ingest/` 가 커버리지 `omit` 목록에 와일드카드(`ingest/*`)로 들어 있습니다. 옮기면서
이 파일이 리포트에서 사라졌습니다. 실측 커버리지는 **57줄 중 8줄 미실행, 86%** 입니다.

그 목록의 근거는 "파트 A 의 검사는 pytest 가 아니라 make 가 돌린다" 인데 이 파일에는
맞지 않습니다. `match.py` · `parse.py` 같은 파일은 pytest 가 진짜로 한 줄도 실행하지
않지만(전부 0%), 이 파일은 pytest 로 검사됩니다.

**와일드카드를 파일 목록으로 풀면 해소되며, 그 목록은 01의 6.1 승인을 받은
예외라 임의로 바꾸지 않았습니다**(회의 안건 G-16). 승인을 받을 때 함께 정리하는 것이
맞아 보이고, 그때까지 사실을 `pyproject.toml` 주석에 적어 두었습니다.

## 6. 3인 합의에 대한 의견 (5절)

### 6.1 가명화 salt — `(b)` 전용 salt 에 동의합니다

**`REVIEW_SALT` 를 다른 용도로 섞으면 안 됩니다.** 그 값은 크롤 후기의 작성자 해시에 이미 쓰였습니다.

```text
624,422   후기 행 전체
618,962   해시가 붙은 행 (닉네임이 없는 5,460건은 NULL)
177,171   고유 작성자
```

한 번 바뀌면 같은 사람이 쓴 후기를 더 이상 같은 사람으로 못 보고, 되돌릴 수 없습니다. 평가 내보내기가 같은 키를 쓰면 그 위험이 한 군데 더 생깁니다.

`EVAL_SALT` 를 따로 두고, 없으면 내보내기가 멈추는 설계도 맞습니다. 저희 쪽 `REVIEW_SALT` 도 같은 방식으로 없으면 멈춥니다.

### 6.2 스냅샷 저장소와 보존 기간 — 그대로 동의합니다

지금은 JSONL, 화면이 붙고 추이가 쌓이면 테이블. 보존 30일. 이견 없습니다.

테이블을 신설하실 때 한 가지만 부탁드립니다 — `reco` 스키마의 테이블 수가 지금 29개이고 배포 문서에 그 숫자가 적혀 있습니다. 늘어나면 `deploy/SETUP_CLOUD.md` 도 함께 고쳐야 합니다.

### 6.3 `Makefile` 대상 추가 — 확인했습니다

`eval` 과 `eval-smoke` 두 대상이 병합돼 있고 다른 대상은 그대로입니다.

`eval-smoke` 가 내보낸 파일에 원본 식별자와 냉장고 필드가 있으면 거기서 멈추게 해 두신 것이 좋습니다. 그 검사가 없으면 가명화가 빠져도 파일이 그냥 만들어집니다.

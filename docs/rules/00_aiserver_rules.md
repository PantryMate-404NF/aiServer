## 1. 한눈에 보기

AI 서버는 **LLM 호출과 임베딩을 전담하는 내부 서비스**다. 자체 모델을 학습하거나 GPU에
올려 서빙하지 않는다.

이 다섯 가지만 지켜도 대부분의 사고를 막을 수 있다.

| # | 규칙 | 어기면 |
| --- | --- | --- |
| 1 | Supabase에 직접 붙지 않는다 | 스키마 변경 시 두 서버가 같이 깨진다 |
| 2 | API 키는 `.env`에만. 커밋 금지 | 키 유출 |
| 3 | 프롬프트는 `prompts/`에 파일로 | 문구 한 줄 고치는 데 배포가 필요해진다 |
| 4 | LLM 출력은 Pydantic으로 검증 | 매핑 테이블이 조용히 오염된다 |
| 5 | 배치 실행 전 예상 비용 출력 | 수십만 건을 두 번 돌린다 |

## 2. 이 서버가 하는 일

| 작업 | 형태 | 상태 |
| --- | --- | --- |
| 레시피 수집 (크롤링) | 배치 | MVP |
| 레시피 재료 문자열 → 식재료 사전 정규화 | 배치 | MVP |
| 레시피 주재료 판정 · 대체 재료 사전 구축 | 배치 | MVP |
| 레시피 중복 제거 · 클러스터링 | 배치 | MVP |
| 재고 기반 레시피 추천 | API | MVP |
| **영수증 OCR 파싱** | API | **MVP** (2026-08-25 범위 편입) |

영수증 OCR은 전용 OCR API로 텍스트를 뽑고 LLM이 품목을 파싱하는 2단계다. 건당 5~10초로
아래 "API는 수 초 안" 기준의 경계에 있어, **동기 API로 두되 타임아웃을 30초로 잡는다.**
실측이 10초를 넘으면 `app/workers/` 도입을 재검토한다.

**영수증에는 개인정보가 있다.** 카드번호·전화번호·승인번호는 추출 스키마에 넣지 않고,
**OCR 원문 텍스트를 로그나 저장소에 남기지 않는다.** 이 서버에서 개인정보가 흐르는 유일한
경로이므로 별도로 주의한다.

### 배치와 API를 먼저 구분한다

이 구분이 구조의 출발점이다.

| | 배치 | API |
| --- | --- | --- |
| 위치 | `scripts/` | `app/routers/` |
| 실행 | 사람이 직접 실행 | 백엔드가 호출 |
| 소요 시간 | 수 시간 | 수 초 |
| 예시 | 재료 정규화 30만 건 | 레시피 추천 |

한 번 돌리고 끝나는 작업을 API로 만들면 타임아웃 · 재시도 · 진행률 관리가 전부 따라온다.
**API는 수 초 안에 끝나는 것만 만든다.**

## 3. 백엔드와의 경계

```
[클라이언트] → [백엔드 서버] → [ai_server]
                     ↓
                [Supabase]
```

| 항목 | 규칙 |
| --- | --- |
| 외부 노출 | 하지 않는다. 백엔드만 호출 가능 |
| DB 접근 | Supabase에 직접 붙지 않는다. 필요한 데이터는 요청 본문으로 받는다 |
| 인증 | 클라이언트 JWT를 검증하지 않는다. 백엔드가 넘긴 내부 API 키만 확인 |
| 권한 · 과금 | 전부 백엔드 책임 |

**DB 접근 규칙의 예외**: 배치 스크립트(`scripts/`)는 정규화 결과를 직접 적재해도 된다.
서비스 트래픽과 무관한 오프라인 작업이기 때문이다.

## 4. 폴더 구조

```
ai_server/
├── app/
│   ├── main.py            # FastAPI 앱, lifespan(클라이언트 초기화)
│   ├── config.py          # 환경변수 → Settings
│   │
│   ├── routers/           # HTTP 엔드포인트
│   ├── schemas/           # 요청/응답 Pydantic 모델
│   ├── services/          # 파이프라인 조립
│   ├── llm/               # LLM 클라이언트 · 임베딩
│   └── core/              # 로깅 · 예외 매핑
│
├── prompts/               # 프롬프트 파일
├── scripts/               # 배치 작업
├── tests/
└── docs/rules/            # 이 문서
```

| 폴더 | 두는 것 | 두지 않는 것 |
| --- | --- | --- |
| `routers/` | 엔드포인트 정의, 스키마 검증, 서비스 호출 | LLM 호출, 데이터 가공 |
| `schemas/` | 요청/응답 모델, LLM 구조화 출력 스키마 | 비즈니스 로직 |
| `services/` | 전처리 → 호출 → 후처리 조립 | 외부 API 직접 호출 |
| `llm/` | LLM 클라이언트, 임베딩, 토큰 계산, 재시도 | FastAPI import |
| `core/` | 로깅, 예외 매핑, 미들웨어 | 특정 기능에만 쓰는 코드 |
| `prompts/` | 버전 붙인 프롬프트 파일 | — |
| `scripts/` | 배치 실행 스크립트 | 배치 전용 로직 (재사용할 것) |

파일은 기능 단위로 나눈다: `health.py`, `normalize.py`, `recommend.py`.
**기능 이름 = 파일 이름 = 담당자**로 경계를 관리한다.

백엔드 서버와 같은 레이어드 구조이며 폴더 이름도 동일하다. 같은 팀이 두
저장소를 오가는데 이름이 다르면 찾는 비용만 늘어난다.

## 5. 판단이 필요한 폴더

표만으로 애매한 세 곳을 설명한다.

### `llm/` — 왜 `services/`와 나누는가

`llm/`은 **FastAPI를 import하지 않는다.** 웹 프레임워크와 분리되어 있어야 노트북에서
실험하고 배치에서 그대로 재사용할 수 있다. 모델 제공자를 바꾸거나 자체 서빙으로 옮길 때도
이 폴더만 교체하면 된다.

백엔드의 `repositories/`에 대응하는 자리다. 백엔드가 DB를 다루듯 AI 서버는 모델을 다룬다.

```python
# app/llm/client.py — 부품
class LLMClient:
    def complete(self, prompt: str, schema: type[BaseModel]) -> BaseModel: ...

# app/services/normalize_service.py — 조립
def normalize_ingredients(raw: list[str], client: LLMClient) -> NormalizeResult:
    prompt = load_prompt("normalize_ingredient_v1")
    parsed = client.complete(prompt.format(items=raw), schema=IngredientList)
    return validate_against_dictionary(parsed)

# app/routers/normalize.py — HTTP만
@router.post("/normalize")
def normalize(req: NormalizeRequest, client=Depends(get_llm_client)):
    return normalize_ingredients(req.items, client)
```

### `prompts/` — 수정하지 말고 버전을 올린다

프롬프트를 코드 문자열로 박으면 한 줄 고치는 데 배포가 필요하다. 파일로 분리하고 이름에
버전을 붙인다.

```
prompts/
├── normalize_ingredient_v1.txt
└── normalize_ingredient_v2.txt   # 기존 파일 수정 대신 새로 만든다
```

품질이 나빠졌을 때 되돌릴 수 있어야 한다.

### `scripts/` — 배치 전용 로직을 만들지 않는다

`app/llm/`과 `app/services/`를 import해서 쓴다. 배치용으로 따로 짜면 API와 결과가 달라진다.

수십만 건 배치는 **중간 저장과 재개**를 반드시 지원한다. 10만 건째에서 죽었을 때 처음부터
다시 돌리면 시간과 비용이 두 배로 든다.

## 6. 아직 만들지 않은 폴더

미리 만들지 않는다. 필요해지는 시점에 이 문서를 갱신하면서 추가한다.

| 폴더 | 추가 시점 |
| --- | --- |
| `app/workers/` | 비동기 큐(작업 ID 발급 후 폴링/콜백)를 도입할 때 |
| `app/deps.py` | 주입할 의존성이 3개 이상일 때. 그 전엔 `app.state`로 충분 |
| `models/` | 임베딩 모델을 로컬 가중치로 올릴 때. 가중치는 커밋하지 않는다 |
| `data/` | 식재료 사전 스냅샷 등을 저장소에 둘 필요가 생길 때 |

`domain/`, `entities/`, `repositories/`, `interfaces/`는 **만들지 않는다.**
AI 서버에는 영속 도메인 객체가 없고, 구현체가 하나뿐인 인터페이스는 빈 껍데기다.

## 7. 개발 규칙

### 7.1 초기화는 앱 시작 시 1회

LLM 클라이언트와 임베딩 모델은 `lifespan`에서 만들어 `app.state`에 보관한다.
요청 핸들러 안에서 생성하면 커넥션 풀이 매번 새로 뜨고, 로컬 임베딩 모델은 첫 요청이
수십 초 걸린다.

### 7.2 헬스체크는 두 개로 분리

| 엔드포인트 | 의미 |
| --- | --- |
| `/health/live` | 프로세스 살아있음 |
| `/health/ready` | 클라이언트 · 모델 초기화 완료 |

초기화가 끝나기 전에 트래픽이 들어오면 전부 실패한다.

### 7.3 LLM 출력은 반드시 검증한다

구조화 출력을 요청하고 Pydantic으로 파싱한다. 파싱 실패는 정상적으로 일어나는 일이므로
재시도 경로를 만들어둔다.

재료명 정규화처럼 결과가 사전에 매핑되어야 하는 작업은, **사전에 없는 값이 나오면 실패로
처리하고 로그에 남긴다.** 임의의 새 재료명이 조용히 들어가면 매핑 테이블이 오염된다.

### 7.4 호출마다 남길 것

```
request_id  model  model_version  prompt_file  input_tokens  output_tokens  latency_ms
```

- `request_id`는 백엔드에서 받은 trace ID를 그대로 전파한다.
- 모델 버전과 프롬프트 버전이 없으면 "언제부터 결과가 이상해졌는지" 추적할 수 없다.

### 7.5 타임아웃과 재시도

| 항목 | 규칙 |
| --- | --- |
| 타임아웃 | 모든 외부 호출에 명시. 기본값에 맡기지 않는다 |
| 재시도 | 지수 백오프, 횟수 상한 |
| 재시도 대상 | 429 · 5xx만. 4xx는 즉시 실패 |
| 실패 응답 | 백엔드가 폴백을 낼 수 있도록 명확한 에러 코드로 반환 |

추천이 실패해도 서비스 본체는 살아있어야 한다.

### 7.6 설정과 비밀값

- 모델 이름, 온도, 타임아웃, 배치 크기는 전부 `config.py`의 환경변수로 뺀다.
  코드 수정 없이 모델을 교체할 수 있어야 롤백이 가능하다.
- **API 키는 `.env`에만. 저장소에는 `.env.example`만 올린다.**
- 매직 넘버 금지. 설정값이나 명명된 상수로 뺀다.

### 7.7 비용

LLM 호출은 건당 비용이 발생한다. 배치 스크립트는 실행 전에 **예상 건수와 예상 비용을
출력하고 확인을 받는다.** 수십만 건 배치를 실수로 두 번 돌리는 것이 가장 흔한 사고다.

## 8. 문서 규칙

### 파일명

`docs/` 하위의 모든 마크다운 문서는 **두 자리 번호 접두사 + 언더스코어**로 시작한다.
단어 구분도 언더스코어를 쓴다.

```
docs/
├── information/
│   ├── 00_project_information.md
│   └── 01_solution_ideation.md
└── rules/
    └── 00_aiserver_rules.md
```

번호는 폴더 안에서의 읽는 순서다. 폴더마다 `00`부터 다시 시작한다.
파일 목록이 알파벳순으로 정렬되어도 의도한 순서가 유지된다.
번호 사이에 문서를 끼워 넣어야 하면 뒤 번호를 밀지 말고 소수점 없이 재부여한다.

저장소 루트의 `00_README.md`는 예외다. GitHub이 자동으로 렌더링하는 관례 파일이므로
이름을 바꾸지 않는다.

### 헤더

모든 문서 첫 줄에 제목, 그 아래에 작성자와 작성일을 적는다.

```markdown
# 문서 제목

> 작성자: 이름 · 작성일: YYYY-MM-DD
```

## 9. Git 컨벤션

### 커밋 메시지 형식

Conventional Commits를 따른다. 제목은 영어로, 명령형 현재시제로 쓴다.

```
<type>: <subject>

<body (선택)>
```

### 타입

| 타입 | 용도 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 (README 등) |
| `style` | 코드 스타일 수정 (포맷팅, 세미콜론 등, 로직 변경 없음) |
| `refactor` | 코드 리팩토링 (기능 변화 없음) |
| `test` | 테스트 코드 추가 및 수정 |
| `chore` | 빌드 프로세스, 패키지 매니저 설정 수정 등 기타 변경 |

### 예시

```
feat: add ingredient normalization endpoint
fix: handle empty inventory in recipe recommendation
docs: add git convention to ai server rules
chore: pin openai sdk version
```

### 규칙

- **하나의 커밋은 하나의 목적만 담는다.** 기능 추가와 리팩토링이 섞이면 되돌릴 수 없다.
- **브랜치명은 영어로.** `feat/ingredient-normalize` 형식으로 타입을 접두사에 쓴다.
- **기본 브랜치에 직접 커밋하지 않는다.** PR을 거친다.
- **`.env`와 API 키는 절대 커밋하지 않는다.** 실수로 올라갔다면 키를 먼저 폐기하고
  재발급한다. 이력에서 지우는 것만으로는 유출이 되돌려지지 않는다.
- 프롬프트 파일 변경은 `feat`이나 `fix`로 분류한다. 프롬프트는 이 서버에서 로직에
  해당하므로 `docs`가 아니다.

## 구성 근거

맨 앞에 "한눈에 보기"를 두어 문서를 다 읽지 않아도 핵심 규칙 5개는 잡히게 했다.
폴더 설명은 표 하나로 요약하고, 판단이 갈리는 세 폴더만 따로 떼어 예시 코드와 함께
설명했다. 이전 버전은 표와 상세 설명이 같은 내용을 두 번 말하고 있었다.

문서를 여러 개로 쪼개지 않는다. 저장소 규모에 비해 문서가 많으면 어느 것을 갱신해야
하는지가 매번 문제가 된다.

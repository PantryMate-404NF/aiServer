# 추천 엔진은 어떻게 동작하는가

**정하는 것**: 팬트리메이트 추천 엔진이 사용자의 취향을 어떻게 만들고, 레시피를 어떻게 고르고 줄 세우는지를 개발자가 아니어도 읽을 수 있는 말로 설명합니다. 내부 식별자와 코드 이름을 쓰지 않습니다

**적용 대상**: 팀 전원, 특히 평가 파트. 노션에 그대로 옮겨 공유합니다. 구현 세부는 이 문서 끝의 기술 문서 목록을 봅니다

**버전**: 1.2.0 · **최종 수정**: 2026-09-12 · **작성자**: 유재현

---

## 1. 이 문서를 읽는 법

추천 엔진은 "사용자가 지금 가진 재료로 만들 수 있고, 그 사람의 입맛에 맞으며, 매번 똑같지는 않은" 레시피 목록을 만듭니다. 이 문서는 그 일을 네 부분으로 나눠 설명합니다.

| 부분 | 무엇을 하나 | 절 |
|---|---|---|
| 취향 만들기 | 사용자가 어떤 맛을 좋아하는지를 숫자로 만듭니다 | 3절 |
| 후보 고르기 | 가진 재료로 만들 수 있는 레시피를 추립니다 | 4절 |
| 점수 매기기 | 추린 레시피마다 "이 사람에게 얼마나 맞는가" 를 셉니다 | 5절 |
| 목록 다듬기 | 비슷한 것끼리 몰리지 않게 섞고, 새로운 시도를 몇 개 끼웁니다 | 6절 |

수식은 되도록 말로 풀었습니다. 숫자 가운데 아직 실제 데이터로 확인하지 않은 것은 `(예시값, 실제 데이터로 대체 필요)` 라고 표시했습니다. 그 값들은 실제 사용자 데이터가 쌓인 뒤 다시 정합니다.

---

## 2. 한눈에 보는 흐름

```text
사용자 (재료, 취향, 최근 행동)
        │
        ▼
 ① 후보 고르기   가진 재료로 만들 수 있는 레시피 최대 500개. 알레르기 재료가 든 것은 여기서 완전히 뺍니다
        │
        ▼
 ② 점수 매기기   레시피마다 17가지 신호를 재서 0~1 점수. 최근 본 것과 이미 만든 것은 감점
        │
        ▼
 ③ 목록 다듬기   비슷한 레시피가 몰리지 않게 순서를 잡고, 20% 는 "새로운 시도" 로 채웁니다
        │
        ▼
 추천 목록 (레시피, 이유 문구, 어떤 경로로 뽑혔는지)
```

세 단계는 각각 독립된 부품입니다. 후보 고르기는 데이터베이스가 하고, 점수 매기기와 목록 다듬기는 추천 엔진이 합니다. 같은 입력을 넣으면 같은 결과가 나오도록 만들어서, 나중에 "왜 이 추천이 나왔는가" 를 그대로 다시 재현할 수 있습니다.

## 3. 사용자의 취향은 어떻게 만드는가

### 3.1 맛을 여섯 가지 축으로 봅니다

모든 레시피는 여섯 가지 맛의 세기를 0에서 1 사이 숫자로 갖습니다 — 매움, 짠맛, 단맛, 신맛, 감칠맛, 기름짐입니다. 이 값은 데이터 파트가 레시피의 재료 구성에서 계산합니다. 예를 들어 김치찌개는 매움과 감칠맛이 높고 단맛은 낮습니다.

사용자의 취향도 같은 여섯 축으로 표현합니다. 그래야 "이 레시피가 이 사람에게 맞는가" 를 같은 잣대로 비교할 수 있습니다. 핵심은 **취향을 사용자에게 직접 묻지 않고, 사용자가 실제로 고른 음식에서 계산한다**는 점입니다.

### 3.2 온보딩에서 받는 두 가지

가입 때 사용자는 두 가지를 알려 줍니다.

| 입력 | 형태 | 취향 계산에 쓰는가 |
|---|---|---|
| 좋아하는 음식 고르기 | 제시된 음식 20개 가운데 3개 이상 | **씁니다.** 고른 음식들의 여섯 축 평균이 그 사람의 첫 취향입니다 |
| 맛 척도 직접 적기 | 짠맛·단맛·매운맛 세 가지를 5단계로 | 고른 음식이 있으면 **쓰지 않고 저장만 합니다** |

직접 적은 척도를 쓰지 않는 이유는 둘이 어긋날 때 고른 음식 쪽이 더 믿을 만하기 때문입니다. "매운맛 3점" 이 사람마다 다른 뜻인 반면, 김치찌개와 마라탕을 골랐다는 사실은 해석의 여지가 없습니다. 척도는 버리지 않고 보관합니다. 나중에 사용자가 말로 요청하는 추천 기능이 생기면 "이 사람이 말하는 3점이 실제 취향과 얼마나 맞는가" 를 보정하는 참고값이 됩니다.

우선순위는 다음과 같습니다.

1. 고른 음식이 있으면 그것으로 취향을 만듭니다.
2. 고른 음식이 없으면 직접 적은 척도로 만듭니다. 이때는 앞 세 축(매움, 짠맛, 단맛)만 알고 나머지 세 축은 "모름" 으로 둡니다.
3. 둘 다 없으면 취향 없이 시작합니다(3.6).

### 3.3 행동이 쌓이면 취향이 움직입니다

사용자가 레시피를 고르거나 저장하거나 만들 때마다 백엔드가 그 레시피를 엔진에 알려 줍니다. 엔진은 그 레시피의 여섯 축 맛과 시각을 기록해 두고, 추천할 때마다 기록을 다시 읽어 취향을 계산합니다. 미리 계산해 둔 값을 갱신하는 것이 아니라 **매번 원본에서 다시 만듭니다.** 그래서 계산 방식이 바뀌어도 과거 기록으로 새 취향을 만들 수 있습니다.

취향은 처음 취향(온보딩)과 행동에서 본 취향을 섞은 것입니다. 축마다 다음과 같이 섞습니다.

```text
취향 = (k x 처음 취향 + S x 행동 취향) / (k + S)
```

- 행동 취향은 기록된 레시피들의 맛을 무게를 두어 평균한 것입니다.
- S 는 그 무게의 합입니다. 행동이 많을수록, 최근일수록 큽니다.
- k 는 처음 취향을 "행동 몇 건과 같은 무게로 볼지" 입니다. 고른 음식으로 만든 처음 취향은 조리 12건(예시값, 실제 데이터로 대체 필요)과 같은 무게이고, 직접 적은 척도로 만든 것은 그 절반입니다.

행동이 하나도 없으면 S 가 0 이라 처음 취향 그대로입니다. 행동이 쌓일수록 행동 쪽으로 옮겨 가고, 행동의 무게가 k 를 넘으면 행동이 더 큰 목소리를 냅니다. 이 상태를 각각 "온보딩", "섞임", "행동" 이라고 부르며 추천 로그에 남깁니다.

행동의 종류에 따라 무게가 다릅니다. 실제로 만든 것이 가장 무겁고(1.0), 저장(0.6), 클릭(0.3) 순입니다. 별점은 높을수록 무겁고 3점 아래는 무게가 없으며, 만점이어도 실제로 만든 것 한 번보다 무거워지지 않습니다. 1~5점 밖의 별점은 잘못된 기록으로 세고 쓰지 않습니다. "관심 없음" 이나 "저장 취소" 처럼 싫다는 신호는 취향을 만드는 데 쓰지 않습니다 — 취향은 좋아한 것으로만 만듭니다.

### 3.4 오래된 선택은 잊습니다

1년 전에 고른 음식과 지난주에 고른 음식이 같은 무게라면 입맛이 바뀐 것을 따라갈 수 없습니다. 그래서 행동 하나의 무게는 시간이 지날수록 줄어듭니다. 줄어드는 속도는 "반감기" 로 정합니다. 반감기가 90일(예시값, 실제 데이터로 대체 필요)이면 석 달 전 행동은 절반, 반년 전 행동은 4분의 1, 1년 전 행동은 6% 의 무게만 남습니다.

이 감쇠는 3.3의 식과 맞물려 자연스러운 결과를 냅니다. 오래된 행동의 무게가 줄면 S 가 줄고, 취향은 다시 처음 취향 쪽으로 돌아옵니다. 한동안 아무것도 하지 않은 사용자는 가입 때의 취향으로 서서히 되돌아가는 셈입니다.

### 3.5 계절과 시기를 봅니다

같은 음식이라도 여름과 겨울에 끌리는 것이 다릅니다. 그래서 행동의 무게에 "지금과 얼마나 같은 시기인가" 를 곱합니다. 지난여름의 냉면은 이번 여름 추천에 더 무겁게, 지난겨울의 김치찌개는 가볍게 반영됩니다.

세 가지 주기를 봅니다 — 1년(계절), 1주(요일), 하루(시간대)입니다. 주기마다 "세기" 가 있어서 0 이면 그 주기를 무시하고, 1 이면 정반대 시기의 행동을 완전히 무시합니다. 지금은 계절만 절반 세기로 켜 두고 요일과 시간대는 꺼 두었습니다(예시값, 실제 데이터로 대체 필요). 세기 1 은 권하지 않습니다 — 반대 계절의 행동이 전부 사라져 취향이 갑자기 비어 버릴 수 있습니다.

### 3.6 취향을 모르는 사용자

고른 음식도 척도도 없는 사용자는 취향이 비어 있습니다. 이때 엔진은 임의의 취향을 지어내지 않습니다. 임의로 넣으면 "일관되게 엉뚱한" 추천이 되기 때문입니다. 대신 맛 신호를 점수에서 빼고(5.2), 목록의 새로운 시도 비율을 20% 에서 40% 로 올려(6.2) 여러 종류의 레시피를 보여 줍니다. 사용자가 무엇이든 고르기 시작하면 그때부터 취향이 만들어집니다.

### 3.7 어디에 저장하는가

사용자마다 파일 하나에 원본을 둡니다 — 고른 음식, 직접 적은 척도, 행동 기록(레시피, 종류, 시각, 그때의 맛)입니다. 계산 결과가 아니라 원본을 두는 이유는 레시피의 맛 값이 나중에 고쳐질 수 있기 때문입니다. 원본이 있으면 다시 계산하면 되고, 결과만 있으면 사용자를 다시 모아야 합니다.

사용자가 늘어도 감당하도록 파일을 256개 폴더에 나눠 두고, 저장할 때 2년보다 오래되었거나 2,000건을 넘는 기록은 잘라냅니다(예시값, 실제 데이터로 대체 필요). 기본 설정에서는 그렇게 오래된 기록의 무게가 1% 도 되지 않아 결과에 영향이 없습니다. 파일 안의 사용자 번호와 요청한 사용자 번호가 다르면 읽지 않고, 같은 사용자의 기록을 동시에 저장해도 서로 덮어쓰지 않게 순서를 세웁니다. 실제 데이터베이스가 연결되면 이 파일의 내용을 데이터베이스로 옮깁니다.

## 4. 후보를 고르는 단계

사용자가 가진 재료 목록으로 "만들 수 있는 레시피" 를 데이터베이스에서 한 번에 뽑습니다. 기준은 셋입니다.

| 기준 | 내용 |
|---|---|
| 알레르기 | 알레르기 재료가 하나라도 들어 있으면 **후보에서 완전히 뺍니다.** 점수를 낮추는 것이 아니라 아예 보이지 않게 합니다 |
| 부족 재료 | 필수 재료 가운데 없는 것이 2개 이하인 레시피만 봅니다 |
| 조리 시간 | 사용자가 상한을 정했으면 그보다 오래 걸리는 레시피는 뺍니다 |

후보는 최대 500개(예시값, 실제 데이터로 대체 필요)까지 봅니다. 후보가 20개도 안 되면 세 단계로 조건을 풉니다 — 먼저 부족 재료 상한을 4개로 늘리고, 그래도 모자라면 인기 있는 레시피로 채웁니다. 조리 시간 상한은 마지막까지 지킵니다. 어떤 단계까지 풀었는지는 로그에 남습니다.

## 5. 점수를 매기는 단계

### 5.1 17가지 신호

후보 레시피마다 17가지 신호를 재고, 각 신호에 정해진 비중을 곱해 더합니다. 신호는 네 묶음입니다.

| 묶음 | 신호 | 비중(예시값, 실제 데이터로 대체 필요) |
|---|---|---|
| 재료 | 필수 재료를 얼마나 갖췄나 · 부족 재료가 몇 개인가 · 유통기한 임박 재료를 쓰는가 · 가진 재료를 얼마나 활용하는가 | 24% · 5% · 15% · (0%) |
| 취향 | 맛이 취향과 맞는가 · 좋아하는 재료가 들었나 · 좋아하는 요리군인가 · 좋아하는 요리 종류인가 · 전에 만든 것과 재료가 비슷한가 | 16% · 11% · 4% · (0%) · 10% |
| 품질 | 인기 · 품질 점수 | 10% · (0%) |
| 상황 | 조리 시간이 맞는가 · 계절에 맞는가 · 난이도가 실력에 맞는가 | 3% · 2% · (0%) |

비중이 0% 인 신호는 재기는 하되 아직 순위에 쓰지 않는 것입니다. 나머지 셋(재료 협업 필터링, 그룹 선호, 내용 기반 유사도)은 계산 수단이 아직 없어 비어 있습니다. 비중은 실제 사용자 데이터로 "어느 레시피가 더 좋았는가" 를 학습해 다시 정할 계획입니다.

맛이 취향과 맞는가는 사용자의 여섯 축 취향과 레시피의 여섯 축 맛이 얼마나 같은 방향인지로 잽니다. 이때 전체 레시피의 평균 맛을 양쪽에서 뺀 뒤 비교합니다. 빼지 않으면 모든 값이 양수라 무엇을 넣어도 비슷하게 나옵니다 — "평균보다 매운 것을 좋아하는 사람에게 평균보다 매운 레시피" 가 맞는 비교입니다.

### 5.2 모르는 것은 빼고 셉니다

어떤 신호는 특정 사용자나 레시피에 대해 잴 수 없습니다. 이력이 없는 새 사용자는 "좋아하는 재료" 를 모르고, 취향의 뒤 세 축을 모르는 사용자는 그 축으로 맛을 비교할 수 없습니다.

이럴 때 그 신호를 0 점으로 치지 않습니다. **아예 계산에서 빼고, 그 신호의 비중도 함께 뺍니다.** 남은 신호들의 비중이 자동으로 커져서 합이 다시 1 이 됩니다. "모른다" 와 "나쁘다" 를 구분하지 않으면 새 사용자가 모든 신호에서 0 점을 받아 인기 레시피만 보게 됩니다. 이 규칙 덕분에 나중에 데이터가 생기면 코드를 고치지 않아도 그 신호가 저절로 켜집니다.

### 5.3 감점은 곱하기입니다

점수를 다 매긴 뒤 두 가지를 감점합니다 — 최근 7일 안에 보여 준 레시피는 0.7 배, 최근 14일 안에 만든 레시피는 0.5 배(예시값, 실제 데이터로 대체 필요)입니다. 기피 재료가 들어 있으면 그 수에 따라 더 깎되 0.8 배까지만 깎습니다. 더하고 빼는 대신 곱하는 이유는 원래 점수가 높은 레시피일수록 더 크게 내려가야 "이미 봤는데 또 1등" 이 되지 않기 때문입니다.

## 6. 목록을 다듬는 단계

### 6.1 비슷한 것끼리 몰리지 않게

점수 순서대로 그냥 자르면 김치찌개, 김치볶음밥, 김치전이 나란히 나옵니다. 그래서 한 자리씩 채울 때마다 "점수가 높으면서, 이미 뽑은 것들과 재료가 다른" 레시피를 고릅니다. 점수와 다양성의 비율은 7 대 3(예시값, 실제 데이터로 대체 필요)입니다. 재료가 겹치는 정도를 잴 때는 소금이나 물처럼 어디에나 들어가는 재료를 가볍게 봅니다.

### 6.2 새로운 시도

목록의 20% 는 취향 점수와 상관없이 "새로운 시도" 로 채웁니다. 취향만 따르면 사용자가 좋아하는 것만 계속 보게 되고, 취향이 바뀌어도 엔진이 알 길이 없기 때문입니다. 새로운 시도는 두 방식을 반씩 씁니다 — 하나는 상위 200개 안에서 무작위로, 다른 하나는 "이 사용자가 아직 잘 안 본 레시피 묶음" 을 골라 그 안에서 가장 좋은 것을 뽑습니다. 후보가 너무 적어 억지로 채워야 할 때는 새로운 시도 칸을 줄이고, 몇 칸을 줄였는지 기록에 남깁니다. 그래서 후보를 고르는 단계는 새로운 시도 칸까지 채울 만큼 후보를 더 가져옵니다(20개 목록에 36개, 취향이 없으면 52개). 레시피 묶음 정보가 아직 없을 때는 두 방식 대신 전부 무작위로 뽑고 그 사실도 기록에 남깁니다.

새로운 시도로 뽑힌 레시피는 목록의 무작위 위치에 끼웁니다. 항상 맨 아래에 두면 아무도 안 보고, 항상 위에 두면 취향 추천을 밀어내기 때문입니다.

### 6.3 노출 확률을 함께 남깁니다

새로운 시도로 뽑힌 레시피에는 "이 레시피가 이 자리에 뽑힐 확률이 얼마였는가" 를 함께 기록합니다. 무작위로 뽑힌 것은 그 확률이 낮고, 취향으로 뽑힌 것은 1 입니다. 이 값이 있어야 평가 파트가 나중에 "새로운 시도가 실제로 반응을 얻었는가" 를 공정하게 잴 수 있습니다. 확률이 낮은 자리에서 얻은 반응은 그만큼 크게 쳐 주는 방식입니다. 이 값은 나중에 채울 수 없으므로 추천하는 순간에 반드시 남깁니다.

### 6.4 추천 이유 문구

레시피마다 "왜 이것을 추천하는가" 를 한 문장으로 붙입니다. 그 레시피의 신호 가운데 다른 후보보다 두드러진 것을 골라 문구로 바꿉니다 — "가지고 계신 재료로 바로 만들 수 있어요", "선호하시는 매운맛에 맞아요" 같은 식입니다. 새로운 시도로 뽑힌 레시피는 "새로운 시도는 어떠세요" 라고 솔직하게 씁니다. 취향과 반대 방향인 맛을 "선호하시는" 이라고 말하지 않도록 방향도 확인합니다.

## 7. 무엇을 기록하고 왜 남기는가

추천 한 번마다 다음을 기록합니다. 기록의 목적은 두 가지입니다 — 나중에 그 추천을 그대로 재현하는 것, 그리고 평가 파트가 추천의 효과를 재는 것입니다.

| 기록 | 왜 남기나 |
|---|---|
| 보여 준 레시피와 순서, 각각의 노출 확률 | 효과 측정의 기본 재료입니다. 확률은 나중에 못 채웁니다 |
| 각 레시피의 17가지 신호 값 | "왜 이 순서였는가" 를 다시 계산하는 데 필요합니다 |
| 그때의 비중과 손잡이 값의 지문 | 값을 바꾼 뒤에도 옛 추천을 그때 방식으로 재현합니다 |
| 취향의 출처와 상태 | 고른 음식 · 척도 · 없음 가운데 무엇으로 만든 취향인지, 온보딩 · 섞임 · 행동 가운데 어느 상태인지. 평가 파트가 사용자 집단을 나눌 때 씁니다 |
| 후보 고르기에서 어느 단계까지 풀었는지 | 재료가 부족해 인기 레시피로 채운 추천은 취향 추천과 따로 봐야 합니다 |

기록 실패가 추천 실패가 되지는 않습니다. 기록에 실패하면 추천은 그대로 내보내고 실패 횟수를 셉니다. 다만 그 횟수를 밖에서 볼 수 있게 하는 일은 아직 남아 있습니다(8절).

## 9. 어떻게 검증했나

실제 데이터베이스와 사용자가 아직 없어서 두 가지로 검증했습니다.

**단위 검사 276건.** 각 부품이 정해진 대로 동작하는지 하나씩 확인합니다. 예를 들면 "알레르기 재료가 든 레시피는 절대 나오지 않는다", "고른 음식이 있으면 직접 적은 척도를 바꿔도 취향이 변하지 않는다", "반감기가 지나면 무게가 정확히 절반이 된다", "같은 행동을 순서만 바꿔 넣어도 취향이 같다" 같은 것들입니다. 전부 통과했고 새로 만든 취향 부품은 모든 줄이 검사를 거쳤습니다.

**세 번째 복기.** 구현이 끝난 뒤 세 관점(회의 결정과 맞는가, 에러 없이 틀리는 자리가 있는가, 규칙과 문서가 맞는가)으로 코드를 다시 읽어 열다섯 곳을 찾았습니다. 별점 하나가 온보딩 취향 전체를 덮을 수 있던 것, 저장 파일의 사용자 번호를 확인하지 않던 것, 같은 사용자를 동시에 저장하면 실패하던 것, 후보가 적을 때 새로운 시도 칸이 설계보다 적게 채워지던 것 같은 것들입니다. 열네 곳을 고치고 각각 재발하면 실패하는 검사를 붙였으며, 한 곳은 문서 문구였습니다.

**가상 사용자 12명.** 재료·취향·알레르기·조리 시간이 다른 열두 명을 만들어 레시피 120개 위에서 추천을 끝까지 돌려 봤습니다. 실제 데이터가 없으므로 "정확한가" 가 아니라 "명세대로 움직이는가" 와 "방향이 맞는가" 를 봅니다.

| 확인한 것 | 결과 |
|---|---|
| 알레르기 재료가 든 레시피가 나온 적이 있는가 | 없음 (해당 사용자 4명 전원) |
| 조리 시간 상한을 넘긴 레시피가 나온 적이 있는가 | 없음 (해당 사용자 9명 전원) |
| 취향 출처 | 고른 음식 10명 · 척도 1명 · 없음 1명 |
| 취향이 없는 사용자의 새로운 시도 칸 | 20개 중 8개 (다른 사용자는 4개) |
| 매운 레시피를 최근 16번 만든 뒤 | 취향의 매움이 0.22 에서 0.57 로, 상위 5개의 매움 평균이 0.40 에서 0.53 으로 오름 |
| 같은 16번을 1년 전에 만든 것으로 두면 | 취향이 0.26 으로 온보딩 값 근처로 돌아옴 (잊는 것이 동작함) |
| 노출 확률이 0 과 1 사이인가 | 전건 |
| 추천 이유 문구가 비어 있는가 | 없음 |
| 후보 500개 기준 소요 시간 | 상위 95% 가 약 20 밀리초 (목표 58 밀리초) |

한 가지 한계가 있습니다. 가상 레시피 120개의 맛 값은 시험용으로 만든 것이라 실제 레시피의 맛 분포와 다릅니다. 그래서 고른 음식으로 만든 취향이 가상 레시피의 평균보다 전반적으로 낮게 놓여, 맛 정합의 효과가 실제보다 작게 나옵니다. 실제 데이터에서는 취향과 레시피가 같은 방식으로 계산되므로 생기지 않는 문제입니다.

## 11. 평가 파트가 자주 물을 것

**취향이 왜 안 바뀌나요?** 행동의 무게 합이 처음 취향의 무게(12)보다 작으면 처음 취향이 더 큰 목소리를 냅니다. 조리 12번 또는 클릭 40번쯤이 넘어야 행동이 앞섭니다. 이것은 의도한 것으로, 한두 번 눌러 본 것으로 취향이 흔들리지 않게 합니다.

**노출 확률이 왜 필요한가요?** 새로운 시도로 뽑힌 레시피는 취향과 상관없이 뽑혔으므로, 그 레시피에 대한 반응을 그대로 세면 편향이 생깁니다. 확률로 나눠서 세면 편향이 사라집니다. 확률은 뽑는 순간에만 알 수 있어서 나중에 채울 수 없습니다.

**"모름" 과 0 은 왜 다른가요?** 0 은 "그 맛이 없다" 이고 모름은 "물어보지 않았다" 입니다. 모름을 0 으로 채우면 신맛을 물어본 적 없는 사람이 신맛을 싫어하는 사람이 됩니다. 그래서 모르는 축은 계산에서 빼고, 데이터가 오면 켭니다.

**추천 로그에서 사용자를 어떻게 나누나요?** 취향 출처(고른 음식 · 척도 · 없음)와 상태(온보딩 · 섞임 · 행동)가 기록마다 있습니다. 취향 없는 사용자는 새로운 시도 비율이 달라서 따로 봐야 합니다. 후보 고르기에서 인기 레시피로 채운 추천도 따로 보는 것이 좋습니다.

**지금 쌓이는 추천 로그를 평가에 써도 되나요?** 아직은 안 됩니다. 웹 입구가 시험용 응답을 내고 있어 실제 엔진의 추천이 아닙니다. 입구와 엔진이 연결된 뒤의 로그부터 씁니다.

# 추천 평가 파트의 타 파트 요청 초안 (Track C)

**정하는 것**: 평가 관측 파이프라인이 실데이터에서 돌기 위해 파트 A, 파트 B, 백엔드, 3인 합의에 요청할 것. 요청마다 무엇을, 왜, 선택지, 파트 C 의 제안, 필요한 시점, 답이 없을 때의 기본값, 그대로 보낼 글

**적용 대상**: 김민경(전달자)과 요청을 받는 파트 A·B, 백엔드. 받는 쪽은 자기 절만 읽어도 됩니다

**버전**: 1.0.0 · **최종 수정**: 2026-09-18 · **작성자**: 김민경

---

## 1. 읽는 법

평가 파이프라인의 코드는 끝났고 합성 기록으로 끝까지 돕니다. 남은 것은 실 DB 에서의 첫 실행이며 아래 요청이 그 선행입니다. 요청은 받는 사람별로 묶었고, 각 요청의 "보낼 글" 은 팀 채널이나 Notion 에 그대로 붙일 수 있게 썼습니다.

| 받는 쪽 | 요청 수 | 가장 급한 것 | 절 |
|---|---|---|---|
| 파트 A | 4 | 읽기 허용 범위 확인 | 2절 |
| 파트 B | 6 | 라우터·엔진 연결일 | 3절 |
| 백엔드 | 2 | 목록 이벤트의 `request_id`·`position` | 4절 |
| 3인 합의 | 3 | 가명화 salt | 5절 |

"필요한 시점" 이 같은 요청은 DB 전환일의 `make eval-smoke SINCE=<연결일>` 첫 실행 전에 한꺼번에 받으면 됩니다. 답이 없으면 기본값으로 진행하고 답이 오면 되돌립니다.

## 2. 파트 A (데이터)

### 2.1 평가 내보내기의 읽기 범위 확인

| 항목 | 내용 |
|---|---|
| 무엇을 | 평가 내보내기가 `recipe_feature.all_ids`, `recipe_ingredient` 의 재료별 레시피 수, `app_user.is_simulated`, `recipe_feature` 건수를 읽는 것 |
| 왜 | 목록 다양성(ILD)의 입력이 레시피의 재료 집합과 재료 IDF 입니다. IDF 는 `log(레시피 수 / 그 재료가 든 레시피 수)` 로 계산합니다. 가상 유저는 평가에서 뺍니다 |
| 선택지 | (a) 읽기 허용 (b) 필요한 값을 `recommendation_log` 에 함께 저장 |
| 제안 | (a). 로그를 키우지 않습니다. 읽기만 하고 SQL 은 `src/features/recommend/repository_eval.py` 한 파일에 있습니다 |
| 필요한 시점 | `make eval-smoke` 첫 실행 전 |
| 기본값 | 허용으로 가정하고 진행 |

```text
[평가 파트 → 파트 A] 읽기 범위 확인 부탁드립니다.
평가 내보내기가 recipe_feature.all_ids, recipe_ingredient 의 재료별 레시피 수(GROUP BY ingredient_id),
app_user.is_simulated, recipe_feature 건수를 읽습니다. 쓰지 않고 읽기만 합니다.
SQL 은 src/features/recommend/repository_eval.py 에 모아 두었습니다.
IDF 를 log(N / df) 로 계산하는데, 엔진이 쓰는 IDF 와 같은 정의인지도 확인 부탁드립니다.
문제가 있으면 알려 주세요. 답이 없으면 허용으로 보고 DB 전환일에 첫 실행을 합니다.
```

### 2.2 카탈로그 커버리지의 분모

| 항목 | 내용 |
|---|---|
| 무엇을 | 카탈로그 커버리지(기간 내 노출된 고유 레시피 수 / 전체 레시피 수)의 분모를 46,353 과 46,552 가운데 무엇으로 할지 |
| 왜 | 두 숫자가 문서에 섞여 있고 분모가 다르면 리포트끼리 비교할 수 없습니다. 목표치 15% 와의 비교에도 쓰입니다 |
| 선택지 | (a) 46,353(추천 후보가 될 수 있는 레시피) (b) 46,552(크롤 전체) (c) 실행 시점의 `recipe_feature` 건수 |
| 제안 | (a) 또는 (c). 추천될 수 없는 레시피를 분모에 넣으면 커버리지가 구조적으로 낮게 나옵니다 |
| 필요한 시점 | 첫 실데이터 리포트 전 |
| 기본값 | `recipe_feature` 건수를 쓰고 리포트의 `stamp.catalog_size_source` 에 출처를 찍습니다. `--catalog-size` 로 덮어쓸 수 있습니다 |

```text
[평가 파트 → 파트 A] 카탈로그 커버리지의 분모를 정해 주세요.
46,353 과 46,552 가 문서에 섞여 있습니다. 평가 리포트는 기본으로 실행 시점의 recipe_feature 건수를 쓰고
출처를 리포트에 찍어 둡니다. 추천 후보가 될 수 있는 레시피 수가 맞는 분모라고 보는데, 그 수가 무엇인지 알려 주세요.
```

### 2.3 맛 벡터가 전부 0 인 레시피의 뜻

| 항목 | 내용 |
|---|---|
| 무엇을 | `recipe_feature.flavor_vec` 가 `[0,0,0,0,0,0]` 인 행이 "배치가 아직 안 돈 것" 인지 "맛이 없는 것으로 계산된 것" 인지 |
| 왜 | 품질 스냅샷의 `flavor_all_zero_ratio` 가 이 비율을 셉니다. 뜻을 모르면 상승이 경보인지 정상인지 가를 수 없습니다. 컬럼이 `NOT NULL` 이라 null 로는 구분되지 않습니다 |
| 선택지 | (a) 미처리는 별도 표시(예: 배치 실행 기록과 조인) (b) 전부 0 은 항상 미처리로 간주 |
| 제안 | 확인만 부탁드립니다. (b) 가 사실이면 스냅샷의 경보 문구를 "배치 미처리 비율" 로 바꿉니다 |
| 필요한 시점 | 첫 `quality --db` 실행 전 |
| 기본값 | 비율만 보고하고 경보는 내지 않습니다 |

```text
[평가 파트 → 파트 A] flavor_vec 가 전부 0 인 레시피는 무엇을 뜻하나요?
배치 미처리인지, 계산 결과가 0 인지 알려 주세요. 품질 스냅샷이 이 비율을 매일 세는데
뜻에 따라 경보로 다룰지가 갈립니다. 미처리를 가를 다른 표시(배치 실행 기록 등)가 있으면 그것도 알려 주세요.
```

```text
옮긴다면 검사 파일도 함께 옮기겠습니다. 급하지 않습니다.
```

### 3.3 Thompson 픽의 노출 확률 귀속

| 항목 | 내용 |
|---|---|
| 무엇을 | 탐색 슬롯 가운데 Thompson 경로로 뽑힌 항목의 `propensity` 를 어떻게 정의할지(파트 B 의 미결 안건) |
| 왜 | 오프폴리시 추정은 `1 / propensity` 로 가중합니다. 확률의 정의가 실제 노출 확률과 다르면 추정치가 조용히 틀립니다 |
| 선택지 | (a) 조건부 확률로 분배 (b) `explore_source` 구분만 두고 그대로 (c) 변경 없음 |
| 제안 | (a). 확률의 정의가 추정의 분모입니다 |
| 필요한 시점 | 없음 |
| 기본값 | 추정기가 `explore_source` 별로 나눠 보고하고 `thompson` 경로의 추정치는 인용하지 않습니다 |

```text
[평가 파트 → 파트 B] Thompson 픽의 propensity 정의를 조건부 확률 분배로 정해 주시면 좋겠습니다.
오프폴리시 추정이 1/propensity 로 가중하기 때문에 이 값이 실제 노출 확률이어야 합니다.
정해지기 전에는 thompson 경로의 추정치를 인용하지 않고 uniform 경로와 나눠서만 보고합니다.
```

## 4. 백엔드

### 4.1 목록 이벤트의 `request_id` 와 `position`

| 항목 | 내용 |
|---|---|
| 무엇을 | 추천 목록에서 일어난 이벤트(`impression`, `click`, `save`, `dismiss`, `rating`)를 `/v1/events` 로 보낼 때 그 추천의 `request_id` 와 목록에서의 `position`(1 부터)을 함께 보내는 것 |
| 왜 | 평가의 정답은 `request_id` 로 추천과 이벤트를 이어서 만듭니다. 없으면 그 반응은 어느 추천의 결과인지 알 수 없어 버려집니다. `position` 은 위치 편향 보정에 필요하고 나중에 채울 수 없습니다 |
| 제안 | 추천 응답의 `request_id` 와 각 항목의 `final_rank` 를 프론트가 보관했다가 이벤트에 실어 주세요. 목록 밖(레시피 상세, 검색)에서 일어난 `cook` 등은 비워 두어도 됩니다 |
| 필요한 시점 | 이벤트 API 실연결 전 |
| 기본값 | 없음. 품질 스냅샷이 이 비율을 매일 세고 0 보다 크면 경보를 냅니다 |

```text
[평가 파트 → 백엔드] 추천 목록에서 일어난 이벤트에 request_id 와 position 을 붙여 주세요.
대상은 impression · click · save · dismiss · rating 입니다. request_id 는 /v1/recommend 응답의 값,
position 은 그 항목의 final_rank(1 부터)입니다. 이 둘이 없으면 그 반응을 추천의 결과로 셀 수 없고
position 은 나중에 채울 수 없습니다. 목록 밖에서 일어난 cook 은 비워 두어도 됩니다.
```

## 5. 3인 합의

### 5.1 가명화 salt

| 항목 | 내용 |
|---|---|
| 무엇을 | 평가 내보내기가 `user_id` 를 가명화할 때 쓰는 salt 를 후기 작성자 해시의 `REVIEW_SALT` 와 같이 쓸지 |
| 왜 | 평가 파일에는 원본 `user_id` 를 싣지 않고 HMAC-SHA256 앞 16자를 씁니다. 같은 salt 면 후기 작성자 가명과 유저 가명이 같은 키로 묶입니다 |
| 선택지 | (a) 같은 salt (b) 평가 전용 salt |
| 제안 | (b). `EVAL_SALT` 를 `.env` 에 따로 둡니다. 없으면 내보내기가 멈춥니다 |
| 필요한 시점 | `make eval-smoke` 첫 실행 전. 값은 팀 비밀 저장소에 넣어야 합니다 |
| 기본값 | (b). 코드가 이미 그렇게 되어 있습니다 |

```text
[3인 합의] 평가 내보내기의 user_id 가명화에 평가 전용 salt(EVAL_SALT)를 쓰려 합니다.
REVIEW_SALT 와 같이 쓰면 후기 작성자 가명과 유저 가명이 같은 키로 묶입니다.
동의하시면 값을 만들어 팀 비밀 저장소에 넣겠습니다. 한번 정하면 바꿀 때 이전 파일의 유저 가명과 이어지지 않습니다.
```

### 5.2 품질 스냅샷의 저장소와 보존 기간

| 항목 | 내용 |
|---|---|
| 무엇을 | 매일 1행씩 쌓이는 품질 스냅샷을 테이블(`reco_quality_snapshot`)로 올릴지, 내보낸 평가 파일의 보존 기간을 30일로 할지 |
| 왜 | 지금은 `data/quality/*.jsonl` 파일입니다. 화면이 붙으면 조회가 필요하지만 DB 테이블 변경은 3인 합의 사항입니다. 평가 파일은 가명화했어도 행동 기록이라 기한이 필요합니다 |
| 선택지 | 스냅샷: (a) 테이블 신설 (b) JSONL 유지. 보존: 30일 또는 다른 값 |
| 제안 | 지금은 (b). 화면이 붙고 추이가 3주 이상 쌓이면 (a). 보존은 30일, 리포트 JSON 과 스냅샷만 남깁니다 |
| 필요한 시점 | 스냅샷은 3주 뒤. 보존 기간은 첫 실데이터 내보내기 전 |
| 기본값 | JSONL 유지, 30일 |

```text
[3인 합의] 두 가지입니다. (1) 품질 스냅샷은 당분간 data/quality 의 JSONL 로 두고, 화면이 붙어 3주 이상 쌓이면 테이블 신설을 다시 올리겠습니다.
(2) 평가용으로 내보낸 JSONL 은 30일 뒤 지우고 리포트 JSON 과 스냅샷만 남기려 합니다. 다른 기간이 맞으면 알려 주세요.
```

| 기본값 | 없음 |


## 구성 근거

요청을 작업 기록의 안건 표에 두지 않고 따로 뺀 것은 독자가 다르기 때문입니다. 안건 표는 파트 C 가 무엇에 막혀 있는지를 적은 것이고, 이 문서는 받는 사람이 자기 절만 읽고 답할 수 있게 쓴 것입니다. 그래서 다른 문서의 번호를 쓰지 않고 요청마다 이유와 기본값을 되풀이해 적었습니다.

요청마다 "답이 없을 때의 기본값" 을 둔 것은 평가 파트가 답을 기다리며 멈추지 않기 위해서입니다. 기본값이 없는 것은 연결일 하나뿐이며, 그 값 없이 돌린 평가는 시험용 응답을 재는 것이라 결과에 뜻이 없습니다. 버린 대안은 요청을 하나의 긴 글로 묶어 보내는 것이었고, 받는 쪽이 자기 몫을 찾아야 하는 글은 답이 늦습니다.

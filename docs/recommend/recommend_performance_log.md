# 추천 엔진 성능 기록

**정하는 것**: 추천 엔진의 성능을 재는 잣대와 재는 법, 지금까지의 측정값, 각 수정의 사유 · 내역 · 효과, 다음 시도의 후보. 평가 산출물 셋(기능 평가 보고서 · 안전성 검증 보고서 · 모델 카드와 운영 가이드)의 수치는 이 기록에서 가져갑니다

**적용 대상**: 파트 B · C(유재현), 산출물을 쓰는 팀원, 개선 시도를 이어 가는 AI 코딩 에이전트

**버전**: 1.0.0 · **최종 수정**: 2026-09-29 · **작성자**: 유재현

---

## 1. 이 기록의 쓰임

성능 개선은 **같은 잣대로 같은 조건에서 재고, 바꾼 것과 바뀐 것을 한 줄로 남기는 일**의 반복입니다. 이 문서가 그 장부입니다.

- 시도 하나는 4절의 **행 하나**입니다. 무엇을 왜 바꿨는지, 어느 커밋인지, 잣대가 어떻게 움직였는지, 남길지 되돌릴지를 적습니다.
- 잣대(2절)와 조건(3절)은 고정합니다. 잣대를 바꾸면 그 전 행과 비교할 수 없으므로, 바꿀 때는 새 이름을 쓰고 4절에 "잣대 변경" 행을 둡니다(R2 에 한 번 있었습니다).
- 수치는 **가상 사용자 200명의 상대 비교**입니다. 절대값은 실제 사용자 표본이 오면 다시 잽니다.
- 결정이 필요한 것(가중치는 파트 A 소유, 회전 폭은 기획)은 시도하기 전에 안건(`recommend_engine_meeting_agenda.md`)에 올리고, 여기에는 스윕 결과만 남깁니다.

## 2. 잣대

정답 라벨이 없어 정확도(NDCG · Recall)는 아직 재지 않습니다(D-64). 대신 여섯 묶음을 잽니다. `@10` 은 상위 10, `@20` 은 목록 전체(top_k 20)입니다.

| 묶음 | 잣대 | 뜻 | 방향 |
|---|---|---|---|
| 안전 | 알레르기 누출률 | 목록 가운데 알레르기 재료(재료 또는 제목)가 든 비율 | 0 이어야 함 |
| 안전 | 조리시간 위반률 | 요청의 상한을 넘는 레시피 비율 | 0 이어야 함 |
| 유용성 | 충족률@10 · 부족 재료@10 | 필수 재료 가운데 가진 비율 · 부족한 개수 | 높게 · 낮게 |
| 유용성 | 내 재료 사용@10 | 사용자가 직접 넣은 재료를 몇 가지 쓰는가 | 높게 |
| 유용성 | 임박 재료 소진@5 | 임박 재료가 있는 사용자 중 상위 5 에 그 재료를 쓰는 레시피가 있는 비율 | 높게 |
| 개인화 | 맛 정합@10 | 취향 벡터와 레시피 맛의 중심화 코사인 평균(취향 있는 사용자만) | 높게 |
| 개인화 | 선호 유형 비율@20 | 선호 음식 유형에 속하는 비율(선호가 있는 사용자만) | 높게 |
| 개인화 | 이력 효과@10 · 이력 신호 켜짐 | 이벤트 5건 전후의 점수 순 상위 10 가운데 바뀐 비율 · 상위 10 에서 `f_ing_pref` · `f_cooccur` 값 있는 비율 | 관찰 · 1.0 |
| 다양성 · 공정 | ILD@10 · 판본 구분@10 · 유형 엔트로피@20 | 재료 자카드 기준 목록 안 거리 · 같은 요리의 판본이 하나뿐인 비율 · 유형 분포 엔트로피 | 높게 |
| 다양성 · 공정 | 카탈로그 커버리지 · 노출 Gini · 상위 1% 노출 비율 | 200명 x 20 에서 한 번이라도 나온 레시피 비율 · 노출 집중도 · 상위 1% 레시피가 가져간 노출 | 높게 · 낮게 · 낮게 |
| 다양성 · 공정 | 필수 재료 수 평균 | 상위 목록 레시피의 필수 재료 수(카탈로그 4.33) | 관찰 |
| 안정 | 새로고침 변동@10 · @20 | 같은 세션의 같은 요청을 다시 보냈을 때 **앞 목록 가운데 사라진 비율** | 명세 "조금" |
| 안정 | 세션 뒤 변동@10 | 유예(30분) 뒤 재방문의 점수 순 상위 10 가운데 사라진 비율 | 제품 결정(G-37) |
| 안정 | 재현성 | 같은 후보 · 같은 시드 → 같은 목록 | 전건 |
| 신뢰 | 이유 충실도 위반률 | 사유 문구의 주장이 데이터와 어긋난 비율 | 0 |
| 운영 | 지연 p50 · p95 | `LiveServing.recommend` 한 건(파일 로그 쓰기 포함) | 예산 3초 |
| 안전 | 안전성 사례 | 악의적 · 경계 입력 43 사례의 기대 일치 | 전건 |

"변동" 은 R2 부터 **앞 목록 가운데 뒤 목록에 없는 비율**입니다. R0 · R1 의 새로고침 변동(99.8%)은 자카드 거리였습니다 — 20건 중 4건이 바뀌면 자카드 거리는 0.33, 이 값은 0.20 입니다. 그 두 행의 99.8% 는 어느 잣대로도 "거의 전부" 입니다.

## 3. 재는 법

```bash
# 벤치마크 — 실증 덤프 위 가상 사용자 200명, 엔진 대 기준선 넷. 약 2~3분, 네트워크 · DB 없음
PYTHONUTF8=1 uv run python scripts/eval_recommend_benchmark.py --users 200 --seed 1
#   → data/eval/recommend_benchmark/{summary.json, summary.md, samples.jsonl, logs/}
# 손잡이 · 가중치를 바꿔 같은 사용자 위에서 비교 (코드를 고치기 전에 먼저 이렇게 돌립니다)
PYTHONUTF8=1 uv run python scripts/eval_recommend_benchmark.py --users 200 --seed 1 \
    --out data/eval/sweep/pantry15 --weight f_pantry_use=0.15 --weight f_coverage=0.09
PYTHONUTF8=1 uv run python scripts/eval_recommend_benchmark.py --users 200 --seed 1 \
    --out data/eval/sweep/penalty09 --policy penalty_recent=0.9
# 안전성 — 실제 앱에 악의적 · 경계 입력 43 사례. 계약 · 검증기를 건드렸으면 반드시
PYTHONUTF8=1 uv run python scripts/eval_recommend_safety.py
```

고정 조건: 실증 덤프 21,491건 · 148종(2026-09-21 표본) · 사용자 200명 시드 1(cold 45 · 온보딩 96 · 이력 59 · 알레르기 133) · top_k 20 · 인기 · 후기 · 제철 신호는 덤프에 없어 꺼진 채. 가상 사용자의 냉장고는 흔한 재료 80종에서 뽑으므로 실제보다 서로 비슷합니다 — 노출 집중 수치는 그만큼 과장될 수 있습니다.

지연은 다른 무거운 프로세스가 없을 때 재고, 스윕을 동시에 돌린 실행의 지연은 적지 않습니다. 결과 폴더는 git 이 무시하므로 수치는 이 문서에 옮겨 적습니다.

행을 더하는 법 — ① 바꾸기 전 값이 5절과 같은지 한 번 돌려 확인, ② 손잡이 · 가중치면 `--policy` · `--weight` 로 먼저 스윕, ③ 코드를 바꾸면 벤치마크(+ 계약을 건드렸으면 안전성) 재실행, ④ 4절에 행 추가 · 5절 갱신 · 남길지 되돌릴지 적기.

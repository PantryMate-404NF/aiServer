# 추천 엔진 성능 기록 (사람용 서술본)

**정하는 것**: 추천 엔진의 성능을 어떻게 재고, 지금 어디에 있으며, 무엇을 왜 고쳤고, 다음에 무엇을 해 볼 수 있는지를 사람 말로 적은 것. 정본은 `docs/recommend/recommend_performance_log.md` 이며 행 번호(R0~R3)와 후보 번호(X-01~X-11)는 정본과 같습니다

**적용 대상**: 산출물을 쓰거나 개선을 고를 팀원

**버전**: 1.0.0 · **최종 수정**: 2026-09-29 · **작성자**: 유재현

---

## 1. 어떻게 재는가

정답이 없습니다. "이 사용자에게 이 레시피가 맞다" 는 라벨이 아직 없어서, 정확도 대신 **여섯 가지 대리 지표**로 잽니다 — 안전(알레르기가 새지 않는가), 유용성(가진 재료로 만들 수 있고 상하기 전에 쓰게 하는가), 개인화(취향과 이력을 따르는가), 다양성과 공정(목록 안이 겹치지 않고, 특정 레시피에만 노출이 몰리지 않는가), 안정(새로고침에 얼마나 바뀌는가), 신뢰(추천 이유가 데이터와 맞는가). 여기에 지연과 악의적 입력 43가지가 더 있습니다.

재는 도구는 둘입니다. 하나는 실제 레시피 2만 건 위에 가상 사용자 200명을 만들어 우리 엔진과 단순한 방식 넷(점수만 · 재료 충족률 순 · 무작위 · 알레르기 무시)을 같은 요청으로 나란히 세우는 것, 다른 하나는 실제 앱에 나쁜 입력을 넣어 보는 것입니다. 둘 다 네트워크와 데이터베이스 없이 몇 분 안에 돌고, 같은 시드면 같은 수가 나옵니다. 손잡이나 가중치를 바꿔 보고 싶을 때는 코드를 고치기 전에 인자로 먼저 돌려 봅니다.

수치는 **가상 사용자의 상대 비교**입니다. 가상 사용자의 냉장고는 흔한 재료에서 나와 실제보다 서로 닮았고, 그래서 "노출이 몰린다" 는 수치는 과장돼 있을 수 있습니다.

## 2. 지금까지의 이력

**R0 — 기준선(2026-09-29).** 처음 재 보니 안전과 유용성은 좋았습니다. 알레르기 누출 0(알레르기를 보지 않는 단순 매칭은 11%), 임박 재료를 상위 5 안에서 쓰는 비율 98%(충족률 순은 73%). 그런데 넷이 눈에 띄었습니다 — 추천 이유 문구 6,747건 중 30건이 데이터와 어긋났고, 새로고침하면 상위 열 개의 99.8% 가 바뀌었고, 가중치 덮어쓰기에 잘못된 값이 오면 서버가 500 을 냈고, 알레르기 라벨에 길이 상한이 없었습니다.

**R1 — 결함 넷 수정.** 이유 문구의 어긋남을 0 으로, 500 을 400 으로, 라벨을 100자 이하로. 다른 지표는 그대로였습니다.

**R2 — 새로고침 유예와 선호 하한.** 새로고침이 목록을 통째로 바꾸던 것은 "최근에 보여 준 레시피를 깎는 규칙" 이 방금 보여 준 목록에까지 걸린 탓이었습니다. 유재현이 명세의 "조금 달라진다" 에 맞추기로 정해, 같은 세션(30분) 안의 재요청은 깎지 않게 했습니다. 이제 새로고침에 바뀌는 것은 "새로운 시도" 칸(20건 중 4~8건)뿐이고 개인화 칸은 그대로입니다. 같은 검사에서 조리 한 건이 시간이 조금만 지나도 선호에서 빠지던 하한을 낮췄고, 줄바꿈이 든 라벨이 로그를 위조할 수 있던 틈을 막았습니다. 이때 "변동" 을 재는 잣대를 "앞 목록 가운데 사라진 비율" 로 바꿨습니다 — 자카드 거리보다 "몇 개가 바뀌었나" 에 가깝습니다.

**R3 — 손잡이 스윕.** 코드는 두지 않고 손잡이 여섯 가지를 같은 사용자 위에서 돌려 봤습니다. 목록 안 다양성을 높이는 손잡이(MMR)는 오히려 노출을 더 몰리게 했고, 음식 유형 칸을 늘리는 것은 효과가 없었으며(카탈로그의 88% 가 한식), 냉장고 활용도 가중치를 올리는 것만이 "재료가 적은 레시피로 쏠리는 것" 과 "노출이 몰리는 것" 을 함께 완화했습니다. 세션이 바뀐 뒤 목록을 얼마나 돌릴지는 손잡이 하나로 34~39% 사이에서 정할 수 있습니다.

## 3. 지금 어디에 있는가

| 묶음 | 판정 | 한 줄 근거 |
|---|---|---|
| 안전 | 좋음 | 누출 0, 43 사례 전건, 이유 문구 어긋남 0 |
| 유용성 | 좋음 | 임박 재료 소진 98%, 충족률 96% |
| 개인화 | 보통 | 맛 정합 0.73(재정렬이 0.05 를 내줌), 선호 유형 비율 52% |
| 목록 안 다양성 | 좋음 | 같은 요리 판본 0, 재료 거리 0.83 |
| 사용자 간 공정 | 약함 | 상위 1% 레시피가 노출의 35%, 상위 목록의 필수 재료 평균 2.4개(카탈로그 4.3개) |
| 안정 | 명세대로 | 새로고침은 새로운 시도 칸만(25%), 세션이 바뀌면 39% |
| 운영 | 좋음 | 한 건 59~85ms, 예산 3초의 3% |

가장 약한 곳은 **사용자 간 공정**입니다. "가진 재료로 바로 만들 수 있다" 를 앞세우는 구조가 재료가 적은 레시피를 자꾸 앞에 세우고, 사용자들이 비슷한 재료를 가지고 있으면 같은 레시피가 모두에게 나갑니다.

## 4. 다음에 해 볼 수 있는 것

결정 없이 바로 할 수 있는 것부터 적습니다. 번호는 정본과 같습니다.

- **X-05 새로운 시도 칸에도 이유 붙이기** — 지금은 네 칸 중 하나가 "새로운 시도는 어떠세요" 뿐입니다. "평소와 다른 양식 요리예요" 처럼 적으면 신뢰가 오릅니다. 바로 됩니다.
- **X-07 후보를 500 에서 1,000 으로** — 지금은 모두가 500 에서 잘립니다. 넓히면 더 다양해질 수 있고 지연이 조금 늡니다. 바로 재 볼 수 있습니다.
- **X-01 냉장고 활용도 가중치 올리기** — 쏠림과 집중을 함께 완화하는 유일한 손잡이였습니다. 가중치는 데이터 파트 소유라 합의가 필요합니다.
- **X-04 음식 유형 가중치 올리기** — 양식 · 일식을 좋아하는 사용자에게 효과가 있을 것입니다. 역시 데이터 파트와.
- **X-02 세션 뒤 회전 폭** — 매일 새 목록(39%)이냐 익숙한 목록에 몇 개(34%)냐. 기획이 정할 일입니다.
- **X-03 노출 균형** — 최근에 많이 나간 레시피를 조금 깎아 노출을 퍼뜨리는 장치. 설계가 필요하고, 인기 신호가 들어오면 더 필요해집니다.
- **X-06 이력이 얼마나 빨리 목록을 바꿀지** — 지금은 조리 · 저장 5건에 상위 열 개의 절반이 바뀝니다. 과한지 판단이 필요합니다.
- **X-08 · X-09 탐색 비율과 새로고침 완전 고정** — 평가 표본의 뜻이 바뀌므로 평가 설계와 함께 정합니다.
- **X-10 · X-11 인기 신호와 정확도** — 각각 백엔드 데이터와 사용자 라벨이 와야 합니다.

## 5. 한계

가상 사용자라는 점, 정답 라벨이 없다는 점, 인기 · 후기 · 제철 신호가 꺼져 있다는 점, 지연이 개발 PC 한 대의 값이라는 점입니다. 실제 표본과 라벨이 오면 같은 도구로 다시 잽니다.

## 1. 지금 어디까지 왔나

2026-09-10 하루 동안 추천 엔진의 **Layer 1**, 즉 데이터베이스 없이 순수 함수만으로 돌아가는 부분을 전부 구현했습니다. 계획서 기준으로는 Step 0(스키마와 가상 데이터), Step 2~4 의 알고리즘(후보 선정, 점수 계산, 감점, 재정렬, 사유 문구), 그리고 Step 5 가운데 파이프라인을 잇는 조립부와 취향 갱신 수식까지입니다. 아직 손대지 않은 것은 Step 1(로그 테이블과 적재), Step 6(종단 검증), 그리고 DB 와 HTTP 라우터를 실제로 연결하는 일입니다.

코드는 `feat/recommend-engine-core` 브랜치에 올라갔고 GitHub 원격에도 push 되어 있습니다. 그 뒤 1차 세 파트 회의의 결정에 따라 엔진을 데이터 파트의 계약 위에서 다시 썼고(아래 2절 마지막 묶음), **데이터 파트 브랜치를 통째로 우리 브랜치에 합쳤습니다**(2절 마지막). 지금은 데이터 파트의 DB 스키마, 배치 파이프라인, 로그 적재, 계약 검증까지 한 브랜치 안에 있고, **전체 단위 테스트 206건이 모두 통과하고 실패가 없으며** 커버리지는 88.18% 입니다. 저장소의 검증 명령 네 가지와 데이터 파트 자신의 검사가 모두 통과합니다.

팀 정책상 지금은 PR 을 만들지 않습니다. 브랜치에 규칙대로 커밋하고 push 만 합니다. `main` 병합은 **B 가 먼저 올리고 데이터 파트가 그 `main` 을 받아 자기 수정을 얹는** 순서로 정해져 있으며, 데이터 파트 개발자와 이야기한 뒤 진행합니다(N-12, P-10). 그 전에 검사 예외 네 건에 대한 Tech Lead 승인이 필요합니다(G-16).

## 2. 계획과 다르게 한 것

계획서 원문과 다르게 결정한 것이 열다섯 가지 있습니다. 이유가 있어서 바꾼 것이지만, 계획서를 쓴 사람이 동의하지 않을 수 있으니 하나씩 적습니다. 각 항목을 되돌리는 조건은 에이전트용 3.2 표에 있습니다.

**결과에 영향을 주는 결정**

- 탐색 슬롯보다 **개인화 슬롯을 먼저** 뽑습니다(D-01). 계획서 그림은 둘을 나란히 그렸지만, 탐색을 먼저 뽑으면 개인화 결과가 난수에 따라 바뀌어 "같은 입력에는 같은 결과"라는 테스트가 깨졌습니다. 개인화가 어차피 보여 줄 레시피를 탐색 슬롯이 다시 고르는 것도 탐색의 취지에 맞지 않습니다.
- 후보가 부족해 조건을 완화하는 기준을 고정 20건이 아니라 **20건과 요청 개수 중 큰 쪽**으로 잡았습니다(D-02). 고정 20이면 50개를 요청한 사용자가 25개만 받는 일이 실제로 생겼습니다.
- 맛 유사도는 코사인 값을 그대로 쓰지 않고 0~1 사이로 옮겼고, 코퍼스 평균이 없으면 계산하지 않고 "측정 불가"로 뺍니다(D-09). 평균 없이 계산하면 어떤 벡터를 넣어도 비슷하다고 답하는 문제가 생기기 때문입니다.
- `dismiss`(무시) 이벤트는 취향 벡터를 움직이지 않습니다(D-14). 무엇이 싫었는지 알려 주지 않는 신호라서입니다.

**구조와 규약 때문에 바꾼 것**

- SQL 은 계획서가 말한 `engine/candidate.py` 가 아니라 `repository.py` 에 둘 예정입니다(D-03). 저장소 규약이 그렇게 정하고 있습니다. `candidate.py` 는 같은 조건을 파이썬으로 한 번 더 확인해서 DB 밖에서도 알레르기 재료가 새지 않게 합니다.
- 가중치와 감점 계수는 당분간 `RankConfig` 라는 설정 묶음의 기본값으로 둡니다(D-04). 규약은 `config.py` 로 빼라고 하지만, 그건 팀 공용 파일과 `.env.example` 을 함께 고치는 일이어서 DB 를 연결하는 Step 5 때 한 번에 하기로 했습니다.
- 요청과 이력을 합쳐 엔진 입력을 만드는 어댑터를 `service.py` 가 아닌 `engine/context.py` 에 두었습니다(D-15). 규약이 `service.py` 에는 흐름 조립만 허용하기 때문이고, 커밋을 단계별로 검증하려면 이 분리가 필요했습니다.
- 응답의 `meta` 를 자유 형식 사전이 아니라 필드 다섯 개짜리 고정 모델로 만들었습니다(D-07). JSON 모양은 같고, 필드가 빠지면 타입 검사가 잡아 줍니다.
- 이벤트의 종류와 시각은 문자열 대신 검증되는 타입으로 받습니다(D-08).
- 테스트 파일 이름은 계획서의 `test_serve.py`, `test_events.py` 가 아니라 규약대로 `test_service.py`, `test_feedback.py` 입니다(D-05).
- 도메인 `__init__.py` 에 아직 아무것도 내보내지 않습니다(D-10). 밖에서 쓰는 곳이 생기면 그때 넣습니다.
- 계획서의 SQL 이 고르는 컬럼보다 네 개(`title`, `all_ids`, `cuisine`, `product_ids`)를 더 요구합니다(D-13). 응답의 제목과 상품 ID, 탐색 슬롯의 요리군, 유사도 계산에 필요합니다.

**도구 때문에 바꾼 것**

- 난수는 `random.SystemRandom()` 을 쓰고, 가상 데이터 생성 스크립트는 난수 대신 해시를 씁니다(D-11). 시드가 있는 `random.Random` 은 린터가 막고, 예외를 두려면 Tech Lead 승인이 필요합니다.
- `pyproject.toml` 의 pytest 설정에 `--import-mode=importlib` 를 넣었습니다(D-12). 영수증 도메인과 추천 도메인이 규약대로 같은 이름의 테스트 파일(`test_service.py`)을 가지게 되는데, 기본 설정에서는 이 둘이 충돌해 테스트 수집이 깨집니다. 팀 공용 파일이므로 알려 두어야 합니다(P-04).
- Step 0 의 "더미 응답 라우터"는 만들지 않았습니다(D-06). 같은 날 엔진을 다 만들어서 더미가 곧 버려질 코드였습니다. 라우터 연결은 Step 5 에서 합니다.

**데이터 파트와 맞추기 위해 바꾼 것**

- 맛 벡터의 축 순서를 (매움, 짠맛, 단맛)으로 고쳤습니다(D-16). 데이터 파트의 설계 결정과 `recipe_feature.flavor_vec` 6축의 앞 세 축이 이 순서인데 B 는 단맛과 짠맛의 자리가 바뀌어 있었습니다. 값이 전부 0~1 이고 길이도 같아 어떤 검사에도 걸리지 않는 종류의 오류라 통합 전에 잡은 것이 다행입니다. 6축 벡터가 그대로 들어와도 앞 세 축만 씁니다.
- 스테이지 사이를 오가는 모델을 `schema.py` 에서 새 파일 `stage.py` 로 옮겼습니다(D-17). 데이터 파트가 같은 배치를 쓰고 있어 병합 충돌을 줄이기 위한 것입니다. 저장소의 규약 문서는 아직 이 파일을 모르므로 개정이 필요합니다(P-11).
- 검증에서 나온 수정 제안을 반영하면서 명세의 점수 수식과 탐색 규칙을 네 군데 확장했습니다(D-18). 중립 취향 사용자의 맛 점수 감쇠, 낯선 후보가 부족할 때의 탐색 축소, 선호 요리군 반영, 맛 거리에 따른 탐색 대상 판정입니다. 검증에서 본 문제(F-02, F-04, F-06, F-07)에 대응하며, 반영한 제안은 X-01, X-02, X-03, X-04, X-05, X-06, X-07, X-08, X-09 와 재검증 중 더한 X-10 입니다. 뒤의 두 개(X-06, X-07)는 회의 뒤 17 피처 체계로 흡수됐습니다.

**1차 회의 뒤 데이터 파트에 맞춘 것**

- 맛 벡터를 **6축**으로 바꿨습니다(D-19). 데이터 파트의 DB 가 레시피 맛, 코퍼스 평균, 사용자 취향 벡터를 모두 6축으로 두기 때문입니다. 지금 사용자에게 받는 것은 앞 세 축(매움·짠맛·단맛)뿐이라 뒤 세 축은 비어 들어오고, 계산은 양쪽에 값이 있는 축에서만 합니다. 비어 있는 축을 0 으로 채우면 신맛을 모르는 사람이 신맛을 싫어하는 사람이 되므로 그렇게 하지 않습니다. 뒤 세 축 데이터가 오면 코드를 고치지 않아도 켜집니다.
- 점수 체계를 다섯 블록에서 데이터 파트의 **열일곱 피처**로 바꿨습니다(D-20). 응답과 요청 모델도 그쪽 것을 쓰기로 해 B 가 만든 `schema.py` 는 지웠습니다. 데이터 파트가 먼저 구현했고 계약 테스트 98건과 DB 스키마가 그 위에서 돌기 때문입니다.
- 노출 확률을 역수에서 **확률**로 바꿨습니다(D-21). 데이터 파트의 DB 와 평가 파트의 계산이 확률을 전제합니다.
- 데이터 파트가 이미 만든 엔진 조각 네 개(사유 선택, 사유 템플릿, 탐색 슬롯, 클러스터 Thompson)를 그대로 쓰고 B 는 점수 계산만 채웁니다(D-22). 같은 것을 두 벌 만들면 노출 확률의 정의가 갈리는 순간 사후 평가가 못 쓰게 됩니다. B 가 만들었던 사유·감점·피드백 모듈은 지웠습니다.

**데이터 파트 브랜치를 통째로 합친 것**

- 데이터 파트 브랜치의 현재 버전을 전부 가져와 우리 브랜치에 합쳤습니다. 병합 커밋 기준으로 `main` 대비 194개 파일, 6만 줄입니다. 겹치는 파일 여덟 개는 우리 쪽을 남겼는데, 그 여덟 개가 이미 데이터 파트의 내용에 지난 세션의 수정 스물여섯 곳을 얹은 것이기 때문입니다.
- 합친 직후에는 검사가 통과하지 않았습니다. 린터 373건, 타입 검사 31건, 커버리지 46%였습니다. 데이터 파트도 이 사실을 자기 설정 파일에 적어 두고 "규칙 맞추기는 다음 작업"이라고 미뤄 둔 상태였습니다.
- 그래서 **서빙 경로인가**를 기준으로 선을 그었습니다. 요청을 처리하는 코드(`src/` 아래 전부)는 손으로 고쳤고(D-23), 사람이 한 번 돌려 결과를 읽는 도구는 범위를 좁힌 예외로 두었습니다(D-24). 예외는 파일마다 실제로 필요한 항목만 적었습니다 — 폴더를 통째로 끄면 나중에 들어올 파일까지 조용히 덮기 때문입니다.
- 손으로 고친 것 중 네 곳은 표기가 아니라 코드였습니다. 그래서 데이터 파트 자신의 검사(시드 검증, 계약 검증, 정규화 검증 125건)를 전부 돌려 결과가 그대로인 것을 확인했습니다.
- 합치는 과정에서 조용한 문제를 두 개 찾았습니다. 하나는 데이터 파트의 테스트 설정이 폴더 단위로 수집을 막고 있어 **B 의 테스트 63건과 영수증 통합 테스트가 아예 세어지지 않는** 것이었고(D-26), 다른 하나는 이미지 라이브러리 버전이 딸려 올라가면서 이 PC 의 보안 정책에 걸려 영수증 테스트 8건이 죽는 것이었습니다(D-25). 둘 다 실패로 보이지 않는 형태라 통과 출력만 봐서는 알 수 없었습니다.
- 검사 예외는 규칙상 Tech Lead 승인이 필요합니다. 근거와 없앨 조건을 결정 기록 한 편으로 정리해 두었습니다.

## 3. 앞으로 할 일

### 3.1 계획서에 있는 일

계획서 순서대로 남은 것은 다음과 같습니다(T-01~T-15).

- Step 1: 로그 테이블 세 개(`recommendation_log`, `event_log`, `user_vector`) 정의(T-02), 서빙 결과 적재 함수(T-03), `/health` 카운터(T-04). DB 접속이 되어야 시작할 수 있습니다.
- Step 2: 실제 레시피 테이블에서 후보를 가져오는 SQL(T-05)과 알레르기 코드를 재료 ID 로 바꾸는 조회(T-06). 여기서 한 가지 설계 결정이 필요한데 아래 4절의 A-10 을 보십시오.
- Step 3: 코퍼스 통계(`feature_stats`) 읽기(T-07).
- Step 4: 요리군별 사후 분포 집계(T-08). 이벤트가 쌓이기 전까지는 균등 분포를 씁니다.
- Step 5: 서비스와 DB 연결과 가중치를 설정 파일로 옮기기(T-09), 이벤트 엔드포인트(T-10), 특성 리포트(T-11).
- Step 6: 계약 검증 42건과 부하 테스트(T-12, T-13). 둘 다 도구 승인이 선행됩니다.
- 정량 지표 실측과 가중치 학습(T-14). 라벨 데이터와 평가 파트의 하네스가 필요합니다.
- 이 문서들을 저장소에 올리는 일(T-15). 처리했습니다.
- 가상 데이터 검증에서 나온 수정 제안을 반영하는 일(T-16). 전부 반영했고 재검증 결과는 검증 기록(`recommend_engine_verification.md`) 7절에 있습니다.
- 데이터 파트와 세 파트 회의에서 정할 안건을 정리하고 병합 계획을 세우는 일(T-17). 1차 회의에서 여섯 건(G-01, G-02, G-03, G-04, G-05, G-07)이 결정되어 반영을 마쳤고, 남은 것은 후보 조회 계약(G-06), 테스트 수집 제외(G-08), 규약 개정 두 건(G-09, G-10), 공유 파일 병합(G-11), 결정 문서 반영(G-12)입니다.
- 사용자 이력을 읽어 오는 저장소 함수(T-18, 회의 안건 N-11). 선호·기피 재료, 조리 이력, 클러스터 관측이 비어 있어 피처 네 종이 아직 계산되지 않습니다.
- 라우터를 실제로 연결하는 일(N-03). 회의에서 파일 소유가 정해져 착수할 수 있게 됐고, 그때 난수 시드를 실제로 쓰도록 함께 정합니다.

### 3.2 계획서에 없지만 먼저 풀어야 할 일

## 4. 데이터가 정해지면 확인할 것

지금 코드는 데이터가 없는 상태에서 만든 선 설계입니다. 실제 데이터, 백엔드 계약, DB 가 정해지면 아래 가정이 맞는지 하나씩 대조해야 합니다(A-01~A-11). 코드 구조 자체는 그때 코드를 읽으면 되지만, 이 가정들은 코드를 읽어도 "가정"이라는 사실이 보이지 않습니다.

엔진이 바깥과 만나는 자리는 여섯 곳입니다. 백엔드가 보내는 요청과 이벤트(I-01), 데이터 파트가 주는 레시피 행(I-02)과 코퍼스 통계(I-03), DB 에서 읽는 사용자 이력(I-04), 엔진이 DB 에 남기는 서빙 로그(I-05), 백엔드와 평가 파트로 나가는 응답과 설정 지문(I-06)입니다. 지금은 전부 가상 데이터나 테스트가 채우고 있고, 실연결 때 각각 저장소 계층과 백엔드 계약이 채웁니다. 어떤 컬럼과 값이 필요한지는 에이전트용 8.1 표에 있습니다.

- 맛 벡터의 축 순서는 데이터 파트와 대조해 (매움, 짠맛, 단맛)으로 확정했습니다(A-01, D-16). 값은 0~1 이고 6축이 들어오면 앞 세 축만 씁니다. 다만 데이터 파트의 DB 는 사용자 취향 벡터도 6축으로 두고 있어 갱신 방식을 맞춰야 합니다(P-15).
- 인기도와 품질 점수가 이미 0~1 로 정규화되어 있다고 가정했습니다(A-02).
- 재료 ID 는 정수이고, 사용자 보유 목록·레시피·알레르기 매핑이 같은 ID 체계를 쓴다고 가정했습니다(A-03). 필수 재료는 전체 재료의 부분집합이라고 가정했습니다(A-04).
- 알레르기 코드군(식약처 19종)을 재료 ID 로 바꾸는 표가 어딘가에 있다고 가정했습니다(A-05). 지금은 가상 데이터 안의 임시 표를 씁니다.
- 레시피의 요리군 이름과 백엔드가 보내는 선호 요리군 문자열이 같은 어휘라고 가정했습니다(A-06). 탐색 슬롯은 문자열이 같은지로만 판단합니다.
- 조리시간이 비어 있는 레시피가 드물다고 가정했습니다(A-07). 비어 있으면 그 레시피는 조리시간 블록이 점수에서 빠집니다.
- 임박 재료 목록이 보유 목록의 부분집합인지는 확인하지 않습니다(A-08).
- 코퍼스 평균과 IDF 가 전체 데이터 기준이고 갱신 주기가 정해져 있다고 가정했습니다(A-09).
- **후보 조회 범위**(A-10). 이것이 가장 중요합니다. 계획서의 SQL 은 "부족 재료 2개 이하"로 걸러 500건만 넘기는데, 제가 만든 완화 로직은 넘겨받은 후보 안에서만 조건을 풉니다. 둘을 그대로 붙이면 완화할 후보가 없어 폴백이 빈손이 됩니다. 저장소 쿼리를 만들 때 "부족 4개 이하로 넉넉히 한 번 가져오기"와 "단계마다 다시 조회하기" 중 하나를 골라야 하고, 인기순 폴백은 어차피 별도 조회입니다. 데이터 파트 브랜치에 후보 조회 함수가 이미 있으므로 새로 짜기보다 그것을 호출하는 쪽으로 방향이 바뀔 수 있습니다.
- 알레르기 매핑(A-05)은 데이터 파트의 DB 에 `user_allergy` 테이블이 있어 그쪽 스키마를 확인하면 됩니다.
- 4만 6천 건 실데이터를 파이썬으로 거르지는 않는다는 원칙입니다(A-11). 파이썬 쪽 필터는 SQL 결과를 재확인하고 가상 데이터로 테스트하기 위한 것입니다.

무언가를 고치거나 되돌려야 할 때는 이렇게 합니다. 점수 수식은 `engine/rank.py` 의 블록 함수 하나만 건드리고, 그때 `test_rank.py` 의 수치 테스트가 먼저 깨지는지 확인합니다. 가중치는 `RankConfig` 한 곳에만 있고 바꾸면 로그의 지문이 따라 바뀝니다. 커밋을 모듈 단위로 쪼개 두었으므로 특정 단계만 `git revert` 로 걷어낼 수 있습니다(뒤 커밋부터 순서대로). 통합 전 상태로 돌아올 기준점이 필요하면 `cbdf312` 에 태그를 붙이면 됩니다.

## 5. 알아두면 좋은 동작

명세가 정하지 않아 제가 정한 동작들입니다(C-01~C-11). 의도한 것이니 버그로 오해하지 않도록 적어 둡니다.

- 인기순 폴백이 조리시간 상한을 무시하던 동작(C-01)은 폐기했습니다. 이제 상한을 먼저 지키고 부족할 때만 풉니다.
- 탐색 슬롯은 후보가 넉넉할 때만 정원을 채웁니다(C-02). 후보 수가 요청 개수와 같거나, 낯선 후보가 슬롯 수의 두 배 미만이거나, 품질이 후보 중위수 아래면 줄어들거나 0이 됩니다. 낯선 후보는 비선호 요리군이거나 맛이 취향과 먼 레시피입니다.
- 가구원 수는 받아 두지만 아직 어떤 점수에도 쓰지 않습니다(C-04).
- 인기도와 품질 중 하나가 비어 있으면 있는 쪽만 쓰고, 둘 다 비면 그 블록을 뺍니다(C-05). 가상 데이터는 스무 건에 한 건씩 품질 점수를 비워 이 경로를 테스트합니다.
- 설정 지문은 가중치뿐 아니라 후보 한도 같은 값까지 전부 포함한 해시라서 자주 바뀔 수 있습니다(C-06).
- 탐색 아이템의 노출 확률 역수(propensity)는 균등 슬롯은 정확히, Thompson 슬롯은 32회 표본으로 추정합니다(C-07). 성능 조정으로 64회에서 줄였습니다.
- 재정렬은 점수 상위 200건만 대상으로 하고 IDF 합을 미리 계산합니다(C-08). 후보 500건 기준 재정렬 8.5 ms, 엔진 전체 p95 22 ms 입니다.
- 가상 데이터의 알레르기 코드는 18종입니다. 아황산류는 대응 재료가 없어 뺐습니다(C-09).
- 임박 재료 목록이 보유 목록 밖의 ID 를 포함해도 그대로 계산에 넣습니다(C-03).
- 가상 데이터 JSON 은 스크립트 산출물이지만 테스트 픽스처 자리에 커밋합니다(C-10). 개인정보는 없습니다.
- `engine/` 폴더의 파일은 일곱 개로 규약의 여덟 개 기준 안입니다(C-11).

## 6. 작업 환경에서 걸린 것

이 PC(Windows 11)에서 확인된 사항입니다(E-01~E-12). 다른 PC 는 다를 수 있습니다.

- `uv run mypy` 가 앱 제어 정책에 막힙니다. `uv run python -m mypy src` 로 실행하면 됩니다(E-01).
- ruff 는 마크다운 안의 코드블록도 포맷 검사합니다(E-02). 한글은 한 글자를 폭 2로 세므로 긴 한글 주석은 100자 제한에 금방 걸립니다(E-04).
- `.env` 를 건드리지 않고 전체 테스트를 돌리려면 유효한 `.env` 를 둔 임시 폴더에서 저장소를 가리켜 실행하는 방법이 있습니다(E-03).
- 한글 문장 안의 곱셈 기호는 린터가 막습니다(E-05). Windows 에서 줄 끝을 확인할 때는 `grep` 대신 파이썬으로 바이트를 봐야 하고(E-06), 파일을 쓰는 스크립트는 줄 끝을 LF 로 고정합니다(E-07). 에이전트가 셸 heredoc 으로 큰 파일을 쓰면 명령이 잘립니다(E-08). pytest 설정에 이미 `-q` 가 있어 명령줄에 `-q` 를 더 주면 요약 줄이 사라집니다(E-09).
- 데이터 파트의 검사 스크립트는 결과를 체크 표시로 찍는데, Windows 기본 콘솔이 그 글자를 못 써서 검사가 통과해도 오류로 끝납니다(E-11). 실행 앞에 인코딩을 UTF-8 로 지정하면 되고, 항구 대책은 회의 안건으로 올렸습니다(G-14).
- 이미지 라이브러리(`pillow-heif`)의 새 버전이 이 PC 의 앱 제어 정책에 차단됩니다(E-12). 이전 버전으로 되돌려 두었고 이것도 회의 안건입니다(G-13).
- 데이터 파트의 계약 검증은 `.env` 가 비어 있으면 **중간에 죽는데 화면상으로는 통과처럼 보입니다**(E-13). 설정값을 채워 주면 98건이 전부 통과합니다.
- 이 두 가지는 이 PC 만의 문제일 수 있습니다. 반대로 평가용 유틸 한 파일이 부르는 곳도 검사도 없는 것(G-17)은 PC 와 무관한 사안입니다.
- git 사용자 설정이 이 PC 에 없어서 저장소 로컬로 `유재현 <yjhorion@gmail.com>` 을 넣었습니다(E-10). 다른 표기를 원하면 바꾸고 push 전에 작성자를 다시 쓰면 됩니다.

## 7. 세션 일지

### 2026-09-10

브랜치 `feat/recommend-engine-core` 를 만들어 Layer 1 을 구현하고 커밋 8개로 나눠 GitHub 에 push 했습니다. 커밋마다 그 시점의 코드로 린트·타입 검사·추천 테스트를 통과시킨 뒤 커밋했습니다. 작업 중 결함 두 개(개인화 슬롯이 난수에 따라 바뀌던 것, 50개 요청에 25개만 나오던 것)를 찾아 고쳤고, 공용 파일은 `pyproject.toml` 한 줄만 바꿨습니다. 작업 기록을 에이전트용과 사람용 두 형식으로 남기기로 정했습니다(근거는 지금 결정 기록에 있습니다). 다음 세션 전에 `.env` 정리(P-01)와 후보 조회 범위 결정(A-10)이 필요합니다.

같은 날 이어서 가상 데이터 검증을 했습니다. 12명의 페르소나에게 파이프라인을 끝까지 돌려 기획서 정합과 동작을 확인하는 스크립트를 만들고, 결과를 검증 기록에 남겼습니다. 코드는 바꾸지 않고 수정 제안 아홉 건을 남겼습니다.

세 번째 세션에서는 수정 제안을 전부 반영했습니다(T-16). 데이터 파트의 공유 문서가 도착해 맛 축 순서가 어긋난 것을 알게 되었고, 이것이 평가 결과 전체를 뒤집는 문제라 가장 먼저 고쳤습니다(D-16). 그다음 제안 아홉 건과 재검증 중 찾은 한 건을 모듈별 커밋으로 반영하고, 도메인 모델을 `stage.py` 로 옮기고(D-17), 다시 평가해 검증 기록 7절에 적었습니다. 데이터 파트 브랜치를 직접 열어 보니 공유 문서가 말한 것보다 겹치는 파일이 많아, 세 파트가 모여 정할 안건을 P-11~P-15 로 정리했습니다(T-17).

다섯 번째 세션은 데이터 파트에 맞추는 작업이었습니다. 회의 결정대로 계약 파일 두 개와 완성된 엔진 조각 네 개를 데이터 파트 브랜치에서 가져오고, 그 위에서 6축 맛과 열일곱 피처와 확률 노출값으로 엔진을 다시 썼습니다. 가져온 파일은 스물여섯 곳만 고쳤는데 대부분 저장소 린터가 지적하는 수학 기호였고 코드는 세 곳(재현용 난수의 예외 표기, 항상 참인 조건, 인자 타입)입니다. 확인해 보니 데이터 파트는 아직 `main` 에 병합되지 않았고 그쪽 브랜치가 `main` 을 받아 준비를 마친 상태였습니다.

네 번째 세션은 문서 정리였습니다. `main` 에 문서 규칙이 별도 문서(04)로 분리되어 올라와서 그것을 브랜치에 합치고, 파트 B 문서를 그 규칙에 맞췄습니다. 폴더를 `docs/recommend/` 로, 파일명을 식별자 대신 내용이 드러나는 이름으로 바꾸고, 문서 목록은 `docs/README.md` 한 곳에만 두고, 계획서를 표준 헤더와 `~합니다`체로 다시 썼습니다. 회의 안건은 타 파트와 정할 것 열두 건(G-01~G-12)과 B 안에서 처리할 것 열 건(N-01~N-10)으로 나눠 별도 문서로 만들었습니다. 이 기록의 선행 조건들은 그 문서에서 축 수(G-01), 모델 통일(G-02), 파일 소유(G-04), 문서 배치(G-09), 결정 문서(G-12)로 이어지고, B 내부로는 `.env` 정리(N-01)와 난수원(N-10)이 걸려 있습니다. 폴더 배치 자체는 규칙에 없어 개정 신청이 남았습니다(P-16).

여섯 번째 세션은 데이터 파트 브랜치를 통째로 합치는 작업이었습니다. 겹치는 파일 여덟 개의 충돌을 풀고, 합친 트리에서 저장소 검사 네 가지가 전부 통과하도록 만들었습니다. 서빙 코드는 손으로 고치고 일회용 도구는 범위를 좁힌 예외로 두는 선을 그었으며, 그 예외의 근거와 없앨 조건을 결정 기록으로 남겼습니다. 합치는 과정에서 테스트가 조용히 세어지지 않던 문제와 이미지 라이브러리 버전 문제를 찾아 고쳤습니다. `main` 병합 자체는 데이터 파트 개발자와 이야기한 뒤 진행합니다.

일곱 번째 세션은 "에러는 안 나는데 기능을 못 하는 것"을 찾는 작업이었습니다. 검사가 전부 통과하는 상태에서, 설정값이 실제 계산에 닿는지·피처가 실제로 변하는지·응답이 근거 있는 값인지 세 축으로 쟀습니다. 여덟 가지를 찾아 셋(F-24, F-25, F-26)을 고치고 다섯(F-27, F-28, F-29, F-30, F-31)을 남겼습니다.

고친 셋은 전부 **기본값 때문에 조용히 넘어가던 것**입니다(D-27). 헬스체크가 데이터베이스를 확인하지 않고 정상이라고 답하고 있었고, 추적 로그에 적는 난수 반복 횟수가 실제 계산에 쓰이지 않았으며, 취향 웜업 문턱이 두 곳에 따로 있었습니다. 셋 다 예외가 오르지 않아서 검사가 없으면 다음에 값을 바꾼 사람이 바뀌지 않은 결과를 보게 됩니다. 재발하면 실패하는 검사 여섯 건을 함께 넣었습니다.

남긴 다섯은 성격이 다릅니다. 조리시간 적합도가 앞 단계 필터와 겹쳐 항상 만점인 것(F-27)과 가중치 1.00 중 0.26 이 순위를 못 바꾸는 것(F-28)은 가중치 학습에서 정할 일이라 안건으로 넘겼습니다(N-13). HTTP 응답이 아직 전부 목업인 것(F-29)은 라우터 실연결(N-03)이 해소이고, 계약 검증이 조용히 멈추는 것(F-30)과 헬스체크의 redis 항목이 근거 없이 참인 것(F-31)은 데이터 파트와 정할 안건으로 올렸습니다(G-18, G-19).

이 과정에서 지난 세션 기록의 오기도 하나 찾았습니다. 계약 검증을 "통과"로 적었는데, 종료 코드를 보지 않고 화면 마지막 줄이 통과 표시인 것만 읽은 결과였습니다. 실제로는 `.env` 가 비어 있어 중간에 죽고 있었습니다(E-13). 설정값을 채우면 98건이 전부 통과합니다. 기록을 바로잡았습니다.

여덟 번째 세션은 데이터베이스를 붙일 때를 대비하는 작업이었습니다.

지금 엔진에는 목업과 기본값으로 채워 둔 자리가 열세 곳 있고 **전부 에러를 내지 않습니다.** 그래서 전환할 때 하나를 빠뜨려도 아무 일이 일어나지 않습니다. 열세 항목을 점검표로 정리하고(C-01~C-13), 그것을 건너뛸 수 없게 검사 열 건을 못처럼 박아 두었습니다. 항목 하나를 건드리면 검사가 깨지고 실패 메시지가 점검표의 번호를 알려 줍니다. 점검표를 읽지 않고 전환하는 경로를 없앤 것입니다.

제가 낸 오보도 규칙으로 막았습니다(D-28). 통과 여부를 화면 마지막 줄로 판단한 것, 돌리지 않은 검사를 통과로 적은 것, 앞선 실행의 숫자를 그대로 옮긴 것 세 건입니다. 01에 3.4 를 넣어 종료 코드로 판정하도록 하고, 개정 사례를 결정 기록에 남겼습니다. 기존 절 번호는 건드리지 않았습니다 — 저장소 안에서 그 번호를 가리키는 곳이 열두 군데라 바꾸면 전부 깨집니다.

지금 고칠 수 있는 것은 고쳤습니다. 계약 검증이 조용히 멈추던 것을 실패로 세게 했고(F-30), 사실과 다른 문서 문장을 바로잡았으며(F-33), 평가 출력이 매번 죽은 가중치와 실효 분모를 내도록 했습니다(F-28). 새로 찾은 것도 둘 있습니다 — 같은 설정이 두 곳에 있고 엔진은 한쪽만 읽는 것(F-32), 로그 실패 횟수를 읽는 곳이 없는 것(F-33)입니다.

지금 할 수 없는 것은 열일곱 줄의 MUST TODO 로 모았습니다(4.3). 하기 싫어서 미룬 것이 아니라 데이터베이스나 파트 간 합의가 없어서 못 하는 것들이고, 줄마다 "언제 가능한가" 를 적어 두었습니다. 사용자 이력이 비어 피처 넷이 계산되지 않는 것(F-15), 데이터베이스가 필요한 데이터 파트 검사 넷을 아직 못 돌린 것(C-12), 설정 손잡이의 정본을 정하는 일(N-02)과 그와 함께 볼 가중치 재조정(N-04, N-05)이 여기 들어 있습니다.

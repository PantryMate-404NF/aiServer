## 1. 지금 어디까지 왔나

2026-09-10 하루 동안 추천 엔진의 **Layer 1**, 즉 데이터베이스 없이 순수 함수만으로 돌아가는 부분을 전부 구현했습니다. 계획서 기준으로는 Step 0(스키마와 가상 데이터), Step 2~4 의 알고리즘(후보 선정, 점수 계산, 감점, 재정렬, 사유 문구), 그리고 Step 5 가운데 파이프라인을 잇는 조립부와 취향 갱신 수식까지입니다. 아직 손대지 않은 것은 Step 1(로그 테이블과 적재), Step 6(종단 검증), 그리고 DB 와 HTTP 라우터를 실제로 연결하는 일입니다.

코드는 `feat/recommend-engine-core` 브랜치에 올라갔고 GitHub 원격에도 push 되어 있습니다. 그 뒤 1차 세 파트 회의의 결정에 따라 엔진을 데이터 파트의 계약 위에서 다시 썼고(아래 2절 마지막 묶음), **데이터 파트 브랜치를 통째로 우리 브랜치에 합쳤습니다**(2절 마지막). 지금은 데이터 파트의 DB 스키마, 배치 파이프라인, 로그 적재, 계약 검증까지 한 브랜치 안에 있고, **전체 단위 테스트 292건이 모두 통과하고 실패가 없으며** 커버리지는 90.64% 입니다. 저장소의 검증 명령 네 가지와 데이터 파트 자신의 검사가 모두 통과합니다.

`main` 병합은 PR 로 합니다(처음의 "PR 없이 브랜치만" 정책 P-10 은 2026-09-11 에 PR 로 바꿨습니다). 첫 PR(#8)은 2026-09-11 에 병합되어 데이터 파트와 추천 엔진이 `main` 에 들어갔고, 그 뒤의 취향 페르소나와 복기 수정, 가상운영데이터 패키지 커밋 열세 개는 아직 `main` 에 없습니다. 새 PR 은 보류 상태입니다(2026-09-12). 2026-09-14 에는 기획측 가상운영데이터를 엔진에 넣어 보는 도구를 만들었고, 그 패키지는 유재현의 결정으로 전부 커밋했고 필요한 라이브러리 두 개도 개발 의존성에 넣었습니다(N-16). 같은 날 저녁 Docker Desktop 을 설치한 뒤 데이터베이스 경로(적재·검증·API)까지 통과시켰습니다. 2026-09-15 에는 온보딩에 새로 생긴 "좋아하는 음식 유형" 문항을 받아 목록에 조금 반영하는 일을 했습니다(D-45~D-47). 검사는 315건이 통과하고 커버리지는 91.02% 입니다.

## 2. 계획과 다르게 한 것

계획서 원문과 다르게 결정한 것이 열다섯 가지 있습니다. 이유가 있어서 바꾼 것이지만, 계획서를 쓴 사람이 동의하지 않을 수 있으니 하나씩 적습니다. 각 항목을 되돌리는 조건은 에이전트용 3.2 표에 있습니다.

**결과에 영향을 주는 결정**

- 탐색 슬롯보다 **개인화 슬롯을 먼저** 뽑습니다(D-01). 계획서 그림은 둘을 나란히 그렸지만, 탐색을 먼저 뽑으면 개인화 결과가 난수에 따라 바뀌어 "같은 입력에는 같은 결과"라는 테스트가 깨졌습니다. 개인화가 어차피 보여 줄 레시피를 탐색 슬롯이 다시 고르는 것도 탐색의 취지에 맞지 않습니다.
- 후보가 부족해 조건을 완화하는 기준을 고정 20건이 아니라 **20건과 요청 개수 중 큰 쪽**으로 잡았습니다(D-02). 고정 20이면 50개를 요청한 사용자가 25개만 받는 일이 실제로 생겼습니다.
- 맛 유사도는 코사인 값을 그대로 쓰지 않고 0~1 사이로 옮겼고, 코퍼스 평균이 없으면 계산하지 않고 "측정 불가"로 뺍니다(D-09). 평균 없이 계산하면 어떤 벡터를 넣어도 비슷하다고 답하는 문제가 생기기 때문입니다.
- `dismiss`(무시) 이벤트는 취향 벡터를 움직이지 않습니다(D-14). 무엇이 싫었는지 알려 주지 않는 신호라서입니다.

**구조와 규약 때문에 바꾼 것**

- SQL 은 계획서가 말한 `engine/candidate.py` 가 아니라 `repository.py` 에 둘 예정입니다(D-03). 저장소 규약이 그렇게 정하고 있습니다. `candidate.py` 는 같은 조건을 파이썬으로 한 번 더 확인해서 DB 밖에서도 알레르기 재료가 새지 않게 합니다.
- 가중치와 감점 계수는 당분간 `RankConfig` 라는 설정 묶음의 기본값으로 둡니다(D-04). 규약은 `config.py` 로 빼라고 하지만, 그건 팀 공용 파일과 `.env.example` 을 함께 고치는 일이어서 DB 를 연결하는 Step 5 때 한 번에 하기로 했습니다.
- 요청과 이력을 합쳐 엔진 입력을 만드는 어댑터를 `service.py` 가 아닌 `engine/context.py` 에 두었습니다(D-15). 규약이 `service.py` 에는 흐름 조립만 허용하기 때문이고, 커밋을 단계별로 검증하려면 이 분리가 필요했습니다.
- 응답의 `meta` 를 자유 형식 사전이 아니라 필드 다섯 개짜리 고정 모델로 만들었습니다(D-07). JSON 모양은 같고, 필드가 빠지면 타입 검사가 잡아 줍니다.
- 이벤트의 종류와 시각은 문자열 대신 검증되는 타입으로 받습니다(D-08).
- 테스트 파일 이름은 계획서의 `test_serve.py`, `test_events.py` 가 아니라 규약대로 `test_service.py`, `test_feedback.py` 입니다(D-05).
- 도메인 `__init__.py` 에 아직 아무것도 내보내지 않습니다(D-10). 밖에서 쓰는 곳이 생기면 그때 넣습니다.
- 계획서의 SQL 이 고르는 컬럼보다 네 개(`title`, `all_ids`, `cuisine`, `product_ids`)를 더 요구합니다(D-13). 응답의 제목과 상품 ID, 탐색 슬롯의 요리군, 유사도 계산에 필요합니다.

**도구 때문에 바꾼 것**

- 난수는 `random.SystemRandom()` 을 쓰고, 가상 데이터 생성 스크립트는 난수 대신 해시를 씁니다(D-11). 시드가 있는 `random.Random` 은 린터가 막고, 예외를 두려면 Tech Lead 승인이 필요합니다.
- `pyproject.toml` 의 pytest 설정에 `--import-mode=importlib` 를 넣었습니다(D-12). 영수증 도메인과 추천 도메인이 규약대로 같은 이름의 테스트 파일(`test_service.py`)을 가지게 되는데, 기본 설정에서는 이 둘이 충돌해 테스트 수집이 깨집니다. 팀 공용 파일이므로 알려 두어야 합니다(P-04).
- Step 0 의 "더미 응답 라우터"는 만들지 않았습니다(D-06). 같은 날 엔진을 다 만들어서 더미가 곧 버려질 코드였습니다. 라우터 연결은 Step 5 에서 합니다.

**데이터 파트와 맞추기 위해 바꾼 것**

- 맛 벡터의 축 순서를 (매움, 짠맛, 단맛)으로 고쳤습니다(D-16). 데이터 파트의 설계 결정과 `recipe_feature.flavor_vec` 6축의 앞 세 축이 이 순서인데 B 는 단맛과 짠맛의 자리가 바뀌어 있었습니다. 값이 전부 0~1 이고 길이도 같아 어떤 검사에도 걸리지 않는 종류의 오류라 통합 전에 잡은 것이 다행입니다. 6축 벡터가 그대로 들어와도 앞 세 축만 씁니다.
- 스테이지 사이를 오가는 모델을 `schema.py` 에서 새 파일 `stage.py` 로 옮겼습니다(D-17). 데이터 파트가 같은 배치를 쓰고 있어 병합 충돌을 줄이기 위한 것입니다. 저장소의 규약 문서는 아직 이 파일을 모르므로 개정이 필요합니다(P-11).
- 검증에서 나온 수정 제안을 반영하면서 명세의 점수 수식과 탐색 규칙을 네 군데 확장했습니다(D-18). 중립 취향 사용자의 맛 점수 감쇠, 낯선 후보가 부족할 때의 탐색 축소, 선호 요리군 반영, 맛 거리에 따른 탐색 대상 판정입니다. 검증에서 본 문제(F-02, F-04, F-06, F-07)에 대응하며, 반영한 제안은 X-01, X-02, X-03, X-04, X-05, X-06, X-07, X-08, X-09 와 재검증 중 더한 X-10 입니다. 뒤의 두 개(X-06, X-07)는 회의 뒤 17 피처 체계로 흡수됐습니다.

**1차 회의 뒤 데이터 파트에 맞춘 것**

- 맛 벡터를 **6축**으로 바꿨습니다(D-19). 데이터 파트의 DB 가 레시피 맛, 코퍼스 평균, 사용자 취향 벡터를 모두 6축으로 두기 때문입니다. 지금 사용자에게 받는 것은 앞 세 축(매움·짠맛·단맛)뿐이라 뒤 세 축은 비어 들어오고, 계산은 양쪽에 값이 있는 축에서만 합니다. 비어 있는 축을 0 으로 채우면 신맛을 모르는 사람이 신맛을 싫어하는 사람이 되므로 그렇게 하지 않습니다. 뒤 세 축 데이터가 오면 코드를 고치지 않아도 켜집니다.
- 점수 체계를 다섯 블록에서 데이터 파트의 **열일곱 피처**로 바꿨습니다(D-20). 응답과 요청 모델도 그쪽 것을 쓰기로 해 B 가 만든 `schema.py` 는 지웠습니다. 데이터 파트가 먼저 구현했고 계약 테스트 98건과 DB 스키마가 그 위에서 돌기 때문입니다.
- 노출 확률을 역수에서 **확률**로 바꿨습니다(D-21). 데이터 파트의 DB 와 평가 파트의 계산이 확률을 전제합니다.
- 데이터 파트가 이미 만든 엔진 조각 네 개(사유 선택, 사유 템플릿, 탐색 슬롯, 클러스터 Thompson)를 그대로 쓰고 B 는 점수 계산만 채웁니다(D-22). 같은 것을 두 벌 만들면 노출 확률의 정의가 갈리는 순간 사후 평가가 못 쓰게 됩니다. B 가 만들었던 사유·감점·피드백 모듈은 지웠습니다.

**데이터 파트 브랜치를 통째로 합친 것**

- 데이터 파트 브랜치의 현재 버전을 전부 가져와 우리 브랜치에 합쳤습니다. 병합 커밋 기준으로 `main` 대비 194개 파일, 6만 줄입니다. 겹치는 파일 여덟 개는 우리 쪽을 남겼는데, 그 여덟 개가 이미 데이터 파트의 내용에 지난 세션의 수정 스물여섯 곳을 얹은 것이기 때문입니다.
- 합친 직후에는 검사가 통과하지 않았습니다. 린터 373건, 타입 검사 31건, 커버리지 46%였습니다. 데이터 파트도 이 사실을 자기 설정 파일에 적어 두고 "규칙 맞추기는 다음 작업"이라고 미뤄 둔 상태였습니다.
- 그래서 **서빙 경로인가**를 기준으로 선을 그었습니다. 요청을 처리하는 코드(`src/` 아래 전부)는 손으로 고쳤고(D-23), 사람이 한 번 돌려 결과를 읽는 도구는 범위를 좁힌 예외로 두었습니다(D-24). 예외는 파일마다 실제로 필요한 항목만 적었습니다 — 폴더를 통째로 끄면 나중에 들어올 파일까지 조용히 덮기 때문입니다.
- 손으로 고친 것 중 네 곳은 표기가 아니라 코드였습니다. 그래서 데이터 파트 자신의 검사(시드 검증, 계약 검증, 정규화 검증 125건)를 전부 돌려 결과가 그대로인 것을 확인했습니다.
- 합치는 과정에서 조용한 문제를 두 개 찾았습니다. 하나는 데이터 파트의 테스트 설정이 폴더 단위로 수집을 막고 있어 **B 의 테스트 63건과 영수증 통합 테스트가 아예 세어지지 않는** 것이었고(D-26), 다른 하나는 이미지 라이브러리 버전이 딸려 올라가면서 이 PC 의 보안 정책에 걸려 영수증 테스트 8건이 죽는 것이었습니다(D-25). 둘 다 실패로 보이지 않는 형태라 통과 출력만 봐서는 알 수 없었습니다.
- 검사 예외는 규칙상 Tech Lead 승인이 필요합니다. 근거와 없앨 조건을 결정 기록 한 편으로 정리해 두었습니다.
- 기획측 가상운영데이터를 시드로 바꾸는 변환기가 온보딩 취향 벡터를 고른 음식과 직접 적은 척도를 반씩 섞어 만들고 있었습니다. 2차 회의 결정은 고른 음식이 있으면 척도를 계산에 쓰지 않는 것이라(D-29), 고른 음식의 평균만 쓰도록 고치고 시드를 다시 만들었습니다(D-42).
- 시드는 데이터베이스에 넣어 API 로 확인하는 것이 안내서의 순서였지만, 이 PC 에는 데이터베이스가 없고 서버가 아직 데이터베이스를 읽지 않습니다. 그래서 시드 파일을 읽어 엔진에 직접 넣는 도구를 따로 두었습니다(D-43). 냉장고와 임박 판정은 데이터 파트의 SQL 규칙을 그대로 따르고, '지금' 은 사용자마다 마지막 활동 한 시간 뒤로 잡습니다.
- 온보딩에 음식 유형 문항이 생겼을 때, 그 답을 맛 여섯 축 취향에 섞어 넣을 수도 있었습니다. 섞지 않았습니다(D-45). 섞으면 "한식을 좋아한다" 가 "짜고 매운 것을 좋아한다" 로 번역되어, 담백한 한식만 좋아하는 사람에게 문항 하나 때문에 틀린 목록이 나가고 그런데도 에러는 없습니다. 유형은 맛과 다른 질문이므로 다른 자리에서 씁니다.
- 유형을 목록에 반영하는 방법으로는 점수 가중치를 올리는 쪽이 간단했지만, 가중치 대신 **자리 몇 칸을 떼는 쪽**을 골랐습니다(D-46). 점수의 절반 가까이가 냉장고 재료와의 일치라 지금 가중치로는 고른 유형이 스무 칸 안에 한 번도 안 나올 수 있고(1,600명 중 460명), 그렇다고 가중치를 올리면 유형 하나가 스무 칸을 다 물들입니다. 자리를 떼면 열여덟 칸은 그대로이고 두 칸만 유형 몫이며, 그 칸의 이유 문구도 "즐겨 드시는 중식이에요" 로 적힙니다. 조리 기록이 쌓인 사용자에게는 이 칸을 만들지 않습니다.
- 유형 값을 화면에 보이는 한글 이름으로 저장할 수도 있었지만 내부 코드로 저장합니다(D-47). 레시피 쪽 분류도 같은 코드라, 이름으로 저장하면 두 축이 영영 만나지 못합니다. 모르는 값이 오면 비슷한 유형으로 바꾸지 않고 거부합니다 — 바꿔 넣으면 사용자가 고르지 않은 음식이 목록에 오르는데 응답은 정상으로 보입니다.
- 시드의 사용자 번호가 1부터 시작해 스모크 테스트의 합성 사용자 여덟 명과 충돌했습니다(F-79). 번호를 100만 대로 옮기고 시퀀스는 건드리지 않으며, 합성 값의 해시 키는 기획 번호로 두어 번호를 옮겨도 내용이 같게 했습니다(D-44).

## 4. 데이터가 정해지면 확인할 것

지금 코드는 데이터가 없는 상태에서 만든 선 설계입니다. 실제 데이터, 백엔드 계약, DB 가 정해지면 아래 가정이 맞는지 하나씩 대조해야 합니다(A-01~A-11). 코드 구조 자체는 그때 코드를 읽으면 되지만, 이 가정들은 코드를 읽어도 "가정"이라는 사실이 보이지 않습니다.

엔진이 바깥과 만나는 자리는 여섯 곳입니다. 백엔드가 보내는 요청과 이벤트(I-01), 데이터 파트가 주는 레시피 행(I-02)과 코퍼스 통계(I-03), DB 에서 읽는 사용자 이력(I-04), 엔진이 DB 에 남기는 서빙 로그(I-05), 백엔드와 평가 파트로 나가는 응답과 설정 지문(I-06)입니다. 지금은 전부 가상 데이터나 테스트가 채우고 있고, 실연결 때 각각 저장소 계층과 백엔드 계약이 채웁니다. 어떤 컬럼과 값이 필요한지는 에이전트용 8.1 표에 있습니다.

- 맛 벡터의 축 순서는 데이터 파트와 대조해 (매움, 짠맛, 단맛)으로 확정했습니다(A-01, D-16). 값은 0~1 이고 6축이 들어오면 앞 세 축만 씁니다. 다만 데이터 파트의 DB 는 사용자 취향 벡터도 6축으로 두고 있어 갱신 방식을 맞춰야 합니다(P-15).
- 인기도와 품질 점수가 이미 0~1 로 정규화되어 있다고 가정했습니다(A-02).
- 재료 ID 는 정수이고, 사용자 보유 목록·레시피·알레르기 매핑이 같은 ID 체계를 쓴다고 가정했습니다(A-03). 필수 재료는 전체 재료의 부분집합이라고 가정했습니다(A-04).
- 알레르기 코드군을 재료 ID 로 바꾸는 표가 어딘가에 있다고 가정했습니다(A-05). 2026-09-17 에 확정됐습니다 — 데이터베이스가 허용하는 그룹은 소문자 열 가지이고, 재료 표의 그룹 칸 하나가 유일한 차단선입니다. 목업도 같은 시드에서 그룹을 읽습니다(D-49).
- 레시피의 요리군 이름과 백엔드가 보내는 선호 요리군 문자열이 같은 어휘라고 가정했습니다(A-06). 탐색 슬롯은 문자열이 같은지로만 판단합니다.
- 조리시간이 비어 있는 레시피가 드물다고 가정했습니다(A-07). 비어 있으면 그 레시피는 조리시간 블록이 점수에서 빠집니다.
- 임박 재료 목록이 보유 목록의 부분집합인지는 확인하지 않습니다(A-08).
- 코퍼스 평균과 IDF 가 전체 데이터 기준이고 갱신 주기가 정해져 있다고 가정했습니다(A-09).
- **후보 조회 범위**(A-10). 이것이 가장 중요합니다. 계획서의 SQL 은 "부족 재료 2개 이하"로 걸러 500건만 넘기는데, 제가 만든 완화 로직은 넘겨받은 후보 안에서만 조건을 풉니다. 둘을 그대로 붙이면 완화할 후보가 없어 폴백이 빈손이 됩니다. 저장소 쿼리를 만들 때 "부족 4개 이하로 넉넉히 한 번 가져오기"와 "단계마다 다시 조회하기" 중 하나를 골라야 하고, 인기순 폴백은 어차피 별도 조회입니다. 데이터 파트 브랜치에 후보 조회 함수가 이미 있으므로 새로 짜기보다 그것을 호출하는 쪽으로 방향이 바뀔 수 있습니다.
- 알레르기 매핑(A-05)은 데이터 파트의 DB 에 `user_allergy` 테이블이 있어 그쪽 스키마를 확인하면 됩니다.
- 4만 6천 건 실데이터를 파이썬으로 거르지는 않는다는 원칙입니다(A-11). 파이썬 쪽 필터는 SQL 결과를 재확인하고 가상 데이터로 테스트하기 위한 것입니다.

무언가를 고치거나 되돌려야 할 때는 이렇게 합니다. 점수 수식은 `engine/rank.py` 의 블록 함수 하나만 건드리고, 그때 `test_rank.py` 의 수치 테스트가 먼저 깨지는지 확인합니다. 가중치는 `RankConfig` 한 곳에만 있고 바꾸면 로그의 지문이 따라 바뀝니다. 커밋을 모듈 단위로 쪼개 두었으므로 특정 단계만 `git revert` 로 걷어낼 수 있습니다(뒤 커밋부터 순서대로). 통합 전 상태로 돌아올 기준점이 필요하면 `cbdf312` 에 태그를 붙이면 됩니다.

## 5. 알아두면 좋은 동작

명세가 정하지 않아 제가 정한 동작들입니다(C-01~C-11). 의도한 것이니 버그로 오해하지 않도록 적어 둡니다.

- 인기순 폴백이 조리시간 상한을 무시하던 동작(C-01)은 폐기했습니다. 이제 상한을 먼저 지키고 부족할 때만 풉니다.
- 탐색 슬롯은 후보가 넉넉할 때만 정원을 채웁니다(C-02). 후보 수가 요청 개수와 같거나, 낯선 후보가 슬롯 수의 두 배 미만이거나, 품질이 후보 중위수 아래면 줄어들거나 0이 됩니다. 낯선 후보는 비선호 요리군이거나 맛이 취향과 먼 레시피입니다.
- 가구원 수는 받아 두지만 아직 어떤 점수에도 쓰지 않습니다(C-04).
- 인기도와 품질 중 하나가 비어 있으면 있는 쪽만 쓰고, 둘 다 비면 그 블록을 뺍니다(C-05). 가상 데이터는 스무 건에 한 건씩 품질 점수를 비워 이 경로를 테스트합니다.
- 설정 지문은 가중치뿐 아니라 후보 한도 같은 값까지 전부 포함한 해시라서 자주 바뀔 수 있습니다(C-06).
- 탐색 아이템의 노출 확률 역수(propensity)는 균등 슬롯은 정확히, Thompson 슬롯은 32회 표본으로 추정합니다(C-07). 성능 조정으로 64회에서 줄였습니다.
- 재정렬은 점수 상위 200건만 대상으로 하고 IDF 합을 미리 계산합니다(C-08). 후보 500건 기준 재정렬 8.5 ms, 엔진 전체 p95 22 ms 입니다.
- 가상 데이터의 알레르기 코드는 18종입니다. 아황산류는 대응 재료가 없어 뺐습니다(C-09).
- 임박 재료 목록이 보유 목록 밖의 ID 를 포함해도 그대로 계산에 넣습니다(C-03).
- 가상 데이터 JSON 은 스크립트 산출물이지만 테스트 픽스처 자리에 커밋합니다(C-10). 개인정보는 없습니다.
- `engine/` 폴더의 파일은 일곱 개로 규약의 여덟 개 기준 안입니다(C-11).

- `uv run mypy` 가 앱 제어 정책에 막힙니다. `uv run python -m mypy src` 로 실행하면 됩니다(E-01).

다섯 번째 세션은 데이터 파트에 맞추는 작업이었습니다. 회의 결정대로 계약 파일 두 개와 완성된 엔진 조각 네 개를 데이터 파트 브랜치에서 가져오고, 그 위에서 6축 맛과 열일곱 피처와 확률 노출값으로 엔진을 다시 썼습니다. 가져온 파일은 스물여섯 곳만 고쳤는데 대부분 저장소 린터가 지적하는 수학 기호였고 코드는 세 곳(재현용 난수의 예외 표기, 항상 참인 조건, 인자 타입)입니다. 확인해 보니 데이터 파트는 아직 `main` 에 병합되지 않았고 그쪽 브랜치가 `main` 을 받아 준비를 마친 상태였습니다.

네 번째 세션은 문서 정리였습니다. `main` 에 문서 규칙이 별도 문서(04)로 분리되어 올라와서 그것을 브랜치에 합치고, 파트 B 문서를 그 규칙에 맞췄습니다. 폴더를 `docs/recommend/` 로, 파일명을 식별자 대신 내용이 드러나는 이름으로 바꾸고, 문서 목록은 `docs/README.md` 한 곳에만 두고, 계획서를 표준 헤더와 `~합니다`체로 다시 썼습니다. 회의 안건은 타 파트와 정할 것 열두 건(G-01~G-12)과 B 안에서 처리할 것 열 건(N-01~N-10)으로 나눠 별도 문서로 만들었습니다. 이 기록의 선행 조건들은 그 문서에서 축 수(G-01), 모델 통일(G-02), 파일 소유(G-04), 문서 배치(G-09), 결정 문서(G-12)로 이어지고, B 내부로는 `.env` 정리(N-01)와 난수원(N-10)이 걸려 있습니다. 폴더 배치 자체는 규칙에 없어 개정 신청이 남았습니다(P-16).

여섯 번째 세션은 데이터 파트 브랜치를 통째로 합치는 작업이었습니다. 겹치는 파일 여덟 개의 충돌을 풀고, 합친 트리에서 저장소 검사 네 가지가 전부 통과하도록 만들었습니다. 서빙 코드는 손으로 고치고 일회용 도구는 범위를 좁힌 예외로 두는 선을 그었으며, 그 예외의 근거와 없앨 조건을 결정 기록으로 남겼습니다. 합치는 과정에서 테스트가 조용히 세어지지 않던 문제와 이미지 라이브러리 버전 문제를 찾아 고쳤습니다. `main` 병합 자체는 데이터 파트 개발자와 이야기한 뒤 진행합니다.

일곱 번째 세션은 "에러는 안 나는데 기능을 못 하는 것"을 찾는 작업이었습니다. 검사가 전부 통과하는 상태에서, 설정값이 실제 계산에 닿는지·피처가 실제로 변하는지·응답이 근거 있는 값인지 세 축으로 쟀습니다. 여덟 가지를 찾아 셋(F-24, F-25, F-26)을 고치고 다섯(F-27, F-28, F-29, F-30, F-31)을 남겼습니다.

고친 셋은 전부 **기본값 때문에 조용히 넘어가던 것**입니다(D-27). 헬스체크가 데이터베이스를 확인하지 않고 정상이라고 답하고 있었고, 추적 로그에 적는 난수 반복 횟수가 실제 계산에 쓰이지 않았으며, 취향 웜업 문턱이 두 곳에 따로 있었습니다. 셋 다 예외가 오르지 않아서 검사가 없으면 다음에 값을 바꾼 사람이 바뀌지 않은 결과를 보게 됩니다. 재발하면 실패하는 검사 여섯 건을 함께 넣었습니다.

남긴 다섯은 성격이 다릅니다. 조리시간 적합도가 앞 단계 필터와 겹쳐 항상 만점인 것(F-27)과 가중치 1.00 중 0.26 이 순위를 못 바꾸는 것(F-28)은 가중치 학습에서 정할 일이라 안건으로 넘겼습니다(N-13). HTTP 응답이 아직 전부 목업인 것(F-29)은 라우터 실연결(N-03)이 해소이고, 계약 검증이 조용히 멈추는 것(F-30)과 헬스체크의 redis 항목이 근거 없이 참인 것(F-31)은 데이터 파트와 정할 안건으로 올렸습니다(G-18, G-19).

이 과정에서 지난 세션 기록의 오기도 하나 찾았습니다. 계약 검증을 "통과"로 적었는데, 종료 코드를 보지 않고 화면 마지막 줄이 통과 표시인 것만 읽은 결과였습니다. 실제로는 `.env` 가 비어 있어 중간에 죽고 있었습니다(E-13). 설정값을 채우면 98건이 전부 통과합니다. 기록을 바로잡았습니다.

여덟 번째 세션은 데이터베이스를 붙일 때를 대비하는 작업이었습니다.

지금 엔진에는 목업과 기본값으로 채워 둔 자리가 열세 곳 있고 **전부 에러를 내지 않습니다.** 그래서 전환할 때 하나를 빠뜨려도 아무 일이 일어나지 않습니다. 열세 항목을 점검표로 정리하고(M-01~M-13), 그것을 건너뛸 수 없게 검사 열 건을 못처럼 박아 두었습니다. 항목 하나를 건드리면 검사가 깨지고 실패 메시지가 점검표의 번호를 알려 줍니다. 점검표를 읽지 않고 전환하는 경로를 없앤 것입니다.

제가 낸 오보도 규칙으로 막았습니다(D-28). 통과 여부를 화면 마지막 줄로 판단한 것, 돌리지 않은 검사를 통과로 적은 것, 앞선 실행의 숫자를 그대로 옮긴 것 세 건입니다. 01에 3.4 를 넣어 종료 코드로 판정하도록 하고, 개정 사례를 결정 기록에 남겼습니다. 기존 절 번호는 건드리지 않았습니다 — 저장소 안에서 그 번호를 가리키는 곳이 열두 군데라 바꾸면 전부 깨집니다.

지금 고칠 수 있는 것은 고쳤습니다. 계약 검증이 조용히 멈추던 것을 실패로 세게 했고(F-30), 사실과 다른 문서 문장을 바로잡았으며(F-33), 평가 출력이 매번 죽은 가중치와 실효 분모를 내도록 했습니다(F-28). 새로 찾은 것도 둘 있습니다 — 같은 설정이 두 곳에 있고 엔진은 한쪽만 읽는 것(F-32), 로그 실패 횟수를 읽는 곳이 없는 것(F-33)입니다.

마지막으로 문서 스물한 편에 문서 규칙 검사를 돌려 두 건을 고쳤습니다. 구분선 위치와 사람용 세션 제목의 번호 형식입니다. 점검표 항목이 고려사항과 같은 기호를 쓰던 것도 분리했습니다. 그리고 1절의 파일 수가 문서를 추가한 뒤 또 낡아 있어 고쳤는데, 방금 만든 규칙에 제가 다시 걸린 셈입니다.

지금 할 수 없는 것은 열일곱 줄의 MUST TODO 로 모았습니다(4.3). 하기 싫어서 미룬 것이 아니라 데이터베이스나 파트 간 합의가 없어서 못 하는 것들이고, 줄마다 "언제 가능한가" 를 적어 두었습니다. 사용자 이력이 비어 피처 넷이 계산되지 않는 것(F-15), 데이터베이스가 필요한 데이터 파트 검사 넷을 아직 못 돌린 것(M-12), 설정 손잡이의 정본을 정하는 일(N-02)과 그와 함께 볼 가중치 재조정(N-04, N-05)이 여기 들어 있습니다.

같은 날 마지막으로 회의 안건 문서를 체크리스트 형태로 바꿨습니다. 서른두 건 전부를 한 표에 모아 상태 열만 훑으면 무엇이 끝났고 무엇이 남았는지 보이게 했고, 결정되어 반영된 것에는 결정일과 반영 커밋과 반영된 코드 파일을, 결정이 필요한 것에는 결정자와 결정 전까지 막히는 일을 적었습니다. 문서 규칙이 문서 안 체크박스에 완료 표시를 남기지 못하게 해서 체크 표시 대신 상태 낱말을 씁니다. 반영 위치는 추정하지 않고 커밋마다 바뀐 파일을 git 에서 직접 확인해 적었습니다.

그 뒤 데이터 파트가 검토를 마치고 자기 코드를 고쳐 올린 두 커밋을 다시 합쳤습니다. 하나는 900줄이 넘던 저장소 파일에서 배치용 SQL 을 떼어 낸 것이고, 다른 하나는 재료가 몇 개의 레시피에 나오는지를 세어 채운 것입니다. 후자는 B 의 동시등장 피처와 다양성 계산이 기다리던 값입니다. 충돌은 한 파일의 두 구간뿐이었고, 파일 맨 위로 올려 둔 import 는 우리 쪽을, 새 파일로 옮겨 간 배치 SQL 은 데이터 파트 쪽을 택했습니다. 검사는 전부 종료 코드로 통과했습니다. 다만 떼어 낸 새 파일이 629줄로 규약의 500줄 상한을 다시 넘고, 도메인 폴더의 파일이 아홉 개가 되어 폴더 상한 여덟 개도 넘습니다(F-34). 데이터 파트의 파일이라 나누지 않고 회의 안건에 올렸습니다. 실제 데이터베이스가 필요한 검사는 이번에도 돌리지 못했습니다.

아홉 번째 세션은 2차 3자 회의의 결정을 구현하는 일이었습니다. 회의에서 여섯 축은 음식의 맛이고 사용자의 취향은 온보딩에서 고른 음식에서 계산하기로 했습니다(G-21, D-29). 직접 적은 세 가지 척도는 고른 음식이 있으면 저장만 하고 계산에 쓰지 않으며, 나중에 말로 하는 추천 기능의 보정값으로 씁니다. 행동은 시각과 함께 저장했다가 매번 다시 계산하고, 오래된 것은 반감기로 잊고 같은 계절·요일·시간대의 것은 더 무겁게 봅니다(G-22, D-30). 사용자마다 원본을 파일 하나에 두고 실제 데이터베이스가 붙으면 옮깁니다(G-23, D-31). 취향을 전혀 모르는 사용자에게는 임의의 취향을 지어내지 않고 새로운 시도 칸을 두 배로 늘립니다(D-32). 싫다는 신호는 취향을 만드는 데 쓰지 않습니다(D-33).

새 검사 마흔여섯 건으로 회의 결정 하나하나를 못 박았습니다 — 척도를 바꿔도 고른 음식이 있으면 취향이 변하지 않는지, 90일 전 행동의 무게가 정확히 절반인지, 같은 순간을 다른 시간대로 넣어도 같은지, 깨진 파일이 추천을 죽이지 않고 세어지는지 같은 것들입니다. 가상 사용자 열두 명에서는 취향 없는 한 명이 새로운 시도 여덟 칸을 받고, 매운 레시피를 최근 열여섯 번 만든 사용자는 행동 모드로 넘어가며, 같은 열여섯 번을 1년 전으로 두면 온보딩 취향 근처로 돌아오는 것을 확인했습니다. 코드는 세 번 복기했습니다 — 새 손잡이 아홉 개가 전부 실제로 읽히는지, 문서가 가리키는 이름과 경로가 전부 실재하는지, 그리고 제가 만든 함수 하나가 인자 다섯 개 규칙을 넘긴 것을 찾아 되돌렸습니다.

새로 본 것이 하나 있습니다(F-35). 가상 레시피의 맛 값 분포가 실제 시드와 달라 맛 정합 효과가 이전보다 작게 나옵니다. 실제 데이터에는 없는 문제라 급하지 않고 내부 안건(N-14)으로 두었습니다. 척도의 범위가 계약(0~4)과 회의 기록(1~5)에서 다른 것은 회의 안건(G-24)으로 올렸습니다. 데이터베이스가 붙을 때 취향 파일을 옮기는 일(M-14)과 온보딩·이벤트 입구를 잇는 일(M-15)은 점검표에 더했습니다.

마지막으로 노션에 올릴 일반 설명서를 따로 썼습니다. 개발자가 아니어도 읽을 수 있게 내부 식별자 없이 취향 만들기부터 목록 다듬기까지를 설명하고, 평가 파트가 자주 물을 것을 끝에 모았습니다. 독자가 사람뿐이라 두 형식 규칙의 대상은 아닙니다.

열 번째 세션은 구현을 끝낸 코드를 다시 읽는 일이었습니다. 지시는 "시간이 걸리더라도 여러 번 전체 코드를 복기" 였고, 앞 세션의 세 번에 더해 이번에는 서로 다른 관점의 독립 검토 셋을 병렬로 돌렸습니다 — 회의 결정과 코드가 맞는가, 에러 없이 틀리는 자리가 있는가, 규칙과 문서가 코드와 맞는가. 셋째 검토는 세션 한도에 걸려 시작하지 못해 문서 규칙 검사기와 지운 이름 검색과 게이트로 직접 대신했습니다. 검토가 실험으로 확인한 것만 발견으로 적었고 열다섯 건이었습니다(F-36~F-50).

가장 큰 것 넷은 이렇습니다. 별점 무게에 상한이 없어 별점 180 하나가 온보딩 취향 전체를 덮을 수 있었습니다(F-36). 취향 파일을 읽을 때 파일 안의 사용자 번호를 확인하지 않아 한 사용자의 행동이 다른 사용자의 파일로 들어갈 수 있었습니다(F-37). "깨진 파일은 취향 없는 사용자로" 약속에 구멍이 있어 형식은 멀쩡한데 내용이 틀린 파일이 추천을 죽였습니다(F-38). 같은 사용자의 기록을 동시에 저장하면 Windows 에서 160번 중 119번이 예외로 끝났습니다(F-39). 넷 다 고치고 재발하면 실패하는 검사를 붙였습니다 — 별점은 만점이어도 조리 한 번을 넘지 않고 범위 밖은 잘못된 기록으로 세며(D-38), 파일은 사용자 번호를 대조하고, 읽기 실패는 한 종류의 예외로만 나며, 저장은 임시 파일 이름을 나누고 순서를 세웁니다.

새로운 시도 칸에서도 둘을 찾았습니다. 후보를 더 가져오는 기준이 새로운 시도 칸 수만 더한 것이어서 실제로는 네 칸 중 한 칸만 채워졌고, 취향 없는 사용자는 여덟 칸 중 한 칸이었습니다(F-41). 앞서 찌꺼기 후보 문제(F-04)의 뿌리가 이것이었습니다. 기준을 36건(취향 없으면 52건)으로 올리자 가상 사용자 열두 명의 칸이 전부 설계값이 되었지만, 대가로 인기 레시피 폴백이 일곱 명으로 늘어 실데이터에서 다시 재기로 했습니다(D-34, N-15). 또 후보에 레시피 묶음 정보가 없으면 새로운 시도의 절반이 조용히 사라졌습니다(F-42). 계약은 그때 전부 무작위로 뽑으라고 적혀 있는데 데이터 파트의 함수가 그렇게 하지 않아서, B 가 밖에서 무작위로 채우고 그 사실과 채우지 못한 칸 수를 기록에 남기게 했습니다(D-35). 함수 자체를 고치는 것은 데이터 파트에 요청합니다(G-27).

나머지는 작은 것들입니다. 맛을 전혀 모르는 행동이 "행동" 으로 세어져 취향은 그대로인데 상태만 바뀌던 것(F-40), 처음 취향이 없는 사용자가 클릭 하나로 "행동" 상태가 되던 것(F-43, 기준을 척도 무게로 둠 — D-36), 손잡이 값에 검증이 없어 잘못된 값이 모델을 뒤집던 것(F-44), 같은 시각의 기록을 잘라낼 때 새 것이 먼저 버려지던 것(F-45), 평가 스크립트가 취향 없는 사용자에게 맛 효과를 지어내던 것(F-46), 한 묶음 안의 같은 행동을 두 번 세던 것(F-47), 범위 밖 척도를 잘라 넣고 같은 음식을 두 번 고르면 두 배로 세고 세 개 미만을 표시하지 않던 것(F-48, 거부하고 세고 하나로 — D-37), 온보딩 저장 때는 오래된 기록을 잘라내지 않던 것(F-49)을 고쳤습니다. 잘라내기 상한이 반감기와 무관한데 문서가 "결과에 영향 없음" 이라고 단정하던 것(F-50)은 문구를 고쳤습니다.

코드로 고치지 않고 안건으로 올린 것도 있습니다. 회의의 "월별 주기" 를 1년 주기의 위상으로 읽은 근거가 어디에도 없어 확인을 요청하고(G-25), 행동 기록에 발생 시각이 없어 오프라인 묶음이 전부 같은 시각을 받는 문제는 계약 변경이라 데이터 파트와 백엔드에 넘겼습니다(G-26). 취향 파일을 데이터베이스로 옮길 때(M-14) 같은 행동이 두 번 온 사용자는 두 저장소가 다르게 셀 수 있어 대조 기준에 적었고, 온보딩·이벤트 입구가 여전히 목업의 척도 기반 값을 돌려주는 것은 그대로 못 박혀 있습니다(M-15).

열세 번째 세션은 "오류 없이 잘못 실행되는 것" 을 다시 찾는 일이었습니다. 검사·수정·재검사를 세 번 반복하고 전부 고쳐졌을 때만 커밋하기로 했습니다. 1회차에는 저장소 검사 네 가지와 데이터 파트 검사, 가상 사용자 평가를 돌리고 검토 둘(랭킹 경로의 무음 실패, 문서와 검사의 품질)을 병렬로 붙였으며, 2회차에는 고친 뒤 전체를 다시 돌리고 변경분을 직접 다시 읽었고(셋째 검토는 세션 한도로 시작하지 못했습니다), 3회차에는 문서를 맞춘 뒤 전부 다시 돌렸습니다.

가장 뼈아픈 발견은 평가 도구였습니다. 시드 없는 난수를 쓰면서 기록에는 "사용자 번호를 시드로 재현 가능" 이라고 적고 있어서(F-51), 같은 명령이 돌릴 때마다 다른 목록을 냈고 검증 수치를 재현할 수 없었습니다. 뿌리는 조립 함수가 난수원과 시드를 따로 받는 구조였고(F-52), 이제 조립 함수가 기록에 적는 시드로 난수원을 직접 만듭니다(D-39). 다음으로 레시피 정보가 없는 후보가 갖춘 재료 하나만으로 만점이 되어 1위에 오르던 것(F-53), 어느 손잡이 값으로 만든 목록인지 기록에 남지 않던 것(F-54), 디버거의 가중치 설정에 오타가 있어도 조용히 통과하던 것(F-55), 같은 레시피가 두 번 노출되던 것(F-61)을 고쳤습니다. 피처가 없는 후보와 중복은 점수 전에 빼고 그 수를 기록에 남깁니다(D-40).

새로운 시도 쪽에서는 "지난번 만드신 X 와 비슷해요" 문구가 필요한 값을 아무도 만들지 않아 한 번도 나온 적이 없던 것(F-56), 후보가 0건일 때 무작위 폴백 표시가 잘못 붙던 것(F-57), 폴백 판정을 재정렬과 기록이 서로 다른 집합으로 내리던 것(F-62)을 고쳤습니다. 판정은 후보 전체를 기준으로 한 곳에서만 합니다(D-41). 감점을 반올림한 값으로 점수를 만들어 기록만으로 점수가 정확히 재현되게 했고(F-58), 랭킹 손잡이 전부에 범위 검증을 붙였으며(F-59), 빈 재료 이름이 깨진 문구를 만들던 것(F-60), 레시피 없이 온 조리·별점 기록이 세어지지 않던 것(F-63), 취향 파일을 읽을 수 없는 시스템 오류가 추천 전체를 죽이던 것(F-64)을 고쳤습니다. 데이터 파트 함수가 Thompson 으로 뽑힌 두 번째 후보에 확률을 제대로 붙이지 않는 것(F-65)은 안건으로 올렸고(G-28), 엔진이 읽지 않는 후보 상한 손잡이(F-66)는 손잡이 정본 안건에 묶었으며, 평가 도구의 문구(F-67)를 바로잡았습니다.

문서도 열 군데가 코드와 어긋나 있었습니다(F-68) — 예비 음식은 4개가 아니라 20개, 기피 재료 감점은 0.8배가 아니라 최대 80%(0.2배까지), 레시피 표의 요리군 칸 이름, 저장 위치의 기본값이 코드에 없다는 것, 빠진 로그 카운터 이름, 살아날 가중치 0.21, 인자 규칙을 넘는 함수 일곱 곳, 점검표 검사가 못을 박은 항목이 열다섯이 아니라 열(이제 열)이라는 것, 점검표에 적힌 검사 명령이 커버리지 문턱 때문에 종료 코드 1 로 끝난다는 것, 척도의 저장 형식입니다. 검사 쪽에서는 다양성 비율·무작위 노출 확률의 값·기록되는 값·점수 분포·뽑힌 경로를 실제로는 못 잡던 것을 새 검사로 잡게 했고 동어반복 검사 셋을 바꿨습니다(F-69). Windows 에서 `make` 가 아예 뜨지 않는 경로 문제(F-70)는 기존 안건(G-14)에 덧붙였습니다.

결과는 검사 292건 통과, 커버리지 90.64%, 데이터 파트 검사 전부 종료 코드 0, 평가 도구는 두 번 돌려 같은 결과입니다. 조립 파일이 446줄로 300줄 검토 기준을 더 넘었고(500 필수 분리는 아님) 인자 규칙을 넘는 함수는 그대로라 손잡이 정본 안건(N-02)과 함께 봅니다. 세 회차를 마친 뒤 코드와 기록을 나눠 커밋했습니다.

열네 번째 세션은 유재현이 준비한 기획측 가상운영데이터를 엔진에 넣어 보는 일이었습니다. 패키지는 기획 파일 열한 개를 증폭해 사용자 1,600명의 시드 SQL 로 바꾸고, 데이터베이스에 넣은 뒤 API 로 콜드에서 웜으로 넘어가는 시나리오를 돌리는 구성입니다. 안내서의 위치대로 저장소에 두고 순서대로 돌렸는데, 이 PC 에 데이터베이스가 없어 적재와 API 의 헬스체크는 돌리지 못했습니다(E-15). 대신 시드 파일을 읽어 엔진에 직접 넣는 도구를 만들었습니다(D-43). 서버가 데이터베이스를 읽는 두 항목이 아직 대기 상태라, 그 일을 파이썬 안에서 대신하는 셈입니다.

데이터와 도구에서 여덟 가지를 찾았습니다. 변환기가 Windows 에서 줄바꿈을 다르게 써서 재생성할 때마다 파일 전체가 달라 보이던 것(F-71), 안내서가 필요한 라이브러리가 이미 있다고 적었지만 실제로는 하나가 잠금 파일에 없던 것(F-72), API 스크립트가 내부 키를 보내지 않아 첫 단계에서 멈추던 것(F-73), 키를 붙여도 헬스체크가 데이터베이스 접속을 무기한 기다리던 것(F-74 — 접속 시간 제한이 없는 것이 원인이고 데이터 파트의 파일이라 안건 G-29 로 올렸습니다), 시드의 온보딩 취향 벡터가 회의 결정과 어긋나던 것(F-75, D-42 로 고침), 시드 설명서가 존재하지 않는 규칙을 엔진의 것처럼 적고 냉장고 없는 사용자에게 후보가 없다고 적은 것(F-76), 시드가 적어 둔 사용자 상태와 엔진이 계산한 상태가 같지 않은 것(F-77 — 클릭 위주 사용자 마흔 명은 엔진에서는 아직 섞임 상태입니다), 그리고 제가 냉장고 시나리오의 판정 기준을 잘못 잡은 것(F-78)입니다. 다섯은 코드로, 셋은 문서로 처리했습니다.

엔진은 시드에 반응했습니다. 1,600명 전원에서 알러지 위반·중복·잘못된 노출 확률·빈 사유 문구·조리시간 초과가 하나도 없었고, 행동 기록이 가장 무거운 사용자의 이력을 시간순으로 따라가면 온보딩에서 섞임을 거쳐 행동 상태로 넘어갑니다. 그 사용자가 상위 다섯 개를 지금 조리했다고 넣으면 상위 열 개 중 아홉 자리가 바뀌고, 아직 없는 재료 두 가지를 임박으로 넣으면 그 재료를 쓰는 레시피가 네 개에서 여덟 개로 늘며, 같은 시드로 두 번 돌리면 목록이 같습니다. 가상 레시피가 120건뿐이라 후보가 모자라 대부분 인기 레시피 폴백까지 내려가는 것은 카탈로그 크기의 문제입니다(N-14, N-15). 검사는 여섯 건이 늘어 298건 통과, 커버리지 90.64%, 데이터 파트 검사 여섯 가지도 전부 종료 코드 0 입니다. 시나리오 도구가 규약의 500줄을 넘어 읽기와 시나리오 두 파일로 나눴습니다. 패키지를 어디까지 커밋할지와 라이브러리를 의존성에 넣을지는 유재현이 정합니다(N-16). 판정은 전부 종료 코드였고 못 돌린 것은 못 돌렸다고 적었습니다(D-28).

열다섯 번째 세션은 데이터베이스가 없어 못 돌린 부분을 마무리하는 일이었습니다. 유재현이 WSL2 와 Docker Desktop 을 설치해 주었고(E-16), 저는 컨테이너를 띄우고 재료 시드와 합성 레시피를 넣은 뒤 가상운영데이터를 적재했습니다. 이 PC 에 `make` 와 `psql` 이 없어서 Makefile 이 부르는 명령을 직접 돌리고 적재는 컨테이너 안의 psql 로 흘려 넣었습니다.

첫 적재는 곧바로 멈췄습니다. 시드가 사용자 번호를 1부터 1600까지 고정해 넣는데, 안내서가 권하는 합성 레시피 검사가 만든 사용자 여덟 명이 이미 1~8 을 쓰고 있었습니다(F-79). 번호를 100만 대로 옮기고 시퀀스는 건드리지 않기로 했습니다(D-44). 그런데 번호만 옮긴 첫 재생성에서 알러지가 90 명에서 89 명, 냉장고가 4,442 건에서 4,474 건으로 바뀌었습니다 — 합성 값을 만드는 해시가 사용자 번호를 키로 쓰고 있었기 때문입니다(F-81). 해시 키를 기획 번호로 바꿔 내용은 이전과 완전히 같고 번호만 다른 시드를 만들었습니다. 검증 쿼리도 합성 검사 사용자를 함께 세고 있어(F-80) 시드 사용자만 세도록 좁혔습니다.

그 뒤 적재는 끝까지 갔고 여섯 표의 건수(1600 · 1600 · 1600 · 90 · 4442 · 10195)와 집단별 상태 분포가 안내서의 기대값과 같았습니다. 데이터베이스를 가리키는 서버를 띄우니 헬스체크가 0.1초에 데이터베이스 정상으로 답했고, API 시나리오도 헬스체크를 포함해 통과했습니다. 상위 목록의 변동이 0 인 것은 서버가 아직 목업을 부르는 전환 전 상태(M-01, M-03) 그대로입니다. 검사 298건 통과, 커버리지 90.64% 입니다. 이제 남은 것은 이 패키지를 어디까지 커밋할지 정하는 일입니다(N-16).

서른한 번째 세션은 추천을 실제로 돌게 만든 일입니다. 유재현이 방향을 정했습니다. 주 브랜치에 올라간 코드는 클라우드의 자동 배포가 곧장 서버에 올리므로, 이제 필요한 것은 시험용이 아니라 명세대로 운용되는 코드라는 것입니다. 그 사이 앞 세션의 작업은 주 브랜치에 합쳐졌고(PR #16), 파트 C 를 맡아 모니터링을 따로 만들었습니다(기록은 모니터링 문서에 있습니다).

결정은 셋입니다. 첫째, 레시피를 우리 데이터베이스에서 뽑지 않고 백엔드의 API 에서 하루 한 번 받아 메모리에 두고 거기서 뽑습니다(D-59). 레시피의 정본이 백엔드이고 번호도 백엔드의 것이어야 하기 때문입니다. 둘째, 실제 엔진으로 답할지 목업으로 답할지를 따로 켜고 끄지 않고 백엔드 주소가 설정돼 있는지로 정합니다(D-60). 주소가 있는데 레시피를 아직 못 받았으면 가짜 목록을 주지 않고 503 으로 답해 백엔드가 자기 인기순으로 대신하게 합니다. 셋째, 점검표는 서빙 개통과 로그 적재를 함께 하라고 했는데 적재를 떼고 열었습니다(D-61). 로그 표가 사용자 표를 참조하는데 사용자의 정본이 백엔드에 있어 우리 쪽 표가 비어 있고, 지금 이으면 한 건도 들어가지 않습니다(F-130). 대신 추천마다 한 줄을 파일에 남겨 노출 기록을 잃지 않게 했습니다.

만들면서 고친 것이 넷 있습니다. 알레르기 검사를 후보 전부에 하니 추천 한 건이 135ms 걸려, 순서를 정한 뒤 앞에서부터 필요한 만큼만 보게 했습니다(F-131). 후보를 자르는 자리에서 동점을 번호로 가르면 번호가 낮은 레시피만 영원히 후보가 되어 사용자마다 다른 순서로 가르게 했습니다(F-132). 스크랩 수가 전부 0 인 서비스 초기에 인기 신호가 0.5 로 메워져 살아 있는 것처럼 보이던 것을 없음으로 바꿨습니다(F-133). 컨테이너에서는 앱이 취향 파일을 쓸 폴더를 만들 권한이 없어 이미지가 그 폴더를 미리 만들게 했습니다(F-129). 마지막 것은 이미지를 다시 지어 확인하지는 못했습니다.

**숫자.** 단위 검사 599건 통과, 커버리지 94.08% 입니다. 계약 검사 99건, 실제 데이터 종단 35건, 실제 HTTP 종단 20건이 전부 통과했습니다. 타입 검사는 이 PC 에서 처음으로 잠금 파일의 판 그대로 돌았고 지적이 없습니다. 실제 데이터 2만 건에서 사전을 만드는 데 2~8초, 추천 한 건에 28~83ms 였습니다. 다만 **실제 백엔드와는 아직 붙여 보지 못했습니다.** 백엔드의 두 API 가 아직 없어 전부 대역으로 확인한 것입니다.

서른 번째 세션은 백엔드 팀장의 댓글 전문을 받아 반영한 일입니다. 앞 세션의 작업은 주 브랜치에 합쳐졌습니다. 이번에 코드를 고친 것은 셋입니다. 같은 요리의 판본이 한 목록에 여러 번 나오지 않게 했고(D-56), 추천을 요청할 때 냉장고와 알레르기를 반드시 보내게 했고(D-57), 백엔드의 유형 코드 ETC 를 아시안으로 읽게 했습니다(D-58). 첫째가 가장 컸습니다. 기준을 머리로 정하지 않고 실제 데이터로 골랐고, 처음 떠올린 기준이 틀렸다는 것을 데이터가 알려 주었습니다. 둘째는 파급이 있습니다. 필수 항목이 둘 생기면서 이 주소를 부르던 기존 코드가 전부 거절당하게 되어 저장소 안의 호출부 여덟 곳을 고쳤습니다. 저장소 밖에서 부르는 대시보드는 제가 고칠 수 없으니 알려야 합니다. 그리고 하나를 분명히 적어 둡니다. 알레르기를 받기 시작했지만 추천 응답이 아직 목업이라 그것으로 목록을 거르지는 못합니다. 목업을 실제 엔진으로 바꿀 때 이 둘을 잇지 않으면 알레르기를 받고도 거르지 않는 서버가 됩니다. 전환 점검표에 그 말을 넣었습니다.

스물아홉 번째 세션은 주 브랜치에 합치기 직전에 들어온 수정이었습니다. 합칠 준비를 하며 비교해 보니 우리 브랜치가 주 브랜치보다 예순두 건 앞서 있고 뒤처진 것은 없어 충돌 없이 들어갑니다. 그 가운데 서른여섯 건은 데이터 파트의 작업입니다. 그때 백엔드가 명세에 답을 달았습니다. 요청이 거절될 때 이유를 실어 달라는 것, 인기 신호는 스크랩 수부터 줄 수 있다는 것, 재료 사전은 명세의 모양 그대로 주겠다는 것입니다. 첫째만 코드를 고칠 일이었습니다(D-55). 거절 응답에 어느 항목이 왜 걸렸는지를 싣되, 영수증 기능은 본문 없는 거절이 계약이라 그대로 두고 경로로 갈랐습니다. 보낸 값은 되돌려주지 않습니다. 나머지 둘은 명세에 반영했고 명세는 2.1.0 이 되었습니다. 이번에 손댄 남의 파일은 영수증 파트의 진입점 하나와 데이터 파트의 계약·문서 생성기 셋입니다. 두 파트에 알려야 합니다. 합치는 방식은 여러 커밋을 하나로 뭉치지 않는 쪽으로 정했습니다. 뭉치면 데이터 파트의 이력이 끊겨 그쪽 브랜치가 나중에 같은 변경으로 다시 부딪힙니다.

스물여덟 번째 세션은 마무리 작업이었습니다. 저장소에 새로 올라온 코드를 합치고 마지막 검증을 한 뒤 백엔드에 전달할 API 명세를 썼습니다. 합치는 과정에서 데이터 파트와 제가 같은 알레르기 표를 따로 만들어 둔 것이 드러나 하나로 합쳤습니다. 명세는 전제부터 다시 세웠습니다. 지금 가진 데이터는 시험용 표본일 뿐이고 운영에서는 백엔드 API 로만 데이터를 받는다는 점입니다. 그래서 데이터마다 주인을 정하고, 백엔드가 주인인 냉장고와 알레르기는 추천을 요청할 때마다 함께 받기로 했습니다. 사본을 따로 들고 있으면 동기화가 한 번 실패했을 때 옛 냉장고로 추천이 나가는데 에러가 없기 때문입니다. 항목마다 지금 코드에 있는지 합의 뒤에 만드는지를 갈라 적었고, 같은 내용을 Notion 에도 올렸습니다.

스물일곱 번째 세션은 유재현의 지적에서 시작했습니다. 제가 "결함은 그대로였다" 고 쓴 것을 두고 문제가 해결되지 않은 것 아니냐고 물었고, 그 말은 제 표현이 부정확했던 탓이었습니다. 다만 다시 재 보니 실제로 남은 결함이 있었습니다. 점수가 같은 후보들 가운데 누가 목록에 들어갈지를 레시피 번호가 정하고 있어, 번호가 낮은 레시피가 모든 사용자에게 언제나 이기고 있었습니다. 사용자마다 다른 순서가 되게 고쳤고(D-52), 난수를 쓰지 않아 같은 사용자는 늘 같은 답을 받습니다.

같은 세션에서 알레르기를 백엔드가 보낼 모양으로 받게 했습니다(D-53). 백엔드는 "우유", "땅콩" 같은 한글 낱말로 보내며, 그것을 막을 재료로 푸는 부분을 새로 만들었습니다. 임의로 만든 데이터로 돌리다가 중요한 구멍을 찾았습니다. 새우 알레르기 사용자의 일위가 건새우볶음이었는데, 그 레시피의 재료 목록에 건새우가 없었습니다. 백엔드 데이터에서 주재료가 빠진 것입니다. 그래서 재료 목록만 믿지 않고 제목도 함께 보게 했습니다(D-54). 통깨가 우리 사전의 이름과 달라 참깨 알레르기 차단에서 빠져 있던 것도 고쳤습니다. 간장 속의 밀처럼 가공품 안에 든 다른 알레르기는 아직 못 막으며, 백엔드에 재료마다 알레르기를 여러 개 달 수 있는 칸을 요청했습니다.

스물여섯 번째 세션은 짧습니다. 유재현이 냉장고를 많이 쓰는 요리를 우대하는 안을 승인해 반영했고, 그 비중을 어디서 가져올지는 다시 측정해서 정했습니다. 같은 세션에서 타입 검사가 막히던 원인도 찾았습니다. 윈도우의 스마트 앱 컨트롤이 서명 없는 프로그램을 막는 것이었고, 이 기능은 예외를 등록할 수 없으며 한 번 끄면 윈도우를 다시 설치하기 전에는 켤 수 없습니다. 컴파일된 부분이 없는 옛 판 검사기로 돌리는 우회로를 만들어 당장은 검사할 수 있게 했고, 앞으로 어디서 돌릴지는 안건으로 올렸습니다.

스물다섯 번째 세션은 백엔드가 보낸 실제 데이터로 엔진을 처음 돌려 본 일이었습니다. 레시피 이만 천여 건과 재료 사전 백사십팔 종을 받아, 그동안 가상 데이터로만 검증하던 파이프라인을 끝까지 통과시켰습니다. 결과는 검증 기록에 있습니다. 요약하면 엔진은 돌지만 재료가 맞는지만으로는 순위가 서지 않았고, 맛 정보를 재료에서 복원하자 목록이 뜻을 갖게 되었습니다. 그 복원 결과가 데이터 파트가 다른 데이터로 계산해 둔 값과 매우 가까워, 방법이 옳다는 것도 함께 확인했습니다. 백엔드 난이도 표기가 우리 코드를 깨뜨리던 것은 고쳤습니다. 다만 이 세션에서는 타입 검사를 돌리지 못했습니다. 이 PC 의 보안 정책이 그 실행 파일을 막았고, 예전에 쓰던 우회로도 같은 이유로 막혔습니다(E-18). 같은 세션에서 백엔드와 주고받을 API 명세도 썼습니다. 우리가 데이터베이스에 직접 붙지 않기로 했으므로, 무엇을 받아야 하고 무엇을 돌려줄지를 엔드포인트 넷으로 정리하고 항목마다 "없으면 무엇이 꺼지는가" 를 적었습니다. 백엔드에 요청할 것 셋과 유재현이 정할 것 하나는 안건으로 올렸습니다.

스물네 번째 세션은 데이터 파트가 만든 묶음이 추천 목록의 다양성에 실제로 닿는지 확인하는 일이었습니다. 가상 레시피 삼천 건을 만들고 데이터 파트의 묶기 코드를 그대로 불러 쉰 묶음을 매긴 뒤, 네 가지 방식을 같은 조건에서 쟀습니다. 결과는 검증 기록에 있습니다. 요약하면 데이터 파트가 만든 것은 제대로 만들어졌고 추천 엔진이 스무 칸 중 두 칸에만 쓰고 있습니다. 묶음 정보를 지워도 목록은 한 칸 반만 바뀌고, 재료 겹침으로 재는 지금의 다양성은 묶음 다양성과 다른 축이라 서로를 대신하지 못합니다. 개인화 칸에 묶음을 반영할지는 유재현이 정할 일이라 선택지와 측정값을 안건으로 올렸습니다. 데이터 파트에는 두 가지를 요청했습니다. 묶기 배치가 계산하고 버리는 벡터를 저장하는 것과, 사용자 반응을 모아 새로운 시도 칸이 배우게 하는 배치입니다. 코드는 바꾸지 않았고 측정 도구는 저장소에 넣지 않았습니다.

스물세 번째 세션도 짧습니다. 클라우드 팀이 환경변수 목록을 요청해 왔고, 유재현이 "백엔드·데이터베이스 구성 논의 뒤에 정해지는 것이 맞는지, 지금 쓸 수 있으면 쓰고 바뀔 것은 할 일로 남겨 달라" 고 했습니다. 이름과 기본값은 코드가 정하는 사실이라 지금 확정할 수 있어 `docs/env_variables.md` 에 필수 여섯 개와 선택 스물네 개를 적었습니다. 값이나 변수의 존재가 논의에 달린 것 여덟 줄 — 데이터베이스 접속값, 연동 방식에 따라 생길 변수, 로그 저장소 분리, 커넥션 풀 상한, OCR 워커 메모리, 키 회전, 예시 파일의 누락 — 은 같은 문서 4절에 "언제 정해지는가" 와 함께 남겼고, 작업 기록의 할 일 표와 에이전트 메모리에도 같은 줄을 두어 회신이 오면 먼저 알리게 했습니다. 대조하다 찾은 것도 있습니다. 받은 목록의 OCR 워커 기본값은 이미지 값(1)이고 코드는 3 이며, "워커당 2.5GB" 는 코드 주석이고 컨테이너 실측은 유휴 0.45GB 라 둘을 다 적었습니다. 데이터베이스 이름은 초기화 SQL 이 만들지 않아 원격에서는 먼저 만들어야 한다는 것도 인수인계 문서에 더했습니다.

스물두 번째 세션은 짧습니다. 컨테이너 인수인계 문서와 함께 클라우드 팀에 물었던 네 가지에 답이 왔습니다. 통합 전 데이터베이스는 AWS RDS for PostgreSQL 16 이고, 우리가 쓰는 확장 네 가지와 로케일 C.UTF-8 을 지원하며, 배치 역할에 스키마 변경과 비우기 권한을 주고 인덱스 생성 메모리를 넉넉히 잡아 두며, 매일 한 번 백업해 7일 보관한다는 내용입니다(I-07). 답을 인수인계 문서에 그대로 옮기고, 그 답이 저장소 쪽에 정하는 것과 적용할 때 부탁할 것을 덧붙였습니다. 어긋날 수 있는 자리 셋(원격 데이터베이스의 기본 시간대가 UTC 인 것, 연결 유지 설정이 로컬에만 있는 것, 역할이 셋인 것)은 안건으로 올렸습니다(G-32). 코드는 바꾸지 않았습니다.

스물한 번째 세션은 데이터 파트의 요청을 처리하는 일이었습니다. 데이터 파트가 `main` 병합분을 검수하고 고친 커밋 열일곱 개를 받아 검수했고, 저장소 검사가 전부 통과하는 것을 본 뒤 우리 브랜치에 합쳤습니다. 데이터 파트의 결정 기록이 추천 엔진에 넘긴 다섯 가지는 전부 타당해 전부 실행했고, 유재현이 실제 데이터베이스 연동은 그 뒤로 미루기로 했습니다.

가장 중요한 것은 새 사용자의 첫 화면이었습니다(D-48). 데이터 파트가 재료 조인 기준을 조이자 냉장고에 상비 재료만 있는 사용자에게는 양념 제조법 94건만 후보로 남는데, 그 수가 "모자라면 인기순으로 채운다" 는 기준을 넘겨 폴백이 걸리지 않았습니다. 사용자가 직접 넣은 재료가 없으면 처음부터 인기순으로 고르게 했고, 온보딩이 냉장고를 채우게 되면 코드를 바꾸지 않아도 원래 길로 돌아갑니다.

목업의 알러지 이름은 데이터베이스의 것과 달랐습니다(D-49). 생성기가 대문자 열여덟 가지를 따로 들고 있어 소문자 열 가지인 정본과 갈렸는데, 목업은 데이터베이스를 거치지 않아 아무도 몰랐습니다. 생성기가 재료 시드에서 그룹을 읽도록 바꾸고 목업 재료 이름 여섯 개를 시드와 맞췄습니다. 같은 자리에서 저장소의 가상 데이터 시드가 변환기와 어긋난 것도 다시 만들었고, 앞으로 어긋나면 검사가 잡습니다.

추천 로그에 피처 판과 군집 판 두 칸을 더했고(D-51), 행동 기록에 발생 시각을 실을 수 있게 했으며, 후보의 피처와 코퍼스 통계를 데이터베이스에서 읽는 함수를 만들었습니다(D-50). 읽기 함수는 데이터베이스 없이 하는 검사만 통과했습니다 — 이 PC 의 Docker 가 꺼져 있어 실제 대조는 못 했습니다(E-17). 데이터 파트가 지적한 기록 오류 넷도 고쳤고, 검수에서 찾은 셋(계열 배정 규칙이 실행마다 다른 답을 내는 것, 배정 건수 불일치, 골든 픽스처에 계열 칸이 없는 것)은 데이터 파트의 파일이라 안건으로 돌려줬습니다(G-31). 검사는 스물한 건이 늘어 358건이 전부 통과하고 커버리지는 91.20% 입니다.

스무 번째 세션은 백엔드에 보낼 요청 문서를 쓰는 일이었습니다. 추천 엔진을 실제 서비스 데이터에 연결하려면 회원·냉장고·레시피의 정본이 어디에 있는지부터 알아야 합니다. 지금 우리 쪽에도 같은 이름의 테이블이 있는데, 서비스 구조상 그 정본은 백엔드일 가능성이 큽니다. 같은 데이터를 두 곳이 각자 들고 있으면 어느 쪽이 맞는지 알 수 없게 되므로, 설계를 정하기 전에 묻는 쪽을 택했습니다.

처음에는 우리가 쓰는 여섯 가지만 어디 있는지 묻는 형태로 썼는데, 유재현의 지적으로 **전체 스키마를 받는 쪽**으로 고쳤습니다. 테스트 버전은 백엔드가 무엇을 모으는지 모르는 채로 만든 것이라, 우리가 아는 것만 물으면 이미 모으고 있는데 몰라서 못 쓰는 데이터는 계속 못 쓰게 됩니다. 주문 이력이나 조리 완료 기록 같은 것이 있으면 추천이 나아질 수 있는데, 지금은 그런 것이 있는지조차 모릅니다.

함께 정하자고 올린 것이 하나 더 있습니다. 지금은 추천 결과의 모든 값이 응답에 실려 나가는데, 그중에는 화면이 쓸 일이 없는 것과 **나가면 안 되는 것**이 섞여 있습니다. 어느 칸이 무작위로 뽑힌 칸인지 응답에 적혀 있으면 클라이언트가 그 칸만 걸러낼 수 있고, 그러면 그 칸으로 하려던 측정이 성립하지 않습니다. 화면에 필요한 것만 남기고 나머지는 우리 쪽 로그로 돌리자고 제안했습니다.

열아홉 번째 세션에서 그동안의 작업을 `main` 에 넣었습니다. PR 9번을 만들어 바로 병합했고, 스무 개 커밋 97 파일이 들어갔습니다. 규칙상 두 가지가 어긋나 PR 본문 맨 위에 그대로 적었습니다 — 변경 라인 상한을 넘은 것(다만 대부분은 스크립트가 다시 만들 수 있는 생성물이고 사람이 읽을 부분은 그 4분의 1입니다)과 리뷰 승인 없이 병합한 것입니다. 승인을 받았다고 적지 않고 받지 않았다고 적었습니다. 병합 전에 충돌 여부와 검증 명령 네 가지를 다시 확인했고, 병합 뒤 브랜치와 `main` 의 내용이 같은 것도 확인했습니다.

열여덟 번째 세션은 추천 엔진이 아니라 저장소 전체에 걸린 일이었습니다. 클라우드 팀이 CI/CD 를 위해 서비스마다 Dockerfile 을 요청했고, 이 저장소는 서비스가 하나라 루트에 하나를 만들었습니다. 요청 문서의 예시와 세 가지가 달라 그대로 쓰면 빌드가 되지 않습니다 — 파이썬이 3.12 이고, 의존성 목록이 `requirements.txt` 가 아니라 잠금 파일이며, 소스 폴더가 따로 있어 패키지를 설치해야 실행 대상이 보입니다.

영수증 OCR 모델 98MB 는 이미지에 구워 넣기로 했습니다. 컨테이너가 뜰 때마다 받게 두면 외부 통신이 막힌 환경에서 준비 상태가 영영 되지 않는데, 에러는 나지 않고 트래픽만 안 받습니다. 굽는 명령은 앱이 실제로 쓰는 함수를 그대로 부르게 해서, 나중에 모델이 바뀌어도 구운 것과 쓰는 것이 갈라지지 않게 했습니다.

만들면서 한 번 걸렸습니다. 시스템 라이브러리를 실행 단계에만 적었더니 모델 굽는 단계에서 없어서 실패했습니다. 빌드와 실행이 같은 바닥을 쓰도록 고쳤는데, 이것을 따로 적으면 빌드는 성공하고 첫 OCR 요청에서야 터집니다.

실제로 빌드해서 확인했습니다. 이미지 2.62GB, 컨테이너를 띄우니 생존 확인과 준비 확인이 8초 만에 정상이고, 내부 키 없이 부르면 401, 키를 주면 데이터베이스까지 붙고, 추천 호출도 정상입니다. 비 root 로 돌고 시간대는 한국이며 이미지 안에 비밀 파일은 없습니다. 로컬에서 데이터베이스와 함께 띄우는 경로도 되살렸습니다.

열일곱 번째 세션은 온보딩에 새로 추가된 문항을 반영하는 일이었습니다. 좋아하는 음식 유형을 한식·중식·일식·양식·아시안 가운데 고르는 문항입니다.

먼저 확인한 것은 "어디까지 이미 있는가" 였습니다. 값을 담을 데이터베이스 칸도, 점수 신호도(작은 가중치로) 이미 있었습니다. 없던 것은 세 가지입니다(F-82~F-84). 서버가 받는 계약에 그 문항이 없어서 백엔드가 보내도 버려졌고, 유형의 이름이 세 곳에서 제각각이라(데이터베이스는 영문 코드, 목업은 "분식", 온보딩 목록은 "기타") 어느 조합도 레시피의 분류와 만나지 못했으며, 가중치만으로는 고른 유형이 목록에 한 번도 안 나올 수 있었습니다.

그래서 이름의 정본을 데이터 파트의 분류 사전 하나로 정하고 세 곳을 거기에 맞췄습니다. 그 과정에서 온보딩 제시 음식 목록의 다섯째 계열 "기타" 아홉 가지가 사실은 태국·베트남 음식과 멕시코·미국 음식이 섞인 묶음이라는 것을 발견해(F-85) 아시안과 양식으로 갈랐습니다. 보여 주는 음식 스무 가지와 각각의 맛 값은 그대로이고 이름표만 바뀌었습니다.

목업 레시피도 손봤습니다. 다섯 유형이 스물네 건씩 고르게 있으면 스무 칸 목록에 다섯 유형이 다 들어와서, "고른 유형이 목록에 없다" 는 상황 자체가 만들어지지 않았습니다(F-86). 실제 크롤 데이터가 한식 편중이므로 목업도 같은 모양으로 바꿨습니다.

결과는 이렇습니다. 가상운영데이터 1,600명에서 유형 칸이 293개 생겼고, 고른 유형이 스무 칸 안에 한 번도 안 나오는 사람이 460명에서 182명으로 줄었습니다. 남은 182명은 목업 레시피 120건에 그 유형이 아예 없는 경우입니다. 불변식 위반은 0건이고, 새 검사 열여섯 건을 더해 314건이 통과합니다.

계약이 바뀌는 자리라 데이터 파트 소유 파일 네 개(유형 목록, 온보딩 계약, 추천 항목 모델, 계약 검사)를 손댈 수밖에 없었고, 이것도 알릴 목록에 넣었습니다(F-90).

구현 뒤 세 번 다시 읽어 여섯 가지를 더 고쳤습니다(F-91~F-96). 가장 큰 것은 유형 칸이 다른 유형을 목록에서 지우던 것이고, 나머지는 목업이 실제 구현과 다르게 돌던 것 둘, 데이터 파트 파일에 함수를 더한 것, 가상 데이터 판정이 기능을 꺼도 통과하던 것, 불필요한 모듈 경로 조작입니다.

결정의 배경과 되돌릴 조건은 `docs/decisions/` 에 파일로 남겼습니다. 데이터베이스 전환 점검표에도 한 항목(M-16)을 더했습니다 — 지금 음식 유형은 취향 파일에만 있어서, 데이터베이스로 옮긴 뒤 선호 표에서 읽어 오지 않으면 모든 사용자가 유형을 고른 적 없는 사람이 되고 응답은 정상입니다. 잊히지 않게 검사로 못을 박았습니다.

다만 **실제 데이터베이스에서는 아직 이 기능이 돌지 않습니다.** 레시피 쪽 음식 유형 칸이 46,353건 전부 비어 있기 때문입니다. 사용자는 문항에 답했는데 목록은 아무 반응이 없는 상태가 되므로, 데이터 파트에 안건으로 올렸습니다(G-30).

열여섯 번째 세션은 짧습니다. 가상운영데이터 패키지를 어디까지 커밋할지 유재현이 (a)안, 즉 전부로 정했고, 변환기에 필요한 라이브러리 두 개(openpyxl, pandas)는 개발 의존성 묶음에 넣었습니다(N-16). 가상환경에는 같은 버전이 이미 있어 잠금 파일만 갱신했습니다. 의존성 커밋과 패키지 커밋을 나눠 올렸고 기록은 그다음 커밋입니다. 공유 경로에 새 폴더가 들어갔으니 데이터 파트에 알리는 일이 남았습니다.

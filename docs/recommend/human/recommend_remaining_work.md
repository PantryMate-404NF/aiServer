# 추천 · 모니터링에 남은 일 — 사람용 서술본

**적용 대상**: 이 작업의 흐름을 알고 싶은 사람. 정본과 어긋나면 정본이 이깁니다

## 1. 어디까지 왔나

추천 엔진은 백엔드와 합의한 명세대로 서빙되는 코드가 완성됐습니다. 모니터링은 관측부터 대시보드까지 실제 엔진 위에서 끝까지 도는 것을 확인했습니다. 다만 둘 다 백엔드 대역 위에서 확인한 것이고, 실제 백엔드 API 는 아직 없습니다. 코드는 브랜치에 있고 주 브랜치에 합치면 곧장 배포됩니다.

## 2. 우리가 할 일

배포와 직접 닿는 것이 넷입니다. 주 브랜치 병합(W-01)은 클라우드가 배포 설정을 넣은 뒤여야 합니다. 그 전에 합치면 운영이 목업으로 답하는데 상태코드는 200 이라 아무도 모릅니다. 배포되면 실제 백엔드와 처음으로 붙는 것을 확인하고(W-02), 첫 주의 수치를 기준선으로 남깁니다(W-04). 이미지에 한 줄을 더한 뒤 다시 지어 보지 않은 것(W-03)은 지금 이 PC 에서 할 수 있습니다.

추천의 질에 닿는 것 가운데 가장 큰 것은 사용자의 조리 이력으로 켜지는 두 신호입니다(W-05). 가중치의 0.21 이 꺼진 채이고 관리자 페이지가 계속 그것을 띄웁니다. 원래는 데이터 파트의 표에서 읽으려 했는데, 레시피가 백엔드에서 메모리로 오게 되면서 원천이 바뀌었습니다. 우리 쪽 이벤트와 메모리 사전만으로 만들 수 있어 다른 파트를 기다리지 않습니다. 그다음은 쌓이는 두 파일을 읽어 칸별 · 순위별 반응을 계산하는 오프라인 평가 스크립트(W-07)입니다. 누적은 되는데 읽는 도구가 없습니다.

나머지는 다른 파트의 답이 먼저입니다. 추천 로그를 데이터베이스에 넣는 일은 사용자 표의 외래키를 어떻게 할지 데이터 파트가 정해야 하고(W-06), 탐색 칸의 군집은 어디서 만들지 함께 정해야 합니다(W-08). 임계값 재조정과 로그 보존 정책, 다중 레플리카 지원은 운영이 돌아 본 뒤의 일입니다.

## 3. 다른 파트에 부탁하는 것

**백엔드**에는 배포 전에 넷이 필요합니다. 두 API 를 여는 것, 그 API 가 내부 키를 받아들이는 것, 추천이 503 일 때 인기순으로 대신하는 것, 그리고 추천 요청의 계약(냉장고와 알레르기 필수, 미리 밀어 두는 경로는 안 씀)을 지키는 것입니다. 이벤트를 모아 보내는 것과 알레르기 라벨 전체 목록도 배포 전에 받고 싶습니다. 운영 중에 계속 부탁할 것은 하나입니다 — 재료를 새로 넣거나 이름을 바꿀 때 알려 주는 것. 우리는 재료를 이름으로 우리 사전에 잇기 때문에, 모르는 이름의 재료는 에러 없이 알레르기 군을 모르는 재료가 됩니다.

**클라우드**에는 배포 설정 넷이 필요합니다. 백엔드 주소, 백엔드로 나가는 길, 지속 볼륨, 지표와 관리자 페이지의 내부망 제한입니다. 첫째가 빠지면 운영이 목업으로 답하고, 둘째가 빠지면 추천이 전부 503 이고, 셋째가 빠지면 배포할 때마다 취향과 로그가 사라집니다. 셋 다 에러가 나지 않습니다. 인수인계 문서가 전에는 "쓰기 경로가 없다" 고 적고 있었으니 최신판을 다시 받아 달라고 해야 합니다. 배포 뒤에는 상태 확인 셋과 첫 빌드 · 메모리 결과를 알려 달라고 부탁합니다.

**데이터 파트**에는 추천 로그 표의 외래키 결정이 가장 급합니다. 그다음이 군집을 어디서 만들지, 그리고 클라우드가 읽는 설치 문서의 옛 설명입니다. 나머지는 정리 항목입니다.

## 4. 순서

클라우드와 백엔드의 배포 전 항목이 끝나면 주 브랜치에 합칩니다. 그 사이 우리는 이미지 빌드, 이력 신호, 오프라인 평가를 진행합니다. 데이터 파트의 외래키 결정이 오면 로그의 DB 적재를 엽니다.

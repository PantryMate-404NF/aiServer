## 1. 이 문서를 읽는 법

안건은 서른여덟 건입니다. 다른 파트와 정할 것이 스물네 건(G), B 안에서 처리할 것이 열네 건(N)입니다.

2절 표가 체크리스트입니다. 상태 열만 훑으면 무엇이 끝났고 무엇이 남았는지 보입니다. 문서 규칙(04의 2.2)이 문서 안 체크박스에 완료 표시를 남기지 못하게 해서, 체크 표시 대신 아래 낱말로 상태를 적습니다.

| 상태 | 뜻 |
|---|---|
| `결정·반영` | 결정됐고 코드에 반영까지 끝났습니다 |
| `일부 반영` | B 가 혼자 할 수 있는 부분만 먼저 반영했고, 나머지는 결정이 필요합니다 |
| `결정 필요` | 회의나 담당자가 정해 줘야 진행할 수 있습니다 |
| `착수 가능` | 정할 것은 다 정해졌고 작업만 남았습니다 |
| `선행 대기` | 실제 데이터베이스나 실데이터, 다른 파트의 확인을 기다립니다 |
| `관찰` | 지금 값을 유지하고 실데이터에서 다시 봅니다 |

지금 가장 급한 것은 **검사 예외 네 건의 사후 확인(G-16)** 입니다. 첫 PR(#8)이 2026-09-11 에 병합되어 예외가 이미 `main` 에 들어갔는데, 규칙이 요구하는 명시 승인 기록은 없습니다. 그다음은 규약 개정 두 건(G-09, G-10)과 2차 회의 후속 네 건(G-24~G-27)입니다.

## 4. 아직 결정이 필요한 것

열세 건입니다. 급한 순서로 적습니다. 각 항목 끝의 "막히는 것" 은 결정이 날 때까지 진행할 수 없는 일입니다.

**G-16 검사 예외 승인 — 결정 필요.** 저장소에 승인 없이 들어간 검사 예외가 네 묶음 있습니다. 데이터 파트가 넣은 한글 기호 전역 제외 하나와, B 가 병합 때 넣은 파일 단위 예외·벤치 폴더 제외·커버리지 측정 범위 축소 셋입니다. 규칙상 모두 Tech Lead 승인이 필요합니다. B 는 네 건을 한 번에 승인 요청하자고 제안하고, 근거와 없앨 조건은 결정 기록 한 편에 정리해 두었습니다. 결정자는 김민경·A·B 입니다. 첫 PR 이 2026-09-11 에 병합되어 예외는 이미 `main` 에 들어갔으므로 막히는 것은 없고, 사후 승인 확인만 남았습니다. 거부되면 해당 항목을 손으로 고치는 후속 PR 을 냅니다.

**G-20 main 보호 설정 — 결정 필요.** 규칙은 `main` 을 보호 브랜치로 두고 직접 push 를 금지하는데, GitHub 에서 확인해 보니 보호 설정이 꺼져 있습니다. 누가 실수로 직접 push 해도 막히지 않습니다. B 는 보호 규칙을 켜자고 제안합니다. 결정자는 김민경입니다. 이번 병합은 PR 로 진행하므로 막히는 것은 없습니다.

**G-09 문서 배치 규칙 — 결정 필요.** 문서 규칙의 폴더 목록에 `docs/recommend/` 같은 도메인 폴더 자리가 없습니다(P-16). B 는 규칙에 도메인 폴더를 추가하자고 제안하고, 데이터 파트는 설계 문서를 저장소 밖에 두고 결정만 올리자고 했습니다. 결정자는 김민경과 팀 전원입니다. 거부되면 이 폴더의 기록을 저장소 밖으로 옮겨야 합니다.

**G-10 도메인 루트 파일 규약 — 결정 필요.** 추천 도메인 루트에 파일이 아홉 개 있습니다(P-11, F-34). 디렉터리 규약의 표에 없는 `stage.py`·`enums.py`·`policy.py`·`repository_ingest.py` 가 있고, 새 도메인 파일을 다섯 개로 묶은 상한도 넘습니다. B 는 규약 표에 네 파일을 추가하자고 제안합니다(D-17). 결정자는 김민경과 A 입니다. 데이터 파트가 904줄이던 `repository.py` 를 나눴지만 떼어 낸 `repository_ingest.py` 가 629줄로 다시 상한 500줄을 넘어, 이것도 이 논의에 묶여 있습니다.

**G-06 후보 조회 계약 — 결정 필요.** 데이터 파트에 후보를 뽑는 SQL 함수(A 의 결정 D-14)가 이미 있고, B 는 받은 후보 안에서 부족 재료 기준을 단계적으로 풉니다(A-10). 데이터 파트 함수가 너무 좁게 돌려주면 완화 단계가 빈손이 됩니다. B 는 넉넉히 받아 안에서 좁히는 방식을 제안합니다. 결정자는 A·B 이고, 막히는 것은 서빙 개통입니다.

**G-12 결정사항 문서 — 결정 필요.** 데이터 파트의 결정사항 문서가 로컬에만 있어서 맛 축 순서 사고가 났습니다. B 는 결정 기록 형식으로 나눠 올리자고 제안하고, B 도 자기 결정을 같은 형식으로 올립니다(N-07). 결정자는 A 입니다.

**G-14 Windows 에서 검사 중단 — 결정 필요.** 데이터 파트의 검사 스크립트가 통과 표시 문자를 찍는데 Windows 콘솔이 그 글자를 못 써서, 검사가 통과해도 오류로 끝납니다(E-11). B 는 `Makefile` 한 곳에서 인코딩을 지정하자고 제안합니다. 결정자는 A 입니다.

**G-17 평가 유틸 — 결정 필요.** `evaluation/threshold.py` 는 부르는 곳도 검사도 없습니다. 평가 파트가 쓸 유틸로 보여 B 는 평가 파트가 인수하고 검사를 붙이자고 제안합니다. 결정자는 A·C 입니다. 막히는 것은 없습니다.

**G-24 맛 척도의 범위 — 결정 필요.** 데이터 파트의 계약은 척도를 0~4 로 받고 2차 회의 기록은 1~5 로 적혀 있습니다. 엔진은 0~1 로 바꾼 값만 받으므로 변환은 한 곳에서만 하면 되지만, 어느 쪽이 맞는지는 정해야 합니다. B 는 계약대로 0~4 를 제안합니다 — 계약 검증 98건이 그것을 전제하고, 화면이 1~5 로 보여도 서버에는 0~4 로 보내면 됩니다. 결정자는 A 와 기획입니다. 어긋나면 척도로 취향을 만든 사용자의 취향이 한 단계씩 밀리는데 에러는 나지 않습니다.

**G-19 헬스체크의 redis 항목 — 결정 필요.** 저장소에 redis 를 쓰는 코드가 없는데 헬스체크가 redis 를 항상 정상이라고 답합니다(F-31). 같은 응답의 데이터베이스 항목은 실제로 확인하도록 이미 고쳤습니다(F-24). B 는 근거 없는 항목을 빼자고 제안합니다. 결정자는 A 입니다.

**G-25 월별 주기의 뜻 — 결정 필요.** 2차 회의는 계절·월·일 주기를 말했는데, B 는 "월별" 을 1년 주기 안에서 달이 다르면 위상이 다른 것으로 읽었고 월초·월말 같은 한 달 안의 주기는 두지 않았습니다. 이 해석이 회의의 뜻과 맞는지 확인이 필요합니다. 틀렸다면 손잡이 하나를 더하면 됩니다. 결정자는 기획과 B 입니다.

**G-26 행동 기록의 발생 시각 — 결정 필요.** 백엔드가 보내는 행동 기록에 발생 시각이 없어서 서버가 받은 시각을 씁니다. 오프라인에서 모아 둔 기록 200건이 한 번에 오면 전부 같은 시각이 되어 요일·시간대 주기를 켤 수 없습니다. B 는 선택 항목으로 발생 시각을 계약에 더하자고 제안합니다. 결정자는 A 와 백엔드입니다. 지금은 요일·시간대 주기가 꺼져 있어 막히는 것은 없습니다.

**G-27 새로운 시도의 무작위 폴백 — 결정 필요.** 후보에 레시피 묶음 정보가 없으면 전부 무작위로 뽑기로 계약에 적혀 있는데, 데이터 파트의 함수는 그 자리를 비워 두어 새로운 시도 칸의 절반이 조용히 사라졌습니다(F-42). B 가 밖에서 무작위로 채우도록 우회했고 그 사실을 기록에 남깁니다(D-35, `b7b25b4`). 계약이 있는 함수 안에서 고치는 것이 맞으므로 A 에게 요청합니다. 결정자는 A 입니다.

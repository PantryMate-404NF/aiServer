# 추천 엔진 통합 회의 안건 (사람용)

**정하는 것**: 에이전트용 회의 안건 `../recommend_engine_meeting_agenda.md` 를 사람이 읽기 위한 문장으로 옮긴 것. 정본은 에이전트용이며 괄호 안 식별자로 대응합니다

**적용 대상**: 3자 회의에 참석하는 파트 A·B·C 담당자와 백엔드

**버전**: 2.0.0 · **최종 수정**: 2026-09-10 · **작성자**: 유재현

---

## 1. 왜 이 회의가 필요한가

데이터 파트(A)가 보낸 공유 문서는 맞출 것을 세 가지로 정리했지만, A 브랜치를 직접 열어 보니 겹치는 곳이 그보다 훨씬 넓었습니다. 양쪽이 서로의 코드를 못 본 채 `src/features/recommend/` 를 각자 만들어서, 같은 경로에 다른 구현이 있고 같은 이름에 다른 모양의 모델이 있습니다. 축 순서(D-16)와 `stage.py` 배치(D-17)처럼 B 가 혼자 맞출 수 있는 것은 이미 맞췄고, 남은 것은 누군가 한쪽을 택해야 하는 결정들입니다. 안건은 타 파트와 정할 것 열두 건(G-01~G-12)과 B 안에서 처리할 것 열 건(N-01~N-10)으로 나눴습니다. 가장 급한 것은 같은 경로 파일과 같은 이름 모델의 정본을 정하는 일(G-02, G-04)입니다. 미룰수록 두 브랜치가 더 벌어집니다. 회의 뒤에는 결정 열을 채우고, 되돌리기 어려운 결론은 `docs/decisions/` 에 파일로 남깁니다.

---

## 2. 다른 파트와 정할 것

**데이터 계약.** 맛 벡터의 축 순서는 맞췄지만 축의 개수가 다릅니다(G-01, P-15). A 의 DB 는 레시피 맛, 코퍼스 평균, 사용자 취향 벡터를 모두 6축으로 두고 B 는 앞 세 축만 계산합니다. B 의 제안은 앞 세 축만 읽고 갱신하되 뒤 세 축은 건드리지 않는 것이고, 6축 전부를 쓸지는 A 의 설계 결정대로 가중치 학습 때 정합니다. 후보 조회(G-06)는 A 에 이미 SQL 함수(A 의 결정 D-14)와 저장소 함수가 있으므로 B 가 새로 짜지 않고 그것을 호출합니다. 다만 A 함수가 부족 재료 2개 기준으로 500건만 돌려주면 B 의 완화 단계가 풀 후보가 없어지므로(A-10), 부족 4개 기준으로 넉넉히 받아 B 가 안에서 좁히는 방식을 제안합니다.

**모델과 파일의 정본.** 스테이지 사이를 오가는 모델(G-02, P-12)은 이름은 같은데 모양이 다릅니다. A 의 `ScoredCandidate` 는 열일곱 개 피처를 사전으로 들고, B 는 다섯 블록을 듭니다. B 의 제안은 엔진 안에서는 블록으로 계산하고 로그로 나가는 경계에서 A 의 형태로 바꾸는 두 층 구조입니다. 같은 경로의 파일들(G-04)은 파일별로 소유를 정하자는 제안입니다. 엔진과 `stage.py` 는 B, 저장소 계층과 DDL 과 수집 코드는 A, 라우터와 서비스는 A 의 엔드포인트 집합에 B 의 파이프라인을 끼우는 공동 작업으로 나눕니다. A 의 mock·reason·serendipity 모듈이 대시보드용이라면 엔진 폴더 밖의 이름으로 옮기는 것이 좋겠습니다.

**API 계약.** 요청과 응답 모델(G-03)은 A 것에 98건의 계약 테스트와 다른 라우터가 물려 있으므로 요청은 A 기준으로 가되, 응답의 `meta` 는 B 처럼 고정 필드로 두고(D-07) 이벤트의 타입과 시각도 검증되는 타입으로(D-08), 그리고 "추천 목록의 순서를 다시 정렬하지 않는다"는 조항(X-09)을 넣자는 제안입니다. 노출 확률(G-05, P-14)은 A 가 확률로, B 가 역수로 기록해 서로 다릅니다. A 의 DB 와 평가 파트의 계산이 확률을 전제하므로 B 가 확률로 바꾸는 쪽을 제안합니다.

**피처 체계.** A 의 열일곱 개 피처와 B 의 다섯 블록을 어떻게 대응시킬지(G-07)는 세 파트가 함께 정해야 합니다. 명세가 말한 "17개 피처"의 목록이 그동안 없었는데(S-23) A 의 코드에 있었습니다. B 의 제안은 블록 점수를 열일곱 개 키로 펼쳐 기록하고, 계산하지 않는 키는 0 이 아니라 비워 두는 것입니다. A 의 규약도 "비어 있음과 0 은 다르다"고 정하고 있습니다. 서빙은 가중치 학습 전까지 다섯 블록으로 합니다. 특성 리포트(T-11)도 이 대응이 정해져야 만들 수 있습니다.

**절차와 문서.** A 의 테스트 설정이 B 의 테스트 열두 파일을 통째로 건너뛰는 문제(G-08, P-13)는 A 가 고치겠다고 했고, 단독 실행 스크립트를 `scripts/` 로 옮기는 편이 규약에 맞습니다. 문서 배치 규칙(G-09, P-16)은 이번에 새로 생긴 04 규칙의 폴더 목록에 `docs/recommend/` 같은 도메인 폴더가 없어 개정 신청이 필요합니다. 두 형식으로 기록을 남기는 근거는 결정 기록으로 올려 두었습니다. 도메인 루트에 `stage.py` 를 두는 것(G-10, P-11)도 02 규약 개정 사항입니다. 공유 파일 병합(G-11)은 내용 충돌이 없고 B 는 이미 `main` 을 합쳐 두었으며, `main` 의 설정 테스트 수정으로 B 의 선행 조건 하나(P-02)도 풀렸습니다. 마지막으로 A 의 결정사항 문서(G-12)를 저장소에 올리는 것을 지지합니다. 그 문서가 로컬에만 있어서 축 순서 사고가 났습니다. B 도 자기 결정을 같은 형식으로 올립니다.

회의 전에 A 의 미푸시 커밋 열 개에 규약 변경이나 모델 형태 변경이 있는지, 피처 키 목록이 최신인지 확인해야 합니다.

## 3. B 안에서 처리할 것

바로 할 수 있는 것부터 적습니다. `.env` 정리(N-01, P-01)는 필수 여섯 개 값만 채우면 되고, `main` 에서 설정 테스트가 개발자의 `.env` 를 읽지 않도록 고쳐졌으므로(P-02) 그 뒤에는 전체 테스트가 통과해야 합니다. 통합 전 기준점으로 태그를 붙일지(N-06)와, 되돌리기 어려운 결정(개인화 선행 D-01, 축 순서 D-16, `stage.py` D-17 등 D-01~D-18 가운데 해당하는 것)을 결정 기록 형식으로 분리하는 일(N-07)도 B 혼자 정합니다. 요리군 선호와 맛 정합이 살짝 부딪히는 현상(N-04, F-13)은 지금 값을 유지하고 실제 데이터에서 다시 봅니다. 탐색과 맛 관련 손잡이 값 다섯 개(N-05)는 전부 예시값이라 실제 후보 500건에서 재조정합니다. 난수원(N-10, D-11)은 재현이 필요해질 때 린터 예외를 신청합니다.

회의 결과에 걸린 것도 있습니다. 가중치를 설정 파일로 옮기는 시점(N-02, D-04, T-09)과 특성 리포트(N-09, T-11)는 피처 대응(G-07)이 정해져야 하고, 라우터 실연결(N-03, D-06, T-01)은 파일 소유(G-04)가, 계약 테스트 42건의 정의(N-08, T-12)는 API 계약(G-03)이 먼저입니다.

## 4. 1차 회의에서 정해진 것

여섯 건이 결정되어 반영을 마쳤습니다. 전부 "데이터 파트를 정본으로 한다"는 한 방향입니다.

- 맛 벡터는 **6축을 유지**합니다(G-01). B 는 지금 앞 세 축만 받고 뒤 세 축은 비운 채 계산에서 뺍니다. 데이터가 오면 코드를 고치지 않아도 켜집니다(D-19).
- 스테이지 모델과 API 계약은 **데이터 파트 것을 씁니다**(G-02, G-03). B 가 만든 요청·응답 모델은 지웠고, 엔진이 데이터 파트의 모델을 직접 채웁니다(D-20).
- 같은 경로에 있던 파일들도 **데이터 파트가 정본**입니다(G-04). B 는 계약 두 파일과 완성된 엔진 조각 네 개를 그대로 쓰고 점수 계산만 채웁니다(D-22).
- 노출 확률은 **확률로 통일**했습니다(G-05). B 가 쓰던 역수를 버렸습니다(D-21).
- 피처는 **데이터 파트의 열일곱 종**을 따릅니다(G-07). 못 재는 것은 0 이 아니라 비워 두고, 가중합이 그것을 분자와 분모에서 함께 뺍니다(D-20).

남은 것은 후보 조회 계약(G-06), 테스트 수집 제외(G-08), 문서와 소스 배치 규칙의 개정(G-09, G-10), 공유 파일 병합(G-11), 데이터 파트 결정 문서의 저장소 반영(G-12)입니다. 이 가운데 규약 개정 두 건이 가장 급합니다. 코드는 이미 데이터 파트에 맞췄는데 배치 규칙만 아직 규약에 없기 때문입니다.

B 안에서는 회의 결과에 걸려 있던 네 건(N-02, N-03, N-08, N-09)이 풀려 착수할 수 있게 됐습니다. 새로 두 건이 생겼는데, 난수 시드를 실제로 쓰지 않는 문제(N-10)와 사용자 이력을 읽어 오는 저장소 함수가 필요한 것(N-11)입니다.

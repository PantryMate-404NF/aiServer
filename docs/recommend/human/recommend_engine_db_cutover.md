# 추천 엔진 DB 전환 점검표 (사람용)

**정하는 것**: 실 데이터베이스를 붙일 때 반드시 처리해야 하는 일들과, 그것을 빠뜨리지 못하게 막아 둔 장치

**적용 대상**: 파트 B 진행 상황을 확인하는 팀원. 에이전트용 정본은 `../recommend_engine_db_cutover.md` 입니다

**버전**: 1.11.0 · **최종 수정**: 2026-09-23 · **작성자**: 유재현

---

## 1. 왜 점검표가 필요한가

지금 추천 엔진은 데이터베이스 없이 돕니다. 그래서 목업과 기본값과 빈 이력으로 채워 둔 자리가 열다섯 곳 있습니다. **그 자리들은 전부 에러를 내지 않습니다.** 목업이 정상 응답을 돌려주고, 기본값이 조용히 쓰이고, 빈 이력이 "값 없음" 으로 흘러갑니다.

데이터베이스를 붙일 때 그중 하나를 빠뜨려도 아무 일도 일어나지 않습니다. 화면도 검사도 조용합니다. 실제로 이런 일이 이미 세 번 있었습니다 — 헬스체크가 데이터베이스를 보지 않고 정상이라고 답했고(F-24), 로그에 적는 값이 실제 계산에 쓰이지 않았으며(F-25), 같은 설정이 두 곳에 따로 있었습니다(F-26).

## 2. 건너뛸 수 없게 해 둔 방법

`tests/unit/recommend/test_db_cutover.py` 가 열다섯 항목 가운데 열 항목이 **아직 전환 전 상태임을 못 박고 있습니다.** 나머지 다섯은 실제 데이터베이스가 있어야 확인되는 것이라 못이 없고 점검표 문구로만 남았습니다. 그중 하나를 건드리는 순간 이 검사가 깨지고, 실패 메시지가 점검표의 항목 번호를 알려 줍니다. 점검표를 읽지 않고 전환하는 경로를 없애는 것이 목적입니다.

검사가 깨지면 점검표에서 그 항목을 열고, 항목마다 적어 둔 "확인 근거" 를 실제로 돌려 통과시킨 뒤, 못을 완료 조건을 재는 검사로 바꿉니다. **못을 그냥 지우면 다음 사람이 같은 자리를 다시 밟습니다.**

## 3. 무엇이 남아 있나

열여섯 항목을 성격별로 묶으면 넷입니다. 취향 원본을 JSON 파일에서 데이터베이스로 옮기는 일(M-14)과 온보딩·이벤트 라우트를 실제 서비스에 연결하는 일(M-15)이 2026-09-11 에 더해졌습니다. 옮긴 뒤 두 저장소를 대조할 때, 같은 행동 기록이 두 번 온 사용자는 파일 쪽만 두 번 세므로 차이가 날 수 있어 따로 봅니다(2026-09-12).

**서빙을 개통하는 일**(M-01, M-02, M-05, M-06, M-15). 라우터를 실엔진에 연결하고, 후보를 데이터베이스에서 받고, 서빙 로그를 쌓고, 난수 시드를 실제로 쓰는 일입니다. 넷을 따로 하면 위험합니다. 라우터만 연결하면 실엔진이 응답하는데 로그가 한 줄도 안 쌓이고, 그 구간의 노출은 나중에 어떤 방법으로도 복원되지 않습니다.

**피처를 개통하는 일**(M-03, M-04, M-14, M-16). 사용자 이력과 코퍼스 통계를 데이터베이스에서 읽는 일입니다. 재료 빈도(IDF 의 원천)를 채우는 배치는 데이터 파트가 만들어 두었고, 2026-09-18 에 코퍼스 통계와 레시피 피처를 읽는 함수(M-02·M-04)를 만들었습니다 — 다만 라우터가 아직 부르지 않고, 실제 데이터베이스와의 대조는 Docker 가 꺼져 있어 못 했습니다. 지금은 이력이 비어 있어 선호 재료와 동시등장 피처가 계산되지 않고, 그 둘의 가중치 0.21 이 순위에 관여하지 않습니다. 이력만 붙이고 코퍼스 평균을 목업 값으로 두면 맛 계산이 틀린 기준에서 이뤄지는데, 값이 0에서 1 사이라 어떤 검사에도 걸리지 않습니다. 2026-09-15 에 더해진 음식 유형(M-16)도 같은 자리입니다. 온보딩이 받은 유형이 지금은 취향 파일에만 있어서, 데이터베이스로 옮긴 뒤 선호 표에서 읽어 오지 않으면 **모든 사용자가 유형을 고른 적 없는 사람이 됩니다.** 유형 칸이 생기지 않고 응답은 정상입니다.

**관측을 개통하는 일**(M-05, M-07, M-12). 로그 쓰기는 모든 예외를 삼키고 실패 횟수만 셉니다. 그런데 그 횟수를 읽는 곳이 지금 한 군데도 없습니다. 적재를 켜면서 이것을 함께 처리하지 않으면 **적재가 전부 실패해도 API 는 정상 응답을 돌려줍니다.**

**정하고 넘어가야 하는 일**(M-08, M-09, M-10, M-11, M-13). 같은 설정이 두 곳에 있는 것을 어느 쪽으로 합칠지, 합성 데이터가 실제 추천에 섞이지 않는지, 조리시간 적합도를 다시 정의할지, 헬스체크의 redis 항목을 어떻게 할지, 커버리지 측정 범위를 언제 되돌릴지입니다.

## 4. 전환 전까지 지킬 것 셋

**이 기간의 서빙 로그를 평가에 쓰지 않습니다.** 라우터가 목업을 서빙하는 동안에는 요청이 보낸 모델 이름을 그대로 되돌려주므로, 실엔진 이름으로 적힌 행이 실은 목업 결과일 수 있습니다.

**데이터가 없는 피처의 가중치를 0 으로 내리지 않습니다.** 지금 방식은 측정할 수 없는 피처를 분자와 분모에서 함께 빼기 때문에 남은 가중치가 알아서 재분배됩니다. 0 으로 내려 두면 데이터가 와도 켜지지 않고, 그때 코드를 고쳐야 한다는 사실을 아무도 기억하지 못합니다.

**같은 값을 두 곳에 두지 않습니다.** 두면 한쪽만 바뀌어도 에러가 나지 않습니다. 이번에 찾은 세 건이 전부 이 형태였습니다.

**2026-09-21 에 더한 것 (M-01).** 냉장고와 알레르기가 이제 추천 요청에 실려 옵니다(D-57). 목업은 그것을 받아 기록만 합니다. 서빙을 개통할 때 요청의 냉장고를 엔진의 문맥으로, 요청의 알레르기를 막을 재료로 이어야 합니다. 잇지 않고 목업만 떼어 내면 알레르기를 받고도 거르지 않는 서버가 되고, 그 서버는 아무 에러도 내지 않습니다.

**2026-09-22 에 처리한 것 (M-07).** 삼킨 예외를 세는 카운터가 이제 밖으로 나갑니다. 서버가 뜰 때 그 카운터를 지표 수집기에 등록했고, 실패가 한 건이라도 생기면 관리자 페이지와 경보가 가장 높은 심각도로 띄웁니다. 헬스체크 응답에는 싣지 않았습니다. 헬스체크는 기계가 몇 초마다 부르는 자리라 거기 실어도 읽는 사람이 없습니다.

**2026-09-22 에 서빙을 개통했습니다 (M-01 · M-02 · M-04 · M-06 · M-15).** 다만 처음 계획과 길이 달라졌습니다. 레시피의 정본이 백엔드로 가면서 우리 DB 에서 후보를 뽑는 대신, 백엔드의 API 에서 레시피를 하루 한 번 받아 메모리에 두고 거기서 뽑습니다. 그래서 M-02 와 M-04 는 "DB 에 연결" 이 아니라 "대체됨" 으로 닫았습니다. 요청에 실려 온 냉장고와 알레르기가 엔진에 이어졌고, 알레르기는 재료와 제목을 함께 보고 거릅니다. 백엔드의 주소가 설정돼 있을 때만 실제 엔진이 답하고, 설정이 없으면 개발용 목업이 답합니다. 레시피를 아직 받지 못한 동안에는 가짜 목록을 주지 않고 503 으로 답해 백엔드가 자기 인기순으로 대신하게 합니다.

남은 것은 셋입니다. 첫째는 추천 로그를 DB 에 남기는 일(M-05)입니다. 점검표는 서빙 개통과 로그 적재를 한 묶음으로 하라고 했는데 이번에 뗐습니다. 로그 표가 사용자 표를 참조하는데 사용자의 정본이 백엔드에 있어 우리 쪽 표가 비어 있고, 지금 이으면 한 건도 들어가지 않기 때문입니다. 대신 추천마다 한 줄을, 그리고 받은 이벤트도 한 줄씩 파일에 남겨 노출과 반응의 기록을 잃지 않게 했습니다. 둘째는 취향 원본을 DB 로 옮기는 일(M-14)입니다. 지금은 파일이라 컨테이너에 지속 볼륨이 필요합니다. 셋째는 사용자의 조리 이력으로 두 신호를 켜는 일(M-03)입니다. 셋째가 꺼져 있는 동안 가중치 0.21 만큼이 쉬고 있고, 관리자 페이지가 그것을 "꺼진 신호" 로 보여 줍니다.


**2026-09-23 에 처리한 것 (M-03).** 사용자의 조리 이력으로 켜지는 두 신호가 켜졌습니다. 원래는 데이터 파트의 표에서 읽으려 했는데, 레시피가 백엔드에서 메모리로 오고 이벤트가 우리 취향 저장소에 쌓이면서 그 둘만으로 만들 수 있게 됐습니다. 최근 2주에 조리한 레시피의 재료가 비슷하면 "지난번 만드신 X 와 비슷해요" 사유가 붙고, 조리 · 저장한 레시피의 재료는 선호 재료가 됩니다. 최근 한 주에 보여 준 레시피는 감점돼 새로고침해도 같은 목록이 반복되지 않습니다. 남은 것은 로그의 데이터베이스 적재(M-05)와 취향 원본의 이전(M-14)입니다.

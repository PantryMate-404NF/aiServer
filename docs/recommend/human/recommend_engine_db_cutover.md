# 추천 엔진 DB 전환 점검표 (사람용)

**정하는 것**: 실 데이터베이스를 붙일 때 반드시 처리해야 하는 일들과, 그것을 빠뜨리지 못하게 막아 둔 장치

**적용 대상**: 파트 B 진행 상황을 확인하는 팀원. 에이전트용 정본은 `../recommend_engine_db_cutover.md` 입니다

**버전**: 1.0.0 · **최종 수정**: 2026-09-11 · **작성자**: 유재현

---

## 1. 왜 점검표가 필요한가

지금 추천 엔진은 데이터베이스 없이 돕니다. 그래서 목업과 기본값과 빈 이력으로 채워 둔 자리가 열세 곳 있습니다. **그 자리들은 전부 에러를 내지 않습니다.** 목업이 정상 응답을 돌려주고, 기본값이 조용히 쓰이고, 빈 이력이 "값 없음" 으로 흘러갑니다.

데이터베이스를 붙일 때 그중 하나를 빠뜨려도 아무 일도 일어나지 않습니다. 화면도 검사도 조용합니다. 실제로 이런 일이 이미 세 번 있었습니다 — 헬스체크가 데이터베이스를 보지 않고 정상이라고 답했고(F-24), 로그에 적는 값이 실제 계산에 쓰이지 않았으며(F-25), 같은 설정이 두 곳에 따로 있었습니다(F-26).

## 2. 건너뛸 수 없게 해 둔 방법

`tests/unit/recommend/test_db_cutover.py` 가 열세 항목이 **아직 전환 전 상태임을 못 박고 있습니다.** 그중 하나를 건드리는 순간 이 검사가 깨지고, 실패 메시지가 점검표의 항목 번호를 알려 줍니다. 점검표를 읽지 않고 전환하는 경로를 없애는 것이 목적입니다.

검사가 깨지면 점검표에서 그 항목을 열고, 항목마다 적어 둔 "확인 근거" 를 실제로 돌려 통과시킨 뒤, 못을 완료 조건을 재는 검사로 바꿉니다. **못을 그냥 지우면 다음 사람이 같은 자리를 다시 밟습니다.**

## 3. 무엇이 남아 있나

열세 항목을 성격별로 묶으면 넷입니다.

**서빙을 개통하는 일**(M-01, M-02, M-05, M-06). 라우터를 실엔진에 연결하고, 후보를 데이터베이스에서 받고, 서빙 로그를 쌓고, 난수 시드를 실제로 쓰는 일입니다. 넷을 따로 하면 위험합니다. 라우터만 연결하면 실엔진이 응답하는데 로그가 한 줄도 안 쌓이고, 그 구간의 노출은 나중에 어떤 방법으로도 복원되지 않습니다.

**피처를 개통하는 일**(M-03, M-04). 사용자 이력과 코퍼스 통계를 데이터베이스에서 읽는 일입니다. 지금은 이력이 비어 있어 선호 재료와 동시등장 피처가 계산되지 않고, 그 둘의 가중치 0.21 이 순위에 관여하지 않습니다. 이력만 붙이고 코퍼스 평균을 목업 값으로 두면 맛 계산이 틀린 기준에서 이뤄지는데, 값이 0에서 1 사이라 어떤 검사에도 걸리지 않습니다.

**관측을 개통하는 일**(M-05, M-07, M-12). 로그 쓰기는 모든 예외를 삼키고 실패 횟수만 셉니다. 그런데 그 횟수를 읽는 곳이 지금 한 군데도 없습니다. 적재를 켜면서 이것을 함께 처리하지 않으면 **적재가 전부 실패해도 API 는 정상 응답을 돌려줍니다.**

**정하고 넘어가야 하는 일**(M-08, M-09, M-10, M-11, M-13). 같은 설정이 두 곳에 있는 것을 어느 쪽으로 합칠지, 합성 데이터가 실제 추천에 섞이지 않는지, 조리시간 적합도를 다시 정의할지, 헬스체크의 redis 항목을 어떻게 할지, 커버리지 측정 범위를 언제 되돌릴지입니다.

## 4. 전환 전까지 지킬 것 셋

**이 기간의 서빙 로그를 평가에 쓰지 않습니다.** 라우터가 목업을 서빙하는 동안에는 요청이 보낸 모델 이름을 그대로 되돌려주므로, 실엔진 이름으로 적힌 행이 실은 목업 결과일 수 있습니다.

**데이터가 없는 피처의 가중치를 0 으로 내리지 않습니다.** 지금 방식은 측정할 수 없는 피처를 분자와 분모에서 함께 빼기 때문에 남은 가중치가 알아서 재분배됩니다. 0 으로 내려 두면 데이터가 와도 켜지지 않고, 그때 코드를 고쳐야 한다는 사실을 아무도 기억하지 못합니다.

**같은 값을 두 곳에 두지 않습니다.** 두면 한쪽만 바뀌어도 에러가 나지 않습니다. 이번에 찾은 세 건이 전부 이 형태였습니다.

# aiServer 컨테이너 인수인계

**정하는 것**: 이 저장소를 이미지로 만들어 배포할 때 필요한 것 — 빌드 방법, 런타임 계약(포트·환경변수·헬스체크), 외부 의존, 실측 자원, 확인한 것과 확인하지 못한 것

**적용 대상**: 이미지 빌드·경량화·보안 스캔과 배포를 맡는 클라우드 팀. 이 저장소를 처음 여는 분을 기준으로 씁니다

**버전**: 1.5.0 · **최종 수정**: 2026-09-22 · **작성자**: 유재현

---

## 1. 무엇을 드리는가

이 저장소는 **서비스 하나**입니다. FastAPI 앱 한 개가 영수증 OCR 과 추천을 함께 서빙하므로 이미지도 하나입니다.

| 파일 | 위치 | 내용 |
|---|---|---|
| `Dockerfile` | 저장소 루트 | 4단계 빌드(base · builder · models · runtime) |
| `.dockerignore` | 저장소 루트 | 빌드 컨텍스트에서 비밀값·데이터·가상환경을 제외 |
| `docker-compose.yml` 의 `reco-api` | `deploy/` | 로컬에서 DB 와 함께 띄우는 용도. 배포용이 아닙니다 |
| `deploy/prometheus/` · `deploy/grafana/` | `deploy/` | 추천 엔진 모니터링(수집 설정 · 경보 규칙 · 대시보드). 쓰실지는 선택입니다(13절) |

## 2. 빌드와 실행

**빌드 컨텍스트는 저장소 루트입니다.** 하위 폴더에서 빌드하면 `pyproject.toml` 과 `uv.lock` 을 찾지 못합니다.

```bash
docker build -t reco-ai-server:<tag> .
docker run --rm -p 8000:8000 \
  -e DB_HOST=... -e DB_NAME=... -e DB_USER=... -e DB_PASSWORD=... \
  -e INTERNAL_API_KEY=... -e GEMINI_API_KEY=... \
  -e BACKEND_BASE_URL=http://<백엔드 내부 주소>:<포트> \
  -v <지속 볼륨>:/app/var \
  reco-ai-server:<tag>
```

빌드 인자는 없습니다. 프록시나 사설 레지스트리가 필요하면 알려 주시면 넣겠습니다.

`BACKEND_BASE_URL` 과 `/app/var` 볼륨은 2026-09-22 에 더한 것입니다. 없어도 컨테이너는 뜨지만 **추천이 목업으로 답하고, 배포할 때마다 사용자의 취향과 추천 로그가 사라집니다**(13절).

## 3. 요청 문서의 예시와 다른 점 셋

예시(`python:3.11-slim` + `requirements.txt`)를 그대로 쓰면 빌드가 되지 않거나 조용히 틀립니다.

| 항목 | 예시 | 이 저장소 | 이유 |
|---|---|---|---|
| 파이썬 | 3.11 | **3.12** | `pyproject.toml` 이 `>=3.12,<3.13` 이라 3.11 에서는 설치가 거부됩니다 |
| 의존성 | `requirements.txt` + `pip` | **`uv.lock`** + `uv sync --frozen --no-dev` | 이 저장소에 `requirements.txt` 가 없습니다. 잠금 파일이 정본이고 개발·CI·운영이 같은 버전을 쓰는 근거입니다 |
| 실행 대상 | `main:app` | **`main:create_app` (팩토리)** | 앱 객체가 아니라 앱을 만드는 함수입니다. 소스 루트가 `src/` 라 패키지를 설치해야 이 이름이 보입니다 |

`requirements.txt` 가 필요하시면 잠금 파일에서 뽑아 드릴 수 있습니다. 다만 그것을 빌드에 쓰면 두 벌이 되어 갈라지므로 권하지 않습니다.

## 4. 이미지 구성

```text
base     python:3.12-slim + 시스템 라이브러리 4종(libgl1 libglib2.0-0 libgomp1 tzdata)
builder  uv 로 의존성 설치 → 앱 설치
models   OCR 모델 가중치 내려받기 (약 98MB)
runtime  base + 실행에 필요한 것만 복사. 비 root 로 실행
```

**시스템 라이브러리를 base 한 곳에만 적은 것이 중요합니다.** 빌드 단계와 실행 단계에 따로 적으면 한쪽에만 있는 라이브러리가 생기고, 그러면 **빌드는 성공한 뒤 첫 요청에서** 터집니다. 실제로 만들다가 한 번 걸렸습니다.

- `libgl1` · `libglib2.0-0` — OpenCV(`import cv2`)
- `libgomp1` — Paddle 의 OpenMP 런타임
- `tzdata` — 없으면 `TZ` 를 줘도 조용히 UTC 로 돕니다

**OCR 모델은 빌드 때 구워 넣습니다.** 런타임에 받게 두면 컨테이너가 뜰 때마다 약 98MB 를 내려받고, 외부 통신이 막힌 환경에서는 준비 상태가 영영 되지 않는데 에러는 나지 않습니다. 구워 두면 같은 태그가 어디서 뜨든 같은 모델을 씁니다. 모델은 `/home/app/.paddlex` 에 있습니다.

### 4.1 크기

빌드 실측 **2.62GB** (linux/amd64). 큰 것부터입니다.

| 항목 | 크기 |
|---|---|
| paddle (딥러닝 런타임) | 719MB |
| opencv (`cv2` + `.libs`) | 182MB |
| pandas | 75MB |
| modelscope | 65MB |
| numpy | 43MB |
| OCR 모델 가중치 | 98MB |
| 가상환경 전체 | 1.5GB |

경량화 여지는 paddle 과 opencv 에 몰려 있습니다. 둘 다 영수증 OCR 에만 쓰이므로, 추천 API 만 필요한 배포라면 OCR 의존성을 뺀 별도 이미지를 만드는 쪽이 멀티스테이지 조정보다 효과가 큽니다. 필요하시면 만들어 드리겠습니다.

## 5. 런타임 계약

| 항목 | 값 |
|---|---|
| 포트 | 8000 |
| 실행 | `uvicorn main:create_app --factory --host 0.0.0.0 --port 8000 --workers 1` |
| 사용자 | 비 root (`uid 10001`, 이름 `app`) |
| 작업 디렉터리 | `/app` |
| 시간대 | `Asia/Seoul` |
| 쓰기 필요 경로 | **`/app/var`**(2026-09-22 부터). 추천이 사용자의 취향 원본(`profiles/`)과 추천 로그(`reco_logs/`)를 여기에 씁니다. **지속 볼륨을 붙여 주십시오.** 나머지는 읽기 전용 파일시스템이어도 됩니다(`/tmp` 는 열어 주십시오). 1.3.0 까지 "쓰기 경로 없음" 이라 적었던 것이 바뀐 것입니다 |
| 종료 | `SIGTERM` 에 OCR 워커 풀을 정리합니다. 유예 30초면 넉넉합니다 |

**워커는 1 로 두십시오.** 이유가 셋입니다. 앱이 프로세스 안에서 OCR 프로세스 풀을 따로 띄우므로 uvicorn 워커를 늘리면 그 풀이 워커 수만큼 생겨 메모리가 배로 듭니다. 추천의 레시피 사전도 워커마다 따로 받아 메모리에 둡니다. `/metrics` 의 숫자도 워커마다 따로라 수집할 때마다 다른 워커의 값이 잡혀 그래프가 널뜁니다. 수평 확장은 레플리카로 해 주십시오. 레플리카는 각자 백엔드에서 레시피를 받고 각자 `/metrics` 를 냅니다 — **레플리카가 둘 이상이면 `/app/var` 를 어떻게 나눌지 먼저 알려 주십시오.** 취향 원본이 파일이라, 볼륨을 따로 쓰면 같은 사용자의 취향이 레플리카마다 달라지고 같이 쓰면 나중 쓰기가 앞의 것을 덮습니다.

### 5.1 환경변수

**필수 6개.** 없으면 기동 시점에 멈춥니다. 비밀값은 이미지에 굽지 않으며 `.dockerignore` 가 `.env` 를 빌드 컨텍스트에서 막고 있습니다.

| 이름 | 비밀 | 설명 |
|---|---|---|
| `DB_HOST` | | PostgreSQL 주소 |
| `DB_NAME` | | 데이터베이스 이름 |
| `DB_USER` | | 접속 계정 |
| `DB_PASSWORD` | 예 | 접속 비밀번호 |
| `INTERNAL_API_KEY` | 예 | 백엔드만 호출하도록 막는 내부 키. 모든 업무 경로가 `X-Internal-Api-Key` 헤더로 검사합니다 |
| `GEMINI_API_KEY` | 예 | 영수증 후처리 LLM 키 |

선택값은 기본값이 있습니다. 컨테이너에서 자주 쓰는 것만 적습니다. **전체 목록(필수 6 · 선택 33)과 백엔드·DB 구성 논의 뒤 바뀌는 것은 `docs/env_variables.md` 에 있습니다.** `.env.example` 은 9개가 빠져 있어 전체 목록이 아닙니다.

| 이름 | 기본값 | 설명 |
|---|---|---|
| `DB_PORT` | 5432 | |
| `LOG_LEVEL` | INFO | |
| `BACKEND_BASE_URL` | (없음) | **운영에서는 반드시 채웁니다.** 백엔드의 내부 주소입니다. 비어 있으면 추천이 목업으로 답하는데 상태코드는 200 입니다(13절) |
| `OCR_WORKERS` | **1** (이미지 기본값) | OCR 워커 수. 메모리를 넉넉히 준 노드에서만 올리십시오 |
| `TZ` | Asia/Seoul | 바꾸면 소비기한 임박 판정 날짜가 달라집니다 |

## 6. 헬스체크와 프로브

| 경로 | 인증 | 뜻 |
|---|---|---|
| `GET /health/live` | 불필요 | 프로세스가 살아 있습니다. 무거운 자원을 건드리지 않습니다 |
| `GET /health/ready` | 불필요 | OCR 모델 적재가 끝났습니다. 그전에는 503 입니다 |
| `GET /health` | 필요 | 모델 버전과 DB 접속 여부를 함께 돌려줍니다. 운영 프로브용이 아닙니다 |
| `GET /metrics` | 필요 | Prometheus 형식의 지표. 내부 키를 `X-Internal-Api-Key` 헤더나 `Authorization: Bearer <키>` 로 받습니다. 프로브용이 아닙니다 |
| `GET /admin/monitoring` | 불필요(페이지) | 추천 엔진 상태를 보는 관리자 페이지. 빈 껍데기 HTML 이고 숫자는 키를 넣어야 나옵니다. **내부망에서만 닿게 해 주십시오** |

이미지 안에 `HEALTHCHECK` 로 `/health/live` 가 걸려 있습니다. 쿠버네티스에서는 아래처럼 나눠 주십시오.

```yaml
livenessProbe:
  httpGet: { path: /health/live, port: 8000 }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /health/ready, port: 8000 }
  periodSeconds: 5
startupProbe:
  httpGet: { path: /health/live, port: 8000 }
  failureThreshold: 12        # 모델 적재까지 실측 8~14초
  periodSeconds: 5
```

**liveness 에 `/health/ready` 를 쓰지 마십시오.** 모델을 올리는 동안 컨테이너가 죽고 다시 뜨기를 반복합니다.

`/health/ready` 는 **추천의 레시피 사전과 무관합니다.** 사전을 받기 전에도 200 이고 그동안 추천만 503 입니다. 영수증 기능이 백엔드 때문에 막히지 않게 나눈 것입니다. `/health` 의 `model_version` 이 `mock-` 으로 시작하면 `BACKEND_BASE_URL` 이 빠진 것입니다.

`/health` 응답의 `redis` 필드는 **근거 없는 값입니다.** 지금 이 앱에는 redis 클라이언트가 없고 의존성에도 없습니다. 항상 참으로 나가므로 모니터링 신호로 쓰지 마십시오. 저장소에도 고칠 항목으로 적혀 있습니다.

## 7. 외부 의존

| 대상 | 필수 | 내용 |
|---|---|---|
| PostgreSQL 16 | 기동에는 예, 추천에는 아니요 | 확장 네 개가 필요합니다 — `vector` · `intarray` · `pg_trgm` · `ltree`. 스키마는 `reco` 입니다. 로컬 기준 이미지는 `pgvector/pgvector:pg16` 이고 초기화 SQL 은 `deploy/init/` 에 있습니다. 통합 전 배치는 **AWS RDS for PostgreSQL 16** 으로 확정됐습니다(12절) |
| Gemini API | 예(영수증 기능) | 아웃바운드 HTTPS 가 필요합니다. 막히면 기동은 되고 영수증 요청만 실패합니다 |
| 백엔드 서버 | 예(추천 기능) | **AI → 백엔드 방향**의 HTTP 가 필요합니다(`BACKEND_BASE_URL`). 기동 직후와 그 뒤 24시간마다 레시피와 재료를 받아 옵니다. 막히면 기동은 되고 추천만 전부 503 입니다 — 백엔드가 인기순으로 대신해 화면은 멀쩡해 보입니다. 지금까지는 백엔드 → AI 방향만 있었습니다 |
| Prometheus | 아니요 | 쓰신다면 **수집기 → AI** 방향으로 `/metrics` 에 닿아야 합니다. 자체 수집 도구를 쓰셔도 됩니다(13절) |
| Redis | 아니요 | 앱이 쓰지 않습니다(6절) |
| 모델 저장소 | 아니요 | 가중치를 이미지에 구워 두어 런타임 다운로드가 없습니다 |

컨테이너 안에서 DB 주소는 `localhost` 가 아닙니다. 서비스 이름이나 실제 엔드포인트를 `DB_HOST` 로 주십시오.

**DB 접속값 넷은 기동에 필수이지만, 2026-09-22 부터 추천은 DB 를 읽지 않습니다.** 레시피는 백엔드에서 받고 취향과 로그는 `/app/var` 에 둡니다. DB 에 닿지 못해도 추천은 나가고 `/health` 의 `db` 만 `false` 입니다. RDS 가 준비되기 전에 추천을 먼저 여실 수 있다는 뜻입니다. DB 는 데이터 파트의 배치와, 추천 로그를 DB 로 옮길 때 다시 쓰입니다.

## 8. 실측치

호스트에서 이미지를 만들어 컨테이너로 띄운 결과입니다. 판정은 전부 종료 코드와 응답 코드로 했습니다.

| 항목 | 값 |
|---|---|
| 빌드 | 종료 코드 0 · 이미지 2.62GB |
| 기동 → `/health/live` 200 | 즉시 |
| 기동 → `/health/ready` 200 | 8~14초 (모델 적재 포함) |
| 유휴 메모리 | 456MiB (`OCR_WORKERS=1`) |
| 영수증 1건 처리 중 메모리 | 536MiB |
| 내부 키 없이 호출 | 401 |
| 내부 키로 `/health` | 200 · `db: true` |
| 추천 호출 `/v1/recommend` | 200 |

이 표는 2026-09-16 의 이미지로 잰 것입니다. 그때의 추천은 목업이었습니다. 실서빙과 `/app/var` 를 더한 뒤로는 이미지를 다시 짓지 못했고, 실서빙은 호스트에서 확인했습니다(13절).
| 실행 사용자 | `uid 10001` |
| 시간대 | KST |
| 이미지 안 `.env` | 없음 |

메모리 요청은 **512Mi**, 상한은 **1Gi** 를 시작점으로 권합니다(`OCR_WORKERS=1` 기준). 워커를 올리면 워커 하나당 수백 MiB 를 더 잡으십시오.

## 9. 확인하지 못한 것

정직하게 적습니다. 아래는 저희 쪽에서 재지 않았습니다.

- **arm64(Graviton)** — linux/amd64 로만 빌드하고 확인했습니다. 멀티아키가 필요하면 알려 주십시오. Paddle 휠이 arm64 에 있는지부터 확인해야 합니다.
- **GPU** — CPU 전용 구성입니다. GPU 런타임은 베이스 이미지와 Paddle 패키지가 모두 달라집니다.
- **부하와 지연시간** — 단건 호출만 확인했습니다. 동시 처리량과 p95 는 재지 않았습니다.
- **쿠버네티스 매니페스트** — 6절의 프로브 예시는 참고용이고 실제로 적용해 보지 않았습니다.
- **2026-09-22 의 Dockerfile 변경** — `/app/var` 를 앱 사용자 소유로 만드는 한 줄을 더했습니다. 그 뒤로 이미지를 다시 지어 보지 못했습니다. 볼륨을 붙였을 때 uid 10001 이 쓸 수 있는지도 확인하지 못했습니다(볼륨 종류에 따라 소유자가 root 로 덮입니다 — 쿠버네티스라면 `securityContext.fsGroup` 으로 맞추는 자리입니다).
- **실제 백엔드와의 연동** — 백엔드의 두 API 가 아직 없어 대역 서버로만 확인했습니다.
- **추천의 메모리** — 레시피 2만 건의 사전이 메모리에 올라갑니다. 8절의 유휴 456MiB 는 그 전의 값이고 사전을 올린 뒤의 값은 재지 않았습니다. 상한 1Gi 가 넉넉한지 첫 배포에서 봐 주십시오.

## 10. 지금 알고 계셔야 하는 결함

**영수증 OCR 요청(`POST /v1/ocr/receipt`)이 500 을 냅니다.** 이미지 문제가 아니라 저장소가 현재 쓰는 라이브러리 조합의 문제이고, 컨테이너 밖 개발 환경에서도 똑같이 재현됩니다.

- 증상: 모델 적재와 헬스체크는 정상(`ready` 200). 실제 인식 요청에서 `NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support` 로 실패합니다.

- 확인한 처방: 엔진을 만들 때 oneDNN 을 끄면 정상 인식됩니다(같은 이미지에서 7건 인식). 적용 여부는 영수증 기능 담당이 정합니다.
- **클라우드 팀이 하실 일은 없습니다.** 다만 CI 의 스모크 테스트에 이 경로를 넣으시면 지금은 실패하므로, 고쳐질 때까지 제외하거나 실패를 예상값으로 두십시오. 추천 경로와 헬스체크는 정상입니다.

## 11. 이미지를 손보실 때 부탁드릴 것

- `/home/app/.paddlex` 를 지우지 마십시오. OCR 모델 가중치이고, 지우면 런타임에 다시 받으려 합니다.
- `RUN mkdir -p /app/var && chown app:app /app/var` 줄을 빼지 마십시오. 빼면 볼륨 없이 띄운 컨테이너에서 앱이 폴더를 만들지 못해 온보딩과 이벤트가 500 이 됩니다.
- 시스템 라이브러리 네 개(`libgl1` · `libglib2.0-0` · `libgomp1` · `tzdata`)를 빼지 마십시오. 넷 다 빼도 **빌드는 성공하고 실행 중에** 터집니다.
- `uv sync --frozen` 의 `--frozen` 을 빼지 마십시오. 잠금 파일을 무시하고 최신 버전을 끌어오면 개발 환경과 배포 이미지가 갈라집니다.
- 비밀값을 `ARG` 나 `ENV` 로 굽지 마십시오. 이미지 레이어에 들어간 값은 저장소에 올라간 뒤 지울 수 없습니다.

바꾸신 Dockerfile 을 저장소에 돌려주시면 저희가 그 위에서 이어 가겠습니다. 두 벌이 되면 어느 쪽이 배포된 것인지 알 수 없어집니다.

## 12. 클라우드 팀 회신 (2026-09-18) — DB 배치

이 문서를 드리면서 함께 물었던 네 가지에 대한 답을 그대로 적고, 그 답이 저장소 쪽에 정하는 것을 붙입니다.

| 물은 것 | 회신 |
|---|---|
| 통합 전까지 이 DB 를 어디에 두는가 | AWS RDS for PostgreSQL 16 인스턴스로 프로비저닝 |
| 매니지드가 확장 4종과 C.UTF-8 을 지원하는가 | `vector` · `intarray` · `pg_trgm` · `ltree` 모두 지원 확인. 인스턴스 생성 시 로케일 C.UTF-8 로 배포 |
| 파트 A 배치 구동과 HNSW 인덱스 생성 권한 | `reco_batch` 역할에 스키마 DDL·TRUNCATE 권한 부여. 인덱스 생성 시 메모리가 모자라지 않게 RDS 파라미터 그룹의 `maintenance_work_mem` 상향 |
| 백업 주기와 보관 기간 | 매일 1회 자동 스냅샷과 시점 복구 활성화, 7일 보관 |

**이 답이 정하는 것.**

- 앱과 DB 는 다른 호스트입니다. `DB_HOST` 는 RDS 엔드포인트이고 연결은 TCP 입니다. `deploy/docker-compose.yml` 의 `tcp_keepalives_*` 는 로컬 컨테이너에만 적용되므로, 같은 값이 필요하면 RDS 파라미터 그룹에 넣어야 합니다. 헬스체크의 접속 대기 문제(6절, `connect_timeout` 없음)는 원격 배치에서 기본 경로가 됩니다.
- 로케일 C.UTF-8 은 저장소가 요구하는 값과 같습니다. `C` 나 `en_US.UTF-8` 이면 한글 trigram 매칭이나 정렬이 깨집니다(`deploy/docker-compose.yml` 의 주석에 실측이 있습니다).
- HNSW 인덱스는 `deploy/post/post_index.sql` 이 세션 단위로 `SET maintenance_work_mem = '1GB'` 을 올려 만듭니다. 파라미터 그룹 값은 그 아래에서의 바닥값이며, 인스턴스 메모리가 그 세션 값을 감당해야 합니다.
- 백업 7일은 추천 로그(`recommendation_log`)의 사후 평가 창보다 짧을 수 있습니다. 평가에 쓰는 로그는 DB 백업이 아니라 별도 내보내기로 보존한다고 전제합니다.

**적용하실 때 부탁드릴 것.**

- 초기화 SQL 은 `deploy/init/00~05` 순서대로 **마스터 사용자**로 실행해 주십시오. 확장 생성(`01_extensions.sql`)은 RDS 에서 마스터 권한이 필요합니다. 데이터베이스 `recodb` 는 초기화 SQL 이 만들지 않습니다(로컬은 compose 의 `POSTGRES_DB` 가 만듭니다) — `01` 을 돌리기 전에 그 이름으로 만들어 주십시오.
- `01_extensions.sql` 의 `ALTER DATABASE recodb SET timezone = 'Asia/Seoul'` 이 반드시 적용돼야 합니다. RDS 기본은 UTC 이고, 그러면 한국 자정~오전 9시 사이에 `current_date` 가 하루 전이 되어 소비기한 임박 판정이 하루씩 어긋납니다. 컨테이너의 `TZ` 로는 부족합니다.
- 역할은 셋입니다 — `reco_app`(앱, 읽기·쓰기) · `reco_batch`(배치, +TRUNCATE·DDL) · `reco_ro`(읽기 전용). `05_roles.sql` 의 비밀번호는 로컬 개발용이므로 원격에서는 다른 값으로 만들어 주십시오. 원격에서는 앱 컨테이너의 `DB_USER` 를 `reco_app` 으로 주는 것이 이 역할 분리의 뜻입니다. 로컬 compose 는 편의상 소유자 계정 `reco` 로 붙습니다.
- 인스턴스 크기와 `maintenance_work_mem` 값이 정해지면 알려 주십시오. 파트 A 가 HNSW 생성 시간을 그 값으로 다시 잽니다.

## 13. 추천의 실서빙과 모니터링 (2026-09-22 추가)

`main` 에 올라간 코드가 CI/CD 로 곧장 배포되므로, 배포 쪽에서 맞춰 주셔야 추천이 실제로 돕니다. 넷입니다.

| # | 무엇 | 안 하면 |
|---|---|---|
| 1 | 환경변수 `BACKEND_BASE_URL` 에 백엔드의 내부 주소를 넣습니다(`env_variables.md` 3.4) | 추천이 **목업 데이터로 답합니다.** 상태코드는 200 이고 레시피 번호는 백엔드 DB 에 없는 번호입니다 |
| 2 | AI 서버에서 백엔드의 포트로 나가는 길(보안 그룹)을 엽니다 | 레시피 사전을 받지 못해 추천이 전부 **503** 입니다. 백엔드가 자기 인기순으로 대신하므로 화면은 멀쩡해 보입니다 |
| 3 | 지속 볼륨을 `/app/var` 에 붙입니다. 컨테이너 사용자(uid 10001)가 쓸 수 있어야 합니다. 그 아래에 취향 원본(`profiles/`)과 추천 · 이벤트 로그(`reco_logs/`, 추천 한 건에 약 19KB — 하루 1만 건이면 약 190MB, 지우는 장치 없음)가 놓입니다. 다른 경로에 붙이시면 `PROFILE_STORE_DIR` · `RECO_LOG_DIR` 로 알려 줍니다 | 배포할 때마다 전원의 취향과 추천 로그가 사라집니다. 에러는 나지 않습니다. 이미지는 `/app/var` 를 앱 사용자 소유로 만들어 두므로(2026-09-22, **이 변경 뒤로 이미지를 다시 지어 보지는 못했습니다**) 볼륨이 없어도 죽지는 않습니다 |
| 4 | `/metrics` 와 `/admin/monitoring` 이 내부망에서만 닿게 합니다 | `/metrics` 는 내부 키를 요구하지만 관리자 페이지의 껍데기는 열려 있습니다 |

기동 순서는 상관없습니다. AI 서버가 먼저 떠도 되고, 백엔드가 늦게 뜨면 60초마다 다시 시도합니다. 레시피 2만 건을 받아 사전을 만드는 데 개발 PC 에서 2~8초 걸렸고(2026-09-22, 백엔드는 대역) 그동안 추천은 503 입니다. `/health/live` 와 `/health/ready` 는 사전과 무관합니다 — 영수증 기능이 사전 때문에 막히지 않게 했습니다.

**uvicorn 워커는 하나로 둡니다.** 지표의 등록부와 레시피 사전이 프로세스마다 따로라, 워커를 늘리면 지표가 널뛰고 메모리도 사전의 수만큼 듭니다. 늘려야 하면 먼저 알려 주십시오.

상태는 세 곳에서 봅니다.

```bash
curl -H "X-Internal-Api-Key: $INTERNAL_API_KEY" http://<AI 서버>/metrics | grep reco_catalog
#   reco_serving_live 1            실서빙이면 1, 목업이면 0
#   reco_catalog_ready 1           사전을 받았으면 1. 0 이면 추천이 전부 503
#   reco_catalog_recipes 21491     사전에 실린 레시피 수
#   reco_catalog_age_seconds ...   마지막 동기화로부터 지난 시간. 이틀을 넘으면 동기화가 멈춘 것
```

관리자 페이지(`/admin/monitoring`)가 같은 것을 "지금 할 일" 로 보여 줍니다. 서버 로그에는 `catalog synced ...` · `catalog sync failed: ...`(백엔드에 닿지 못했거나 응답이 계약과 다름) · `catalog sync crashed`(예상하지 못한 실패, 60초 뒤 다시 시도)가 남고, 기동할 때 `recommend=live` 또는 `recommend=mock` 한 줄이 찍힙니다. `/health` 의 `model_version` 으로도 실서빙인지 보입니다(6절). 수집은 자체 도구를 쓰셔도 되고(`/metrics` 는 Prometheus 표준 형식입니다) 저장소의 `deploy/prometheus/` 를 그대로 올리셔도 됩니다(`recommend/recommend_monitoring.md`).

# 추천 엔진과 백엔드의 API 계약

**정하는 것**: 추천 AI 서버가 백엔드에서 받아야 하는 데이터와 돌려주는 결과, 그 네 개 엔드포인트의 요청·응답 모양, 그리고 각 항목이 없을 때 추천이 어떻게 달라지는가

**적용 대상**: 백엔드 개발자와 추천 엔진(파트 B). 2026-09-21 백엔드 덤프로 엔진을 실제로 돌려 본 결과를 근거로 씁니다

**버전**: 1.1.0 · **최종 수정**: 2026-09-21 · **작성자**: 유재현

---

## 1. 전제와 읽는 법

추천 서버는 **백엔드 DB 에 직접 붙지 않습니다.** 필요한 것을 API 로 받습니다. 그래서 이 문서가 두 방향을 다 정합니다 — 우리가 백엔드에서 당겨 오는 것과, 백엔드가 우리를 부를 때 함께 보내야 하는 것입니다.

표의 "없으면" 칸이 가장 중요합니다. **빠진 항목은 에러를 내지 않고 그 신호만 조용히 꺼집니다.** 추천은 계속 200 으로 나가고 품질만 떨어지므로, 무엇이 꺼지는지 미리 적어 둡니다.

필드 이름은 2026-09-21 덤프(`pantry_recipe_domain_dump`)의 컬럼명을 그대로 씁니다. 이미 있는 이름을 바꾸자는 제안이 아닙니다.

---

## 2. 연동 구조 — 레시피는 동기화, 사용자는 요청에 동봉

실측으로 정했습니다. 레시피 21,491건을 엔진 모델로 바꾸면 **4.2MB** 입니다. 프로세스 메모리에 전량이 올라갑니다. 반대로 추천 한 번에 보는 후보는 500건이고, 그것을 매 요청 API 로 받으면 왕복마다 수백 KB 가 오갑니다. 점수 계산과 재정렬이 이미 500건에 57.9ms 를 쓰므로 그 위에 왕복을 얹으면 응답 목표가 위태롭습니다.

| 데이터 | 방식 | 주기 | 이유 |
|---|---|---|---|
| 레시피·재료 사전 | AI 가 당겨서 캐시 | 하루 1회 + 수동 호출 | 전량 4.2MB. 자주 안 바뀝니다 |
| 사용자 냉장고·취향 | 추천 요청에 동봉 | 요청마다 | 사용자마다 다르고 자주 바뀝니다 |
| 행동 이벤트 | 백엔드가 밀어 줌 | 발생 시 또는 배치 | 취향 학습의 원천입니다 |

당기는 쪽을 AI 로 둡니다. 재시도와 주기를 우리가 통제하고, 백엔드는 읽기 전용 엔드포인트 두 개만 열면 됩니다.

## 3. 백엔드가 열어 줄 것

### 3.1 레시피 동기화

```text
GET {BACKEND}/internal/ai/recipes?updated_after=2026-09-21T00:00:00Z&cursor=&limit=1000
인증: X-Internal-Api-Key (백엔드와 AI 가 같은 값을 씁니다)
```

```json
{
  "items": [
    {
      "recipe_id": 1,
      "title": "카레 맛있게 만드는 집밥레시피",
      "cuisine_type": "KOREAN",
      "cooking_time": 30,
      "servings": 4,
      "difficulty": "EASY",
      "thumbnail_url": "https://...",
      "is_published": true,
      "updated_at": "2026-08-31T01:09:30Z",
      "ingredients": [
        {"ingredient_id": 37, "name": "소고기", "is_main": true, "unit": "g"},
        {"ingredient_id": 24, "name": "감자", "is_main": true, "unit": "개"}
      ],
      "popularity": {"view_count": 0, "scrap_count": 0, "order_count": 0},
      "rating": {"average": null, "count": 0}
    }
  ],
  "next_cursor": "eyJpZCI6MTAwMH0=",
  "total": 21491
}
```

| 필드 | 필수 | 쓰는 곳 | 없으면 |
|---|---|---|---|
| `recipe_id` | 예 | 모든 곳의 키 | 동기화 자체가 불가 |
| `title` | 예 | 응답 표시, 맛 강도 추정 | 화면에 제목이 안 나갑니다 |
| `cuisine_type` | 예 | `f_cuisine`, 음식 유형 슬롯 | 온보딩의 "좋아하는 음식 유형" 이 목록에 닿지 않습니다 |
| `cooking_time` | 예 | 조리시간 상한 필터, `f_time_fit` | "30분 안에" 요청을 거를 수 없습니다 |
| `difficulty` | 아니요 | `f_skill_fit` | 그 신호만 꺼집니다. 지금 94.5%가 EASY 라 변별력은 낮습니다 |
| `is_published` | 예 | 후보에서 제외 | 미공개 레시피가 추천에 섞입니다 |
| `ingredients[].ingredient_id` | 예 | 재료 매칭 전부 | 추천이 동작하지 않습니다 |
| `ingredients[].is_main` | 예 | 필수 재료 판정, 부족 재료 계산 | 전 재료를 필수로 보게 되어 만들 수 있는 레시피가 거의 없어집니다 |
| `ingredients[].unit` | 아니요 | 맛 강도 추정(5절) | 맛 추정이 거칠어집니다. 단위 종류만 보고 수량은 안 봅니다 |
| `popularity.*` | **요청** | `f_popularity` (가중치 0.10) | 지금 상태입니다. 인기 신호가 통째로 꺼집니다 |
| `rating.*` | **요청** | `f_quality` | 품질 신호가 꺼집니다 |
| `updated_at` | 예 | 증분 동기화 | 매번 전량을 받아야 합니다 |

`ingredients` 배열의 순서는 **레시피에 적힌 순서 그대로** 주십시오. 한국 레시피는 주재료를 앞에 적는 관행이 있어 맛 추정이 그 순서를 신호로 씁니다.

### 3.2 재료 사전 동기화

```text
GET {BACKEND}/internal/ai/ingredients
```

```json
{
  "items": [
    {
      "ingredient_id": 1,
      "name": "마늘",
      "category": "채소류",
      "default_storage_type": "REFRIGERATED",
      "default_shelf_life_days": 30,
      "extended_consumption_days": 30,
      "is_staple": false,
      "allergens": []
    }
  ]
}
```

| 필드 | 필수 | 쓰는 곳 | 없으면 |
|---|---|---|---|
| `ingredient_id` · `name` | 예 | 매칭의 키, 부족 재료 문구 | 이름 없이 번호만 화면에 나갑니다 |
| `category` | 아니요 | 맛 추정의 기본값 | 그 재료가 맛에 기여하지 않는 것으로 처리됩니다 |
| `default_shelf_life_days` | 예 | 소비기한 추정 | 사용자가 날짜를 직접 넣지 않으면 임박 판정을 못 합니다 |
| `extended_consumption_days` | 아니요 | 소비기한 경과 후 표시 | 유통기한과 소비기한을 구분하지 못합니다 |
| `is_staple` | **요청** | 상비 재료 자동 포함 | 지금은 우리 사전으로 대신합니다(148종 중 23종 — 간장·설탕·소금·식용유 등). 빈도로 짐작하면 마늘·양파·대파가 상비로 들어가 없는 재료를 있다고 치게 됩니다 |
| `allergens` | **요청** | 알레르기 하드컷 | 5.3 을 보십시오. 지금은 우리 사전으로 대신합니다. **배열이어야 합니다** — 간장은 대두이면서 밀입니다 |

## 4. AI 가 열어 줄 것

### 4.1 추천 요청

```text
POST {AI}/v1/recommend
인증: X-Internal-Api-Key
```

```json
{
  "user_id": 1024,
  "top_k": 20,
  "max_minutes": 30,
  "session_id": "c-8f3a...",
  "pantry": [
    {"ingredient_id": 37, "quantity": 300, "unit": "g",
     "purchased_at": "2026-09-18", "expires_at": "2026-09-23"},
    {"ingredient_id": 5, "purchased_at": "2026-09-20"}
  ],
  "preference": {
    "taste_scales": {"spicy": 3, "salty": 2, "sweet": 1},
    "onboarding_picks": [0, 3, 9],
    "preferred_cuisines": ["KOREAN", "JAPANESE"],
    "allergies": ["우유", "땅콩"],
    "avoid_ingredient_ids": [19]
  }
}
```

| 필드 | 필수 | 쓰는 곳 | 없으면 |
|---|---|---|---|
| `user_id` | 예 | 로그와 취향 저장의 키 | 요청 거부 |
| `pantry[].ingredient_id` | 예 | 재료 매칭 | 냉장고가 빈 것으로 보고 인기순으로 냅니다 |
| `pantry[].expires_at` | 아니요 | 임박 재료 가산(가중치 0.15) | `purchased_at` 과 재료 사전의 소비기한으로 추정합니다. 둘 다 없으면 임박 신호가 꺼집니다 |
| `pantry[].purchased_at` | 아니요 | 소비기한 추정의 기준점 | 같습니다 |
| `preference.onboarding_picks` | 아니요 | 취향 6축의 원천 | 맛 신호(0.16)가 꺼지고 새로운 시도 칸이 20%에서 40%로 늘어납니다 |
| `preference.taste_scales` | 아니요 | 고른 음식이 없을 때의 대체 | 같습니다 |
| `preference.preferred_cuisines` | 아니요 | 음식 유형 슬롯 | 그 칸이 생기지 않습니다 |
| `preference.allergies` | 아니요 | 하드컷 | **알레르기 재료가 추천에 섞입니다.** 빈 배열과 생략은 같은 뜻으로 봅니다. 백엔드 DB 의 값을 **한글 라벨 그대로** 주시면 됩니다(`["우유", "땅콩"]`). 받는 라벨과 모르는 라벨의 처리는 5.3 에 있습니다 |
| `max_minutes` | 아니요 | 조리시간 상한 | 상한 없이 추천합니다 |
| `session_id` | 아니요 | 로그 분석 | 세션 단위 분석을 못 합니다. 접두어는 `c-` 실사용자 · `g-` 게스트 · `d-` 개발입니다 |

`pantry` 에 상비 재료(소금·간장 같은 것)를 넣지 않아도 됩니다. 추천 서버가 자동으로 더합니다. 다만 **사용자가 직접 넣은 것만 `pantry` 에 담아 주십시오** — 그 구분으로 "냉장고가 사실상 비었는가" 를 판정하고, 비었으면 재료 매칭을 건너뛰고 인기순으로 냅니다.

### 4.2 추천 응답

```json
{
  "contract_version": "v1",
  "request_id": "0d5f...",
  "user_id": 1024,
  "model_version": "reco-v0",
  "served_at": "2026-09-21T19:00:00+09:00",
  "items": [
    {
      "recipe_id": 8821,
      "final_rank": 1,
      "title": "백종원 순두부찌개 그대로 따라만 하세요",
      "thumbnail_url": "https://...",
      "cuisine_type": "KOREAN",
      "cooking_time": 20,
      "coverage": 1.0,
      "missing_ingredients": [],
      "used_pantry_ingredient_ids": [37, 5, 6, 36, 41, 11],
      "reason": "두부(D-3)를 소진할 수 있고, 냉장고 재료를 11가지나 써요"
    }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `request_id` | 이벤트를 보낼 때 이 값을 함께 주십시오. 노출과 반응을 잇는 유일한 열쇠입니다 |
| `final_rank` | 화면에 보이는 순서. 1부터입니다 |
| `coverage` | 필수 재료 충족률 0~1 |
| `missing_ingredients` | `[{ingredient_id, name}]`. 장보기로 잇는 자리입니다 |
| `used_pantry_ingredient_ids` | 이 레시피가 쓰는 사용자 냉장고 재료 |
| `reason` | 한국어 한 문장. 서버가 만듭니다 |

응답에 **넣지 않는 것**이 있습니다. 피처 17종, `score`, 노출 확률, 새로운 시도 칸 표시, 추적 정보는 로그로만 남깁니다. 특히 새로운 시도 칸 표시가 응답에 있으면 클라이언트가 그 칸을 걸러 낼 수 있고, 그러면 탐색 효과를 영영 측정하지 못합니다. 디버깅이 필요하면 `include_trace: true` 로 요청하십시오. 내부 키가 있는 호출에만 허용합니다.

### 4.3 행동 이벤트

```text
POST {AI}/v1/events
```

```json
{"events": [
  {"user_id": 1024, "event_type": "cook", "recipe_id": 8821,
   "request_id": "0d5f...", "position": 1,
   "occurred_at": "2026-09-21T19:32:11+09:00"}
]}
```

`event_type` 은 여덟 가지입니다 — `impression` · `click` · `save` · `unsave` · `cook` · `rating` · `dismiss` · `search`. 소문자이며 **뜻을 바꾸거나 지울 수 없습니다.** 과거 로그가 그 뜻으로 쌓이기 때문입니다. `occurred_at` 은 선택이고 시간대가 반드시 있어야 합니다. 없으면 서버가 받은 시각을 씁니다. **오프라인에서 모아 두었다가 한 번에 보내는 경우에는 반드시 실어 주십시오.** 200건이 같은 시각을 받으면 시간 감쇠와 요일·시간대 주기가 뭉개집니다.

### 4.4 온보딩 저장

```text
POST {AI}/v1/onboarding
```

고른 음식 번호, 3축 척도, 알레르기 그룹, 좋아하는 음식 유형을 받아 취향 6축을 계산해 돌려줍니다. 계약은 `src/features/recommend/schema.py` 의 `OnboardingIn` · `OnboardingOut` 입니다.

## 5. 지금 없어서 못 하는 것

2026-09-21 덤프로 엔진을 끝까지 돌려 확인한 것입니다. 없는 것을 억지로 0 으로 채우지 않았습니다.

### 5.1 인기도와 품질 — 백엔드가 주셔야 합니다

레시피 순위 가중치 가운데 인기도가 0.10 입니다. 덤프에 조회수·스크랩·주문·평점이 하나도 없어 이 신호가 완전히 꺼져 있습니다. `recipe_scraps` 는 0건이었습니다.

셋 중 하나라도 주시면 켜집니다. 조회수가 가장 구하기 쉽고, 스크랩 수가 가장 정확하며, 주문 수가 가장 사업에 가깝습니다. 원값 그대로 주시면 되고 정규화는 우리가 합니다. 꼬리가 극단적이라 백분위 순위로 바꿔 씁니다.

### 5.2 맛 — 우리가 만듭니다

덤프에 맛 정보가 없습니다. 그런데 맛은 재료에서 나오므로 우리가 복원할 수 있고, 실제로 복원해 확인했습니다. 백엔드 재료 148종 가운데 147종이 우리 맛 사전에 붙고, 복원한 코퍼스 평균이 데이터 파트가 다른 코퍼스에서 잰 값과 0.023 안에서 일치했습니다.

그래서 백엔드에 맛 데이터를 요청하지 않습니다. 대신 3.1 의 `unit` 과 재료 순서를 주시면 추정이 정확해집니다.

### 5.3 알레르기 — 라벨은 백엔드가, 전개는 우리가 합니다

사용자의 알레르기는 백엔드 DB 에 있고 `["우유", "땅콩"]` 처럼 한글 라벨로 받습니다. 추천 서버가 그 라벨을 **막을 재료 집합**으로 풉니다(`src/features/recommend/engine/allergy.py`).

| 받는 라벨 | 막는 범위 (2026-09-21 재료 148종 기준) |
|---|---|
| 알류 · 난류 · 달걀 · 계란 | 달걀 · 마요네즈 · 메추리알 |
| 우유 · 유제품 | 우유 · 버터 · 생크림 · 연유 · 요거트 · 치즈 4종 · 초콜릿 |
| 땅콩 · 호두 · 잣 · 아몬드 · 견과류 | 견과 4종 전부 |
| 대두 · 콩 | 간장 · 고추장 · 된장 · 두부 · 콩나물 |
| 밀 · 글루텐 | 밀가루 · 식빵 · 면류 · 부침가루 · 튀김가루 · 빵가루 · 만두 · 또띠아 등 10종 |
| 참깨 · 깨 · 들깨 | 통깨 · 참기름 · 들기름 · 들깨가루 |
| 고등어 · 생선 · 어류 | 고등어 · 멸치 · 참치 · 어묵 · 액젓 · 맛살 · 북어 · 명란젓 · 참치액 |
| 새우 · 게 · 갑각류 · 조개류 · 굴 · 오징어 | 새우 · 건새우 · 새우젓 · 바지락 · 굴 · 굴소스 · 오징어 · 진미채 · 김치 |
| 해산물 | 위 두 줄을 합친 18종 |
| 돼지고기 · 쇠고기 · 닭고기 · 토마토 | 그 고기와 가공품(베이컨·햄·소시지·스팸), 토마토·케첩·토마토소스 |
| 메밀 · 복숭아 | 지금 재료 사전에 해당 재료가 없습니다 |

**넓게 막습니다.** "땅콩" 을 고르면 호두까지, "새우" 를 고르면 조개류와 김치(젓갈)까지 막습니다. 덜 막아서 생기는 일과 더 막아서 생기는 일의 무게가 다르기 때문입니다. 영문 군 코드(`dairy` 등)도 같은 자리에서 받습니다.

**모르는 라벨은 버리지 않습니다.** 위 표에 없는 라벨(예: `아황산류`)이 오면 아는 것은 그대로 막고, 모르는 라벨을 추적 로그와 카운터에 남깁니다. 조용히 버리면 그 사용자는 보호받지 못하는데 응답은 200 이기 때문입니다. **백엔드가 쓰는 라벨 목록을 한 번 보내 주십시오.** 표에 없는 것을 미리 더해 두겠습니다.

**재료 목록만 믿지 않습니다.** 6.3 의 이유로 제목도 함께 봅니다. 제목에 막힌 재료의 이름이나 그 다른 말(계란 · 에그 · 쉬림프 · 피넛 · 크림 · 제육 등)이 있으면 재료 행에 없어도 막습니다.

**못 막는 것이 있습니다.** 가공품 안의 다른 알레르기입니다. 간장은 대두이면서 밀이고 굴소스에는 대두가 들어가지만, 우리 사전은 재료마다 알레르기를 하나만 달고 있습니다. 밀 알레르기 사용자에게 간장이 든 레시피가 나갑니다. 이것을 닫으려면 재료 사전에 `allergens` 배열(3.2)이 있어야 하고, 그 정본은 백엔드에 두는 편이 안전합니다.

### 5.4 사용자 이력 — 선행 조건이 있습니다

선호 재료와 재료 궁합이 가중치 0.21 을 차지하는데, 둘 다 사용자가 무엇을 만들어 먹었는지를 알아야 계산됩니다. 4.3 의 이벤트가 쌓이면 자동으로 켜집니다. 지금은 꺼져 있습니다.

## 6. 실데이터 검증에서 나온 것

덤프로 엔진을 돌려 확인한 사실입니다. 자세한 수치는 `docs/recommend/recommend_engine_verification.md` 21절에 있습니다.

### 6.1 재료 매칭만으로는 순위가 안 나옵니다

냉장고에 재료 일곱 가지를 넣고 돌리니 **후보 500건이 전부 충족률 1.0 이었고 점수가 전원 1.000 이었습니다.** 레시피가 21,491건이나 되어 "가진 재료로 만들 수 있는 것" 이 500건을 훌쩍 넘기 때문입니다. 그 결과 상위에 쌈장 만들기, 흙마늘 만들기 같은 손질법이 올라왔습니다. 필수 재료가 한두 개뿐이라 충족률이 쉽게 1.0 이 되는 것들입니다.

이 문제는 인기도(5.1)와 맛(5.2)이 켜지면 상당 부분 풀립니다. 맛을 복원해 다시 돌리니 점수가 0.72에서 0.86 사이로 퍼지고 상위가 순두부찌개, 두부김치처럼 실제 요리로 바뀌었습니다.

### 6.2 비슷한 레시피가 너무 많습니다

제목이 완전히 같은 레시피가 782건, 재료 구성이 완전히 같은 묶음이 1,005개(2,856건)입니다. 필수 재료가 같은 묶음은 2,285개이고 가장 큰 묶음에는 115건이 들어 있습니다.

추천 목록 스무 칸에 두부조림 변형이 네 개 들어가는 일이 실제로 생겼습니다. 저희 쪽 재정렬에서 막을 수 있는지 보고 있는데, 백엔드에서 중복을 정리할 계획이 있으면 알려 주십시오. 같은 레시피의 다른 판본을 묶는 대표 번호가 있으면 가장 깔끔합니다.

### 6.3 재료 행이 빠진 레시피가 있습니다

**제목에는 있는데 재료 목록에는 없는** 경우입니다. 새우 알레르기를 넣고 돌렸더니 1위가 「고추장 건새우볶음」 이었습니다. 그 레시피(`recipe_id` 1194)의 `recipe_ingredients` 에는 다진마늘·고춧가루·고추장·참기름 등 아홉 줄이 있고 **건새우가 없습니다.**

| 제목에 이 말이 있는 레시피 | 그중 재료 행에 그 재료가 없는 것 |
|---|---|
| 새우 618건 | 17건 (2.8%) |
| 오징어 669건 | 52건 (7.8%) |
| 땅콩 31건 | 4건 (12.9%) |
| 우유·치즈·버터·크림 1,179건 | 46건 (3.9%) |
| 달걀·계란 1,446건 | 22건 (1.5%) |

재료 사전 148종에 닿지 못한 재료가 정규화 과정에서 떨어진 것으로 보입니다. 추천 품질에도 나쁘지만 **알레르기 하드컷에 구멍이 납니다.** 저희는 제목을 함께 보는 것으로 막았습니다(5.3). 다만 제목에도 재료가 안 적힌 레시피는 여전히 못 잡습니다. 떨어진 재료를 복구할 수 있는지 봐 주십시오.

### 6.4 음식 유형이 한식에 쏠려 있습니다

한식 18,890 · 양식 2,071 · 중식 326 · 일식 204 입니다. 일식이나 중식을 고른 사용자는 선택지가 매우 적어 유형 칸이 자주 비게 됩니다. 데이터의 성질이므로 요청은 아니고, 그렇게 동작한다는 것만 적어 둡니다.

## 7. 규약

| 항목 | 값 |
|---|---|
| 인증 | 모든 경로가 `X-Internal-Api-Key` 헤더를 요구합니다. 양쪽이 같은 값을 씁니다 |
| 시간대 | 모든 시각은 시간대를 포함합니다. 시간대 없는 값은 거부합니다 |
| 식별자 정본 | `ingredient_id` 와 `recipe_id` 는 백엔드 값이 정본입니다 |
| 오류 | `{"error": "...", "detail": "...", "request_id": "..."}` |
| 타임아웃 | 추천 요청은 3초를 넘기지 않습니다. 동기화는 30초까지 기다립니다 |
| 페이지 | 동기화는 커서 방식입니다. `limit` 기본 1,000, 최대 5,000 |
| 버전 | 응답의 `contract_version` 이 계약 판입니다(지금 `v1`). 필드를 빼거나 뜻을 바꿀 때만 올립니다 |

추천 서버에 새로 생기는 설정은 백엔드 주소와 내부 키 둘입니다. 이름과 기본값은 `docs/env_variables.md` 에 함께 적습니다.

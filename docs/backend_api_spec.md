# 추천 AI 서버와 백엔드의 API 명세

**정하는 것**: 추천 AI 서버와 백엔드가 주고받는 API 전부 — 백엔드가 열어 줄 두 개와 AI 서버가 여는 여섯 개의 요청·응답 모양, 필드마다 없을 때 생기는 일, 알레르기 라벨의 처리, 공통 규약, 그리고 각 항목이 지금 코드에 있는지 합의 뒤에 만드는지

**적용 대상**: 백엔드 개발자. 추천 엔진(파트 B)과 데이터 파트(A)는 계약의 정본으로 봅니다

**버전**: 2.4.0 · **최종 수정**: 2026-09-22 · **작성자**: 유재현

---

## 1. 전제

**AI 서버는 백엔드 DB 에 직접 붙지 않습니다.** 운영에서 쓰는 모든 실데이터는 이 문서의 API 로만 오갑니다.

2026-09-21 에 받은 덤프(레시피 21,491건 · 재료 148종)는 **테스트용 표본**입니다. 엔진을 실제 모양의 데이터로 돌려 보려고 받은 것이고 운영 데이터가 아닙니다. 이 문서에 나오는 건수와 비율은 전부 그 표본에서 잰 것이며, 설계를 정한 근거로만 씁니다. 필드 이름은 그 덤프의 컬럼명을 그대로 따랐습니다. 이미 있는 이름을 바꾸자는 제안이 아닙니다.

읽는 법 두 가지입니다.

- 표의 **"없으면"** 칸이 가장 중요합니다. 빠진 값은 에러를 내지 않고 그 신호만 조용히 꺼집니다. 추천은 계속 200 으로 나가고 품질만 떨어지므로, 무엇이 꺼지는지 미리 적어 둡니다.
- **구현 상태**를 항목마다 적었습니다. `있음` 은 지금 코드에 있는 것이고 `합의 후` 는 이 명세에 동의해 주시면 만드는 것입니다. AI 서버는 **모르는 필드가 오면 요청 전체를 400 으로 거부**합니다. 어느 필드였는지는 400 의 본문에 실립니다(6.1).
- 2026-09-21 에 백엔드가 주신 회신을 반영했습니다. 회신과 반영 결과는 8절에 모았습니다.
- **2.4.0(2026-09-22)은 새 합의가 아닙니다. 문서를 지금 코드에 맞춘 판입니다.** AI 서버의 실서빙을 만든 뒤 문서 전체를 코드와 대조해 어긋난 곳을 고쳤습니다. 백엔드가 보실 곳은 넷입니다 — 재료를 **이름으로** AI 쪽 사전에 잇는다는 것(3.1), 추천이 503 일 수 있다는 것(4.4 · 6절), 이벤트 응답의 `rejected` 가 뜻하는 것(4.5), 냉장고를 미리 밀어 두는 경로는 실서빙에서 쓰이지 않는다는 것(4.4 · 8절).

## 2. 누가 무엇의 주인인가

| 데이터 | 주인 | AI 서버가 받는 방법 |
|---|---|---|
| 레시피 · 재료 사전 | 백엔드 | AI 가 하루 한 번 당겨 가 메모리에 둡니다 (3절) |
| 사용자의 냉장고 · 알레르기 | 백엔드 | **추천 요청마다 동봉**합니다 (4.4) |
| 온보딩 응답 — 고른 음식 · 맛 척도 · 좋아하는 음식 유형 | 백엔드가 받아 AI 에 전달 | `POST /v1/onboarding/{user_id}` (4.3) |
| 취향 벡터 · 추천 로그 · 행동 이벤트 | AI | AI 가 저장합니다. 지금은 AI 서버의 파일입니다(취향 원본과 추천 로그). DB 로 옮기는 것은 AI 쪽의 일이고 이 계약은 바뀌지 않습니다 |
| 레시피의 파생값 — 맛 6축 · 재료 희소도 · 인기 점수 | AI | 받은 레시피에서 AI 가 계산합니다. 군집은 아직 계산하지 않습니다 |

나누는 기준은 하나입니다. **백엔드가 주인인 데이터는 AI 가 사본을 오래 들고 있지 않습니다.** 냉장고와 알레르기를 AI 쪽에 따로 저장하면 동기화가 한 번 실패했을 때 옛 냉장고로 추천이 나가는데 에러가 없습니다. 알레르기는 그 일이 생기면 안 되는 자리입니다. 그래서 요청마다 받습니다.

레시피는 반대입니다. 전량을 엔진 모델로 바꾸면 4.2MB 라 메모리에 다 올라가고, 추천 한 번이 후보 500건을 보므로 매번 API 로 받으면 왕복마다 수백 KB 가 오갑니다. 점수 계산과 재정렬이 후보 500건에 이미 48ms 를 쓰므로 그 위에 왕복을 얹지 않습니다.

```text
[기동 직후 · 그 뒤 24시간마다]
            AI ──── GET /internal/ai/ingredients ────▶ 백엔드
            AI ──── GET /internal/ai/recipes ─────────▶ 백엔드     AI 가 맛·희소도·인기를 계산해 메모리에

[가입 때]   백엔드 ─ GET  /v1/onboarding/presented ───▶ AI         화면에 그릴 음식 20개
            백엔드 ─ POST /v1/onboarding/{user_id} ───▶ AI         고른 음식 · 맛 척도 · 음식 유형

[추천 때]   백엔드 ─ POST /v1/recommend ──────────────▶ AI         냉장고 · 알레르기 동봉
            백엔드 ◀ recipe_id 목록 · 순위 · 이유 ───── AI         백엔드가 제목·썸네일을 붙여 화면에

[행동 때]   백엔드 ─ POST /v1/events ─────────────────▶ AI         조회 · 저장 · 조리 · 평점
```

## 3. 백엔드가 열어 주실 API

둘 다 **구현 상태: 신규**입니다. AI 서버가 호출하는 읽기 전용 엔드포인트입니다. 경로는 제안이고 편하신 대로 정해 주십시오.

**AI 서버 쪽 구현은 끝났습니다**(2026-09-22). 이 두 API 가 열리고 AI 서버에 백엔드의 주소가 설정되면 바로 받아 갑니다. 호출에는 `X-Internal-Api-Key` 헤더(양쪽이 같은 값)와 쿼리 `limit`, 그리고 둘째 쪽부터 `cursor` 가 붙습니다. **지금은 하루 한 번 전량을 받습니다.** `updated_after` 는 아직 보내지 않습니다 — 받아 주시되 없을 때 전량을 주시면 됩니다.

동기화는 **AI 서버가 뜬 직후 한 번, 그 뒤 24시간마다**입니다. 새벽으로 고정돼 있지 않고 수동 호출은 없습니다 — AI 서버를 다시 띄우면 그것이 곧 다시 받기입니다. 실패하면 60초 뒤에 다시 부르고, 그동안은 앞에 받은 것으로 서빙합니다. 한 번도 못 받았으면 추천이 503 입니다(6절). **매번 전량을 통째로 갈아 끼우므로** 응답에서 빠진 레시피는 다음 동기화부터 추천되지 않습니다.

깨진 항목(`recipe_id` 가 없는 레시피처럼 필수 값이 빠진 것)은 그 항목만 버리고 셉니다. **한 번의 동기화에서 5% 넘게 깨져 있으면 계약이 갈라진 것으로 보고 그 동기화를 통째로 버립니다** — 앞의 사전이 그대로 남습니다. 모르는 필드가 더 실려 오는 것은 괜찮습니다. AI 가 받는 요청과 달리 이쪽은 무시합니다.

**응답은 백엔드의 공통 응답 래퍼 없이 아래 구조 그대로입니다**(2026-09-21 백엔드 확인). AI 서버는 최상위의 `items` 를 바로 읽습니다. 래퍼가 씌워지면 `items` 를 찾지 못해 동기화가 실패합니다.

### 3.1 재료 사전

```text
GET {BACKEND}/internal/ai/ingredients
```

```json
{
  "items": [
    {
      "ingredient_id": 1,
      "name": "마늘",
      "category": "채소류",
      "default_storage_type": "REFRIGERATED",
      "default_shelf_life_days": 30,
      "extended_consumption_days": 30,
      "is_staple": false,
      "allergens": []
    }
  ]
}
```

| 필드 | 필수 | 쓰는 곳 | 없으면 |
|---|---|---|---|
| `ingredient_id` · `name` | 예 | 매칭의 키, 부족 재료 문구, 알레르기 전개 | 추천이 동작하지 않습니다 |
| `category` | 아니요 | **지금은 읽지 않습니다** | 영향 없습니다. 맛은 아래의 이름 잇기로 정합니다 |
| `default_shelf_life_days` | 예 | 소비기한 추정 | 사용자가 날짜를 직접 넣지 않으면 임박 판정을 못 합니다 |
| `extended_consumption_days` | 아니요 | **지금은 읽지 않습니다** | 영향 없습니다 |
| `is_staple` | **요청** | 상비 재료 자동 포함 | 지금은 AI 쪽 사전으로 대신합니다(148종 중 23종 — 간장·설탕·소금·식용유 등). 빈도로 짐작하면 마늘·양파·대파가 상비로 들어가 없는 재료를 있다고 치게 됩니다 |
| `allergens` | **요청** | 알레르기 하드컷 | 지금은 AI 쪽 사전으로 대신합니다(5절). **배열이어야 합니다** — 간장은 대두이면서 밀입니다 |

**재료는 `name` 으로 AI 쪽 재료 사전에 잇습니다.** 맛 6축, 양념 여부, 그리고 `is_staple` · `allergens` 를 안 주신 동안의 상비 여부와 알레르기 군이 전부 그 사전에서 옵니다. 표본의 148종은 전부 이어졌습니다. 그래서 **재료를 새로 추가하시거나 이름을 바꾸시면** 그 재료는 AI 쪽에서 맛이 0 이고 알레르기 군을 모르는 재료가 됩니다. 에러는 나지 않고 AI 서버의 로그와 지표(`catalog_unmapped_ingredients`)에만 남습니다. 알레르기와 닿는 재료라면 그 재료가 든 레시피가 하드컷을 지나갑니다(제목에 그 말이 없을 때). 그 재료에 `allergens` 를 실어 주시면 이름이 안 이어져도 알레르기는 막힙니다. 새 재료를 넣으실 때 알려 주시면 사전에 더하겠습니다.

### 3.2 레시피

```text
GET {BACKEND}/internal/ai/recipes?limit=1000                    첫 쪽
GET {BACKEND}/internal/ai/recipes?limit=1000&cursor=<next_cursor>   둘째 쪽부터. next_cursor 가 null 이거나 없으면 끝
```

```json
{
  "items": [
    {
      "recipe_id": 1,
      "title": "카레 맛있게 만드는 집밥레시피",
      "cuisine_type": "KOREAN",
      "cooking_time": 30,
      "servings": 4,
      "difficulty": "EASY",
      "is_published": true,
      "updated_at": "2026-08-31T01:09:30Z",
      "ingredients": [
        {"ingredient_id": 37, "name": "소고기", "is_main": true, "unit": "g"},
        {"ingredient_id": 24, "name": "감자", "is_main": true, "unit": "개"}
      ],
      "popularity": {"view_count": 0, "scrap_count": 0, "order_count": 0},
      "rating": {"average": null, "count": 0}
    }
  ],
  "next_cursor": "eyJpZCI6MTAwMH0=",
  "total": 21491
}
```

| 필드 | 필수 | 쓰는 곳 | 없으면 |
|---|---|---|---|
| `recipe_id` | 예 | 모든 곳의 키 | 동기화가 안 됩니다 |
| `title` | 예 | 맛 강도 추정, **알레르기 2차 방어선**(5.4) | 재료 행이 빠진 레시피를 못 걸러 냅니다 |
| `cuisine_type` | 예 | 음식 유형 신호와 유형 칸 | 온보딩의 "좋아하는 음식 유형" 이 목록에 닿지 않습니다 |
| `cooking_time` | 예 | 조리시간 상한 필터 | "30분 안에" 요청을 거를 수 없습니다 |
| `difficulty` | 아니요 | 난이도 신호 | 그 신호만 꺼집니다. 표본에서 94.5%가 `EASY` 라 변별력은 낮습니다 |
| `is_published` | 예 | 후보에서 제외 | 미공개 레시피가 추천에 섞입니다 |
| `ingredients[].ingredient_id` | 예 | 재료 매칭 전부 | 추천이 동작하지 않습니다 |
| `ingredients[].is_main` | 예 | 필수 재료 판정, 부족 재료 계산 | 전 재료를 필수로 보게 되어 만들 수 있는 레시피가 거의 없어집니다 |
| `ingredients[].unit` | 아니요 | 맛 강도 추정 | 추정이 거칠어집니다. 단위 종류만 보고 수량은 안 봅니다 |
| `popularity.scrap_count` | **합의** | 인기 신호 (순위 가중치 0.10) | 인기 신호가 통째로 꺼지고, **신규 사용자의 첫 화면이 사실상 임의**가 됩니다(7.1). 백엔드가 즉시 제공할 수 있다고 회신했습니다 |
| `popularity.view_count` | 아니요 | 인기 신호의 보강 | 스크랩 수만으로 계산합니다. 백엔드가 레시피 테이블에 컬럼을 추가해 보겠다고 회신했습니다. 생기면 실어 주십시오 |
| `popularity.order_count` | 아니요 | 인기 신호의 보강 | 위와 같습니다 |
| `rating.*` | **요청** | 품질 신호 | 품질 신호가 꺼집니다 |
| `updated_at` | 아니요 | **지금은 읽지 않습니다**(증분 동기화를 시작하면 씁니다) | 영향 없습니다. 매번 전량을 받습니다 |
| `servings` · `total` · `ingredients[].name` | 아니요 | 읽지 않습니다. `ingredients[].name` 만 재료 사전에 그 번호가 없을 때의 대신 이름으로 씁니다 | 영향 없습니다 |

세 가지를 부탁드립니다.

- `ingredients` 배열은 **레시피에 적힌 순서 그대로** 주십시오. 한국 레시피는 주재료를 앞에 적는 관행이 있어 맛 추정이 그 순서를 신호로 씁니다.
- 비공개이거나 지워진 레시피는 **빼고 주셔도 되고 `is_published: false` 로 주셔도 됩니다.** 지금은 매번 전량을 갈아 끼우므로 둘 다 추천에서 빠집니다. 나중에 증분(`updated_after`)을 쓰게 되면 그때는 `is_published: false` 로 **실어 주셔야** 합니다 — 안 실리면 지워진 레시피가 AI 의 메모리에 남아 계속 추천됩니다. 증분을 시작하기 전에 다시 말씀드리겠습니다.
- 제목·썸네일·조리 단계는 AI 가 화면용으로 돌려드리지 않습니다(4.4). 추천 응답의 `recipe_id` 로 백엔드 DB 에서 붙여 주십시오.
- **필수 재료(`is_main: true`)가 하나도 없는 레시피는 추천하지 않습니다.** 부족한 재료를 셀 수 없어 어느 냉장고에서나 "다 갖춤" 이 되기 때문입니다. 양념장 만드는 법 같은 레시피가 여기 해당합니다.
- 커서가 끝나지 않는 경우를 대비해 **같은 커서가 두 번 오면 거기서 멈추고**, 2,000쪽을 넘기지 않습니다.

## 4. AI 서버가 여는 API

전부 `X-Internal-Api-Key` 헤더가 필요합니다. 예외는 4.6 의 `live` · `ready` 둘입니다.

### 4.1 온보딩 제시 목록

**구현 상태: 있음.** 온보딩 화면에 보여 줄 음식 스무 개입니다.

```text
GET {AI}/v1/onboarding/presented
```

```json
{
  "list_version": 2,
  "items": [
    {"name": "오징어볶음", "family": "korean"},
    {"name": "불고기", "family": "korean"}
  ]
}
```

**이 목록을 복사해 두지 마십시오.** 목록은 바뀝니다. 화면을 그리기 직전에 받고, 사용자가 고른 것을 `name` 으로 돌려보내 주십시오. 번호(자리)로 보내면 목록이 바뀐 날부터 같은 번호가 다른 음식을 가리키는데 에러가 나지 않습니다.

### 4.2 맛 척도의 이름과 범위

**구현 상태: 있음.**

```text
GET {AI}/v1/onboarding/taste-axes
```

```json
{
  "axes": [
    {"key": "spicy", "label": "매움"},
    {"key": "salty", "label": "짠맛"},
    {"key": "sweet", "label": "단맛"}
  ],
  "min": 1,
  "max": 5
}
```

**구현 상태: 있음.** 온보딩 응답을 받아 취향을 계산하고 저장합니다.


```json
{
  "picks": ["오징어볶음", "불고기", "계란말이"],
  "taste_preferences": {"spicy": 4, "salty": 3, "sweet": 2},
  "preferred_cuisines": ["한식", "일식"],
```

```json
{
  "user_id": 1024,
  "taste": {"spicy": 0.75, "salty": 0.5, "sweet": 0.25},

  "unmapped_allergens": ["아황산류"],
```

| 필드 | 필수 | 뜻 | 없으면 · 틀리면 |
|---|---|---|---|
| `picks` | 예 (1~20개) | 4.1 에서 받은 `name` | 목록에 없는 이름이면 **요청을 거부**합니다. 가까운 음식으로 짐작하면 고르지 않은 것이 취향이 됩니다 |
| `taste_preferences` | 아니요 | 4.2 의 `key` 세 개, 각 1~5 | 고른 음식만으로 취향을 만듭니다. **배열로 보내지 마십시오** — 순서가 어긋나도 숫자 세 개는 통과합니다 |
| `preferred_cuisines` | 아니요 (최대 5) | 백엔드가 저장하는 코드 `KOREAN` · `CHINESE` · `JAPANESE` · `WESTERN` · `ETC` 를 **대소문자 무관하게** 받습니다. **`ETC` 는 아시안으로 읽습니다**(2026-09-21 백엔드 요청). 한글 라벨 `한식` · `중식` · `일식` · `양식` · `아시안` 과 AI 쪽 코드 `asian_other` 도 받습니다 | 모르는 값이면 **요청을 거부**합니다 |
| `allergy_groups` | 아니요 | 5절의 라벨 | 모르는 라벨은 거부하지 않고 `unmapped_allergens` 로 돌려드립니다 |
| `household_size` | 아니요 | 1~10 | 지금은 받기만 하고 쓰지 않습니다 |

응답의 `unmapped_allergens` 가 비어 있지 않으면 **그만큼 차단되지 않은 것**입니다. 사용자에게 알리거나 저희에게 그 라벨을 알려 주십시오.

**AI 는 온보딩의 알레르기를 저장하지 않습니다.** 여기서는 그 라벨이 읽히는지(`unmapped_allergens`)와 몇 가지 재료를 막게 되는지(`n_blocked_ingredients`)만 답해 드립니다. 추천은 **4.4 의 요청에 실린 `allergies` 만** 봅니다. 온보딩에 보냈으니 막히리라고 기대하시면 안 됩니다. `n_blocked_ingredients` 는 AI 가 재료 사전을 아직 못 받았으면 0 입니다.

### 4.4 추천

```text
POST {AI}/v1/recommend
```

```json
{
  "user_id": 1024,
  "session_id": "c-1024-8f3a2b1c9d0e",
  "top_k": 20,
  "max_minutes": 30,
  "include_trace": false,
  "pantry": [
    {"ingredient_id": 37, "purchased_at": "2026-09-18", "expires_at": "2026-09-23"},
    {"ingredient_id": 5, "purchased_at": "2026-09-20"}
  ],
  "allergies": ["우유", "땅콩"]
}
```

| 필드 | 상태 | 필수 | 쓰는 곳 | 없으면 |
|---|---|---|---|---|
| `user_id` | 있음 | 예 | 취향과 로그의 키 | 요청 거부 |
| `session_id` | 있음 | 아니요 | 로그 분석 | 세션 단위 분석을 못 합니다. `c-` 실사용자 · `g-` 게스트 · `d-` 개발 로 시작해야 합니다 |
| `top_k` | 있음 | 아니요 (기본 20, 1~100) | 목록 길이 | |
| `max_missing` | 있음 | 아니요 (기본 2, 0~10) | 부족한 필수 재료를 몇 개까지 허용하고 찾기 시작할지 | **시작값입니다.** 그 값으로 찾은 후보가 목록을 채우기에 모자라면 AI 가 한 칸씩 풀어 4까지(더 큰 값을 주셨으면 그 값까지) 넓히고, 그래도 모자라면 인기순으로 채웁니다. 그래서 `0` 을 주셔도 부족 재료가 있는 항목이 올 수 있습니다. 엄격하게 거르시려면 응답의 `items[].missing_count` 로 거르십시오. 넓혔는지는 추적의 `stages[0].fallback` 에 남습니다 |
| `max_minutes` | 있음 | 아니요 | 조리시간 상한 | 상한 없이 추천합니다 |
| `include_trace` | 있음 | 아니요 (기본 true) | 응답에 추적 정보를 실을지 | **운영에서는 `false` 로 보내 주십시오.** 응답이 크게 줄어듭니다 |
| `pantry[]` | 있음 | **예** | 재료 매칭 | **400 입니다.** 냉장고가 비었으면 빈 배열 `[]` 을 보내 주십시오. 그때는 인기순으로 냅니다 |
| `pantry[].ingredient_id` | 있음 | 예 | 재료 매칭의 키 | 400 |
| `pantry[].purchased_at` | 있음 | 아니요 | 소비기한 추정의 기준점 | `expires_at` 도 없으면 그 재료의 임박 신호가 꺼집니다 |
| `pantry[].expires_at` | 있음 | 아니요 | 임박 재료 가산 (가중치 0.15) | `purchased_at` 과 재료 사전의 소비기한으로 추정합니다 |
| `allergies[]` | 있음 | **예** | 하드컷 | **400 입니다.** 알레르기가 없으면 빈 배열 `[]` 로 **명시**해 주십시오 |

**`pantry` 와 `allergies` 는 둘 다 필수입니다**(2026-09-21 백엔드 제안). 기본값을 두면 백엔드의 버그로 필드가 빠졌을 때에도 200 이 나가고, 알레르기 재료가 섞인 목록이 에러 없이 서빙됩니다. 그래서 "없음" 은 빈 배열로 명시하고, 필드가 빠지면 400 입니다. 빠진 것과 없는 것을 구분하기 위해서입니다.

**수량과 단위는 받지 않습니다.** 백엔드가 팬트리의 수량을 관리하지 않고(기능 명세상 MVP 범위 밖) 엔진도 쓰지 않습니다. `quantity` 나 `unit` 을 보내시면 모르는 필드로 400 입니다.

**받은 값으로 실제로 뽑고 거릅니다**(2026-09-22). 냉장고의 재료와 필수 재료가 하나라도 겹치는 레시피가 후보가 되고, 알레르기에 걸리는 레시피는 재료와 제목 둘 다 보고 뺍니다(5절). 무엇이 도착했는지도 남깁니다 — 응답의 `trace.stages[0].params` 에 `pantry_received`(건수) · `allergy_labels` · `allergy_labels_unknown`(모르는 라벨) · `allergy_blocked_ingredients`(막은 재료 수)가 실리고, `GET /v1/recommendations/{request_id}` 의 `pantry_snapshot` · `allergy_snapshot` 에 엔진이 실제로 쓴 재료 번호가 남습니다. **재료 사전에 없는 `ingredient_id` 는 조용히 빠집니다**(AI 쪽에서 세어 둡니다). 재료를 새로 넣으신 직후 AI 의 다음 동기화 전까지 그럴 수 있습니다.

`pantry` 에는 **사용자가 직접 넣은 것만** 담아 주십시오. 소금·간장 같은 상비 재료는 AI 가 자동으로 더합니다. 그 구분으로 "냉장고가 사실상 비었는가" 를 판정합니다. 상비 재료만 있는 사용자에게 재료 매칭을 돌리면 양념 만드는 법만 나오기 때문에, 그때는 인기순으로 냅니다.

**냉장고를 미리 밀어 두는 경로(`PUT /v1/users/{user_id}/pantry`)는 쓰지 마십시오.** 경로는 남아 있지만 개발용 목업의 것이고, 실서빙의 추천은 그 값을 읽지 않습니다. 추천에 닿는 냉장고는 요청에 동봉한 것뿐입니다.

응답입니다.

```json
{
  "contract_version": "v1",
  "request_id": "75f2aab5-9792-44fb-8996-175b6aa61cf8",
  "user_id": 1024,
  "model_version": "reco-b-linear-v0",
  "served_at": "2026-09-21T10:00:00Z",
  "items": [
    {
      "recipe_id": 8821,
      "final_rank": 1,
      "reason": "두부(D-3)를 소진할 수 있고, 냉장고 재료를 11가지나 써요",
      "coverage": 1.0,
      "missing_count": 0,
      "missing_ids": []
    }
  ]
}
```

**200 이 아닐 수 있습니다.** AI 서버가 레시피를 아직 한 번도 받지 못했으면 **503** 입니다(6절). 그때는 백엔드의 인기순으로 대신해 주십시오. `items` 가 `top_k` 보다 짧을 수도 있습니다 — 알레르기와 조리시간으로 거르고 나면 남는 레시피가 적은 경우입니다. 빈 배열도 정상 응답입니다.

| 화면에 쓰실 필드 | 뜻 |
|---|---|
| `request_id` | **이벤트를 보낼 때 이 값을 함께 주십시오.** 노출과 반응을 잇는 유일한 열쇠입니다 |
| `items[].recipe_id` | 백엔드 DB 에서 제목·썸네일을 붙이는 키 |
| `items[].final_rank` | 화면에 보이는 순서. 1부터입니다. **이 순서를 바꾸지 마십시오** |
| `items[].reason` | 한국어 한 문장. AI 가 만듭니다 |
| `items[].missing_ids` | 부족한 필수 재료의 `ingredient_id`. 장보기로 잇는 자리입니다 |
| `items[].coverage` | 필수 재료 충족률 0~1 |

응답에는 이 밖에도 필드가 더 실려 옵니다 — `features`(신호 17종) · `score` · `propensity` · `is_exploration` · `is_cuisine_slot` · `weights` 등입니다. 전부 **평가와 디버깅용이라 무시하셔도 됩니다.** 다만 하나는 지켜 주십시오.

**`is_exploration` 이 `true` 인 항목을 걸러 내거나 뒤로 보내지 마십시오.** 목록의 20%는 일부러 섞은 "새로운 시도" 입니다. 클라이언트가 그 칸을 빼면 사용자의 숨은 취향을 찾지 못하고, 그 효과를 영영 측정하지 못합니다.

### 4.5 행동 이벤트

**구현 상태: 있음.** 한 번에 1~200건입니다.

```text
POST {AI}/v1/events
```

```json
{
  "events": [
    {
      "user_id": 1024,
      "event_type": "cook",
      "recipe_id": 8821,
      "request_id": "75f2aab5-9792-44fb-8996-175b6aa61cf8",
      "position": 1,
      "occurred_at": "2026-09-21T19:32:11+09:00"
    }
  ]
}
```

```json
{"accepted": 1, "rejected": 0, "errors": []}
```

| 필드 | 필수 | 뜻 |
|---|---|---|
| `event_type` | 예 | `impression` · `click` · `save` · `unsave` · `cook` · `rating` · `dismiss` · `search`. 소문자이며 **뜻을 바꾸거나 지울 수 없습니다** — 과거 로그가 그 뜻으로 쌓입니다 |
| `recipe_id` | `search` 가 아니면 예 | |
| `request_id` | 추천에서 나온 행동이면 예 | 4.4 응답의 값. 없으면 그 행동을 어느 추천의 결과로도 셀 수 없습니다 |
| `position` | 아니요 | 목록에서 몇 번째였는가 (`final_rank`) |
| `value` | `rating` 이면 예 | 평점, 또는 머문 시간(초) |
| `occurred_at` | 아니요 | **시간대가 반드시 있어야 합니다.** 없으면 요청을 거부합니다 |

`impression`(노출)은 보내지 않으셔도 됩니다. 추천 응답을 낼 때 AI 가 스스로 기록합니다.

`occurred_at` 은 선택이고 없으면 AI 가 받은 시각을 씁니다. **오프라인에서 모아 두었다가 한 번에 보내실 때는 반드시 실어 주십시오.** 200건이 같은 시각을 받으면 최근 행동에 무게를 더 주는 계산이 뭉개집니다.

취향은 `cook` · `save` · `rating` · `click` 에서 배웁니다. **맛 취향에는 받은 즉시 반영됩니다**(2026-09-22) — 그 레시피의 맛이 그 사용자의 취향으로 쌓여 다음 추천부터 쓰입니다. "선호 재료" 와 "재료 궁합" 두 신호(순위 가중치 0.21)는 아직 꺼져 있습니다. 이벤트는 쌓이고 있고 그것을 읽는 부분이 AI 쪽에 남아 있습니다.

**응답의 `rejected` 는 "버렸다" 가 아닙니다.** `recipe_id` 는 있는데 `request_id` 가 없는 이벤트를 그렇게 세고 `errors` 에 사유를 적습니다. 어느 추천에서 나온 행동인지 이을 수 없다는 뜻입니다. 검색에서 나온 조리처럼 원래 `request_id` 가 없는 행동이면 정상이고, **그 이벤트도 취향에는 반영됩니다. 다시 보내지 마십시오** — 같은 이벤트가 두 번 쌓입니다. 한 요청 안에서 같은 이벤트(같은 사용자 · 레시피 · 종류 · `request_id`)가 겹치면 하나만 씁니다. 요청을 넘는 중복은 거르지 못합니다.

### 4.6 헬스체크

**구현 상태: 있음.**

| 경로 | 키 | 뜻 |
|---|---|---|
| `GET /health/live` | 불필요 | 프로세스가 살아 있는가 |
| `GET /health/ready` | 불필요 | 트래픽을 받을 준비가 됐는가. 준비 전에는 503 |
| `GET /health` | 필요 | DB 연결 여부와 지금 답하는 모델의 이름(`model_version`). 실서빙이면 `reco-b-linear-v0`, 개발용 목업이면 `mock-` 으로 시작합니다. **운영에서 `mock-` 이 보이면 AI 서버에 백엔드 주소가 설정되지 않은 것입니다** |

세 경로 모두 **레시피를 받았는지는 말해 주지 않습니다.** `ready` 가 200 이어도 추천은 503 일 수 있습니다(영수증 기능이 레시피 때문에 막히지 않게 나눴습니다). 추천이 되는지는 추천의 상태코드로 아십시오. `/health` 의 `db` 가 `false` 여도 추천은 됩니다 — 실서빙의 추천은 DB 를 읽지 않습니다.

| 해산물 | (셋) | `fish` + `shellfish` + `mollusk` |
| `돼지고기` · `쇠고기` · `닭고기` · `토마토` | 없음 | 재료 이름으로 막습니다 — 그 고기와 가공품(베이컨·햄·소시지·스팸), 토마토·케첩·토마토소스 |
| `아황산류` | 없음 | **막지 못합니다.** 가공 첨가물이라 재료 사전에 표제어가 없습니다. 모르는 라벨로 돌려드립니다 |

코드 글꼴로 적은 라벨이 계약 어휘(`src/features/recommend/enums.py` 의 `ALLERGEN_LABELS`)이고, 나머지는 같은 뜻으로 받는 다른 말입니다.

### 5.3 세 가지 원칙

**군 전체를 막습니다.** "땅콩" 을 고르면 호두까지, "새우" 를 고르면 조개류와 김치(젓갈)까지 막습니다. 덜 막아서 생기는 일과 더 막아서 생기는 일의 무게가 다릅니다.

**군의 경계는 넘지 않습니다.** 오징어·낙지(두족류)는 갑각류·조개류와 다른 알레르기입니다. 새우를 고른 사용자에게서 오징어까지 빼지 않습니다.

**모르는 라벨은 버리지 않습니다.** 표에 없는 라벨이 오면 아는 것은 그대로 막고, 모르는 것은 온보딩 응답의 `unmapped_allergens` 로 돌려드리며 로그에 남깁니다. 조용히 버리면 그 사용자는 보호받지 못하는데 응답은 200 입니다. **백엔드가 쓰는 라벨 전체 목록을 한 번 보내 주십시오.** 표에 없는 것을 미리 더해 두겠습니다.

### 5.4 재료 목록만 믿지 않습니다

표본에 **제목에는 있는데 재료 행에는 없는** 레시피가 있었습니다. 새우 알레르기를 넣고 돌렸더니 1위가 「고추장 건새우볶음」 이었습니다. 그 레시피(`recipe_id` 1194)의 `recipe_ingredients` 에는 다진마늘·고춧가루·고추장 등 아홉 줄이 있고 **건새우가 없습니다.**

| 제목에 이 말이 있는 레시피 | 그중 재료 행에 그 재료가 없는 것 |
|---|---|
| 새우 618건 | 17건 (2.8%) |
| 오징어 669건 | 52건 (7.8%) |
| 땅콩 31건 | 4건 (12.9%) |
| 우유·치즈·버터·크림 1,179건 | 46건 (3.9%) |
| 달걀·계란 1,446건 | 22건 (1.5%) |

그래서 AI 는 재료 id 와 함께 **제목**도 봅니다. 제목에 막힌 재료의 이름이나 그 다른 말(계란 · 에그 · 쉬림프 · 피넛 · 크림 · 제육)이 있으면 재료 행에 없어도 막습니다. 넓게 걸립니다 — "노밀가루 홈베이킹" 처럼 그 재료가 없다고 적은 제목도 막힙니다. 부정 표현을 읽으려 들지 않았습니다. 잘못 읽으면 그 방향이 위험합니다.

다만 **제목에도 재료가 안 적힌 레시피는 여전히 못 잡습니다.** 운영 데이터에서 떨어진 재료 행을 복구할 수 있는지 봐 주십시오(7.3).

### 5.5 아직 못 막는 것

가공품 안의 다른 알레르기입니다. 간장은 대두이면서 밀이고 굴소스에는 대두가 들어가지만, AI 쪽 사전은 재료마다 알레르기를 하나만 달고 있습니다. **밀 알레르기 사용자에게 간장이 든 레시피가 나갑니다.** AI 쪽은 재료마다 여러 군을 받을 준비가 끝났습니다(2026-09-22). 재료 사전에 `allergens` 배열(3.1)을 실어 주시면 **그 재료부터** 닫힙니다 — 일부 재료에만 채워 주셔도 되고, 안 채운 재료는 AI 쪽 사전으로 계속 막습니다. 빈 배열 `[]` 은 "알레르기 없음" 으로 읽으니, 모르는 재료는 필드를 빼고 주십시오.

## 6. 공통 규약

| 항목 | 값 |
|---|---|
| 인증 | `X-Internal-Api-Key` 헤더. 양쪽이 같은 값을 씁니다. 백엔드 쪽 설정 이름은 `AI_INTERNAL_API_KEY` 입니다. 키가 없거나 틀리면 **401** `{"detail":"Unauthorized"}` |
| 검증 실패 | **400, 본문에 사유**(6.1). 필수 필드가 빠졌거나, 값이 범위를 벗어났거나, **모르는 필드가 있을 때**입니다 |
| 없는 자원 | 404 |
| 추천할 레시피가 아직 없음 | **503.** AI 서버가 3절의 두 API 에서 레시피를 아직 한 번도 받지 못했을 때 `/v1/recommend` 가 냅니다. 기동 직후 수 초 동안, 또는 두 API 에 닿지 못하는 동안입니다. **백엔드의 인기순으로 대신해 주십시오.** 가짜 목록을 200 으로 드리지 않습니다. 본문은 `{"detail": "..."}` 입니다. 온보딩과 헬스체크는 이때도 정상으로 답합니다. 이벤트도 200 으로 받지만 **그동안 받은 이벤트는 취향에 반영되지 않습니다** — 그 레시피의 맛을 아직 모르기 때문입니다 |
| 식별자 정본 | `recipe_id` 와 `ingredient_id` 는 백엔드 값이 정본입니다 |
| 시각 | 전부 시간대를 포함합니다(`2026-09-21T19:32:11+09:00`). 날짜만이면 `2026-09-21` |
| 타임아웃 | 추천은 3초 안에 답합니다. 동기화 호출은 AI 가 30초까지 기다립니다 |
| 동기화 페이지 | 커서 방식. `limit` 기본 1,000 · 최대 5,000 |
| 계약 판 | 응답의 `contract_version`(지금 `v1`). 필드를 빼거나 뜻을 바꿀 때만 올립니다. 필드 추가는 올리지 않습니다 |

### 6.1 검증 실패의 본문

**구현 상태: 있음**(2026-09-21 백엔드 요청으로 추가). 모르는 필드 하나로 요청 전체가 거부되므로 어느 필드가 왜 걸렸는지를 돌려드립니다. 아래는 합의 전 필드를 보냈을 때 실제 서버가 낸 응답입니다.

```json
{"user_id": 1024, "pantry": [{"ingredient_id": 37}], "allergies": ["우유"]}
```

```json
{
  "error": "validation_failed",
  "fields": [
    {"location": "body", "field": "pantry", "code": "extra_forbidden",
     "message": "Extra inputs are not permitted"},
    {"location": "body", "field": "allergies", "code": "extra_forbidden",
     "message": "Extra inputs are not permitted"}
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `error` | 언제나 `validation_failed` |
| `fields[].location` | `body` · `query` · `path` · `header` |
| `fields[].field` | 걸린 필드의 경로. 배열 안이면 `events.0.occurred_at` 처럼 자리까지 적습니다 |
| `fields[].code` | 사유의 종류. 자주 보실 것은 `missing`(필수 누락) · `extra_forbidden`(모르는 필드) · `less_than_equal` · `greater_than_equal`(범위 밖) · `value_error`(그 밖의 규칙 — 시간대 없는 시각, 제시 목록에 없는 음식) |
| `fields[].message` | 사람이 읽는 문구. **문구는 바뀔 수 있으니 분기는 `code` 로 하십시오** |

걸린 필드가 여럿이면 전부 실립니다. **보내신 값은 되돌려드리지 않습니다** — 요청 본문이 응답과 로그로 복사되지 않게 하려는 것입니다. 다만 제시 목록에 없는 음식 이름처럼 그 값이 곧 사유인 경우는 `message` 에 적힙니다.

영수증 경로(`/v1/ocr`)의 400 은 그 파트의 계약대로 본문이 없습니다. 401 과 404 의 본문은 `detail` 하나를 가진 객체 그대로입니다.

## 7. 백엔드 데이터에 부탁드리는 것

표본으로 엔진을 끝까지 돌려 확인한 것입니다. 운영 데이터가 같은 모양이면 같은 일이 생깁니다.

### 7.1 인기 신호

조회수·스크랩·주문·평점이 표본에 하나도 없었습니다(`recipe_scraps` 0건). 순위 가중치의 0.10 이 통째로 꺼져 있습니다. 특히 **냉장고가 빈 신규 사용자는 "인기순" 으로 받는데 인기 데이터가 없어 이름만 인기순**입니다.

셋 중 하나만 주셔도 켜집니다. 조회수가 가장 구하기 쉽고, 스크랩 수가 가장 정확하며, 주문 수가 가장 사업에 가깝습니다. 원값 그대로 주시면 되고 정규화는 AI 가 합니다.

**백엔드 회신(2026-09-21)**: 사용자 스크랩 수는 즉시 제공할 수 있고, 조회수는 레시피 테이블에 컬럼을 추가해 보겠다고 하셨습니다. 그래서 **스크랩 수 하나로 먼저 켭니다.** 조회수는 생기는 대로 같은 자리(`popularity.view_count`)에 실어 주시면 함께 씁니다. 서비스 초기에는 스크랩이 0 인 레시피가 대부분일 것이라 그동안의 인기 신호는 약합니다. 조회수가 그 구간을 메웁니다.

### 7.2 재료별 알레르기와 상비 표시

3.1 의 `allergens`(배열)와 `is_staple` 입니다. 지금은 둘 다 AI 쪽 사전에서 이름으로 이어 씁니다. 알레르기는 틀리면 사람이 다치는 자리인데 판정 근거가 한쪽에만 있습니다. **AI 쪽은 받을 준비가 끝났습니다**(2026-09-22). `allergens` 는 재료마다 따로 읽고, `is_staple` 은 **한 재료에라도 실려 오면 그때부터 백엔드의 값만** 씁니다 — 그러니 `is_staple` 은 전 재료에 한꺼번에 채워 주십시오. 일부만 `true` 로 주시면 나머지는 전부 상비가 아닌 것이 됩니다.

### 7.3 빠진 재료 행

5.4 입니다. 재료 사전에 닿지 못한 재료가 정규화 과정에서 떨어진 것으로 보입니다. 추천 품질에도 나쁘지만 알레르기 차단에 구멍이 납니다.

**백엔드 회신(2026-09-21)**: 재료 사전에 없는 재료는 빼는 방향으로 가공하셨고, 데이터 재가공은 시간상 확답하기 어렵다고 하셨습니다. 그래서 **AI 쪽의 제목 방어선(5.4)을 계속 유일한 안전판으로 둡니다.** 남는 구멍은 그대로입니다 — 제목에도 그 재료가 안 적힌 레시피는 막지 못합니다. 재가공이 어려우면 알레르기와 닿는 재료(새우 · 땅콩 · 우유 · 달걀 · 밀 등)가 빠진 레시피만이라도 먼저 봐 주시면 위험이 가장 많이 줄어듭니다.

### 7.4 비슷한 레시피

제목이 완전히 같은 레시피가 782건, 필수 재료가 같은 묶음이 2,285개(가장 큰 묶음 115건)였습니다. 추천 스무 칸에 두부조림 변형이 네 개 들어간 적이 있습니다. 같은 레시피의 판본을 묶는 대표 번호가 있으면 가장 깔끔합니다. 없으면 AI 쪽 재정렬에서 막는 길을 찾겠습니다.

**백엔드 회신(2026-09-21)**: 대표 묶음 번호가 없으니 재정렬에서 찾아 달라고 하셨습니다. **구현했습니다.** 한 목록에 같은 요리는 하나만 나갑니다. 같은 요리로 보는 기준은 셋이고 하나라도 같으면 같은 판본입니다.

| 기준 | 예 |
|---|---|
| 제목이 같다 (기호 · 공백을 뺀 뒤) | `소시지 도리아` 와 `[소시지] 도리아!!` |
| 요리 이름이 같다 — 제목에서 조리법으로 끝나는 낱말을 찾아 그 안의 주재료부터 끝까지 | `매콤 두부조림` · `두부 조림 만들기` · `백종원두부조림 황금레시피` 가 모두 `두부조림` |
| 재료 전체가 같다 (네 가지 이상일 때만) | 재료 다섯 가지가 똑같은 감자채볶음 셋 |

남는 판본은 그 사용자에게 점수가 가장 높은 것입니다. 냉장고에 참치가 있으면 참치김치찌개가, 돼지고기가 있으면 돼지고기김치찌개가 남습니다. 표본의 여섯 가지 냉장고 60개 목록에서 남는 판본이 차지한 칸이 목록당 1.9칸에서 0칸이 됐고(한 목록에 감자조림이 여섯 건 든 경우가 있었습니다), 개인화 칸의 평균 점수는 0.7% 내려갔습니다. 다른 요리를 잘못 묶지 않도록 `닭볶음탕` 과 `닭곰탕`, `새우호박볶음` 과 `건새우볶음` 은 다른 요리로 둡니다. 제목에서 요리 이름을 못 찾는 레시피가 25% 있고 그것들은 제목과 재료 기준으로만 묶입니다.

### 7.5 맛 정보는 필요 없습니다

표본에 맛 정보가 없었지만 맛은 재료에서 나오므로 AI 가 계산합니다. 표본 재료 148종이 전부 AI 의 맛 사전에 닿았고, 복원한 값이 다른 데이터로 계산한 값과 0.023 안에서 일치했습니다. 3.2 의 `unit` 과 재료 순서만 주시면 됩니다.

AI 서버가 백엔드를 부르려면 백엔드의 주소(`BACKEND_BASE_URL`) 하나가 필요합니다. 호출 키는 새로 만들지 않고 같은 내부 키를 씁니다. 3절의 경로가 제안과 달라지면 알려 주십시오 — 코드가 아니라 설정 둘(`BACKEND_INGREDIENTS_PATH` · `BACKEND_RECIPES_PATH`)만 바꾸면 됩니다(`docs/env_variables.md` 3.4).

아직 없는 것은 셋입니다. 추천 로그를 DB 에 남기는 것(지금은 최근 5,000건을 메모리에, 전량을 AI 서버의 파일에 둡니다 — `GET /v1/recommendations/{request_id}` 는 메모리의 것만 답하므로 재배포 뒤에는 그 전의 `request_id` 가 404 입니다), 증분 동기화(`updated_after`), 그리고 사용자의 조리 이력으로 켜지는 두 신호(선호 재료 · 재료 궁합)입니다.

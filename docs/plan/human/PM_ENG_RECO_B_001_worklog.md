팀 정책상 지금은 PR 을 만들지 않습니다. 브랜치에 규칙대로 커밋하고 push 만 하며, `main` 병합은 A(데이터)·B(추천)·C(평가) 파트 중 최소 A·B 가 끝난 뒤 논의합니다(P-10).

## 2. 계획과 다르게 한 것

계획서 원문과 다르게 결정한 것이 열다섯 가지 있습니다. 이유가 있어서 바꾼 것이지만, 계획서를 쓴 사람이 동의하지 않을 수 있으니 하나씩 적습니다. 각 항목을 되돌리는 조건은 에이전트용 3.2 표에 있습니다.

**결과에 영향을 주는 결정**

- 탐색 슬롯보다 **개인화 슬롯을 먼저** 뽑습니다(D-01). 계획서 그림은 둘을 나란히 그렸지만, 탐색을 먼저 뽑으면 개인화 결과가 난수에 따라 바뀌어 "같은 입력에는 같은 결과"라는 테스트가 깨졌습니다. 개인화가 어차피 보여 줄 레시피를 탐색 슬롯이 다시 고르는 것도 탐색의 취지에 맞지 않습니다.
- 후보가 부족해 조건을 완화하는 기준을 고정 20건이 아니라 **20건과 요청 개수 중 큰 쪽**으로 잡았습니다(D-02). 고정 20이면 50개를 요청한 사용자가 25개만 받는 일이 실제로 생겼습니다.
- 맛 유사도는 코사인 값을 그대로 쓰지 않고 0~1 사이로 옮겼고, 코퍼스 평균이 없으면 계산하지 않고 "측정 불가"로 뺍니다(D-09). 평균 없이 계산하면 어떤 벡터를 넣어도 비슷하다고 답하는 문제가 생기기 때문입니다.
- `dismiss`(무시) 이벤트는 취향 벡터를 움직이지 않습니다(D-14). 무엇이 싫었는지 알려 주지 않는 신호라서입니다.

**구조와 규약 때문에 바꾼 것**

- SQL 은 계획서가 말한 `engine/candidate.py` 가 아니라 `repository.py` 에 둘 예정입니다(D-03). 저장소 규약이 그렇게 정하고 있습니다. `candidate.py` 는 같은 조건을 파이썬으로 한 번 더 확인해서 DB 밖에서도 알레르기 재료가 새지 않게 합니다.
- 가중치와 감점 계수는 당분간 `RankConfig` 라는 설정 묶음의 기본값으로 둡니다(D-04). 규약은 `config.py` 로 빼라고 하지만, 그건 팀 공용 파일과 `.env.example` 을 함께 고치는 일이어서 DB 를 연결하는 Step 5 때 한 번에 하기로 했습니다.
- 요청과 이력을 합쳐 엔진 입력을 만드는 어댑터를 `service.py` 가 아닌 `engine/context.py` 에 두었습니다(D-15). 규약이 `service.py` 에는 흐름 조립만 허용하기 때문이고, 커밋을 단계별로 검증하려면 이 분리가 필요했습니다.
- 응답의 `meta` 를 자유 형식 사전이 아니라 필드 다섯 개짜리 고정 모델로 만들었습니다(D-07). JSON 모양은 같고, 필드가 빠지면 타입 검사가 잡아 줍니다.
- 이벤트의 종류와 시각은 문자열 대신 검증되는 타입으로 받습니다(D-08).
- 테스트 파일 이름은 계획서의 `test_serve.py`, `test_events.py` 가 아니라 규약대로 `test_service.py`, `test_feedback.py` 입니다(D-05).
- 도메인 `__init__.py` 에 아직 아무것도 내보내지 않습니다(D-10). 밖에서 쓰는 곳이 생기면 그때 넣습니다.
- 계획서의 SQL 이 고르는 컬럼보다 네 개(`title`, `all_ids`, `cuisine`, `product_ids`)를 더 요구합니다(D-13). 응답의 제목과 상품 ID, 탐색 슬롯의 요리군, 유사도 계산에 필요합니다.

**도구 때문에 바꾼 것**

- 난수는 `random.SystemRandom()` 을 쓰고, 가상 데이터 생성 스크립트는 난수 대신 해시를 씁니다(D-11). 시드가 있는 `random.Random` 은 린터가 막고, 예외를 두려면 Tech Lead 승인이 필요합니다.
- `pyproject.toml` 의 pytest 설정에 `--import-mode=importlib` 를 넣었습니다(D-12). 영수증 도메인과 추천 도메인이 규약대로 같은 이름의 테스트 파일(`test_service.py`)을 가지게 되는데, 기본 설정에서는 이 둘이 충돌해 테스트 수집이 깨집니다. 팀 공용 파일이므로 알려 두어야 합니다(P-04).
- Step 0 의 "더미 응답 라우터"는 만들지 않았습니다(D-06). 같은 날 엔진을 다 만들어서 더미가 곧 버려질 코드였습니다. 라우터 연결은 Step 5 에서 합니다.

## 4. 데이터가 정해지면 확인할 것

지금 코드는 데이터가 없는 상태에서 만든 선 설계입니다. 실제 데이터, 백엔드 계약, DB 가 정해지면 아래 가정이 맞는지 하나씩 대조해야 합니다(A-01~A-11). 코드 구조 자체는 그때 코드를 읽으면 되지만, 이 가정들은 코드를 읽어도 "가정"이라는 사실이 보이지 않습니다.

엔진이 바깥과 만나는 자리는 여섯 곳입니다. 백엔드가 보내는 요청과 이벤트(I-01), 데이터 파트가 주는 레시피 행(I-02)과 코퍼스 통계(I-03), DB 에서 읽는 사용자 이력(I-04), 엔진이 DB 에 남기는 서빙 로그(I-05), 백엔드와 평가 파트로 나가는 응답과 설정 지문(I-06)입니다. 지금은 전부 가상 데이터나 테스트가 채우고 있고, 실연결 때 각각 저장소 계층과 백엔드 계약이 채웁니다. 어떤 컬럼과 값이 필요한지는 에이전트용 8.1 표에 있습니다.

- 맛 벡터는 (매운맛, 단맛, 짠맛) 순서이고 값은 0~1 이라고 가정했습니다(A-01). 사용자 취향, 레시피 벡터, DB 기본값이 모두 이 척도여야 합니다.
- 인기도와 품질 점수가 이미 0~1 로 정규화되어 있다고 가정했습니다(A-02).
- 재료 ID 는 정수이고, 사용자 보유 목록·레시피·알레르기 매핑이 같은 ID 체계를 쓴다고 가정했습니다(A-03). 필수 재료는 전체 재료의 부분집합이라고 가정했습니다(A-04).
- 알레르기 코드군(식약처 19종)을 재료 ID 로 바꾸는 표가 어딘가에 있다고 가정했습니다(A-05). 지금은 가상 데이터 안의 임시 표를 씁니다.
- 레시피의 요리군 이름과 백엔드가 보내는 선호 요리군 문자열이 같은 어휘라고 가정했습니다(A-06). 탐색 슬롯은 문자열이 같은지로만 판단합니다.
- 조리시간이 비어 있는 레시피가 드물다고 가정했습니다(A-07). 비어 있으면 그 레시피는 조리시간 블록이 점수에서 빠집니다.
- 임박 재료 목록이 보유 목록의 부분집합인지는 확인하지 않습니다(A-08).
- 코퍼스 평균과 IDF 가 전체 데이터 기준이고 갱신 주기가 정해져 있다고 가정했습니다(A-09).
- **후보 조회 범위**(A-10). 이것이 가장 중요합니다. 계획서의 SQL 은 "부족 재료 2개 이하"로 걸러 500건만 넘기는데, 제가 만든 완화 로직은 넘겨받은 후보 안에서만 조건을 풉니다. 둘을 그대로 붙이면 완화할 후보가 없어 폴백이 빈손이 됩니다. 저장소 쿼리를 만들 때 "부족 4개 이하로 넉넉히 한 번 가져오기"와 "단계마다 다시 조회하기" 중 하나를 골라야 하고, 인기순 폴백은 어차피 별도 조회입니다.
- 4만 6천 건 실데이터를 파이썬으로 거르지는 않는다는 원칙입니다(A-11). 파이썬 쪽 필터는 SQL 결과를 재확인하고 가상 데이터로 테스트하기 위한 것입니다.

무언가를 고치거나 되돌려야 할 때는 이렇게 합니다. 점수 수식은 `engine/rank.py` 의 블록 함수 하나만 건드리고, 그때 `test_rank.py` 의 수치 테스트가 먼저 깨지는지 확인합니다. 가중치는 `RankConfig` 한 곳에만 있고 바꾸면 로그의 지문이 따라 바뀝니다. 커밋을 모듈 단위로 쪼개 두었으므로 특정 단계만 `git revert` 로 걷어낼 수 있습니다(뒤 커밋부터 순서대로). 통합 전 상태로 돌아올 기준점이 필요하면 `cbdf312` 에 태그를 붙이면 됩니다.

## 5. 알아두면 좋은 동작

명세가 정하지 않아 제가 정한 동작들입니다(C-01~C-11). 의도한 것이니 버그로 오해하지 않도록 적어 둡니다.

- 인기순 폴백은 조리시간 상한을 무시하고 알레르기만 거릅니다(C-01).
- 탐색 슬롯이 0개가 되는 경우가 있습니다: 후보 수가 요청 개수와 같거나, 비선호 요리군 후보가 없거나, 요리군 정보가 없는 레시피만 남았을 때입니다(C-02).
- 가구원 수는 받아 두지만 아직 어떤 점수에도 쓰지 않습니다(C-04).
- 인기도와 품질 중 하나가 비어 있으면 있는 쪽만 쓰고, 둘 다 비면 그 블록을 뺍니다(C-05). 가상 데이터는 스무 건에 한 건씩 품질 점수를 비워 이 경로를 테스트합니다.
- 설정 지문은 가중치뿐 아니라 후보 한도 같은 값까지 전부 포함한 해시라서 자주 바뀔 수 있습니다(C-06).
- 탐색 아이템의 노출 확률 역수(propensity)는 균등 슬롯은 정확히, Thompson 슬롯은 64회 표본으로 추정합니다(C-07).
- 재정렬의 계산량은 후보 수 곱하기 슬롯 수이고 실측 지연시간은 아직 없습니다(C-08).
- 가상 데이터의 알레르기 코드는 18종입니다. 아황산류는 대응 재료가 없어 뺐습니다(C-09).
- 임박 재료 목록이 보유 목록 밖의 ID 를 포함해도 그대로 계산에 넣습니다(C-03).
- 가상 데이터 JSON 은 스크립트 산출물이지만 테스트 픽스처 자리에 커밋합니다(C-10). 개인정보는 없습니다.
- `engine/` 폴더의 파일은 일곱 개로 규약의 여덟 개 기준 안입니다(C-11).

## 6. 작업 환경에서 걸린 것

이 PC(Windows 11)에서 확인된 사항입니다(E-01~E-10). 다른 PC 는 다를 수 있습니다.

- `uv run mypy` 가 앱 제어 정책에 막힙니다. `uv run python -m mypy src` 로 실행하면 됩니다(E-01).

# 백엔드 DB 스키마 요청 (추천 엔진 연동)

**정하는 것**: 추천 엔진을 실제 서비스 데이터에 연결하기 위해 백엔드에 요청하는 것 — **전체 스키마**와 연동 방식, 식별자, 갱신 시점, 규모, 개인정보. 추천 응답에 무엇을 싣고 무엇을 로그로만 남길지도 여기서 함께 정합니다

**적용 대상**: 백엔드 팀. 추천 엔진(파트 B)이 요청하고, 답변은 데이터 파트(파트 A)와 함께 봅니다

**버전**: 2.0.0 · **최종 수정**: 2026-09-17 · **작성자**: 유재현

---

## 1. 무엇을 요청하는가

**백엔드 데이터베이스의 전체 스키마를 주십시오.** 테이블 목록과 각 칼럼의 이름·타입·뜻이면 됩니다.

필요한 것만 골라 달라고 하지 않는 이유가 있습니다. 지금 추천 엔진은 **백엔드가 무엇을 모으는지 모르는 상태에서** 만든 테스트 버전입니다. 우리가 필요하다고 생각한 것(냉장고 재료 · 온보딩 응답 · 알러지)만 가정하고 그에 맞춰 자체 스키마를 만들었습니다. 이 상태에서 "이것만 주세요" 라고 요청하면, **이미 모으고 있는데 우리가 몰라서 못 쓰는 데이터**는 계속 못 쓰게 됩니다.

전체를 한 번 보면 그중 추천 품질에 쓸 수 있는 것을 우리가 찾아 제안드릴 수 있습니다. 예를 들어 주문 이력이 있다면 "산 적 있는 재료"를, 레시피 리뷰가 있다면 별점 대신 실제 반응을 신호로 쓸 수 있습니다. 지금은 그런 것이 있는지조차 모릅니다.

---

## 2. 요청 1 — 전체 스키마

### 2.1 형식

아래 중 **편하신 것 하나**면 됩니다. 완벽하지 않아도 되고, 초안이라도 먼저 주시면 그 위에서 질문을 좁히겠습니다.

| 형식 | 비고 |
|---|---|
| `pg_dump --schema-only` (또는 해당 DB 의 동등 명령) | **가장 좋습니다.** 제약·인덱스·기본값·코멘트까지 한 번에 보입니다 |
| ERD 이미지 + 칼럼 설명 | 관계를 보기에 좋습니다 |
| 테이블별 칼럼 목록 (이름 · 타입 · NULL 허용 · 뜻) | 스프레드시트도 괜찮습니다 |

마이크로서비스별로 DB 가 나뉘어 있다면 **서비스별로 나눠 주셔도 됩니다.** 어느 서비스의 것인지만 표시해 주십시오.

### 2.2 범위

- **모든 테이블을 주십시오.** 추천과 무관해 보이는 것도 포함해 주시면 좋겠습니다. 무엇이 쓸모 있는지는 받아 보고 저희가 판단해 다시 여쭙겠습니다.
- **값(데이터)은 필요 없습니다.** 구조만 주시면 됩니다.
- **빼 주셔야 하는 것**: 비밀번호 해시 · 토큰 · 결제 수단 상세처럼 우리가 알 필요가 없는 칸은 목록에서 빼셔도 됩니다. 어떤 칸을 뺐는지만 알려 주시면 됩니다.
- 칼럼 이름만으로 뜻이 불분명한 것(상태 코드, enum, 플래그)은 가능한 값의 목록을 함께 주시면 좋습니다.

### 2.3 함께 알려 주시면 좋은 것

- 각 테이블이 **어느 서비스 소유**인지
- 지금 **실제로 쌓이고 있는** 테이블과, 만들어만 두고 비어 있는 테이블의 구분
- 사용하지 않기로 했지만 아직 안 지운 테이블이 있다면 그 표시

## 3. 최소한 이것만은 어디 있는지 알려 주십시오

전체 스키마를 받으면 저희가 찾아보겠습니다만, 아래 여섯 가지는 추천 1건을 만들 때 **반드시 필요한 것**이라 위치를 짚어 주시면 시간을 아낄 수 있습니다.

| 무엇 | 왜 필요한가 | 지금 우리 쪽 위치 | 백엔드에서는 어디에 |
|---|---|---|---|
| 사용자 식별 | 모든 조회의 기준 | `app_user.id` (BIGINT) | |
| 냉장고 재료 | 후보를 고르는 1차 조건. **재료가 하나도 안 겹치면 후보가 아닙니다** | `pantry_item` (재료 id · 수량 · 단위 · 구매일 · 소비기한 · 소비기한 출처) | |
| 온보딩 응답 | 취향 페르소나의 출발점 | `user_preference` (맛 3축 · 조리시간 상한 · 실력 · 가구원 수 · 음식 유형) · `user_vector` (고른 음식) | |
| 알러지·기피 재료 | **절대 제약.** 하나라도 들어간 레시피는 아예 뺍니다 | `user_allergy` · `user_ingredient_pref` | |
| 레시피 | 후보 자체 | `recipe` · `recipe_ingredient` · `recipe_feature` | |
| 행동 이벤트 | 취향을 시간에 따라 갱신 | `event_log` (노출 · 클릭 · 저장 · 조리 · 별점 · 무시) | |

### 3.1 특히 확인이 필요한 세 가지

**① 재료 사전을 누가 갖고 있습니까.** 추천의 거의 모든 계산이 "재료 id" 로 이뤄집니다. 우리 쪽에는 정규화된 재료 사전 536종과 표기 변형 사전이 있고, 냉장고 재료와 레시피 재료를 이 id 로 맞춥니다. 백엔드의 냉장고가 **재료명 문자열**로 저장한다면 그 문자열을 우리 사전에 붙이는 단계가 하나 더 필요합니다.

**② 소비기한을 사용자가 입력합니까, 시스템이 추정합니까.** 이 값이 추천의 가장 큰 차별점(임박 재료 소진)을 만듭니다. 우리 쪽은 두 경우를 `expires_at_source` 로 구분해 저장합니다 — 구분하지 않으면 "추정이 실제로 쓸 만한가" 를 영영 측정할 수 없습니다. 백엔드에도 같은 구분이 있는지, 없다면 만들 수 있는지 알려 주십시오.

**③ 레시피의 정본이 어디입니까.** 우리 쪽에는 크롤한 레시피 46,353건과 서빙용으로 미리 계산한 테이블(재료 집합 · 맛 6축 · 인기 점수 · 조리시간)이 있습니다. 서비스가 보여줄 레시피가 이것과 같은 것인지, 백엔드가 따로 관리하는 목록이 있는지에 따라 연동 지점이 달라집니다.

## 4. 전체를 보며 우리가 찾아볼 것

이런 데이터가 **있으면** 추천이 좋아질 수 있습니다. **없으면 없는 대로 괜찮습니다** — 만들어 달라는 요청이 아니라, 이미 있는지 확인하려는 것입니다.

| 있으면 쓸 수 있는 것 | 추천에서 어떻게 쓰이는가 |
|---|---|
| 주문·장바구니 이력 | "산 적 있는 재료" 는 앞으로도 살 재료입니다. 부족 재료가 하나 있어도 그 재료를 늘 사는 사람에게는 부담이 아닙니다 |
| 레시피 조회·체류 이력 | 클릭보다 촘촘한 관심 신호입니다 |
| 리뷰·평점 | 지금은 크롤 후기를 쓰는데, 우리 사용자의 평가가 있으면 그쪽이 정확합니다 |
| 조리 완료·조리 타이머 기록 | **가장 강한 신호입니다.** 클릭은 호기심이지만 조리는 실제 선택입니다 |
| 알림 반응(열었는가 · 무시했는가) | 소비기한 임박 알림에 반응하는 사람과 아닌 사람은 추천 전략이 달라야 합니다 |
| 검색어 | 무엇을 찾다가 못 찾았는지가 후보 부족 구간을 알려 줍니다 |
| 가구 구성 · 식이 제약(비건 등) | 양과 후보 자체를 거르는 조건입니다 |
| 재료 폐기·소진 기록 | 추천이 실제로 재료를 쓰게 만들었는지를 재는 유일한 방법입니다 |

목록에 없는 것이라도 "이런 것도 있다" 고 알려 주시면 저희가 쓸모를 판단하겠습니다.

## 5. 요청 2 — 연동 방식 (셋 중 하나를 함께 정합니다)

스키마 다음으로 중요한 결정입니다. **추천 1건은 DB 왕복 한 번으로 끝나게 설계돼 있습니다** — 후보 조회 SQL 함수 하나가 냉장고·알러지 전개·재료 매칭을 안에서 처리합니다(후보 500건 기준 p95 17.6ms). 방식이 바뀌면 이 예산을 다시 잡아야 합니다.

| 방식 | 내용 | 확인해야 하는 것 |
|---|---|---|
| ① 백엔드 DB 직접 읽기 | 추천 서버가 읽기 전용 계정으로 조회 | 접속 정보 · 읽기 권한 범위 · 커넥션 수 상한 · 재료 사전을 어느 쪽에 둘지 |
| ② 백엔드 API 호출 | 추천 요청마다 냉장고·알러지를 API 로 받아 옴 | 엔드포인트와 응답 형식 · 지연시간(왕복이 추가됩니다) · 타임아웃과 실패 시 동작 |
| ③ 우리 DB 로 동기화 | 백엔드가 변경을 밀어주거나 주기 배치로 당겨 옴 | 전달 방식(이벤트 · 배치) · 주기 · 지연 허용치 · 초기 적재 방법 |

**추천 엔진 입장의 의견**은 ① 또는 ③ 입니다. ② 는 추천 1건마다 백엔드 왕복이 붙어 지연시간이 가장 불리하고, 백엔드 장애가 곧 추천 장애가 됩니다. 다만 **데이터 소유권은 백엔드 판단이 우선**이므로 정해 주시는 대로 맞추겠습니다.

## 6. 요청 3 — 식별자와 타입

| 항목 | 우리 쪽 | 백엔드 | 확인할 것 |
|---|---|---|---|
| 사용자 id | `BIGINT` (내부 발급) | | 타입과 발급 주체. UUID 라면 우리 쪽 테이블을 바꿔야 합니다 |
| 레시피 id | `BIGINT` | | 같은 레시피를 양쪽이 같은 번호로 부르는지 |
| 재료 id | `INT` (우리 사전) | | 백엔드에 재료 id 체계가 따로 있는지 |

번호가 다르면 매핑 테이블을 어느 쪽에 둘지도 함께 정해야 합니다.

## 7. 요청 4 — 갱신 시점과 규모

**갱신 시점**

- 사용자가 냉장고에 재료를 넣은 뒤 **몇 초 안에** 추천에 반영돼야 합니까. (실시간 / 분 단위 / 시간 단위)
- 온보딩 응답이 바뀌면 곧바로 반영돼야 합니까.
- 레시피가 추가·수정되는 주기는 어떻게 됩니까. 우리 쪽 서빙 테이블은 배치로 다시 계산하므로 주기를 맞춰야 합니다.

**규모** (대략의 자릿수면 충분합니다)

- 사용자 수 (현재 / 예상)
- 사용자당 냉장고 항목 수 (평균 / 최대)
- 레시피 수
- 하루 추천 요청 수 (예상)

---

## 8. 요청 5 — 개인정보와 동의

- 우리가 **받지 말아야 할 칸**을 알려 주십시오. 추천에 필요한 것은 재료·취향·행동뿐이고, 이름·연락처·주소·결제 정보는 받지 않는 것이 서로 안전합니다.
- 사용자 동의 여부를 나타내는 칸이 있습니까. 우리 쪽에는 동의 시각과 범위를 두고, 분석에 쓰기 전에 반드시 확인하도록 해 두었습니다.
- 사용자가 탈퇴하면 추천 쪽 데이터(행동 이벤트 · 추천 로그)는 어떻게 처리해야 합니까.

## 9. 우리가 드리는 것 — 응답과 로그의 경계

추천 엔진이 만드는 값은 아래가 전부입니다. **응답으로 나갈 것과 우리 쪽 로그에만 남길 것을 지금 갈라 두려고 합니다.** 지금은 계약상 전부 응답에 실려 나가는데, 실서비스에서는 그럴 이유가 없는 값이 섞여 있습니다.

### 9.1 제안 — 응답에 싣는 것

프론트가 화면을 그리는 데 필요한 것만 남깁니다.

| 필드 | 내용 |
|---|---|
| `request_id` | 이 추천의 식별자. **행동 이벤트를 보낼 때 함께 보내 주셔야 합니다** — 이것이 없으면 클릭이 어느 추천의 결과였는지 영영 알 수 없습니다 |
| `recipe_id` · `final_rank` | 무엇을 몇 번째로 보여줄지 |
| `reason` | 추천 이유 한 문장 ("가진 재료로 바로 만들 수 있고, 두부(D-2)를 소진할 수 있어요") |
| `missing_count` · `missing_ids` | 부족한 재료 수와 그 재료. 장바구니 연결에 씁니다 |
| `coverage` | 가진 재료로 얼마나 만들 수 있는가 (0~1) |
| `model_version` · `served_at` | 어느 버전이 언제 응답했는가 |

### 9.2 제안 — 로그에만 남기는 것

우리 쪽에 남기고 응답에서는 뺍니다. 두 가지 이유입니다. **첫째, 클라이언트가 쓸 일이 없습니다.** 둘째, **일부는 노출되면 평가가 깨집니다** — 어느 칸이 무작위 탐색 칸인지 응답에 적혀 있으면 클라이언트가 그 칸만 걸러낼 수 있고, 그러면 그 칸으로 하려던 측정이 성립하지 않습니다.

| 필드 | 무엇 |
|---|---|
| `features` (17종) | 점수를 만든 신호의 원값. 나중에 랭킹 모델을 학습할 때 쓰는 유일한 근거입니다 |
| `score` · `penalty` · `mmr_penalty` | 점수와 감점 |
| `propensity` · `is_exploration` · `explore_source` | 그 칸이 무작위로 뽑혔는지와 그 확률 |
| `is_cuisine_slot` | 온보딩에서 고른 음식 유형 몫으로 채운 칸인지 |
| `cluster_id` | 레시피 묶음 |
| `trace` | 단계별 후보 수·지연시간·정책 값 |

### 9.3 함께 정할 것

1. **`score` 를 응답에 넣습니까.** 화면에 점수를 보여줄 계획이 있으면 넣고, 없으면 빼는 쪽을 권합니다. 숫자가 나가면 "왜 이 레시피가 0.72 인가" 를 설명할 의무가 생깁니다.
2. **부족 재료를 id 로 드립니까, 이름으로 드립니까.** 이름이 필요하면 재료 사전을 어느 쪽이 갖는지(3.1 ①)와 이어집니다.
3. **행동 이벤트를 누가 보냅니까.** 노출(impression)은 추천 서버가 응답하면서 스스로 기록합니다. **클릭·저장·조리·별점은 백엔드가 보내 주셔야 합니다** — 사용자가 실제로 무엇을 했는지는 백엔드만 압니다. 지금 계약은 `POST /v1/events` 이고 한 번에 200건까지 받습니다. 이 방식이 괜찮은지, 다른 경로를 쓰실지 알려 주십시오.
4. **추천 로그를 어느 DB 에 남깁니까.** 지금은 우리 쪽에 남기게 설계돼 있습니다. 백엔드가 같은 것을 따로 남기실 계획이면 중복을 피하게 맞추겠습니다.

## 10. 답변 방법과 기한

- **2절의 전체 스키마를 파일로 주시는 것이 가장 빠릅니다.** 덤프 한 번이면 3절·4절의 질문 대부분이 함께 풀립니다.
- 나머지(5~9절)는 이 문서에 **답변만 덧붙여 돌려주셔도** 됩니다.
- **가장 급한 것은 2절(전체 스키마)과 5절(연동 방식), 9.3(응답·로그 경계)** 입니다. 이 셋이 정해지면 나머지는 구현하면서 맞출 수 있습니다.
- 회신 희망 시점을 알려 주시면 그에 맞춰 설계를 진행하겠습니다. 초안이라도 먼저 주시면 질문을 좁혀 다시 여쭙겠습니다.

# 백엔드 DB 스키마 요청 (추천 엔진 연동)

**정하는 것**: 추천 엔진을 실제 서비스 데이터에 연결하기 위해 백엔드에 요청하는 정보와 함께 정해야 하는 결정 — 스키마 정의, 소유권과 연동 방식, 식별자, 갱신 시점, 규모, 개인정보. 추천 응답에 무엇을 싣고 무엇을 로그로만 남길지도 여기서 함께 정합니다

**적용 대상**: 백엔드 팀. 추천 엔진(파트 B)이 요청하고, 답변은 데이터 파트(파트 A)와 함께 봅니다

**버전**: 1.0.0 · **최종 수정**: 2026-09-17 · **작성자**: 유재현

---

## 1. 왜 요청하는가

추천 엔진은 지금 **목업으로 응답합니다.** 랭킹·재정렬·취향 페르소나는 구현이 끝났고 검사도 돌지만, 라우터가 실제 데이터베이스를 읽지 않습니다. 엔진 자체 스키마(`reco`)를 만들어 두고 가상 사용자 1,600명으로 동작을 확인한 단계입니다.

실제로 연결하려면 **어느 데이터가 어디에 있고 누가 정본인지**를 알아야 합니다. 지금 우리 쪽에는 회원·냉장고·레시피 테이블이 있지만, 서비스 구조상 그 정본은 백엔드에 있을 가능성이 큽니다. 같은 데이터를 두 곳이 각자 들고 있으면 어느 쪽이 맞는지 알 수 없게 되므로, 설계를 확정하기 전에 여쭙습니다.

**이 문서 하나로 끝내려는 것**: ① 백엔드 스키마 파악 ② 연동 방식 결정 ③ 추천 응답과 로그의 경계 확정.

---

## 2. 우리가 쓰는 데이터 여섯 가지

추천 1건을 만들 때 읽는 것은 아래가 전부입니다. **오른쪽 칸을 채워 주시면 됩니다.**

| 무엇 | 왜 필요한가 | 지금 우리 쪽 위치 | 백엔드에서는 어디에 있습니까 |
|---|---|---|---|
| 사용자 식별 | 모든 조회의 기준 | `app_user.id` (BIGINT) | |
| 냉장고 재료 | 후보를 고르는 1차 조건. **재료가 하나도 안 겹치면 후보가 아닙니다** | `pantry_item` (재료 id · 수량 · 단위 · 구매일 · 소비기한 · 소비기한 출처) | |
| 온보딩 응답 | 취향 페르소나의 출발점 | `user_preference` (맛 3축 · 조리시간 상한 · 실력 · 가구원 수 · 음식 유형) + `user_vector` (고른 음식 인덱스) | |
| 알러지·기피 재료 | **절대 제약.** 하나라도 들어간 레시피는 아예 뺍니다 | `user_allergy` (그룹 코드 · severity) · `user_ingredient_pref` | |
| 레시피 | 후보 자체 | `recipe` · `recipe_ingredient` · `recipe_feature` | |
| 행동 이벤트 | 취향을 시간에 따라 갱신 | `event_log` (노출 · 클릭 · 저장 · 조리 · 별점 · 무시) | |

### 2.1 특히 확인이 필요한 세 가지

**① 재료 사전을 누가 갖고 있습니까.** 추천의 거의 모든 계산이 "재료 id" 로 이뤄집니다. 우리 쪽에는 정규화된 재료 사전 536종과 표기 변형 사전이 있고, 냉장고 재료와 레시피 재료를 이 id 로 맞춥니다. 백엔드의 냉장고가 **재료명 문자열**로 저장한다면 그 문자열을 우리 사전에 붙이는 단계가 하나 더 필요합니다. 어느 쪽인지 알려 주십시오.

**② 소비기한을 사용자가 입력합니까, 시스템이 추정합니까.** 이 값이 추천의 가장 큰 차별점(임박 재료 소진)을 만듭니다. 우리 쪽은 두 경우를 `expires_at_source` 로 구분해 저장합니다 — 구분하지 않으면 "추정이 실제로 쓸 만한가" 를 영영 측정할 수 없습니다. 백엔드에도 같은 구분이 있는지, 없다면 만들 수 있는지 알려 주십시오.

**③ 레시피의 정본이 어디입니까.** 우리 쪽에는 크롤한 레시피 46,353건과, 서빙용으로 미리 계산한 테이블(재료 집합 · 맛 6축 · 인기 점수 · 조리시간)이 있습니다. 서비스가 보여줄 레시피가 이것과 같은 것인지, 백엔드가 따로 관리하는 목록이 있는지에 따라 연동 지점이 달라집니다.

## 3. 요청 1 — 스키마 정의

아래 중 **편하신 형식 하나**면 됩니다. 완벽하지 않아도 되고, 초안이라도 먼저 주시면 그 위에서 질문을 좁히겠습니다.

- `pg_dump --schema-only` 결과 (가장 좋습니다. 제약·인덱스·기본값까지 보입니다)
- ERD 이미지 + 칸 설명
- 테이블별 칼럼 목록 (이름 · 타입 · NULL 허용 · 뜻)

**우선순위**는 이렇습니다. 위 세 개만 있어도 설계를 시작할 수 있습니다.

1. 회원 · 냉장고 · 알러지/식이 제약
2. 레시피와 레시피-재료
3. 주문/장바구니 (있다면 — 추천 후보의 보조 신호로 쓸 수 있습니다)

---

## 4. 요청 2 — 연동 방식 (셋 중 하나를 함께 정합니다)

가장 중요한 결정입니다. **추천 1건은 DB 왕복 한 번으로 끝나게 설계돼 있습니다**(후보 조회 SQL 함수 하나가 냉장고·알러지 전개·재료 매칭을 안에서 처리합니다. 후보 500건 기준 p95 17.6ms). 방식이 바뀌면 이 예산을 다시 잡아야 합니다.

| 방식 | 내용 | 우리가 확인해야 하는 것 |
|---|---|---|
| ① 백엔드 DB 직접 읽기 | 추천 서버가 읽기 전용 계정으로 백엔드 DB 를 조회 | 접속 정보 · 읽기 권한 범위 · 커넥션 수 상한 · 재료 사전을 어느 쪽에 둘지 |
| ② 백엔드 API 호출 | 추천 요청마다 냉장고·알러지를 API 로 받아 옴 | 엔드포인트와 응답 형식 · 지연시간(왕복이 추가됩니다) · 타임아웃과 실패 시 동작 |
| ③ 우리 DB 로 동기화 | 백엔드가 변경을 우리 쪽에 밀어주거나 주기 배치로 당겨 옴 | 전달 방식(이벤트 · 배치) · 주기 · 지연 허용치 · 초기 적재 방법 |

**추천 엔진 입장의 의견**은 ① 또는 ③ 입니다. ② 는 추천 1건마다 백엔드 왕복이 붙어 지연시간이 가장 불리하고, 백엔드 장애가 곧 추천 장애가 됩니다. 다만 **데이터 소유권은 백엔드 쪽 판단이 우선**이므로 정해 주시는 대로 맞추겠습니다.

---

## 5. 요청 3 — 식별자와 타입

| 항목 | 우리 쪽 | 백엔드 | 확인할 것 |
|---|---|---|---|
| 사용자 id | `BIGINT` (내부 발급) | | 타입과 발급 주체. UUID 라면 우리 쪽 테이블을 바꿔야 합니다 |
| 레시피 id | `BIGINT` | | 같은 레시피를 양쪽이 같은 번호로 부르는지 |
| 재료 id | `INT` (우리 사전) | | 백엔드에 재료 id 체계가 따로 있는지 |

번호가 다르면 매핑 테이블을 어느 쪽에 둘지도 함께 정해야 합니다.

---

## 6. 요청 4 — 갱신 시점과 일관성

- 사용자가 냉장고에 재료를 넣은 뒤 **몇 초 안에** 추천에 반영돼야 합니까. (실시간 / 분 단위 / 시간 단위)
- 온보딩 응답이 바뀌면 곧바로 반영돼야 합니까.
- 레시피가 추가·수정되는 주기는 어떻게 됩니까. 우리 쪽 서빙 테이블은 배치로 다시 계산하므로 주기를 맞춰야 합니다.

---

## 7. 요청 5 — 규모

용량 산정과 인덱스 설계에 필요합니다. 대략의 자릿수면 충분합니다.

- 사용자 수 (현재 / 예상)
- 사용자당 냉장고 항목 수 (평균 / 최대)
- 레시피 수
- 하루 추천 요청 수 (예상)

---

## 8. 요청 6 — 개인정보와 동의

- 우리가 **받지 말아야 할 칸**이 있으면 알려 주십시오. 추천에 필요한 것은 재료·취향·행동뿐이고, 이름·연락처·주소·결제 정보는 받지 않는 것이 서로 안전합니다.
- 사용자 동의 여부를 나타내는 칸이 있습니까. 우리 쪽에는 동의 시각과 동의 범위를 두고, 분석에 쓰기 전에 반드시 확인하도록 해 두었습니다.
- 사용자가 탈퇴하면 추천 쪽 데이터(행동 이벤트 · 추천 로그)는 어떻게 처리해야 합니까.

## 9. 우리가 드리는 것 — 응답과 로그의 경계

추천 엔진이 만드는 값은 아래가 전부입니다. **응답으로 나갈 것과 우리 쪽 로그에만 남길 것을 지금 갈라 두려고 합니다.** 지금은 계약상 전부 응답에 실려 나가는데, 실서비스에서는 그럴 이유가 없는 값이 섞여 있습니다.

### 9.1 제안 — 응답에 싣는 것

프론트가 화면을 그리는 데 필요한 것만 남깁니다.

| 필드 | 내용 |
|---|---|
| `request_id` | 이 추천의 식별자. **행동 이벤트를 보낼 때 함께 보내 주셔야 합니다** — 이것이 없으면 클릭이 어느 추천의 결과였는지 영영 알 수 없습니다 |
| `recipe_id` · `final_rank` | 무엇을 몇 번째로 보여줄지 |
| `reason` | 추천 이유 한 문장 ("가진 재료로 바로 만들 수 있고, 두부(D-2)를 소진할 수 있어요") |
| `missing_count` · `missing_ids` | 부족한 재료 수와 그 재료. 장바구니 연결에 씁니다 |
| `coverage` | 가진 재료로 얼마나 만들 수 있는가 (0~1) |
| `model_version` · `served_at` | 어느 버전이 언제 응답했는가 |

### 9.2 제안 — 로그에만 남기는 것

우리 쪽에 남기고 응답에서는 뺍니다. 두 가지 이유입니다. **첫째, 클라이언트가 쓸 일이 없습니다.** 둘째, **일부는 노출되면 평가가 깨집니다** — 어느 칸이 무작위 탐색 칸인지 응답에 적혀 있으면 클라이언트가 그 칸만 걸러낼 수 있고, 그러면 그 칸으로 하려던 측정이 성립하지 않습니다.

| 필드 | 무엇 |
|---|---|
| `features` (17종) | 점수를 만든 신호의 원값. 나중에 랭킹 모델을 학습할 때 쓰는 유일한 근거입니다 |
| `score` · `penalty` · `mmr_penalty` | 점수와 감점 |
| `propensity` · `is_exploration` · `explore_source` | 그 칸이 무작위로 뽑혔는지와 그 확률 |
| `is_cuisine_slot` | 온보딩에서 고른 음식 유형 몫으로 채운 칸인지 |
| `cluster_id` | 레시피 묶음 |
| `trace` | 단계별 후보 수·지연시간·정책 값 |

### 9.3 함께 정할 것

1. **`score` 를 응답에 넣습니까.** 화면에 점수를 보여줄 계획이 있으면 넣고, 없으면 빼는 쪽을 권합니다. 숫자가 나가면 "왜 이 레시피가 0.72 인가" 를 설명할 의무가 생깁니다.
2. **부족 재료를 id 로 드립니까, 이름으로 드립니까.** 이름이 필요하면 재료 사전을 어느 쪽이 갖는지(2.1 ①)와 이어집니다.
3. **행동 이벤트를 누가 보냅니까.** 노출(impression)은 추천 서버가 응답하면서 스스로 기록합니다. **클릭·저장·조리·별점은 백엔드가 보내 주셔야 합니다** — 사용자가 실제로 무엇을 했는지는 백엔드만 압니다. 지금 계약은 `POST /v1/events` 이고 한 번에 200건까지 받습니다. 이 방식이 괜찮은지, 아니면 다른 경로를 쓰실지 알려 주십시오.
4. **추천 로그를 어느 DB 에 남깁니까.** 지금은 우리 쪽에 남기게 설계돼 있습니다. 백엔드가 같은 것을 따로 남기실 계획이면 중복을 피하게 맞추겠습니다.

## 10. 답변 방법과 기한

- 3절의 스키마는 파일로 주시는 것이 가장 좋습니다. 나머지(4~9절)는 이 문서에 **답변만 덧붙여 돌려주셔도** 됩니다.
- **4절(연동 방식)과 9.3(응답·로그 경계)이 가장 급합니다.** 이 둘이 정해지면 나머지는 구현하면서 맞출 수 있습니다.
- 회신 희망 시점을 알려 주시면 그에 맞춰 설계를 진행하겠습니다. 초안이라도 먼저 주시면 질문을 좁혀 다시 여쭙겠습니다.

## 11. 부록 — 지금 우리 쪽 구조 요약

참고용입니다. 백엔드와 겹치는 것이 있으면 **백엔드 쪽을 정본으로 두고 우리 것을 지우는 방향**으로 맞추겠습니다.

| 묶음 | 테이블 | 성격 |
|---|---|---|
| 재료 | `ingredient` (536종) · `ingredient_alias` · `ingredient_category` · `ingredient_substitute` | 사전. 표기 변형과 계층(알러지 전개에 씀) |
| 레시피 | `recipe` · `recipe_ingredient` · `recipe_step` · `recipe_feature` | 크롤 원본과 서빙용 사전 계산 |
| 사용자 | `app_user` · `user_preference` · `user_vector` · `user_allergy` · `user_ingredient_pref` · `pantry_item` | **백엔드와 겹칠 가능성이 큰 묶음** |
| 로그 | `recommendation_log` · `event_log` | 추천 1건과 그 뒤의 행동 |
| 운영 | `batch_run` · `feature_stats` · `scoring_config` 등 | 배치와 설정 |

전체 정의는 저장소의 `deploy/init/02_schema.sql` 에 있고, 후보 조회 SQL 함수는 `deploy/init/04_functions.sql` 입니다. 필요하시면 그대로 보내 드리겠습니다.

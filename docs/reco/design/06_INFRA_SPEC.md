# 0. 요약 — 이것만 보면 됨

| | 최소 (동작은 함) | **권장 (신청값)** | 여유 (있으면 좋음) |
|---|---|---|---|
| CPU | 2 core | **8 core** | 16 core |
| RAM | 8 GB | **32 GB** | 64 GB |
| 디스크 | 20 GB | **100 GB** | 200 GB |
| GPU | 불필요 | **없어도 됨** (온라인 기준) | **통합 16GB 또는 VRAM 8GB** — 트랙1 LLM 사유용 |

**필요량 실측치는 4코어 / 16GB / 50GB 다.** 신청값을 2배로 잡는 이유는 아래와 같다.

> 🔑 **이 표는 한 대에 다 올린다는 전제의 합산값이다.**
> DB 를 별도 장비로 분리한다면 **8절 D** 의 분할표를 쓴다 — 그대로 쓰면 안 된다.

### 🔑 왜 실측의 2배를 신청하는가 *(v2.6)*

이 문서는 **예산 산정과 실운영 테스트**에 쓰인다. 실측치를 그대로 신청하면
아래 항목들이 전부 여유분을 잡아먹는다 — **한 번 받은 서버는 늘리기 어렵다.**

| 여유가 필요한 곳 | 근거 |
|---|---|
| **죽은 공간(dead tuple)** | 🔴 실측: 스모크 테스트 뒤 `recipe_feature` 가 **행 3개인데 29 MB** 였다. `VACUUM FULL` 로 51 MB → 1.9 MB 로 줄었다. 재정규화가 TRUNCATE+전량재삽입이라(4-1) **이 현상이 반복된다** |
| **후기 저장** | 02 C-5 미확정. 레시피당 30건이면 **+0.83 GB** |
| **크롤 건수 변동** | ~~4.4만은 상한 추정~~ → **실적재 46,353** (09-02 완료). 재크롤 시 늘 수 있다 |
| **모델 실험** | MLflow 아티팩트 · LightGBM 모델 파일 · 임베딩 재계산본 |
| **동시 실행** | 크롤 적재 + 임베딩 배치 + 개발 서버가 겹치는 순간 |
| **8주 이후 로그 누적** | 월 350 MB (실유저 100명 기준) |

> **CPU 를 8 core 로 올리는 이유는 하나 더 있다** — 임베딩 배치가 CPU 3~6시간인데
> 코어를 2배로 하면 절반이 된다. GPU 없이 갈 것이라면 **코어가 곧 배치 시간**이다.

### 배치 목록 — "1회성" 이 아니다 *(v2.0~v2.6 누적)*

초판은 "배치는 1회성"을 전제했으나 **상시 배치가 여럿 생겼다.**
전부 CPU 수 분 이내라 **사양 산정은 바뀌지 않지만**, 운영 항목이므로 9절에 cron 으로 남긴다.

| 배치 | 주기 | 비용 | 근거 |
|---|---|---|---|
| ko-SBERT 임베딩 | 신규 레시피 발생 시 | 4.4만 건 CPU 3~6h / GPU·MPS 20~45분 | 6-4-3 |
| **k-means K≈50 (S-A)** | 주 1회 | 분 단위 | 5-3-5 · 04 |
| `user_cluster_stat` 갱신 (S-B) | 시간당 | 초 단위 | 5-3-5 |
| **`flavor_vec` 산출** *(v2.5)* | 신규 레시피 발생 시 | 재료 조회 + 집계, 초~분 | 2-5-1 ⑤ |
| **맛 코퍼스 평균 μ** *(v2.6)* | `flavor_vec` 재계산 시 | 초 | 2-5-1 ⑤ (중심화) |
| `freq_count` / IDF | 주 1회 | 분 단위 | 6-4-3-1 |
| 정규화 P1~P4 | 크롤 적재 시 | 300만 행 · 사전은 메모리 상주 | ④ |
| Bradley-Terry 가중치 학습 | 쌍대비교 수집 후 | **초 단위** (파라미터 5~12) | 5-2-5 |
| LightGBM v1 | 조건부 (라벨 확보 시) | 분 단위 | 5-2-6 |
| **트랙1 Top-N 사전계산** *(v3.0 · D-19)* | **매일 새벽** | 유저 100명 · 초 단위 | 9절 · `daily_recommendation` |
| **트랙1 LLM 사유 생성** *(v2.7)* | **매일 새벽** | 유저 100명 Top-18 · 약 30분 | 5-6 · 🔴 **RAM 7.64 GB 피크** |

> 🔴 **`flavor_vec` 과 μ 는 짝이다.** 레시피가 추가되면 μ 가 변하고, 그러면 과거 `f_taste`
> 값과 달라진다. **μ 를 로그에 함께 남겨야 재현된다** (07 E-3 ⑧ 와 같은 성격).

> 🔴 **GPU 는 없어도 된다.** 두 가지 이유가 겹친다.
>
> 1. **추천 서비스(실시간)는 GPU 를 쓸 일이 없다.** 연산량이 작아 GPU 로 보내는
>    전송 오버헤드가 계산보다 크다 — **CPU 가 실제로 더 빠르다** (5절).
> 2. **GPU 학습을 하지 않는다.** ko-SBERT 는 남이 학습시킨 것을 **추론**에만 쓴다.
>    *(v2.1 정정)* CPU 소규모 학습은 **한다** — Bradley-Terry(파라미터 11, 초 단위) ·
>    LightGBM(분 단위) · k-means K≈50 · (조건부) ALS. 전부 CPU 로 수 분 내 작업이라
>    GPU 판단은 바뀌지 않는다.
> 근거는 [`03_모델_선정_사유.md`](03_모델_선정_사유.md) 4절 —
> Two-Tower 파라미터 70만 개는 fp32 로 2.8MB 이고, **부족한 것은 VRAM 이 아니라 데이터**다
> (필요 유저 3.2만 명 vs 확보 가능 100명). GPU 를 "딥러닝 학습용"으로 신청하면
> 실제 용도와 어긋난다.

## 1-0. 🔑 샘플 실측 기반 DB 산정 *(v2.6 · 크롤 샘플 3건)*

> ⚠️ **먼저 정정한다.** 개발 DB 가 한때 59 MB 였으나 그것은 **레시피 건수와 무관**했다 —
> 스모크 테스트(합성 5만~20만 건)가 남긴 **죽은 공간**이었고, `VACUUM FULL` 후
> **recodb 10 MB · reco 스키마 1.9 MB** 다. 시드만 든 상태의 실제 크기다.

크롤 샘플 3건(`tests/fixtures/real/`)에서 행당 크기를 실측해 4.4만 건으로 투영했다.

> ⚠️ **이 문서 전체에서 "4.4만"은 산정 당시의 추정 건수다. 실적재는 46,353건이다.**
> 차이 5.3% 만큼 아래 투영치가 **낮게 잡혀 있다** — 보수적인 방향이 아니라 낙관적인 방향이라
> 인용할 때 주의한다. 다시 계산하면 테이블 합계 0.34 → **0.36 GB**, 총계 0.48 → **0.51 GB** 다.
> **판단이 바뀌는 크기가 아니라 표를 다시 그리지 않았다.**
> 반면 **본문 크롤분은 추정이 아니라 실측 507 MB** 다 (0절) — 이쪽이 정본이다.

**샘플 실측** — JSON 평균 2,001 B · `raw_json` 압축 **1,876 B** · 재료 **11.3개** · 조리단계 3.3개

#### `maintenance_work_mem` 은 전역이 아니라 세션에서 올린다

HNSW 인덱스는 그래프가 `maintenance_work_mem` 안에서 만들어진다.

> 문서에 없어 **미확인**이고, 확인 전에 안전장치를 걷어낼 이유가 없다.
그래서 전역은 256 MB 로 두고 `deploy/init/post_index.sql` 이 세션 단위로만 올린다:

```sql
SET maintenance_work_mem = '1GB';
SET max_parallel_maintenance_workers = 3;   -- 리더 포함 4 프로세스 → CPU 4 core
CREATE INDEX ... USING hnsw ...;
```

| 역할 | `statement_timeout` | `idle_in_transaction` | `lock_timeout` |
|---|---|---|---|
| `reco_app` (온라인) | **5s** — 실측 p95 30ms 대비 관대 | 30s | — |
| `reco_batch` (배치) | **없음** — 적재·인덱스가 길다 | **60s** | 10s |
| `reco_ro` (대시보드) | 30s | 30s | — |

> 원격 TCP 는 서버가 세션 사망을 모르고 OS 기본 **7200초**를 기다린다.
> `tcp_keepalives_idle=60` 과 이 설정이 함께 그 창을 막는다.

# 5. GPU — 온라인은 없어도 된다 *(v2.7 정정)*

> **v2.6 까지 이 절의 제목은 "GPU — 없어도 된다" 였다.**
> 추천이 2트랙으로 나뉘면서(`01` 5-6-1) **트랙 1 의 LLM 사유 생성이 GPU 를 쓴다.**
> 다만 **배치 전용**이고, 유저 100명 규모에서는 **개발 노트북으로 충분하다** — 5-6 참조.
> 온라인 추천 경로가 GPU 를 쓰지 않는다는 결론은 그대로다.

## 5-1. 온라인 추천은 CPU 가 **더 빠르다**

GPU 가 유리하려면 **두 조건**이 모두 필요하다.

| 조건 | 우리 온라인 경로 |
|---|---|
| ① 연산이 **행렬곱** 구조여야 한다 | ❌ 선형 가중합 · 트리 분기 — **신경망이 아니다** |
| ② 연산이 **대량**이어야 한다 | ❌ 후보 500 × 피처 17 ≈ **17,000 회** |

```
CPU 연산 시간              수 μs
GPU 로 데이터 보내는 시간만  수십~수백 μs   ← 계산보다 전송이 오래 걸린다
```

**LightGBM(v1) 도 마찬가지다.** 트리 모델은 조건 분기의 연속인데 GPU 는 분기에 약하다.
LightGBM 의 GPU 지원은 **학습**용이며, 추론은 CPU 가 빠르다 (500건 1ms 미만).

> 설계 1-4 는 **가용성** 때문에 "온라인 경로 GPU 의존 금지"를 정했다.
> 성능 관점에서도 같은 결론이 나온다.

## 5-2. 배치 임베딩은 GPU 가 10~20배 빠르다

여기는 조건 ①②가 모두 성립한다 — Transformer 는 행렬곱이고, 4.4만 건은 대량이다.

| | 연산량 (대략) |
|---|---|
| **ko-SBERT 문서 1건** | **약 44 GFLOPs** (파라미터 1억 × 토큰 200) |
| 우리 랭킹 500건 전체 | 약 17 KFLOPs |

**약 260만 배 차이**다.

| 레시피 수 | GPU | CPU |
|---|---|---|
| 1만 | 약 2분 | 20~40분 |
| 4.4만 | 약 40분 | 3~6시간 |

**그래도 없어도 된다** — 초기 1회성 작업이고, 밤에 CPU 로 돌려두면 된다.

## 5-3. 학습에는 아예 쓰지 않는다

|---|---|---|
| **Bradley-Terry 가중치 학습** *(v2.5)* | ❌ | 파라미터 5~12. **CPU 초 단위** (5-2-5) |
| LightGBM LambdaRank | ❌ | CPU 수 초 |
| **k-means K≈50** *(v2.0)* | ❌ | CPU 분 단위 |

# 7. 네트워크 (원격 DB 사용 시)

| 항목 | 값 |
|---|---|
| 쿼리당 응답 | 약 25 KB (후보 500 × 50B) |
| 요청당 왕복 | **1회** — `retrieve_for_user()` 로 감쌈 |
| 8주 총 전송량 | 약 50 MB |
| 교내망 RTT | 0.5~2 ms 예상 |

**대역폭은 문제가 아니다.** 문제는 왕복 횟수다.

> 🔴 애플리케이션에서 스테이지마다 DB 를 따로 조회하도록 리팩터링하면
> **왕복 횟수만큼 RTT 가 곱해진다.** 원격 DB 에서는 "함수로 감싸 1왕복" 원칙(설계 1-7)이
> 로컬일 때보다 훨씬 중요하다.

## 🔑 그래서 분리해도 지연은 거의 그대로다 *(v2.7)*

```
in-DB retrieve_for_user()    13.2ms    ← DB 가 하는 일
Python 왕복 포함 p95         30.2ms
                             ─────
                             약 17ms    ← localhost 에서도 나는 오버헤드
```

**17ms 는 DB 가 같은 기계에 있어도 발생한다.** 원격이면 RTT 0.5~2ms 가 더해져
**약 32ms** 다. 목표 300ms 에서 무의미하다. 사양 분할은 **8절 D** 참조.

## 배치의 대량 전송은 다르다 *(v2.7)*

온라인은 요청당 25KB 지만 **배치는 다르다.**
임베딩 적재 시 ~~4.4만 × 3,080 B ≈ 690 MB~~ → **46,353 × 3,080 B ≈ 143 MB** 가 네트워크를 탄다.

> 🔴 **09-03 정정 — 690 MB 는 산수가 안 맞았다.** `44,000 × 3,080 B = 135 MB` 다.
> 690 MB 는 23만 건 전제(`230,000 × 3,080 = 708 MB`)의 잔재가 레시피 수만 바뀐 채 남은 것이다.

교내망에서 대역폭은 문제가 아니지만 `COPY` 성능이 로컬보다 떨어진다.
**적재는 크롤 시점 1회성**이므로 감수할 수 있다.

## D. DB · AI 서버 분리 *(v2.7 신규)*

C 는 "같은 인스턴스를 공유"하는 경우고, 여기는 **DB 가 물리적으로 다른 장비**인 경우다.
0절 표는 한 대에 다 올린다는 전제의 **합산값**이므로 그대로 쓰면 안 된다.

### 🔑 먼저 — 성능은 사실상 달라지지 않는다

Retrieval 30.2ms 의 내역이 이것을 말해준다 (2-12 실측):

```
in-DB retrieve_for_user()    13.2ms   ← DB 가 하는 일
Python 왕복 포함 p95         30.2ms
                             ─────
                             약 17ms   ← localhost 에서도 나는 드라이버·직렬화 오버헤드
```

**17ms 는 DB 가 같은 기계에 있어도 발생한다.** 원격이 되면 여기에 교내망 RTT
0.5~2ms 가 더해질 뿐이라 **약 32ms** 다. 목표 300ms 에서 무의미한 차이다.

> 🔴 **단, "요청당 왕복 1회" 원칙(1-7)이 지켜질 때만이다.**
> `retrieve_for_user()` 로 감싸 1회로 만들어 뒀는데, 나중에 스테이지마다 따로
> 조회하도록 리팩터링하면 **RTT 가 왕복 횟수만큼 곱해진다.**
> 로컬에서는 티가 안 나던 것이 원격에서는 바로 드러난다. 7절 참조.

### DB 서버 — 최소 · 권장 · 여유 *(레시피 46,353 기준)*

| | **최소** (동작은 함) | **권장** (신청값) | **여유** (있으면 좋음) |
|---|---|---|---|
| CPU | 2 core | **4 core** | 8 core |
| RAM | 4 GB | **8 GB** | 16 GB |
| 디스크 | 20 GB | **50 GB** | 100 GB |
| `shared_buffers` | 512 MB | **2 GB** | 4 GB |
| `maintenance_work_mem` (전역) | 128 MB | **256 MB** | 512 MB |
| 〃 (인덱스 생성 세션) | 512 MB | **1 GB** | 2 GB |
| `effective_cache_size` | 2 GB | **4 GB** | 12 GB |
| GPU | 불필요 | 불필요 | **불필요** (pgvector 는 CPU) |

레시피 **1만** 시나리오면 한 단계씩 내려도 된다 (디스크 1.7 GB · `shared_buffers` 512 MB).

#### 각 단계가 무엇을 의미하는가

> 🔴 **09-03 정정 — 아래 표의 1,013 MB · 676 MB 는 23만 건 전제의 잔재다.**
> 2절이 이미 46,353건에서 **임베딩 129 MB · HNSW 194 MB** 로 다시 계산했는데
> 이 표만 옛 값을 붙들고 있었다. 값이 5배 다르면 **권장 사양의 근거 자체가 달라진다.**

| 단계 | 무엇이 달라지는가 *(46,353건 기준)* |
|---|---|
| **최소** (`shared_buffers` 512 MB) | 돌아간다. 벡터 전량(임베딩 129 + HNSW 194 = **323 MB**)이 이미 들어가므로, ~~"HNSW 가 캐시에 다 안 올라간다"~~ 는 **더 이상 사실이 아니다.** 밀리는 것은 `recipe`·`recipe_review` 쪽이다 |
| **권장** (2 GB) | `recipe_feature` 전체 + 벡터 + 자주 읽는 `recipe` 까지 상주한다. 쿼리당 워킹셋 실측 42 MB 가 넉넉히 들어간다 |
| **여유** (4 GB) | `reco` 스키마 **전량(실측 497 MB + 임베딩 투영)** 이 메모리에 상주한다 |

> 🔑 **그래서 `shared_buffers` 권장을 2 GB 로 유지하는 근거가 바뀌었다.**
> 이전 근거는 "벡터 1.7 GB 를 담기 위해"였다. 지금 근거는 **"`recipe`(160 MB) +
> `recipe_review`(186 MB) + 벡터(323 MB) + 인덱스가 함께 도는 배치 창"** 이다.
> **1 GB 로 내려도 온라인 서빙은 문제없다** — 실측 워킹셋이 쿼리당 42 MB 다.

##### 🔴 CPU 2 core 로는 HNSW 인덱스 생성이 제 속도가 안 난다

pgvector 의 HNSW 병렬 빌드는 **리더 + `max_parallel_maintenance_workers`** 만큼 프로세스를 쓴다.
현재 실행 중인 DB 실측값이 `max_parallel_maintenance_workers = 2` 이므로 **3 프로세스**다.
2 core 면 기본값조차 못 채운다. **권장 4 core 는 여기서 나온 값이다.**

##### 🔴 `maintenance_work_mem` 은 전역이 아니라 세션에서 올린다

HNSW 그래프는 `maintenance_work_mem` 안에서 만들어지고, 넘치면 훨씬 느린 on-disk 경로로
간다. 필요량은 대략 **최종 인덱스 크기** = ~~1,013 MB~~ → **194 MB** (2절 · 46,353건 투영)다.

> 🔴 **그러면 전역 256 MB 로 충분한 것 아닌가?** 산술적으로는 그렇다.
> **그래도 세션 설정을 걷어내지 않는다** — 인덱스 **빌드 중 피크 메모리가 최종 크기와
> 같은지가 확인되지 않았고**(pgvector 문서에 없다), 확인 전에 안전장치를 빼면
> 실패가 조용히 on-disk 경로로 나타난다(느려질 뿐 에러가 안 난다).
> 3절의 같은 항목과 판단을 일치시킨 것이다.

그런데 **전역을 1 GB 로 잡으면 autovacuum 워커마다 물린다** (기본 3워커 = 최대 3 GB).
그래서 전역은 256 MB 로 두고 **`deploy/init/post_index.sql` 이 세션 단위로만 올린다** — 반영 완료:

```sql
SET maintenance_work_mem = '1GB';
SET max_parallel_maintenance_workers = 3;   -- 리더 포함 4 프로세스
CREATE INDEX ... USING hnsw ...;
```

> 🔴 **디스크 최소 20 GB 는 빠듯하다.** 데이터가 ~~7.8 GB~~ → **약 1.3 GB** 로 줄었지만
> **권고는 바뀌지 않는다** — 얹히는 것이 데이터가 아니기 때문이다:
> 인덱스 재빌드 중 임시 공간 · WAL 버스트 · `pg_dump` 사본(압축 약 0.3 GB × 3일) ·
> 재크롤 시 이중 보유. **50 GB 를 권한다.**

### 🔑 임베딩 벡터는 어디에 있나 — 별도 벡터 DB 가 없다

**`reco` 스키마 안, PostgreSQL + `pgvector` 다.** Milvus·Qdrant 같은 별도 벡터 DB 를
쓰지 않는다. 따라서 **분리하면 벡터도 전부 DB 서버로 간다.**

| 위치 | 내용 | 46,353 기준 크기 | 인덱스 |
|---|---|---|---|
| `reco.recipe_feature.content_emb` | 레시피 임베딩 (제목+재료+카테고리) | ~~676 MB~~ → **136 MB** *(46,353 × 3,080 B)* | HNSW `idx_rf_emb` — ~~1,013 MB~~ → **약 200 MB** |
| `reco.ingredient.embedding` | 재료 임베딩 (정규화 `MatchMethod.EMBED` 용) | 재료 사전 포함 16 MB | HNSW `idx_ing_emb` |
| `reco.user_vector.content_emb` | 유저 임베딩 (좋아한 레시피 가중평균) | 유저 100명 = **0.3 MB** | **없음** — `user_id` PK 조회라 불필요 |

```
확장은 public, 테이블은 reco  (deploy/init/01_extensions.sql · 02_schema.sql)
  CREATE EXTENSION vector SCHEMA public;
  SET search_path TO reco, public;
```

~~**벡터 합계 약 1.7 GB 로 DB 디스크의 절반 가까이를 차지한다**~~
→ **벡터 합계 약 0.34 GB** (46,353건 투영). DB 순수 데이터 0.66 GB 의 절반이다 —
**비율은 여전히 절반이지만 절대량이 5배 작다.**
`vector(768)` 행당 3,080 B (`768 × 4 + 8`) 이므로 fp32 다. **이 행당 크기만 실측이고
합계는 투영이다** — `recipe_feature` 는 09-03 현재 **0행**이다.

> 🔴 **HNSW 인덱스는 대량 적재 후에 만든다** (9절 · `deploy/init/post_index.sql`).
> 빈 테이블에 만들면 INSERT 마다 느려진다. `make post-index` 로 분리해 뒀다.
> 생성에는 `maintenance_work_mem` 이 필요하니 **DB 서버 RAM 이 여기서도 쓰인다.**

> ⚠️ **분리 시 임베딩 적재가 네트워크를 탄다.** ko-SBERT 는 AI 서버(또는 GPU)에서
> 돌고 결과 **약 143 MB**(46,353 × 3,080 B)를 DB 로 보낸다. 크롤 시점 1회성이라
> 감수 가능하다 (7절). *(이전 판의 690 MB 는 23만 건 전제였다.)*

### AI 서버 — 최소 · 권장 · 여유

| | **최소** (동작은 함) | **권장** (신청값) | **여유** (있으면 좋음) |
|---|---|---|---|
| CPU | 4 core | **8 core** | 16 core |
| RAM | 8 GB | **16 GB** | 32 GB |
| 디스크 | 30 GB | **50 GB** | 100 GB |
| GPU | 없음 | 없어도 됨 | **통합 16GB / VRAM 8GB** |

디스크 내역(실측 필요 약 20.6 GB): 컨테이너 이미지 · **LLM 모델 blob 7.15 GB** ·
`/artifacts` 모델 버전 · venv · 크롤 원본 · 로그 · 빌드 캐시 · **`pg_dump` 사본**.
30 GB 로는 덤프 사본을 둘 자리가 빠듯하다.

#### 각 단계가 무엇을 의미하는가

| 단계 | 무엇이 달라지는가 |
|---|---|
| **최소** | 서빙과 경량 배치는 된다. 🔴 **트랙1 LLM 사유 생성이 안 된다** — 모델만 7.64 GB 라 8 GB 에 안 들어간다. 사유 생성은 개발 노트북에서 돌려야 한다 |
| **권장** | 배치 창 피크 11.3 GB 가 들어간다 (평시 1.2 + torch 2 + **LLM 7.64**). 단 **ko-SBERT 와 LLM 배치를 겹치지 않게** 스케줄해야 한다 |
| **여유** | 두 배치가 겹쳐도(13.3 GB) 버틴다. GPU 가 있으면 임베딩 3~6시간 → 40분, 사유 생성 30분 → 더 짧아진다 |

### 두 대 합산 — 한 대일 때와 비교

| | 한 대 (8절 B) | DB 서버 | AI 서버 | 분리 합계 |
|---|---|---|---|---|
| CPU | 8 core | 4 | 8 | **12 core** |
| RAM | 32 GB | 8 | 16 | **24 GB** |
| 디스크 | 100 GB | 50 | 50 | **100 GB** |

**CPU 는 늘고(8→12) RAM 은 줄며(32→24) 디스크는 같다(100).**
코어가 느는 것은 장비마다 OS 와 여유를 따로 가져야 하기 때문이고,
RAM 이 주는 것은 한 대일 때 잡아둔 공용 여유가 쪼개지기 때문이다.
디스크는 **`pg_dump` 사본을 양쪽에 두면서** 줄어들 여지가 없어진다.

#### 근거

**DB 서버**
- `shared_buffers` 2 GB + 커넥션 50×10MB 500 MB + OS page cache
- **쿼리당 워킹셋 실측 42 MB** (버퍼 5,437 × 8KB) — `shared_buffers` 2GB 에 넉넉히 담긴다
- 디스크: 데이터 ~~3.9 GB → 7.8 GB~~ → **0.66 GB → 여유 ×2 = 약 1.3 GB** (2절) + 인덱스 재빌드 임시공간 + `pg_dump` 사본
- CPU: 온라인 쿼리는 13.2ms 로 가볍다. **HNSW 인덱스 생성이 가장 무겁다**
- **GPU 를 넣지 말 것.** pgvector 연산은 CPU 다

**AI 서버**
- Redis 512 MB + reco-api 300 MB + dashboard 400 MB = 평시 1.2 GB
- **+ 배치 창 피크**: ko-SBERT(torch) 약 2 GB · **LLM 7.64 GB** (5-6)
- 디스크: 컨테이너 이미지 4.3 GB + **LLM 모델 6.66 GiB** + `/artifacts` + MLflow + 로그
- CPU: 8 core 를 신청하는 이유는 여전히 **배치**다 (4절). DB 분리로 줄지 않는다

### 🔴 LLM 은 상주시키지 않는다 — 배치 창에만 올린다

콜드 로드 **5.46s** · 웜 0.44s 실측. 30분 배치에서 5.46초는 **0.3%** 다.

따라서 7.64 GB 는 **평시 RAM 이 아니라 새벽 배치 창의 피크**다.
온라인 경로는 트랙2 = 템플릿이라 LLM 을 아예 쓰지 않는다 (`01` 5-6-1).

> ⚠️ **ko-SBERT 배치와 겹치면 피크가 합산된다** (2 + 7.64 ≈ 9.6 GB).
> 9절 cron 에서 **순서를 갈라야** RAM 신청값을 16 GB 로 유지할 수 있다.

### 분리하면 새로 생기는 것

한 대일 때는 없었던 항목만 적는다. **v2.7 에서 ①⑧ 은 고쳤다.**

| | 항목 | 왜 한 대일 때는 없었나 | 상태 |
|---|---|---|---|
| ① | **타임아웃 3종** | 유닉스 소켓은 클라이언트가 죽으면 **커널이 즉시 소켓을 닫는다.** TCP 는 서버가 세션 사망을 모르고 OS 기본 **7200초**를 기다린다. 그동안 `TRUNCATE` 의 ACCESS EXCLUSIVE 락이 유지되고, 열린 트랜잭션의 xmin 이 **인스턴스 전체 autovacuum 을 멈춘다** | ✅ **해결** — `05_roles.sql` 역할 단위 타임아웃 + `tcp_keepalives_idle=60` (3절) |
| ② | **인증 · 암호화 · 바인딩** | 한 대일 때는 전부 `localhost` 안이라 안 터졌다. 현재 `docker-compose.yml` 은 `POSTGRES_PASSWORD:-reco` **기본값**을 쓰고 포트를 0.0.0.0 에 연다. Redis 에 `requirepass` 가 없고, Grafana 데이터소스는 `sslmode: disable` 이다 | 🔴 **미해결** — 원격 전에 반드시. `.env` 분리 + `scram-sha-256` + `sslmode=require` + 출발지 IP 제한 |
| ③ | **DB 다운 시 폴백이 없다** | 한 대에서 "DB 다운"과 "앱 다운"은 **같은 사건**이었다. 분리하면 독립 사건이 되는데, `01` 1-5 상 PG 가 SoT 이고 Redis 는 순수 캐시라 대신할 수 없다. `retrieve_for_user()` 자체가 PG 함수다 | 🔴 **미해결** — 설계 결정 필요 (02 I-17) |
| ④ | **커넥션 풀링이 선택 → 필수** | 원격 접속 수립 = TCP 3-way + PG 스타트업 + SCRAM + TLS ≈ **커넥션당 5~10 ms**. 유닉스 소켓은 ~0.1 ms 였다. 7절 표는 **쿼리 왕복만 세고 접속 왕복을 안 셌다** | 🟡 원격 결정 시 |
| ⑤ | **적재는 `COPY (FORMAT BINARY)` 로** | 로컬에서는 포맷 차이가 안 보였다. `vector(768)` 을 **텍스트로 보내면 행당 약 9 KB → 46,353건 약 417 MB**, 바이너리면 3,080 B → **143 MB**. 🔴 *(09-03 — 이전 판의 2 GB/708 MB 는 23만 건 전제였다.)* 비용은 대역폭이 아니라 **양쪽 CPU 와 WAL** 이다 | 🟡 크롤 적재기 작성 시 |
| ⑥ | **"왕복 1회" 회귀를 탐지할 수단** | 로컬 소켓 RTT ≈ 0.05 ms 라 **1왕복이 30왕복으로 회귀해도 노트북에서 1.5 ms 늘 뿐 아무도 못 본다.** 원격에서만 드러난다 | 🟡 계약 테스트에 왕복 수 단언 |
| ⑦ | **백업의 낙하 지점** | 한 대일 때는 "어느 디스크"가 질문이 아니었다. 압축 덤프 약 1.2~1.5 GB × 3일을 어디에 둘지 정해야 한다 (AI 디스크 50 GB 의 근거) | 🟡 미해결 |
| ⑧ | **원격 스키마 적용 경로** | 컨테이너 `initdb.d` 자동 실행이 없다. `apply_schema.sh` 가 `00_databases.sql` 을 **조용히** 건너뛰어 `mlflowdb` 가 안 생기고, MLflow 가 테이블 15개를 `reco` 에 만든다 (`01` 1-6) | ✅ **완화** — 스크립트가 이제 경고하고 대안 2가지를 안내한다 |
| ⑨ | **트랙1 사유 저장 협의** | `01` 1-5 가 PostgreSQL 을 SoT 로 못 박아 사유가 DB 에 들어간다. 공유 DB 면 소유자와 스키마 협의 대상 | 🟡 02 I-16 |

### 개발 환경은 여전히 한 대다

시나리오 A(개발 노트북)는 `make up` 으로 postgres + redis 를 같이 띄운다.
**개발은 한 대, 운영은 두 대**가 되므로 접속 설정이 환경별로 갈린다 —
설계 1-7 의 스키마·역할 분리를 그대로 쓰되 **호스트만 환경변수로 분리**하면 된다.

## 🔴 적재 멱등성 — **실제로 데이터가 2배가 됐다** *(09-02)*

```
제약 이전   적재 2회 → recipe_ingredient_raw  451,862 → 903,724   (전량 2배)
제약 이후   UNIQUE (recipe_id, position)                          ← 2회차가 충돌한다
            recipe_review UNIQUE NULLS NOT DISTINCT (recipe_id, author_hash, written_at)
```

**에러가 나지 않고 조용히 늘어난다.** 그리고 그 위에서 계산한 인기도(`review_count` 기반) ·
재료 커버리지 · `freq_count` 가 전부 틀리는데, 값이 그럴듯해서 아무도 눈치채지 못한다.

> 🔴 **`NULLS NOT DISTINCT` 가 없으면 후기 멱등이 깨진다.** PostgreSQL 의 기본 UNIQUE 는
> NULL 을 서로 다른 값으로 보므로, `author_hash` 나 `written_at` 이 NULL 인 후기는
> **몇 번을 넣어도 매번 새 행**이 된다. 크롤 후기의 상당수가 그 형태다.

## 🔴 `autovacuum` 확인 — 실제로 겪었다 *(v2.6)*

`recipe_ingredient` 는 재정규화마다 TRUNCATE + 전량 재삽입된다 (설계 4-1).

**실측 사례** — 스모크 테스트(합성 5만~20만 건) 뒤 개발 DB 상태:

```
VACUUM FULL 전   recodb 59 MB   recipe_feature 29 MB (행 3개)  recipe 20 MB (행 3개)
VACUUM FULL 후   recodb 10 MB   reco 스키마 1.9 MB
```

**행이 3개인 테이블이 29 MB 였다.** autovacuum 이 회수하지 못한 상태였고,
그 59 MB 를 "레시피 데이터 크기"로 오독할 뻔했다.

### 🔴 원인 정정 — `TRUNCATE` 가 아니었다 *(v2.7)*

v2.6 은 이 현상을 "TRUNCATE + 전량 재삽입이 dead tuple 을 쌓는다"고 설명했다. **틀렸다.**

**`TRUNCATE` 는 dead tuple 을 만들지 않는다.** 새 relfilenode 를 할당하고 커밋 시
구 파일을 통째로 drop 하므로 autovacuum 이 회수할 것 자체가 없다.

그리고 **위 실측이 그 설명과 맞지 않는다.** 부푼 것은 `recipe_feature`(29 MB) 와
`recipe`(20 MB) 인데, TRUNCATE 대상으로 지목된 `recipe_ingredient` 는 목록에 없다.

실제 원인은 **스모크 테스트를 반복 실행한 것**이다 — 실측으로 확인했다.

```
스모크 1회차 직후    recipe 0 dead · recipe_feature 0 dead    (전부 신규 INSERT)
스모크 2회차 직후    recipe 10,007 dead · recipe_feature 10,007 dead
                     recipe_ingredient 0 dead   ← TRUNCATE 대상인데 깨끗하다
```

`tests/smoke_test.py` 는 합성 레시피 1만 건을 `ON CONFLICT` 로 넣는다(`:76,85,203,212`).
두 번째 실행부터는 같은 `source_id` 와 충돌하는데, PostgreSQL 은 **투기적 삽입**을
하므로 튜플을 먼저 쓰고 충돌을 확인한 뒤 dead 로 표시한다. 그래서 **실행 1회당
약 1만 개**가 쌓인다. 원래 관측된 두 테이블이 정확히 이 두 개다.

> ✅ **따라서 이 현상은 운영에서 반복되지 않는다.** 개발 중 스모크 반복의 산물이다.
> 디스크 여유를 두는 이유는 여전히 유효하지만(인덱스 재빌드 임시공간·WAL 버스트·덤프),
> **"재정규화가 매번 테이블 크기만큼 죽은 공간을 만든다"는 근거는 철회한다.**

```sql
-- 대량 재적재 후에는 명시적으로 돌린다
VACUUM (ANALYZE) reco.recipe_ingredient, reco.recipe_feature;
```

> 🔴 **HNSW 인덱스가 생긴 뒤에는 `VACUUM FULL` 을 쓰지 말 것.**
> 회수할 것이 없는데도 **1 GB 인덱스를 ACCESS EXCLUSIVE 락 아래 단일 스레드로 재빌드**한다.
> 현재 `maintenance_work_mem` 실측값이 64 MB 라 그 재빌드는 디스크 경로로 떨어진다.
> 공유 DB(8-C)라면 남의 테이블까지 멈춘다. **`VACUUM (ANALYZE)` 로 충분하다.**

## 10-1. DB 를 분리해서 신청하는 경우 *(v2.7 신규)*

```
[요청 ①] 추천 시스템 — DB 서버
```

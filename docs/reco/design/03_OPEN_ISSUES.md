# C. 크롤러팀과 협의

크롤링이 **진행 중**이다. 실제 출력 형태를 아직 보지 못했으므로,
**어느 형태로 오든 받아낼 수 있는 어댑터 층을 먼저 만들어 두었다.**

## ✅ 준비 완료 — 확인 절차만 남았다 *(2026-08-27)*

```bash
make probe SAMPLE=경로/샘플.json
```

[`src/features/recommend/ingest/`](../src/features/recommend/ingest/) 가 크롤러 출력을 우리 스키마로 매핑한다.
**실제 JSON 이 오면 `src/features/recommend/ingest/sources/mangae.yaml` 의 `paths` 만 고치면 되고**,
`adapter.py` · DB 스키마 · 정규화 파이프라인은 건드리지 않는다.

`probe` 가 리포트하는 것:

| | |
|---|---|
| 매핑 성공 | 어느 경로에서 잡혔는지 + 실제 값 |
| **재료 그룹명 보유율** | C-1 을 자동 판정 |
| 누락 · 폴백 | 🔴 치명 / 🟡 품질 하락 / ⚪ 무시 가능 + **없으면 무엇이 나빠지는지** |

합성 샘플 3종(그룹명 있음 · 없음 · 최소)으로 어댑터 자체는 검증했다 (`make probe-all`).

> **크롤링 담당자에게는 "이 필드 주세요"가 아니라 probe 출력을 그대로 보내면 된다.**
> "없으면 무엇이 나빠지는지"가 문장으로 적혀 있다.

### 🔴 C-5. `reviews` 를 원문 그대로 수집하고 있는가 *(v2.1 신규 — 최우선)*

## ✅ 해결 — 전량 적재 확정 *(2026-09-02)*

**크롤 데이터가 도착해 협의가 불필요해졌다.** "무엇을 받을지"가 아니라
"받은 것을 어떻게 적재할지"가 됐고, 그것은 우리 결정이다.

### 실측 (46,552건 전수)

| | |
|---|---|
| 후기 있는 레시피 | **46,353 / 46,552 (99.6%)** |
| 총 후기 | **627,610건** · 레시피당 평균 13.5 (중앙값 4 · 최대 1,079) |
| 고유 작성자 | **177,875명** |
| 2개 이상 쓴 사람 | 73,465명 (41.3%) · 5개 이상 23,801명 |
| (작성자, 레시피) 쌍 | **552,144** |
| **아이템당 상호작용** | **11.86건** |

> 🔴 fixture 3건으로 추정했던 2.0건의 **6.7배**다. 극소 표본 추정이 크게 빗나갔다.

### 🔴 딥러닝 판정이 흔들린다

`03` 이 *"모든 미채택 판정의 근거는 아이템당 상호작용 한 줄"* 이라고 못 박았는데
그 숫자가 바뀌었다. 우리 유저 로그 예상치(0.091)의 **130배**다.

```
K=8    필요 16건 →  11.9건 · 1.3배 부족
K=16   필요 32건 →  11.9건 · 2.7배 부족
```

**K=8 이 손에 닿는다.** 5개 이상 쓴 23,801명만으로도 `07` E-1 의
DeepFM(8,000명)·LightGCN(5,000명) 문턱을 넘는다.

> ⚠️ **다만 후기 작성자는 우리 유저가 아니다.** 냉장고도 온보딩도 없으므로
> `item-item CF` 와 `recipe×ingredient` 는 열려도, **우리 유저에게 개인화하는
> 모델은 여전히 안 열린다.** 이 구분을 리포트에서 흐리면 안 된다.

### 적재 방식

**전량(본문 포함) + 닉네임 해시.** `recipe_review` 신설 (약 200MB).
용량은 근거가 못 된다 — `raw_json` 이 이미 원본 219MB 를 통째로 담는다.

**닉네임은 원문을 저장하지 않는다.** 동의를 받을 수 없는 제3자 정보이기 때문이다.
`HMAC-SHA256(닉네임, salt)` 앞 16hex 를 쓴다 — 복원은 불가하지만 재계산은 되므로
삭제 요청자가 닉네임을 대면 그 행을 찾을 수 있다. salt 는 `.env`.

파싱은 두 형식이 섞여 있어 정규식을 넓혔다 (**99.14%** 성공).
닉네임이 없는 0.86% 는 `author_hash NULL` 로 둔다.

### 재크롤은 불가능하다

후기는 레시피 본문과 달리 **작성자·운영자가 지우면 사라지고**, 차단 위험이 있으며,
크롤링이 크리티컬 패스라 두 번째 자리가 없다. **지금 안 넣으면 영구 소실이다.**


**실측 fixture 3건 모두 `reviews` 배열에 작성자 닉네임 + 타임스탬프 + 텍스트가 들어 있다.**

```
리뷰어A  2026-08-23 06:58:11  (후기 본문 — 저장소에 원문을 싣지 않는다)
리뷰어B  2026-08-21 19:35:47  (후기 본문 — 저장소에 원문을 싣지 않는다)
```
> 🔴 실제 닉네임·후기 원문은 여기 적지 않는다. DB 에도 `author_hash`(HMAC)만 남긴다
> (`scripts/load_recipes.py:72`). 원문은 `raw_data/` 안에만 두고 저장소 밖으로 내보내지 않는다.

이것은 **진짜 `(user, recipe)` 상호작용**이다. 그런데 현재 어댑터는
`transform: count` 로 **개수만 세고 버린다** (`src/features/recommend/ingest/sources/mangae.yaml:103`).

#### 왜 최우선인가 — 크롤링 스펙 동결은 로그 스키마 동결과 같은 무게다

4.4만 건 크롤링에서 "reviews 는 무거우니 빼자"가 한 번 내려지면
재크롤 비용 + 차단 위험 + 삭제된 후기 소실로 **사실상 소급 불가**다.
그리고 head 레시피의 후기가 수백 건이면, `03` 이 유저 수 부족으로 기각한
**item-item CF·ALS 가 실유저 0명으로 열린다** (07 부록 Y C-1).

#### 🔑 요청이 아니라 **확인 한 문장**이다

`reviews` 도 **이미 수집되고 있다.** 크롤러의 진행 방식을 바꿀 것이 없다.
그리고 이것으로 열리는 item-item CF 는 **04 의 P0/P1/P2 어디에도 없는 범위 밖**이라
**8주 프로젝트에는 필수가 아니다.**

그럼에도 한 문장을 보내는 이유는 **비대칭** 때문이다.

| | |
|---|---|
| 지금 확인 | 메시지 한 줄 · 크롤링에 영향 0 |
| 나중에 필요해졌을 때 | 4.4만 건 재크롤 — 차단 위험 + 삭제된 후기 소실로 사실상 불가 |

**보낼 문장:**

> "샘플 3건 모두 `reviews` 가 2건씩 오는데 **전량인가요, 첫 페이지만인가요?**
> 그리고 **지금 주시는 필드 구성 그대로 4.4만 건 가시면 됩니다** — 바꿀 것 없습니다."

뒷문장이 실은 더 중요하다 — "후기는 무거우니 빼자"는 판단이 **나중에 조용히 내려지는 것**을 막는다.

- 닉네임은 개인정보다 — 적재 시 **가명화(해시) 규칙**을 A 절 동의 항목과 함께 정한다 (A-5)

**필요한 답** — 예상 완료일 + 예상 레시피 수 + 중간 스냅샷 제공 가능 여부

**제안** — 전량 완료를 기다리지 말고 **1만 건 스냅샷을 먼저** 받는다. 정규화 파이프라인
개발과 커버리지 1차 측정에는 그 정도면 충분하다.

# B. 백엔드팀과 협의

### 🔴 B-1. `public` 스키마를 쓰지 않기로 합의

**이슈**
AI 파트 테이블은 `reco` 스키마에 있다. 그런데 테이블 이름이 이렇다.

```
recipe   app_user   event_log   ingredient
```

**극도로 일반적인 이름들**이라 백엔드팀이 `public` 에 `recipe` 를 만들면 충돌한다.

**결정 안 하면** — 양쪽 다 깨진다. 나중에 옮기면 테이블 + 모든 쿼리 + 함수 + 뷰를 전부 수정.

**제안**
```
recodb
├── reco     ← AI 파트 (우리가 생성. 완료)
├── app      ← 백엔드팀 (백엔드팀이 생성. 이름은 협의)
└── public   ← 확장만. 어느 팀도 테이블을 만들지 않는다
```

**주의** — `app` 스키마는 **우리가 만들지 않았다.** 백엔드팀이 직접 만들어야 한다.

---

### 🔴 B-2. 확장은 `public` 한 곳에만 설치

**이슈**
`vector` · `intarray` · `pg_trgm` · `ltree` 를 스키마마다 따로 설치하면
**타입이 스키마별로 달라져 조인·비교가 실패한다.**

**제안** — 확장 설치는 `public` 에만. `search_path` 에 `public` 을 항상 포함.
누가 설치하든 `CREATE EXTENSION ... SCHEMA public` 을 지킨다.

---

### 🟡 B-3. 역할 이름 규칙 — 스키마로 격리되지 않는다

**이슈**
역할(`ROLE`)은 **클러스터 전역**이다. 스키마 분리로 격리되지 않는다.

우리가 쓰는 이름: `reco_app` · `reco_batch` · `reco_ro`

**제안** — 파트 접두어를 강제한다 (`reco_*` / `app_*`). DB 관리자가 이름 대장을 관리.

---

### 🟡 B-4. 유저 계정을 어떻게 연결할 것인가

**이슈**
AI 파트에 `reco.app_user` 가 있고, 백엔드팀에도 유저 테이블이 생길 것이다.
같은 사람인데 두 곳에 있으면 어느 쪽이 SoT 인가?

**선택지**

| 안 | 내용 | 장단 |
|---|---|---|
| ① 완전 분리 | AI 파트는 자체 유저(팀원 + 시뮬)만. 연결 안 함 | 단순. 실서비스 연동 시 재작업 |
| ② FK 참조 | `reco.app_user.external_id` → 백엔드 유저 ID | 연동 쉬움. 백엔드 스키마에 의존 |
| ③ 백엔드 유저 직접 사용 | `reco.app_user` 폐기 | 시뮬 유저(`is_simulated`)를 둘 곳이 없어짐 |

**제안 — ①로 시작하고 `external_id` 컬럼만 미리 뚫어둔다 (②로 가는 문).**
현재 범위에 유저 앱이 없으므로(설계 0-2) 지금 연동할 이유가 없다. 다만 컬럼 하나
추가는 비용이 0이고, 나중에 필요해지면 소급이 어렵다.

**주의** — ③은 안 된다. `is_simulated` 로 시뮬 유저를 격리하는 구조가 무너진다 (설계 2-5).

## ✅ 해결 방향 확정 — **대표 레시피 선택형** *(2026-08-27)*

문항을 늘리는 대신 **"이 중에 좋아하는 요리를 고르세요"** 방식을 쓴다.

```
레시피 전체 → 임베딩 클러스터링 K=20 → 각 클러스터 대표 1개
  ↓
설문에서 20개 제시 → 유저가 3~5개 선택
  ↓
선택한 레시피들의 flavor_vec 평균 = 유저 taste_vec (6축 전부)
```

| | 척도 문항 방식 | **대표 레시피 선택형** |
|---|---|---|
| 6축 커버 | ❌ 3축만 | ✅ **전부** |
| 문항 수 | 6개 이상 필요 | **1개** |

### ✅ pantry 소진/폐기 1비트 — 확정 *(2026-09-02 · S0 ⑤)*

**"다 썼어요" 와 "상해서 버렸어요" 는 부호가 반대인 신호다.** 합치면 영원히 못 나눈다.
소비기한 낭비율 · `shelf_life_days` 추정 검증 · 재료 소진 시퀀스가 전부 여기 달려 있다.

#### UI — 행별 버튼 2개 + 축소 모달

삭제 버튼을 **"다 썼어요" / "버렸어요"** 둘로 나눈다. **추가 클릭이 0** 이다 —
어차피 눌러야 하는 버튼이 두 개인 것뿐이다. 라벨률 85% 추정.

전체 교체(`PUT`)로 조용히 사라진 건은 저장 후 **1회 모달**로 묻고,
건너뛰기 1클릭을 둔다. 병목은 구현이 아니라 마찰이다.

#### 🔴 사유를 3값으로 — 2값이면 NULL 이 두 가지를 뜻한다

```
NULL      물어보지 않았다 (버튼 없던 시절 · 조용히 사라진 건)
unknown   물었는데 유저가 건너뛰었다
consumed / discarded
```

스킵이 **폐기 쪽에 몰리면**(버린 걸 밝히기 싫어서) MNAR 이라,
이 둘을 못 가르면 **낭비율의 상한·하한조차 못 낸다.** 지금은 공짜, 나중은 소급 불가.

#### API — UI 방식을 서버가 알지 않는다

`PUT /v1/users/{id}/pantry` 바디에 선택 키 하나만 더한다.

```
removed: [{ingredient_id, reason}]
```

**버튼으로 받든 모달로 받든 클라이언트 사정이고 서버는 사유만 받는다.**
그래야 UI 를 바꿔도 API 가 안 바뀐다. 새 엔드포인트는 표면을 늘리고,
`POST /v1/events` 우회는 `event_log` 에 `ingredient_id` 가 없어 불가능하다.

#### 기대치는 낮게

유저 100명 × 8주면 **약 600건**, 폐기 20% 면 **120~140건**.
**피처가 아니라 검증 지표다** — 전체 낭비율 하나(±3%p)는 나오지만
재료 536종별 검증은 안 된다.

### ✅ 개인정보 동의 — **2단 동의(C안) 확정** *(2026-09-01 · S0 ③)*

> ⚠️ **법률 자문이 아니다.** 아래는 검토용 초안이고 **제출 전 사람이 확인한다.**
> `[파기일]`·`[연락처]` 는 팀이 채운다.

#### 문구 (초안)

```
「냉장고 레시피 추천 — 참여 안내」

부트캠프 최종 프로젝트입니다. 참여하시면 닉네임, 온보딩 답(맛 선호·고른 레시피·가구원 수),
알러지·기피 재료, 냉장고에 넣고 뺀 재료와 시점, 누른 기록(클릭·저장·조리·평가)이
저장됩니다.

알러지는 건강에 관한 정보이며 추천에서 그 재료를 빼는 데만 씁니다.

목적은 추천 개선과 프로젝트 리포트뿐이고 외부에 제공하지 않습니다.
리포트에는 개인이 특정되지 않는 집계값만 싣습니다.

닉네임은 [파기일] 에 지웁니다. 남는 기록은 닉네임 없이 보관하나,
참여자가 적어 완전한 익명은 아닙니다(가명처리).

삭제는 [연락처] 로 요청하실 수 있습니다.

☐ (선택) 종료 후에도 기록을 연구 목적으로 보관하는 데 동의합니다.
```

#### 왜 2단인가

**필수를 좁혀야 100명이 모인다.** 100명은 LightGBM 이 성립하는 하한선이고,
무기한 보관을 필수로 걸면 동의율이 떨어진다.
선택 체크 하나가 **8주 이후를 연다** — 없으면 파기일에 전부 지워야 한다.

#### 🔴 "익명" 이라고 쓰지 않는다

`07` 이 **"50~100명이면 재식별이 자유롭다"** 고 못 박았고,
`recommendation_log.pantry_detail` 과 `allergy_snapshot` 이 알러지·재료 값을
로그에 복제한다. 정확한 표현은 **가명처리**다.

#### 🔴 삭제 요청은 `DELETE` 가 아니라 가명화로 처리한다

`app_user` 행을 지우면 **CASCADE 가 로그 원장까지 지운다**
(`event_log`·`recommendation_log`·`pantry_item` 전부 `ON DELETE CASCADE`).
`username` 만 가명화해야 분석 데이터가 살아남는다.

#### 스키마

`app_user.consent_at` · `consent_version` · **`consent_research BOOLEAN`**(신규).
`consent_version` 은 날짜가 아니라 **`'v1-min'`**(필수만) / **`'v1-res'`**(연구 보관까지).
어느 문구에 동의했는지가 값만 보고 판별된다.

CHECK 두 개로 모순 상태를 막는다 — 동의 없이 버전만 있거나,
동의 없이 연구 보관에 체크된 상태는 들어가지 않는다.

```
레시피 3개 + 척도 3축   0.633   42초
레시피 8개 + 척도 3축   0.737   87초      ← 이전 확정안
레시피 3개 + 척도 6축   0.787   57초      ← 더 짧고 더 좋다
```

단가가 다르다 — **레시피 1개는 9초인데 척도 1축은 5초**다.
그리고 척도는 **체계 편향을 깨는 유일한 수단**이라, 레시피를 아무리 많이 골라도
"내가 된장 감칠맛을 일관되게 높게 본다" 같은 편향은 평균으로 줄지 않는다.

**결정: 3축(매움·짠맛·단맛).** MVP 단계에서 유저에게 묻는 문항을 늘리지 않는다.
6축이 측정상 낫다는 것을 알고 고른 것이므로, 리포트에 그렇게 쓴다 —
*"성능을 알고도 MVP 범위로 3축을 택했다"* 가 *"3축이 최선이라 믿었다"* 보다 정확하다.

##### 3축이면 나머지 3축은 어디서 오나

`taste_vec` 은 `flavor_vec` 과 축을 맞춰야 하므로 **6차원 그대로**다.
매움·짠맛·단맛은 **척도 답 + 레시피 평균**을 섞고,
신맛·감칠맛·기름짐은 **레시피 평균만** 쓴다.

즉 뒤 3축은 체계 편향이 그대로 남는다 — "내가 된장 감칠맛을 일관되게 높게 본다"가
평균으로 안 줄어든다. `f_taste` 품질이 축마다 다르다는 뜻이고,
나중에 축별 기여도를 볼 때 이 비대칭을 기억해야 한다.

##### 🔴 늘릴 거면 **유저 모집 전**에 늘려야 한다

3축 → 6축은 15초짜리 변경이지만, **모집 중에 바꾸면 두 집단이 생긴다** —
먼저 온 유저는 3축, 나중 유저는 6축이라 `taste_vec` 품질이 다르다.
그러면 학습에서 두 집단을 같이 쓸 수 없고, 나눠 쓰기엔 각각 표본이 부족하다.

**결정 창은 W6(유저 모집 시작) 까지**다. 그 전에 마음이 바뀌면 싸고, 그 후엔 비싸다.

#### ✅ LLM 교차검증 — 측정 완료 *(2026-08-31 · `scripts/reco/bench/flavor_llm_agreement.py`)*

**Gemma 4 12B QAT** 를 로컬에서 돌려 수기 시드 `overrides` 33종 전량을 대조했다.
공정성을 위해 **같은 축 정의·같은 의미론**("통상 조리량 투입 시 그 축이 얼마나 서는가",
소금=[0,1,0,0,0,0] 예시 포함)을 프롬프트에 그대로 넣었다.

```
전체 MAE 0.044   중앙값 0.000   |차이|≤0.15  87.9%
```

일치도는 높다. **그러나 계통 편향이 있다:**

| | 매움 | 짠맛 | 단맛 | 신맛 | 감칠맛 | 기름짐 |
|---|---|---|---|---|---|---|
| 부호차 (LLM−수기) | **−0.011** | **+0.052** | **+0.048** | +0.020 | +0.023 | +0.023 |

전체 +0.026. LLM 이 더 높게 매긴 축 50 / 낮게 21 / 동일 127.
**짠맛·단맛을 일관되게 부풀린다** — 값을 그대로 채택하면 전 축이 올라가 변별력이 준다.

- [ ] DB 관리자가 `scram-sha-256` 을 쓰는가

#### ② 🔴 DB 다운 시 폴백이 없다

- [ ] 트랙1(오늘의 추천)은 **사전계산이라 캐시로 버틸 수 있는가** —
      사유까지 미리 만들어 두므로 Redis 에 그날치를 얹으면 읽기만으로 뜬다.

## 부록 — Docker 이미지 적재 타이밍

### 결론: **지금. 다만 `postgres` 하나만 먼저.**

**지금 해야 하는 이유 4가지**

1. **미검증 코드가 누적되고 있다.** 지금은 29테이블뿐이라 오류가 나도 원인이 명확하다.
   C(정규화 코드)·D(스켈레톤)를 더 올린 뒤 처음 실행하면 오류가 한꺼번에 터져
   **어느 층의 문제인지 분리하기 어려워진다.**

2. **`make smoke` 가 설계 자체를 검증한다.** 결정 2(staple) · 결정 3(배열 GIN) ·
   알러지 4경로가 실제로 동작하는지를 확인한다. **틀렸다면 설계를 되돌려야 하고,
   되돌리는 비용은 지금이 가장 싸다.**

3. **크롤링 완료가 크리티컬 패스다.** 데이터가 오는 순간 바로 적재해야 하는데
   그때 처음 Docker 를 설치하면 그 시간만큼 전체가 밀린다.

4. **팀 20명이 같은 환경을 쓰려면 누군가 먼저 검증해야 한다.** 각자 설치하다
   각자 다른 곳에서 막히면 그게 더 큰 비용이다.

### 비용은 작다

| | |
|---|---|
| 설치 | `brew install --cask orbstack` — 5분 |
| 이미지 | postgres 400MB · redis 40MB · grafana 400MB · mlflow 1GB |
| 첫 기동 | 1분 |

### 단계적으로 하면 더 싸다

```bash
# 1단계 — postgres + redis (약 440MB). 핵심 경로를 먼저 검증
make bootstrap          # up → seed → smoke

# 2단계 — 관측 도구. 대시보드 트랙 착수 시점에
make up-obs             # grafana + mlflow
```

**1단계만으로 스키마 · 시드 · Retrieval · 성능이 전부 검증된다.**

**MLflow 는 컨테이너가 아예 필요 없을 수도 있다.** 순수 Python 패키지이고 서버가 상태를
갖지 않으므로 `make mlflow-ui` 로 로컬에서 띄워도 같은 백엔드 DB(`mlflowdb`)를 보면
같은 실험 데이터가 보인다. 1GB 이미지를 받을 이유는 "항상 켜져 있는 공용 UI 주소"가
필요할 때뿐이다.

### 나중으로 미뤄도 되는 경우

디스크 여유가 2GB 미만이거나 교내망 정책상 이미지 pull 이 막힌 경우뿐이다.
그 경우 대안은 `brew install postgresql@16 pgvector` 후
`DATABASE_URL=... ./infra/apply_schema.sh` 인데, `pgvector` 설치가 번거로워
컨테이너 쪽이 훨씬 쉽다.

## 1. 접근과 절대 원칙

**접근 A(순수형)** 를 택했다 — LLM 없이 규칙 + 전통 ML 로 4단계를 짠다.
대안 B(Two-Tower 단일 모델)는 유저 50명으로 학습이 불가능하고 합성 데이터로 학습하면
순환 논리가 된다. C(LLM 추천기)는 비용·지연·재현성 문제에 ML 기여가 얕다.

A 의 핵심 이점은 **학습 데이터가 0건이어도 돌아가고 가중치가 곧 기여도라
설명가능성이 공짜**라는 것이다.

### 절대 원칙 넷

**① 온라인/오프라인 분리** (`01` 1-4). p95 < 300ms.
허용은 인덱스 조회·사전계산 내적·가중합, 금지는 임베딩 추론·전체 스캔·재학습·GPU 의존이다.
근거가 명확하다 — **GPU 는 배치 전용이라, 온라인이 GPU 에 의존하면 GPU 서버가 죽을 때
서비스 전체가 죽는다.**

**② 정합성 경계** (`01` 1-5). SoT 는 PostgreSQL 이다.
**Redis 에만 존재하는 데이터를 만들지 않는다** — 날아가도 배치 재실행으로 복구 가능해야 한다.
서빙 경로가 MLflow 를 조회하지 않는다. 모델은 `/artifacts` 버전 디렉터리에 두고
롤백은 심볼릭 링크 교체 한 번이다.

**③ 스키마·권한 분리** (`01` 1-7). `reco` 스키마를 쓰고 확장은 `public` 한 곳에만 설치한다
(스키마별로 설치하면 `vector`·`ltree` 타입이 갈려 조인이 실패한다).
공유 DB 에서 `ALTER DATABASE SET search_path` 를 하지 않는다.
**`reco_app` 에 TRUNCATE 권한을 주지 않는다** — 재정규화가 TRUNCATE 기반이라
버그 하나로 크롤링 데이터가 전멸한다.

> 🔴 **`ALTER DATABASE ... SET timezone` 은 예외로 한다 (09-03).** 금지 대상은
> `search_path` 다 — 그건 백엔드팀 쿼리가 **어느 스키마를 보는지**를 바꿔 놓는다.
> 시간대는 반대로 **DATABASE 수준이어야만** 맞는다: 컨테이너 `TZ`/`PGTZ` 는 컨테이너 안에서만
> 유효하고 **밖에서 붙는 psycopg2 연결에는 적용되지 않는다**(09-03 실측).
> UTC 로 두면 한국 자정~오전 9시에 `current_date` 가 하루 전이라 `f_expiring` 임박 판정이
> 하루씩 어긋난다. 그래서 `01_extensions.sql` 에 `Asia/Seoul` 을 박았다.
> **DB 를 백엔드와 공유하게 되면 이 한 줄은 재협의 대상이다.**

**④ 안전은 점수로 다루지 않는다.** 알러지는 ① 의 하드 컷이다.
페널티로 두면 **점수가 아주 높을 때 언젠가 통과한다.**

## 2. 데이터와 스키마

~~27테이블~~ **29테이블 적용 완료** (뷰 2 · 함수 6). 검증은 스모크 **13**건 ·
계약 ~~44~~ **98**건 · `make ddl-test` ~~17~~ **47**건이다 *(09-03 실측)*.

**원문을 절대 건드리지 않는다.** `recipe_ingredient_raw`(원문) → `recipe_ingredient`(정규화)
→ `recipe_feature`(서빙 전용) 3단이다. 규칙이 8주 내내 바뀌고 사전을 보강할 때마다
전체를 다시 정규화하는데, 원문이 없으면 그게 불가능하다.

**그래서 로더가 멱등이어야 한다.** `recipe_ingredient_raw UNIQUE(recipe_id, position)` 과
`recipe_review UNIQUE(recipe_id, author_hash, written_at) NULLS NOT DISTINCT`.
이게 없을 때 2회 적재로 원문 재료가 전량 2배(451,862 → **903,724**)가 됐다.
`NULLS NOT DISTINCT` 가 핵심이다 — 기본 동작에서는 `author_hash` 가 NULL 인 후기가
서로 다른 것으로 취급돼 무한히 쌓인다.

**배열 3종을 분리한다.** `essential_ids`(만들 수 있는가) · `all_ids`(알러지) ·
`category_ids`(대체재). 안전과 편의가 서로 다른 집합을 요구하므로 **합치면 하나가 반드시 틀린다.**
스모크 A7(알러젠이 고명에만 있어도 차단)이 `all_ids` 의 필요성을 증명한다.

**`pantry_item` 은 UNIQUE 대신 tombstone 이다.** `removed_at` + 부분 유니크
`idx_pantry_active WHERE removed_at IS NULL` 로 활성 유일성만 강제한다.
재투입 시 새 행이 필요하고, **한 행에 재료의 생애가 담겨야 보유기간·폐기율이 조인 없이 나온다.**

**소비기한 추정의 기준일은 `purchased_at`(구매일)이다** *(09-02 신설)*.
`added_at`(앱 등록 시각)이 아니다 — 마트에서 사고 사흘 뒤에 등록하면 그 사흘을
**공짜로 벌어주고**, 그만큼 임박 판정이 늦어져 재료가 상한다. 미래 구매일은 CHECK 로 막는다.

```
effective_expiry = COALESCE(expires_at,               -- 유저 입력이 이긴다
                            COALESCE(purchased_at, added_at::date)
                            + shelf_life_days)         -- 없으면 등록일로 폴백
```

> ⚠️ **`expires_at` 은 소비기한(use-by)이지 유통기한(sell-by)이 아니다.** 계약에도 그렇게 적혀 있다.

**온보딩 원본을 남긴다** — `user_vector.onboarding_picks`(제시 20개 중 고른 인덱스) ·
`onboarding_scales`(척도 3축 0~4 원본) *(09-02 신설 · D-16)*.
`taste_vec` 은 고른 레시피 `flavor_vec` 의 **평균**이라 결과만 남기면 되돌릴 수 없다.
09-02 에 실제로 시드 2건을 고쳤고(식용유 기름짐 0.60→**1.00** · 멸치 3종 분리),
**원본이 없었다면 유저를 다시 모아야 했다.** 앞으로도 검수로 사전이 계속 바뀐다.

**트래픽 표식은 소급 불가라 지금 박았다** *(D-15)*. `session_id` 접두어
**`c-` 실사용자 · `g-` 게스트 · `d-` 개발·디버거·시딩** (CHECK `^[cgd]-`), 그리고
0단계 난수 점수는 `model_version LIKE 'mock-%'`. `v_real_events`·`v_real_recommendations`
가 둘을 모두 거르고, **평가·지표는 원본 테이블이 아니라 이 뷰를 읽는다.**

> 🔴 **`app_user.is_simulated` 만으로는 부족했다.** 그건 '가상 유저'만 잡는다 —
> **개발자가 실유저 ID 로 디버거를 눌러본 것은 그대로 통과한다.**

**`daily_recommendation` 을 미리 만들었다** *(D-19)*. 트랙1을 사전 계산으로 정했고,
배치 구현은 남은 3주 밖이지만 **빈 테이블의 비용은 0 이고 나중에 만들면 전원 재초기화**다.

**`scoring_config` 와 `feature_stats` 를 가른다.** 앞은 사람이 정하는 가중치 레지스트리,
뒤는 배치가 계산하는 코퍼스 통계(`flavor_mu`)다. **갱신 주기가 달라서** 한 테이블에 두면
"어떤 가중치였나"와 "어떤 μ였나"가 뒤엉킨다.

**`flavor_vec` 은 6축으로 저장한다** *(D-11)*. 온보딩 척도는 3축(매움·짠맛·단맛)이고

**실제 점수에 몇 축을 쓸지는 W3 쌍대비교에서 정한다** — 넓게 저장했다가 슬라이스를 줄이는

## 3. ① Retrieval

레시피 ~~4.4만 건~~ **46,353건**(실적재)에서 500건으로 줄인다. `intarray` 집합 연산 넷을 AND 로 겹친다.

```
essential_ids && pantry_ids                          겹치는가
NOT (all_ids && allergy_ids)                         알러젠이 없는가
icount(essential_ids - pantry_ids) <= max_missing    부족이 k개 이하인가
cook_minutes <= 상한                                  시간 안에 되는가
```

**`max_missing` 기본 2.** 이 값 하나가 아키텍처를 안 바꾸고 서비스 성격을 옮긴다 —
0 이면 순수 재료 소비, 5 면 개인화 추천이다.

**기본양념 ~~28종~~ 39종을 "항상 보유"로 친다.** 안 하면 간장 미등록 유저에게 한식 95%가 탈락한다.
알고리즘이 아니라 데이터 모델링 문제라서 **SQL 함수 안에 가뒀다.**
(목표는 ~40종이었고 **현재 39종** — 실측 `cardinality(user_pantry_ids(빈유저)) = 39`.
튜닝 대상이지만 방식은 확정이다)

**알러지 4갈래 차단** — 직접 지정 · ltree 카테고리 전개 · `allergen_group` 일치 · 그룹 확산.
카테고리만 쓰면 메밀을 놓친다(메밀은 잡곡류인데 같은 잡곡류 보리·귀리는 메밀 알러젠이 아니다).
그룹 확산은 `severity='allergy'` 에서만 적용한다 — `avoid` 까지 넓히면
"오이 기피"가 "오이 계열 전면 차단"이 된다.

**GIN 을 강제하지 않는다.** `&&` 선택도가 6.2%(12,438/200,007)로 높아
Seq Scan 9.4ms 와 GIN 강제 9.2ms 가 사실상 같았다. "GIN 을 타야 한다"를
요구사항이 아니라 **가정**으로 재분류했다.

**실측 p95 30.2ms** (in-DB 13.2ms + Python 왕복 17ms).

### 09-02~03 에 확정된 셋

**① 인기도 정렬은 `row_number + recipe_id` tie-break 다** *(D-9 · `percent_rank` 는 기각)*.

```sql
popularity_score =
  (row_number() OVER (ORDER BY ln(1 + recipe.review_count), recipe.id))::real
  / count(*) OVER ()
```

`review_count` 가 이산값이라 `percent_rank` 는 동점이 거대한 블록을 만든다 —
실측에서 **3분위가 통째로 비었고 8,470건이 정확히 같은 점수**였다.
`retrieve_candidates` 가 `ORDER BY missing_count, popularity_score DESC LIMIT 500` 이므로
**500 경계가 실행마다 달라지고, 그 위에서 계산한 propensity 가 재현되지 않는다** —
propensity 재현성은 S0 ① 에서 동결한 로그 규약이다.
쓰는 값은 실적재 행수가 아니라 **크롤 원문 개수 `recipe.review_count`** 다
(원문 합 627,605 vs 실적재 624,422). 파싱 규칙이 바뀌어도 인기도가 안 흔들린다.

**② 필수재료 0개는 미매칭 비율로 가르고, 판정은 SQL 함수 안에서 한다** *(D-10 · D-14)*.

```sql
AND (rf.n_unmatched::real / NULLIF(rf.n_total + rf.n_unmatched, 0)) <= 0.3
```

7.2%(약 3,340건)에 정상(간장계란밥)과 정규화 실패가 섞여 있다. **임계 0.3 은 임시값**이고
`recipe_feature` 를 다시 만들면 되므로 소급 가능하다. **전 레시피에 적용하면 20.1%가 사라지므로
(실측 2,962/14,735) `n_essential=0` 인 것에만 적용해서 시작한다.**
파이썬이 아니라 함수에 두는 이유는 알러지·staple 과 같다 — **두 곳에 두면 반드시 어긋난다.**

**③ 합성 피처는 조회에서 자동 제외된다** *(D-17)*.

```sql
retrieve_candidates(..., p_include_test BOOLEAN DEFAULT FALSE)
retrieve_for_user  (..., p_include_test BOOLEAN DEFAULT FALSE)
    → WHERE (p_include_test OR rf.feature_version NOT LIKE 'test-%')
```

B·C 가 스코어러·화면을 만들려면 합성 `recipe_feature` 가 필요한데, 필터가 없어서
**합성 5만 건이 실추천에 그대로 섞였다.** "테스트 후 지우세요"는 언젠가 잊는다 —
**규율이 아니라 구조로 막는다.** `feature_version` 이 이미 있어서 새 컬럼도 필요 없었다.

> 🔴 **시그니처가 바뀌면 `CREATE OR REPLACE` 가 구버전을 남긴다**(오버로드). 기본 인자로
> 부를 때 어느 쪽이 잡힐지 모호해진다 — `04_functions.sql` 맨 앞에 `DROP FUNCTION IF EXISTS`
> 를 넣었고 `make doc-check` 가 "`retrieve_for_user` 가 한 벌만"으로 회귀를 막는다.

## 4. ② Ranking

```
A   = { i : wᵢ > 0  ∧  fᵢ ≠ None }
raw = ( Σ_{i∈A} wᵢ·fᵢ ) / Σ_{i∈A} wᵢ
score = raw × p_recent × p_cooked × (1 − p_avoid)
```

**결측은 재분배하지 않고 나눈다.** 재분배는 웜 전환·임베딩 NULL·이력 없음 등
네 경로에서 각각 일어나 **적용 순서에 따라 값이 달라진다.** 나눗셈은 순서와 무관하고
`config_hash` + `warm_alpha` + `features` 의 `None` 패턴으로 복원되므로
**로그 컬럼을 늘리지 않아도 된다.**

`W_A = 0` 이면 `raw = 0` 이라 전부 동점이 되고 Retrieval 정렬이 살아난다.

**페널티는 곱한다.** 더하면 점수 높은 항목이 페널티를 이긴다.
최근 7일 impression ×0.7, 14일 내 cook ×0.5.

**웜 전환** α = min(1, n_events/20) → `w_content = 0.08α`, `w_taste = 0.16 − 0.05α`.
이 시점에서 Σw 가 1 을 벗어나지만 **맞추려 하지 않는다** — 위 나눗셈이 흡수한다.

### 가중치 17종

```
f_coverage .24 · f_taste .16 · f_expiring .15 · f_ing_pref .11
f_cooccur .10 · f_popularity .10 · f_missing .05 · f_cuisine .04
f_time_fit .03 · f_season .02 · 나머지 7종 0
```

**`w=0` 의 사유가 세 갈래로 다르다** — 영구 수단 없음(`f_ing_cf`·`f_group_pref`,
`UNAVAILABLE_FEATURES` 등재), 웜 전용(`f_content`), 계산되나 미점화(나머지 4종).

이 구분은 **실제 사고에서 나왔다.** 이전 판이 가중치 예산의 16%를 만들 수 없는 피처에
배정해 합은 1.00 인데 서빙은 0.84 짜리 랭커가 될 뻔했다.
그래서 **"w>0 이면 반드시 계산 가능"을 계약 테스트에 넣었다.**

### 🔴 "수단이 없다"와 "데이터가 없다"는 반대로 다룬다 *(D-4 · 09-03)*

| 집합 | 뜻 | 가중치 |
|---|---|---|
| `UNAVAILABLE_FEATURES` = {`f_ing_cf`, `f_group_pref`} | 수단이 없다 | **0 이어야 한다** (계약이 강제) |
| `PENDING_DATA_FEATURES` = {`f_cuisine`, `f_season`} | 데이터가 없다 | **그대로 둔다** |

`PENDING` 쪽 가중치를 0 으로 내리면 데이터가 왔을 때 **가중치를 다시 유도해야 한다.**
나눗셈 정규화가 분자·분모에서 함께 빼주므로 지금 값이 왜곡되지 않고, 데이터가 오면 그냥 켜진다.

**그래서 문서에 쓰는 오늘의 실효 가중치는 `ACTIVE_WEIGHT_TODAY = 0.94` 다**
(설계 의도 1.00 − `f_cuisine` 0.04 − `f_season` 0.02). 두 상수 모두 `src/features/recommend/enums.py` 에 있다.

> 🔴 **`None` 을 `0.0` 으로 메우지 않는다.** `0.0` 은 "계산했더니 0", `None` 은 "계산할 수 없음" —
> LightGBM 은 결측을 native 로 처리하므로 학습에서 완전히 다른 뜻이 된다.
> 같은 이유로 `freq_count = 0` 이면 `f_cooccur` 를 **`None` 으로 내보낸다** (D-3) —
> IDF `log(N/freq_count)` 가 0 나눗셈이거나, 가드가 있으면 **가중 자카드가 그냥 자카드로
> 조용히 퇴화한다.** 예외도 안 나고 점수도 정상 범위라 아무도 모른다.

> ⚠️ **이 가중치는 학습값이 아니라 도메인 직관으로 매긴 임시값이다.**
> 리포트에 "학습된 가중치"라고 쓰면 안 된다. 교체 계획은 쌍대비교 600쌍 + BT 다.

## 5. ③ Re-ranking과 탐색

**MMR λ=0.7**, 유사도는 임베딩이 아니라 **재료 자카드 + staple 제외 IDF** 다.
임베딩은 배치 미실행 시 NULL 일 수 있고 재료 배열은 항상 있다.
IDF 를 붙이는 이유는 양파처럼 어디에나 있는 재료가 유사도를 부풀리기 때문이다.

**클러스터 K≈50 · cap 2** 가 분류축 캡을 대체한다. 점수 유지율 ~~99.0% vs 89.3%~~
**98.6% vs 89.0%** 이고 유사도 계산이 0회다.
k-means 는 데이터 분포에 맞춰 균형이 잡히는데 택소노미는 안 잡힌다.

| 다양화 방식 | ILD | 근중복 쌍 | 점수 유지 |
|---|---:|---:|---:|
| 점수순 (다양화 없음) | 0.934 | 8.0 | 100.0% |
| 분류축 캡 (k-means 없을 때) | 0.952 | 5.8 | **89.0%** |
| **클러스터 쿼터 K=50 cap=2** | 0.965 | **3.0** | **98.6%** |

*(`scripts/reco/bench/kmeans_worth_it.py` 재실행 09-03. `01` 5-3-2 에 있는 99.0%/89.3%/3.1 은
seed 가 다른 이전 실행이다 — `04` 와 이 문서는 위 숫자로 통일한다.)*

> **K=50 은 군집 품질 지표로 정한 값이 아니다.** 8주 노출 20,000회 ÷ 50 = **arm당 400회**,
> 즉 통계적으로 학습이 되는 최소선에서 역산했다.

> 🔴 **클러스터는 A-4 직후 한 번만 매긴다** *(D-12)*. `recipe_feature.cluster_version` 은
> 있는데 **`recommendation_log` 에는 판 번호 칸이 없다.** 재클러스터링하면 과거 로그의
> `cluster_id` 가 무엇을 가리켰는지 복원 불가고, Thompson belief 와 탐색 분석이 조용히 오염된다.
> 구현은 `sklearn.KMeans`(`n_init=10` · `random_state` 고정), 2회차가 불가피하면
> `cluster_version='v2-…'` 로 올리고 **그 시각을 `batch_run` 에 남긴다** — 로그에 칸이 없으니
> 시각이 유일한 대용물이다.

**탐색 정책 π = ½ 균등 + ½ Thompson.** Thompson 단독은 50개 중 32개가
propensity 0 이 되고(MC 를 5배로 늘려도 27개), **확률이 0 이면 IPS 분모가 0 이라
그 영역은 영원히 평가 불가**다. 균등 절반은 발견 3.89 → 3.54 로 **0.35 를 주고
평가 가능성을 산 것**이다.

**UCB 는 성능이 가장 좋은데(4.14) 기각했다** — 결정적이라 확률 자체가 없다.

**탐색 슬롯 2칸은 상위 200 에서, 위치는 매 요청 무작위.**
위치를 고정하면 얻는 게 두 점뿐인데 IPS 에 필요한 건 위치별 검사확률 **곡선**이다.

> 🔴 **09-03 까지 이게 설계로만 있었다.** `exploration_slots()` 를 계산해 놓고 **결과를 버려서**
> 탐색 아이템이 점수 순서 그대로 남아 있었다 — propensity 는 기록되는데 위치가 안 퍼지니
> 정작 필요한 곡선이 안 나온다. 지금은 실제로 꽂히고, 계약 검증
> "탐색 아이템이 여러 위치에 퍼진다(8종)"가 회귀를 막는다.

## 6. 추천 이유 — 2트랙

**z-salience** `w·(f−μ)/σ` 를 **그 요청의 후보 500건 기준**으로 계산해 상위 2개를 잇는다.

기여도(`w·f`) argmax 는 **이유가 1종으로 붕괴한다** — ①이 이미 걸러서 상위 후보의
`f_coverage` 가 거의 1.0 이고 가중치 0.24 가 최대라 곱의 argmax 가 사실상 상수다.
z-salience 상위 2개면 4종이 나온다.

**σ 하한 0.05 가 필수다.** 없으면 반대로 깨진다 — 값이 전부 0.98~0.99 면 σ≈0.003 이라
0.01 차이가 z=3 으로 튀어 지각 불가능한 차이가 이유가 된다.

**템플릿 15종 중 실가용 10종** (w=0 피처에 걸린 5종은 발화 불가 — 실측 확인).
그중 `f_cuisine`·`f_season` 은 **데이터가 올 때까지 사실상 안 뜬다**(`PENDING_DATA_FEATURES`)라,
오늘 실제로 발화하는 것은 **8종**이다.
종결형·연결형을 두 벌로 적고 조사는 받침으로 자동 선택한다.
**연결어미를 `고`/`며`/`여` 로 제한한 것이 안전장치였다** — 중립 접속만 허용한다는 뜻이라
이 코드는 인과를 만들어낼 문법적 수단이 없다. LLM 은 10건 중 7건에서 없는 인과를 지어냈다.

### 트랙 분리 — **트랙1은 사전 계산으로 만든다** *(D-19 · 09-03)*

| | 트랙 1 — 오늘의 추천 | 트랙 2 — 잔여 재료 |
|---|---|---|
| 트리거 | 배치 1일 1회 | 실시간 |
| 사유 | **LLM** (G1~G4 통과분 · 실패 시 템플릿) | **템플릿** — 남긴다 |
| 응답 | 조회 ~30ms | ~58ms |

근거는 지연 하나다 — 사유 ~~18건 = 450~~ **10건 = 250 출력토큰**을 300ms 에 내려면
~~**1,500 tok/s**~~ **833 tok/s** 가 필요한데 가장 빠른 로컬 모델이 90.9 tok/s 다
(~~16.5배~~ **약 9배** 부족). 처리량과 비용은 기각 사유가 **아니다.**
**메인화면 사유 건수를 10 으로 잡은 것이 정정의 내용이고, 결론은 그대로다.**

**트랙2에 템플릿 사유를 남긴다** (D-19 ①). 비용이 0ms 이고,
**디버거와 ablation 이 여기 걸려 있다** — 사유가 없으면 "왜 이게 나왔나"를 화면에서 못 보인다.

오프라인으로 옮긴 것이 지연만 푼 게 아니다 — **정확성 문제도 같이 풀린다.**
게이트 통과분에도 오류가 25% 남는데, 배치라서 사람이 검수할 시간이 있다.

```
user_id · rank · recipe_id · score
reason · reason_source          'llm' | 'template' | 'fallback'
```

🔴 **`pantry_fingerprint` 가 핵심이다.** 새벽에 계산했는데 낮에 재료를 쓰면 사유가 어긋난다 —

## 7. 로그와 평가

**로그 4층** (L1 trace · L2 행동 · L3 MLflow · L4 품질)을
`request_id`·`user_id`·`mlflow_run_id`·`feature_version` 4키로 잇는다.

**기여도가 아니라 피처 원값 17종을 저장한다.** 기여도(`w·f`)만 남기면 w=0 인 ~~6종~~ **7종**이
로그에서 사라져 소급 학습이 막히고(~~11/17~~ **10/17** 만 남는다), 온라인 SQL 과 오프라인 pandas 로
두 번 계산하면 반드시 어긋난다. **서빙 시점 값을 그대로 학습에 쓰면 이 문제가 원천 제거된다.**
*(09-03 실측: `FEATURE_KEYS` 17 · `w>0` 10 · `Σw` 1.00.)*

**`None` 과 `0.0` 은 다르다.** 앞은 계산 불가, 뒤는 계산 결과 0 이다.
LightGBM 은 결측을 native 로 처리하므로 0 으로 메우면 정보가 왜곡된다.

### impression 은 서버가 기록한다 — 그리고 `source` 로 시대를 가른다 *(09-02)*

프론트 합의가 어려워 **A안(서버가 응답 생성 시점에 기록)** 으로 간다.
그 대가로 `event_log.source` 를 신설했다 (NOT NULL · DEFAULT 없음).

```
served    서버가 응답에 담았다. 본 것이 아니라 보낸 것이다
viewport  클라이언트가 실제 화면 노출을 관측했다
client    사용자 행위 보고 (click·cook…)
```

> 🔴 **이 열이 없으면 두 시대가 섞여 둘 다 못 쓰게 된다.** A 시대 impression 은 영구히
> "보냈다"만 뜻하고, 사용자가 실제로 본 것은 **어떤 백필로도 복원되지 않는다.**
> 전환기에 둘을 동시에 쓰면 `r(p) = viewport(p)/served(p)` 로 환산계수가 나오고,
> 부분 유니크 `ux_ev_impression(request_id, recipe_id, source)` 이 그 dual 기록을 공존시킨다.

`position` 도 CHECK 로 강제한다 — impression 에 없으면 '상위 k 만 잘라 보기'조차 안 되고
position bias 보정이 불가능하다. **DDL 이 막지 않으면 라이터 버그 하나로 조용히 비어간다.**

> ⚠️ **CHECK 를 하나 더 걸었다가 걷어냈다.** `CHECK (source <> 'served' OR request_id IS NOT NULL)`
> 은 FK 의 `ON DELETE SET NULL` 과 충돌해 **`recommendation_log` 행 삭제를 막았다**(실측 `CheckViolation`).
> 보존기간 만료분 정리가 막히면 **개인정보 파기 의무와 충돌한다.** 이 불변식은 라이터가 지킨다.

**평가·지표는 `v_real_events`·`v_real_recommendations` 뷰를 읽는다** *(D-15)* —
원본 테이블을 직접 읽으면 `d-` 세션(디버거·시딩)과 `mock-` 버전이 섞인다.

### 평가 방침

**주 지표는 요청 단위 pairwise 정확도**이고 NDCG@10 은 보조다.
positive 0건 요청이 13.5% 라 IDCG=0 으로 NDCG 가 정의되지 않고, 음수 라벨이
NDCG 에서 클리핑돼 사라진다. NDCG 는 승패 판정이 아니라 **회귀 감시**다.

**지표보다 하네스를 먼저 검증한다.** IDCG 를 top-K 안에서만 계산하는 버그는
편향이 +0.182 인데 재려는 효과크기(0.01~0.03)의 6~18배다.

**A/B 는 기각.** 배정 단위가 유저라 arm 당 유효표본이 `(U/2)/ICC` 로 **포화한다** —
유저당 노출을 아무리 늘려도 검정력을 살 수 없다. 100명이면 검출 가능 ΔCTR 이 4.2%p 다.

**대신 Team-Draft Interleaving.** 같은 사람이 두 랭커를 동시에 평가하므로
유저 간 분산이 상쇄되고 검정 단위가 요청이 된다. 목표를 표본 수가 아니라
**검출 가능한 최소 δ 로 역산**해 보고한다(요청 1,000 → δ 0.059).

**OPE 는 지금 불가.** 위치당 100노출·상대오차 30% 인데 곡선 차이가 5.9% 다.
해금 조건 **ESS ≥ 1,764** 로 명시했다.

**가중치 학습은 Bradley-Terry 600쌍** (20명 × 30쌍 + 5% 중복 출제로 일관성 산출).
11개 개별 추정 0.874 vs **5블록 축약 0.926** — 같은 예산에서 축약이 전 구간 우세다.

**쌍은 블록별로 120쌍씩 층화 추출한다** *(D-18 · 09-03)*. 무작위로 뽑으면
**어떤 블록의 차분이 0인 쌍만 모여 그 가중치가 식별되지 않고, 우리는 그 사실조차 모른다.**
가장 위험한 것은 **임박소진**(`f_expiring`, w=0.15) — 피처가 하나뿐이라 대체할 것이 없고
냉장고를 고정하면 두 레시피의 값이 같아지기 쉽다. 그래서 냉장고 시나리오를 2~3개로 나누고
**각각에 임박 재료 2~3개를 필수 포함**하되, **임박이 없는 대조군 시나리오를 반드시 하나 둔다** —
"임박이 없을 때의 순서"와 비교해야 `f_expiring` 의 효과가 분리된다.

> 🔴 **뽑기 전에 점검한다.** 각 블록에서 `|차분| > 0.1` 인 쌍이 120개 미만이면
> 그 블록은 600쌍으로 학습 불가다 — **쌍을 더 뽑아도 안 나오고 시나리오를 늘려야 한다.**
> 그리고 이 계산은 `recipe_feature` 가 채워진 뒤(A-4 후)에야 가능하다.

**수집 수단은 구글폼이다 — 개발 0일.** 한 번 쓰고 끝나는 수집에 화면을 만들지 않는다.
`scripts/reco/bench/pair_export.py` 가 630문항(600 + 5% 중복)을 TSV 로 내보내고
`scripts/reco/bench/pair_import.py` 가 응답을 학습 입력으로 바꾼다.
문항에는 레시피 이름만으로 부족해 **재료와 조리시간을 같이 보여준다**(크롤에 이미지가 0건이다).
**"둘 다 아니다"를 반드시 넣고 학습에서 제외한다** — 억지 선택은 노이즈다.

> ⚠️ **이 숫자는 "정답 회복률"이다.** 우리가 손으로 정한 가중치를 정답으로 놓고 라벨을
> 합성해 되찾은 비율이라, **실제 추천 성능이 아니다.** 확정된 것은
> *"600쌍이면 블록 가중치를 식별할 수 있다"* 이지 *"0.926 만큼 좋아진다"* 가 아니다.
절대평가가 아닌 이유는 척도가 사람마다 다르고 **우리가 배우려는 게 순서**이기 때문이다.

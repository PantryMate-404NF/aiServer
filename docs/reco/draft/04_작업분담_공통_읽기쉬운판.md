# 셋이 나눠서 만들기 — 시작하기 전에

> 작성자: 박재우 · 작성일: 2026-09-03

우리는 **냉장고에 있는 재료로 만들 수 있는 요리**를 추천하는 시스템을 만들고 있습니다.
그중 AI 부분을 세 사람이 나눠서 동시에 진행합니다.

이 문서 하나만 읽으면 시작할 수 있게 썼습니다.

---

## 누가 무엇을 만드나

| | 맡는 일 | 한 문장으로 |
|---|---|---|
| **A** | 데이터 | 레시피 4만 6천 건의 재료를 정리해서, 추천이 실제로 돌아가게 만듭니다 |
| **B** | 엔진 | 지금 아무 숫자나 내놓는 점수를 진짜 점수로 바꿉니다 |
| **C** | 화면·평가 | 결과를 눈으로 볼 수 있게 하고, 잘 되고 있는지 재는 도구를 만듭니다 |

각자 자기 폴더에서 작업하므로 서로 파일이 겹치지 않습니다.
자세한 할 일은 각자 문서에 있습니다.

---

## 지금 어디까지 와 있나

데이터는 들어와 있습니다.

```
레시피        46,353건
재료 목록    451,862줄
조리 순서    362,677단계
후기         624,422건
```

그런데 **아직 추천이 한 건도 안 나옵니다.** 세 곳이 비어 있기 때문입니다.

```
재료 정리 결과    비어 있음   ← A가 채웁니다
레시피 특성       비어 있음   ← A가 채웁니다
추천 기록         비어 있음   ← B가 흐르게 합니다
화면              없음        ← C가 만듭니다
```

---

## 첫날 — 셋이 동시에 시작합니다

서로를 기다릴 필요가 없습니다.

| | 첫 작업 |
|---|---|
| **A** | 재료 정리 프로그램 만들기 |
| **B** | 추천 기록이 저장되게 연결하기 |
| **C** | 개발 환경 띄우기 + 평가 도구 뼈대 |

**B의 첫 작업이 제일 급합니다.** 지금 추천 기록이 하나도 없어서
**C가 화면에 띄울 것이 없기 때문입니다.** 반나절이면 끝나는 일인데,
그게 끝나야 C가 진짜 데이터로 작업할 수 있습니다.

## 환경 만들기

```bash
brew install uv        # 없으면 설치
uv venv
make install TRACK=A   # 자기 트랙 글자를 넣으세요 (A · B · C)
```

트랙마다 필요한 도구가 달라서 자기 것만 깔립니다.

> **`uv sync`를 그냥 치지 마세요.**
> 목록에 없는 프로그램을 **지워버립니다.** 실제로 이것 때문에 서버가 한 번 죽었습니다.
> 꼭 `make install TRACK=?` 로 하세요.

uv 를 깔 수 없는 컴퓨터(코랩·채점 서버 같은 곳)라면 사본을 쓰세요:

```bash
pip install -r requirements/B.txt   # 자기 트랙 글자
```

> 이 사본은 자동으로 뽑아낸 것입니다. **손으로 고치지 마세요.**
> 고칠 일이 있으면 `pyproject.toml` 을 고치고 `make requirements` 를 실행하세요.

## 서로 부딪히지 않는 방법 — 다섯 가지

### 1. 데이터베이스 구조는 건드리지 않습니다

필요한 표는 이미 다 만들어져 있습니다.
구조를 바꾸면 데이터베이스를 다시 만들어야 하고, **그러면 다른 두 사람이
작업하던 결과가 사라집니다.** 바꿔야 할 일이 생기면 혼자 하지 말고 셋이 모여서 하세요.

### 2. 오래 걸리는 작업을 시작하기 전에 알려주세요

A의 재료 정리는 15분 동안 35만 줄을 씁니다.
그동안 B나 C가 속도를 재면 엉뚱한 숫자가 나옵니다. 한마디만 하면 됩니다.

### 3. 같이 쓰는 파일은 말하고 고칩니다

| 파일 | 주인 |
|---|---|
| 계약 파일 (`src/features/recommend/schema.py` · `stage.py`) | B — 고치면 셋 다 영향받습니다 |
| 가짜 서버 (`app/main.py`) | B |
| 재료 정리 (`app/services/normalize/`) | A |
| 화면 (`infra/app/`) | C |
| `Makefile` | 공용 — 자기 명령만 추가 |

### 4. `.env` 파일의 `REVIEW_SALT`를 절대 바꾸지 마세요

후기 62만 건의 작성자 정보가 이 값으로 암호화돼 있습니다.
바꾸면 **"같은 사람이 쓴 후기"를 알아볼 수 없게 됩니다.**
지우거나 새로 만들지 마세요. 팀 채널에 있는 값을 그대로 쓰면 됩니다.

### 5. 다 됐다는 건 명령으로 증명합니다

이 프로젝트에서 **에러 없이 조용히 틀린 적이 열한 번** 있었습니다.
후기 60만 건이 사라졌는데 아무 일도 없어 보였고, 데이터가 두 배로 쌓였는데
에러가 안 났습니다. **화면상으로는 전부 정상이었습니다.**

그래서 "됐습니다"가 아니라 **명령을 돌려서 초록불이 뜨는 것**으로 확인합니다.

```
make validate         재료 사전이 온전한가
make contract         입출력 약속이 지켜지나
make normalize-test   재료 정리가 제대로 되나
make ddl-test         데이터베이스 구조가 맞나
make smoke            추천 후보가 제대로 나오나
make smoke-py         파이썬에서도 같은 결과인가
make log-test         기록이 제대로 남나
make doc-check        문서의 숫자가 실제와 맞나
```

자기 작업을 마치면 **전부** 돌려보세요. 남의 것을 깨뜨리지 않았는지 확인하는 겁니다.

## 지금 바꿔도 되는 것, 곧 못 바꾸는 것

### 지금은 대부분 바꿀 수 있습니다

실제 사용자가 아직 없어서 쌓인 데이터가 없습니다.
기록 방식도, 설문 문항도, 점수 비중도 지금은 자유롭게 바꿀 수 있습니다.

### 곧 못 바꾸게 됩니다

| 무엇 | 언제부터 |
|---|---|
| 기록 방식 | **B가 기록을 연결하는 순간** |
| 설문 문항 | 사용자를 모으기 시작하는 순간 |

기록이 쌓이기 시작하면, 방식을 바꿨을 때 **이전 것과 이후 것을 같이 쓸 수 없습니다.**
설문도 마찬가지로, 100명에게 물어본 뒤 문항을 바꾸면 그 답이 절반쯤 쓸모없어집니다.

> **B가 기록을 연결하기 전이 마지막 기회입니다.** 지금 다시 보면 공짜고,
> 연결한 뒤에는 그때까지 쌓인 것을 버려야 합니다.

## 백엔드에 꼭 부탁해야 하는 것

우리는 화면(프론트)과 직접 이야기하지 않습니다. **백엔드를 거칩니다.**

```
백엔드 → 우리    "이 사용자에게 추천해줘"
우리 → 백엔드    추천 20개 + 각각의 이유 + 요청 번호
백엔드 → 우리    "사용자가 3번째 것을 눌렀어요"
```

**세 번째가 중요합니다.** 우리가 준 요청 번호와 순위를 **그대로 돌려줘야** 합니다.

빠뜨려도 에러가 안 납니다. ⚠️ 하지만 **그 기록은 저장되지 않습니다** —
응답은 성공(200)처럼 보이는데 "거부됨"으로 세어질 뿐입니다.
그런데 **"몇 번째 자리에 있던 것을 눌렀는지"를 알 수 없게 됩니다.**

그러면 우리가 위에 올려놓은 것이 마치 인기가 많아서 눌린 것처럼 보이고,
그 데이터로 학습한 모델은 같은 착각을 반복합니다. **몇 주 뒤에야 드러납니다.**

이건 B가 백엔드 담당자에게 전달합니다.

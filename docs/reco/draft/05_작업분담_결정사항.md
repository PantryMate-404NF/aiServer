## D-1. `data_quality_snapshot` 은 **C 전담**

**A 는 이 테이블에 쓰지 않는다.** A 의 배치 기록은 `batch_run` 에 넣는다 —
그 테이블이 정확히 그 용도이고 이미 있다.

| 테이블 | 소유 | 무엇을 |
|---|---|---|
| `batch_run` | **A** | 배치 1회 = 1행. `job_name` · `status` · `input_count` · `output_count` · `params` |
| `data_quality_snapshot` | **C** | 품질 시계열 1회 = 1행. 화면이 읽는다 |

### 왜 이렇게 가르나

같은 컬럼에 두 정의가 들어가면 **시계열이 조용히 꺾인다.** 실제로
`mention_total` 을 A 는 "도구 제외 파싱 언급"(약 44만), C 는 "원문 행수"(451,862)로
쓰려 하고 있었다. 둘 다 맞는 말인데 한 칸에 섞이면 A 배치 전후로 그래프가 튄다.

**A 가 배치를 돌리면 `batch_run` 에 쓰고 끝.** C 의 기록기가 나중에
`batch_run` 을 읽어 "마지막 배치가 언제 무엇을 처리했나"를 화면에 띄운다.

```
A:  batch_run(job_name='normalize', input_count=451862, output_count=349811, ...)
C:  data_quality_snapshot(coverage_rate=0.808, mention_total=451862, ...)
    └ 필요하면 batch_run 을 조인해서 "미적용 배치" 를 표시
```

> 🔴 **`mention_total` 정의는 "원문 행수"로 통일한다** (C 기준).
> A 가 실제로 매칭한 수는 `batch_run.output_count` 에 있다.

## D-2. 검수 큐 `suggested` 는 **객체 형식** · C 가 정한다

`normalization_queue.suggested` 는 `jsonb` 다. 형식을 하나로 못박는다.

```json
{
  "candidates": [
    {"name": "매실청", "score": 0.62, "method": "jamo_trgm"},
    {"name": "매실",   "score": 0.41, "method": "jamo_trgm"}
  ],
  "blocked_by": null
}
```

| 필드 | 뜻 |
|---|---|
| `candidates[].name` | **반드시 사전에 있는 표제어.** 없는 이름을 만들지 않는다 |
| `candidates[].score` | 0~1. 화면이 정렬·표시에만 쓴다 |
| `candidates[].method` | `exact` · `alias` · `rule` · `jamo_trgm` |
| `blocked_by` | 구조 차단 사유 (`hyponym`·`sibling`·`unrelated`). 없으면 `null` |

### 왜 배열이 아니라 객체인가

배열 `[["매실청", 0.62, "trgm"]]` 은 **위치로 의미를 기억해야 하고 필드를 못 늘린다.**
`blocked_by` 를 나중에 넣으려면 전부 고쳐야 한다.

### 왜 C 가 정하나

**읽는 쪽이 형식을 정한다.** 화면(C-9)이 이걸 그리고, 시더는 그 모양에 맞춰 넣는다.
반대로 하면 화면이 시더에 끌려다닌다.

> 🔴 **자동 확정 금지.** `score` 가 아무리 높아도 사람이 누르기 전엔 반영하지 않는다.
> 실측에서 임계값 0.6 재현율이 **0%** 였다 — 정탐 중앙값 0.143 vs 오탐 0.118 로 겹친다.

**시더는 C 가 만든다** (`scripts/reco/bench/queue_seed.py`). A 는 미매칭 목록만 넘긴다.

## D-3. `ingredient.freq_count` 는 **A 가 먼저** · A-3 직후

지금 **536종 전량 0** 이다. B 의 `f_cooccur`(w=0.10)와 `00` 의 MMR IDF 가 여기 묶여 있다.

```
A-3 (전량 정규화)  →  A-14 (freq_count UPDATE)  →  B-7 (f_cooccur)
```

**B 는 A-14 를 기다리되 멈추지 않는다.** `f_cooccur` 는 10% 이고, B 가 먼저 할 수 있는
피처가 `f_coverage`(24%) · `f_expiring`(15%) · `f_popularity`(10%) · `f_missing`(5%) 로
**54% 있다.** 순서만 바꾸면 된다.

> 🔴 **B 는 `freq_count = 0` 을 그냥 쓰면 안 된다.** IDF 가 `log(N/freq_count)` 라
> 0 이면 0 나눗셈이거나, 가드가 있으면 IDF 가 상수가 되어 **가중 자카드가 그냥
> 자카드로 조용히 퇴화한다.** 예외도 안 나고 점수도 정상 범위다.
> **0 이면 `f_cooccur` 를 `None` 으로 내보낸다** — 나눗셈 정규화가 알아서 뺀다.

## D-4. 스코어러 결측 처리 — **나눗셈**. 재분배가 아니다

```
A = { i : wᵢ > 0 ∧ fᵢ ≠ None }
raw = (Σ_{i∈A} wᵢ·fᵢ) / (Σ_{i∈A} wᵢ)
```

**가중치를 재분배하지 않는다.** 계산 불가한 피처는 분자·분모에서 **함께** 빠진다.
그래서 피처를 켜고 끄는 순서와 무관하게 결과가 같고, 데이터가 오면
**가중치를 다시 유도할 필요 없이** 켜진다.

| 집합 | 뜻 | 가중치 |
|---|---|---|
| `UNAVAILABLE_FEATURES` | 수단이 없다 (`f_ing_cf`·`f_group_pref`) | **0 이어야 한다** |
| `PENDING_DATA_FEATURES` | 데이터가 없다 (`f_cuisine`·`f_season`) | **그대로 둔다** |

문서에 쓰는 숫자는 `ACTIVE_WEIGHT_TODAY = 0.94` 다 (설계 의도 1.00).

> 🔴 **`None` 을 `0.0` 으로 메우지 않는다.** 0.0 은 "계산했더니 0",
> `None` 은 "계산할 수 없음" — 학습에서 완전히 다른 뜻이다.

## D-9. 인기도는 `recipe.review_count` 로 계산한다

두 값이 다르다 — 크롤 원문 합 **627,605** vs 실적재 **624,422** (차이 3,183은 중복 제거분).

**원문 개수를 쓴다.** 크롤 시점의 인기를 반영하고, **재적재해도 값이 안 변한다.**
중복 후기도 "반응이 많았다"는 신호로 본다.

```sql
-- log1p 후 순위. 🔴 recipe_id 로 tie-break 를 **명시**한다
popularity_score =
  (row_number() OVER (ORDER BY ln(1 + recipe.review_count), recipe.id))::real
  / count(*) OVER ()
```

### 🔴 `percent_rank` 를 쓰면 안 되는 이유 (09-02 정정)

처음에 `percent_rank` 로 정했다가 실측에서 두 가지가 드러났다.

**① 분포가 균등하지 않다.** `review_count` 가 이산값이라 동점이 거대한 블록을 만든다.

```
percent_rank  1분위 8,102 · 2분위 8,470 · 3분위 0 · …   ← 3분위가 비었다
row_number    전 분위 4,632~4,636                        ← 균등
```

**② 후보 절단이 비결정적이 된다 — 이게 더 크다.**

`retrieve_candidates` 가 `ORDER BY missing_count, popularity_score DESC LIMIT 500` 인데
**8,470건이 정확히 같은 점수**면 500 경계가 실행마다 달라진다.
그 위에서 계산한 **propensity 가 재현되지 않고**, propensity 재현성은
S0 ① 에서 동결한 로그 규약이다.

`recipe_id` tie-break 를 넣으면 같은 데이터에 항상 같은 순서가 나온다.

> 후기 2건짜리 8,470건이 0.17~0.35 로 퍼지는 **가짜 정밀도**가 생기지만,
> w=0.10 짜리 피처에서 그건 순위 안정성보다 싸다.

**A-6 완료기준은 `Pearson corr ≥ 0.92`** — row_number 실측 0.9242 로 통과한다.

> ⚠️ 실적재 행수(`COUNT(*) FROM recipe_review`)를 쓰면 **후기 파싱 규칙이 바뀔 때마다
> 인기도가 흔들린다.** 파싱은 앞으로도 손볼 수 있으므로 원문 쪽이 안정적이다.

## D-11. `flavor_vec` 은 **6축 유지**. 단 실제 사용은 미정

| | 축 | 어디서 |
|---|---|---|
| 온보딩 척도 | **3축** — 매움·짠맛·단맛 | 사용자가 직접 답 |
| `flavor_vec`·`taste_vec` | **6축** — +신맛·감칠맛·기름짐 | 뒤 3축은 **레시피 선택에서 파생** |

**저장은 6축으로 한다.** 사용자에게 더 묻는 것이 아니라 레시피 20개 중 3개를
고른 결과에서 나오므로 **온보딩 시간이 1초도 안 늘어난다.**

> 🔑 **다만 실제 점수 계산에서 3축만 쓸 수도 있다.** 뒤 3축(신맛·감칠맛·기름짐)은
> 척도 문항이 없어 체계 편향이 그대로 남고, `f_taste` 품질이 축마다 다르다.
> 6축 전부를 쓸지 앞 3축만 쓸지는 **W3 쌍대비교 학습에서 정한다.**
>
> **이 결정은 소급 가능하다** — `flavor_vec` 은 시드에서 언제든 재생성되고,
> 축을 빼는 것은 코사인 계산에서 슬라이스만 바꾸면 된다. 그래서 **지금은 넓게
> 저장해 두는 것이 안전하다.** 반대로 3축으로 저장했다가 6축이 필요해지면
> 유저를 다시 모아야 한다.

### 남은 것 — 시드 결함 2건 (02 I-15)

| | 어느 축 | 6축을 실제로 쓰면 |
|---|---|---|
| 식용유 기름짐 `0.60` → `1.00` | **기름짐** | 영향 있음. 안 쓰면 무의미 |
| 멸치 = 국물용 + 볶음용 뭉침 | **짠맛** | **항상 영향 있음** (짠맛은 3축에 포함) |

**멸치는 축 선택과 무관하게 영향이 있다.** 유저 모집 전에 정해야 한다.

```sql
AND (rf.n_unmatched::real / NULLIF(rf.n_total + rf.n_unmatched, 0)) <= 0.3
```

이렇게 하면 `recipe_feature` 46,353행 계약이 살고(A-4 완료기준 ①),
C 가 **"몇 건을 왜 버렸나"를 셀 수 있다.**

> ⚠️ **임계값을 전 레시피에 적용하면 20.1% 가 사라진다**(실측 2,962/14,735).
> 그래서 **`n_essential=0` 인 것에만** 0.3 을 적용하는 것으로 시작한다.
> `n_essential ≥ 1` 인데 미매칭이 많은 3.16% 는 A-4 에서 분포를 보고 따로 정한다.

## D-17. 합성 피처 격리 — `feature_version='test-*'` *(구현 완료)*

B·C 가 스코어러·화면을 만들려면 합성 `recipe_feature` 가 필요하다. 그런데
`retrieve_candidates` 에 필터가 없어서 **합성 5만 건이 실추천에 그대로 섞였다.**

```
v1, v2, …    A 의 실배치 산출물 — 추천에 나간다
test-*       B·C·스모크        — 조회에서 자동 제외
```

조회 함수가 직접 거른다. 테스트는 명시적으로 열어야만 본다.

```sql
retrieve_for_user(user_id, max_missing, max_minutes, limit, p_include_test)
                                                            └ 기본 FALSE
```

```python
retrieve(uid, 2, None, 500)                    # 실서빙 — test-* 안 보임
retrieve(uid, 2, None, 500, include_test=True) # 테스트 — 보임
```

**실증 (09-03)** — `test-scorer` 피처 1건을 넣고 두 경로로 조회:
실서빙 ✅ 안 보임 · 테스트 모드 ✅ 보임.

**규율이 아니라 구조로 막는다.** "테스트 후 지우세요" 는 언젠가 잊는다.
잊어도 안 섞이는 편이 낫다. 그리고 `feature_version` 이 이미 있어서
**새 컬럼을 만들 필요가 없었다.**

> 🔴 **A-8 게이트 ⑦ 이 바뀐다.** "`feature_version='smoke'` 행이 0건" 이 아니라
> **"실배치 행에 `test-` 접두어가 없다"** 로. B 가 테스트를 돌려도 A 가 빨개지지 않는다.

> ⚠️ **함수 시그니처를 바꾸면 `CREATE OR REPLACE` 가 구버전을 남긴다**(오버로드).

## D-18. 쌍대비교 — 쌍을 **블록별로 뽑는다** *(09-03)*

**팀원 20명 × 30쌍 = 600쌍.** 검수 스프린트(75분)와 같은 날에 5분 추가. ✅ 가능 확인.

### 문제 — 점수 차가 작은 쌍만 뽑으면 블록이 죽는다

BT 가 배우는 것은 **5블록의 비율**이다. 어떤 블록의 **차분이 0인 쌍만 모이면
그 가중치는 식별되지 않는다** — 직관값 그대로 남고, 우리는 그 사실조차 모른다.

| 블록 | 피처 | 살아나는 조건 |
|---|---|---|
| 재료매칭 | `f_coverage`·`f_missing` | 부족 재료 수가 다른 쌍 |
| **임박소진** | `f_expiring` | 🔴 **임박 재료를 쓰는 쪽 vs 안 쓰는 쪽** |
| 취향 | `f_taste`·`f_ing_pref`·`f_cuisine` | 맛 벡터 거리가 다른 쌍 |
| 협업신호 | `f_cooccur` | 최근 조리 이력과 겹침이 다른 쌍 |
| 품질·상황 | `f_popularity`·`f_time_fit`·`f_season` | 인기도·조리시간이 다른 쌍 |

**임박소진이 가장 위험하다.** 가중치 0.15 인데 피처가 하나뿐이라 대체할 것이 없고,
냉장고를 고정하면 두 레시피의 `f_expiring` 이 같아지기 쉽다.

### 제안 — 블록 층화 추출

**600쌍을 블록별로 120쌍씩 배정한다.** 한 쌍이 여러 블록에 기여해도 되지만,
**각 블록에서 "그 블록의 차분이 큰 쌍" 120개를 보장**한다.

```
1. 후보 레시피 풀에서 모든 쌍의 블록별 차분을 계산한다
2. 블록마다 |차분| 상위에서 120쌍을 뽑는다 (중복 허용)
3. 합집합이 600쌍을 넘으면 블록 균형을 유지하며 줄인다
4. 🔴 뽑은 뒤 블록별 차분 분포를 **찍어서 확인한다**
```

> 🔴 **뽑기 전에 사전 점검을 한다.** 각 블록에서 `|차분| > 0.1` 인 쌍이
> **120개 미만이면 그 블록은 600쌍으로 학습 불가**다. 그때는 냉장고 시나리오를
> 늘려서 차분을 만들어야 한다 — 쌍을 더 뽑아도 안 나온다.

### 냉장고 시나리오 — 임박소진을 살리는 장치

기본안대로 **시나리오 2~3개**로 나누고, 각각에 **D-3 임박 재료 2~3개를 필수 포함**한다.

```
시나리오 A  임박: 두부·대파      보통: 달걀·양파·간장
시나리오 B  임박: 돼지고기·애호박  보통: 쌀·마늘·고추장
시나리오 C  임박: 없음           보통: (대조군)
```

C 를 두는 이유는 **"임박이 없을 때의 순서"** 와 비교해야 `f_expiring` 의 효과가
분리되기 때문이다.

### 나머지는 기본안 그대로

| | |
|---|---|
| "둘 다 아니다" | **허용.** 억지 선택은 노이즈다. 학습에서 제외 |
| 5% 중복 출제 | **한다.** 라벨 일관성이 없으면 v0→v1 전환 판단 자체가 불가 |
| 300쌍 미만이면 | 5블록도 포기, 직관값 유지 + 리포트에 "미검증" 명시 |

### 수집 수단 — **구글폼** (개발 0일)

**C 트랙이 화면을 만들지 않는다.** C 는 이미 11일치라 넘치고, 이건 한 번 쓰고
끝나는 수집이다. 쌍 추출 스크립트가 **폼에 붙여넣을 형태로 바로 내보낸다.**

문항에는 **레시피 이름만으로는 부족하다** — 재료와 조리시간을 같이 보여준다.
크롤에 이미지가 0건이라 텍스트로 낸다.

```
"둘 중 어느 쪽을 만들겠습니까?"

A) 김치찌개                    B) 된장찌개
   부족 재료 1개                  부족 재료 0개
   조리 20분                      조리 15분
   재료: 배추김치·돼지고기·두부…   재료: 된장·두부·애호박…

○ A     ○ B     ○ 둘 다 아니다
```

> 🔴 **"둘 다 아니다" 를 반드시 넣는다.** 억지 선택은 노이즈이고,
> 학습에서 제외하면 그만이다.

산출물은 `scripts/reco/bench/pair_export.py` — 630문항(600 + 5% 중복)을 TSV 로 내보낸다.
응답은 스프레드시트로 받아 `scripts/reco/bench/pair_import.py` 가 학습 입력으로 바꾼다.

### 언제 확정하나

**`recipe_feature` 가 채워진 뒤**(A-4 완료 후)에 실측한다. 지금은 0행이라
차분을 계산할 수 없다. **쌍 추출 스크립트는 그전에 만들어 둔다** — A-4 를
기다리는 동안 B 나 C 가 짤 수 있고, 입력이 `recipe_feature` 하나뿐이라

## D-19. 트랙1(오늘의 추천) — **만든다.** 사전 계산 방식 *(09-03)*

메인화면은 **실시간이 아니라 미리 계산한 결과를 조회**한다.
근거는 지연이다 — 사유 10건을 300ms 에 내려면 833 tok/s 가 필요한데
가장 빠른 로컬 모델이 90.9 tok/s 다. **배치로 밀면 시간 제약이 사라진다.**

| | 트랙 1 오늘의 추천 | 트랙 2 잔여 재료 |
|---|---|---|
| 트리거 | 배치 1일 1회 | 실시간 |
| 사유 | **LLM** (실패 시 템플릿) | 템플릿 |
| 응답 | ~30ms (조회만) | ~58ms |

### 저장 테이블을 먼저 만들었다 — `daily_recommendation`

**결정을 미루더라도 테이블은 지금 만드는 것이 옳다.** 나중에 필요해지면
DDL 변경이라 전원이 재초기화해야 한다. 비어 있는 테이블의 비용은 0 이다.

```
user_id · rank · recipe_id · score
reason · reason_source          'llm' | 'template' | 'fallback'
pantry_fingerprint              🔴 stale 판정
config_hash · stats_version     점수 재현
batch_run_id · computed_at
```

### 🔴 `pantry_fingerprint` 가 핵심이다

새벽에 계산했는데 **낮에 재료를 쓰면 사유가 어긋난다** —
"두부가 상하기 전에 쓰세요" 인데 두부를 이미 다 썼다.

계산 시점 냉장고의 지문을 남겨 두고, 조회할 때 현재 값과 비교한다.
다르면 **stale 로 표시**한다. 지문이 없으면 어긋났다는 사실조차 알 수 없다.

### 아직 안 정한 것 — 만들기로 정했으니 이제 답이 필요하다

| | 질문 |
|---|---|
| ① | 트랙2 에 템플릿 사유를 남기나 → **남긴다** (0ms · 디버거와 ablation 이 여기 걸림) |

| ③ | LLM 출력 사람 검수를 누가·언제 (게이트 통과분 잔여 오류 25%) |
| ④ | stale 을 어디까지 허용하나 — 표시만 하나, 재생성하나 |
| ⑤ | 트랙1 Top-N (현재 20, 탐색 2 제외 시 18) |

**②~⑤ 는 배치를 짤 때 정하면 된다.** ① 은 위에 답을 적었다.

> ⏳ 배치 구현 자체는 3주 계획에 없다. **테이블과 계약만 준비**하고,

> 안 만들면 프론트에 알려야 한다.

## D-20. 주고받는 JSONB 칸에 계약을 만들었다 *(09-03 · 구현 완료)*

## D-21. 아직 막지 않은 두 자리 — **B 가 그 코드를 짤 때 같이 막는다**

09-03 조사에서 같은 종류의 공백을 더 찾았다. **주고받는데 형식을 강제하는 것이
없는 자리**다. 둘 다 B 소유이고 아직 코드가 없어서, **지금 제약만 걸어두면
B 가 "이게 왜 있지" 하며 우회할 수 있다.** 짤 때 같이 넣는 편이 낫다.

| 어디 | 어긋나면 | 언제 막나 |
|---|---|---|
| `recommendation_log.model_version` | 난수 점수 행이 실지표에 섞인다 | **B-1** |
| `scoring_config.base_weights` | 과거 점수가 틀리게 재현된다 | **B-11** |

### 왜 위험한가 — 둘 다 조용하다

**`model_version`** — 0단계 동안 쌓이는 행은 점수가 난수다. 걸러내는 장치는
`v_real_recommendations` 뷰의 `NOT LIKE 'mock-%'` 한 줄뿐이라, 쓰는 쪽이 접두어를
안 붙이면 필터가 헛돈다. 실측 — `'mock_linear_v0'`(밑줄)이면 실지표에 그대로 잡힌다.

**`base_weights`** — 17키를 다 넣어야 과거 점수가 재현되는데 **몇 개를 넣든
등록이 성공**한다. 2키만 넣으면 빠진 `f_expiring`(0.15)이 재현 코드에서 0 으로

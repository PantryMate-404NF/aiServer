# 트랙 C — 화면과 평가 도구

> 작성자: 박재우 · 작성일: 2026-09-03

우리는 **냉장고에 있는 재료로 만들 수 있는 요리**를 추천하는 시스템을 만들고 있습니다.
AI 부분은 세 사람이 나눠서 동시에 만듭니다.

- **A** — 레시피 4만 6천 건의 재료를 정리해서, 추천이 실제로 돌아가게 만듭니다.
- **B** — 지금 아무 숫자나 내놓는 점수를 진짜 점수로 바꿉니다.
- **C** — **결과를 눈으로 볼 수 있게 하고, 잘 되고 있는지 재는 도구를 만듭니다.** ← 이 문서

분량은 **10.5일**, 남은 기간은 15영업일입니다.
셋 중 **가장 큰 덩어리이고, 아직 한 줄도 없습니다.**

---

## 무엇을 만드나

### 화면 4종

| 화면 | 무엇을 보는 곳 |
|---|---|
| **홈** | 지금 무엇이 살아 있나 — API·DB 상태, 주요 표의 행 수, 그리고 **지금 보고 있는 게 진짜 엔진인지 가짜 서버인지** |
| **추천 디버거** | 이 사람에게 왜 이게 추천됐나 — 점수가 무엇으로 이뤄졌고, 후보가 어디서 걸러졌나 |
| **검수 큐** | 사람이 재료명을 판단하는 곳 — "다진마늘"은 "마늘"인가? |
| **데이터 품질** | 데이터가 얼마나 채워졌나, 기록이 새고 있지 않나 |

`make up-all` 한 줄로 이 넷이 다 떠야 합니다.

### 평가 도구 — 추천이 좋아졌는지 재는 자

세 가지를 잽니다. K는 "상위 몇 개까지 볼 것인가"이고, 보통 10입니다.

| 이름 | 무엇을 재나 |
|---|---|
| **nDCG@K** | 좋아할 만한 것이 **위쪽에** 있나. 같은 것을 추천해도 아래에 놓으면 점수가 깎입니다. |
| **Recall@K** | 좋아할 만한 것 **전체 중 몇 개를** 상위 K개 안에 담았나. |
| **IPS** | 과거 추천 기록만 가지고 **"다르게 추천했으면 더 나았을까"** 를 되짚어보는 계산. |

**이 자가 틀리면 앞으로 하는 모든 실험이 무의미해집니다.**
그래서 C-2가 이 트랙에서 제일 중요한 작업입니다.

## 지금 어디까지 와 있나

비어 있는 것들입니다.

```
infra/app/ 폴더          없음    ← make up-all 이 지금 빌드 단계에서 실패한다
평가 코드             없음    ← app/services/eval/ 에 threshold.py 하나뿐
검수 큐               0행     ← 여기에 넣는 코드가 리포지토리 전체에 없다
데이터 품질 기록      0행     ← 마찬가지로 쓰는 코드가 없다
추천 기록             0행     ← B가 연결해야 채워진다
재료 정리 결과        0행     ← A의 배치가 채운다
```

하나 더 있습니다. 로그 쓰기가 실패한 횟수를 세는 카운터가 `app/core/counters.py` 에 있는데,
**그 값을 읽는 코드가 하나도 없습니다.** 세어만 놓고 아무도 안 봅니다.

도구도 안 깔려 있습니다 — 지금 `.venv` 에는 streamlit·scikit-learn·pandas가 없습니다.

### 그래도 아무도 기다릴 필요가 없습니다

가짜 서버(`app/main.py`)가 이미 **진짜와 같은 모양의 응답**을 돌려줍니다.
특성값 17종, 점수, 최종 순위, 추천 이유, 후보가 단계별로 얼마나 걸러졌는지까지 전부 채워서 옵니다.
평가 도구 쪽도 합성 데이터만으로 전부 검증됩니다.

그래서 **화면도 평가 도구도 지금 전부 만들 수 있습니다.**
B가 실제 기록을 연결하는 날, `make eval-smoke` 한 줄만 추가로 통과시키면 끝납니다.

## C-2 — nDCG·Recall 정답 고정 + 틀린 구현을 잡는 테스트 · 1일

**무엇을**

`app/services/eval/metrics.py` 를 새로 만듭니다 — nDCG, Recall, MAP, MRR, 쌍 비교 정확도.

라벨을 어떻게 다룰지 **첫 커밋에 못 박습니다.**
nDCG는 음수 라벨을 0으로 깎아서 쓰고, 쌍 비교는 원래 값 그대로 씁니다.
별점을 라벨로 바꾸는 것은 반드시 기존 변환 함수 하나만 거칩니다 —
따로 상수 표를 만들면 **별점 5와 별점 1이 둘 다 0이 되는** 사고가 납니다.

그리고 정답 숫자를 **손으로 박습니다.** 같은 파일에 **고의로 틀린 구현**을 나란히 둡니다.

| | 제대로 만든 것 | 흔히 저지르는 실수 |
|---|---|---|
| nDCG@10 | 0.319147 | 0.501266 |
| Recall@10 | 0.583333 | 0.700000 |

nDCG 쪽 실수는 **0.18만큼 후하게** 나옵니다. 값이 0~1 안에 얌전히 들어 있어서
눈으로는 절대 구분할 수 없습니다. 그래서 테스트가 이 틀린 구현을
**실제로 잡아내는지까지** 확인합니다.

성질 검사 세 가지도 함께 넣습니다.

1. 점수가 같은 것끼리 자리를 바꿔도 값이 변하지 않는다
2. 상위 K 밖에 좋아할 만한 것을 하나 더 붙이면 nDCG@K가 **반드시 내려간다**
3. K 안에서 좋은 것을 위로 올릴 때만 값이 올라간다

**완료 기준**

`make eval-test` 가 위 네 숫자와 성질 세 가지를 전부 확인.

**막히면** 해당 없음. 추천 기록이 0행인 것과 무관하므로 1주차 최우선입니다.

> ⚠️ **조용히 틀리는 방식**
>
> 정답 숫자를 구현으로 만들어내면 **자기가 자기를 채점하는 꼴**이 됩니다 —
> 버그가 들어오면 기대값도 같이 틀려서 초록불이 뜹니다. 그래서 손으로 옮겨 적고,
> 틀린 구현을 옆에 둡니다.
>
> 쓸모없는 테스트도 두 종류 있습니다. 로그의 밑을 2에서 e로 잘못 쓰는 실수는
> 분자와 분모에서 상쇄되어 값이 사실상 안 바뀝니다(차이가 소수점 열여섯째 자리).
> 그걸 잡겠다는 테스트는 **항상 통과하는 빈 테스트**입니다.
> "상관없는 항목을 추가해도 값이 안 변한다"도 정답판과 버그판 둘 다 변화가 0이라
> 아무것도 판별하지 못합니다. 반드시 위 2번(K 밖에 관련 있는 것 추가)이어야 합니다.

## C-3 — 성질 검사 · 0.5일

**무엇을**

성질 검사 다섯 가지 중 남은 둘입니다.

- **누출 검사** — 학습용과 평가용에 **같은 사용자가 겹치지 않는지.**
  (요청 번호가 겹치는지는 정의상 항상 안 겹치므로 검사하지 않습니다.)
- **바깥 기준 대조** — 널리 쓰이는 계산 도구(scikit-learn)와 값이 일치하는지.
  단 조건이 맞을 때만 비교합니다 — 라벨이 0/1이고, 그룹이 하나이고, K가 전체 길이일 때.

`scikit-learn` 을 `.venv` 와 `infra/app/requirements.dashboard.txt` 에 추가합니다.

**완료 기준**

`make eval-test` 에 대조가 포함된 채로 통과.
그리고 scikit-learn이 없는 환경에서 한 번 돌려서,
**건너뛰는 게 아니라 실패하는지** 확인합니다.

**막히면** 해당 없음.

> ⚠️ **조용히 틀리는 방식**
>
> import 실패를 조용히 넘기거나 테스트를 건너뛰게 만들면,
> **바깥 기준이 영원히 안 도는데 화면은 초록입니다.**
> 우리 계산이 맞는지 확인해 줄 유일한 외부 잣대가 조용히 죽습니다.
>
> 반대로 비교 조건을 넓히면(그룹이 여럿이거나 K가 전체보다 작으면)
> 그 도구의 평균 내는 방식이 우리 정의와 달라서
> **우리가 맞는데 테스트가 틀립니다.** 조건을 함수 정의에 박고, 벗어나면 거부합니다.

## C-4 — 나누기·신뢰구간·검출력 · 0.5일

**무엇을**

`app/services/eval/split.py` 를 새로 만듭니다.

- **나누는 방식 두 가지** — 시간으로 자르기, 사람으로 자르기
- **신뢰구간** — **사람 단위로** 복원추출하고, 뽑힌 사람의 요청은 통째로 가져갑니다
- **검출력** — "얼마나 큰 차이라야 알아볼 수 있나"를 매 실행마다 찍습니다.
  가정하지 말고, 그때그때 실제로 잰 흩어짐(sd)과 상관(rho)으로 계산합니다.

  ```
  MDE = 2.8016 × sd × √(2×(1−rho)) / √n
  ```

시간으로 자른 결과에는 코드가 **주의 문구를 강제로 붙이게** 합니다(아래 참조).

**완료 기준**

`make eval-test` 가 다음을 확인 —
사람으로 자르면 양쪽에 겹치는 사람이 없다 /
시간으로 자르면 평가 데이터가 전부 학습 데이터보다 뒤다 /
`sd=0.30, rho=0.7, n=200` 일 때 값이 `0.046` ±0.001 /
실행 출력에 sd·rho·MDE 세 값이 실제로 찍힌다.

**막히면** 해당 없음 — 합성 데이터로 전부 검증됩니다.

> ⚠️ **조용히 틀리는 방식**
>
> 요청 하나하나를 단위로 복원추출하면, 같은 사람의 요청들은 같은 냉장고와
> 같은 취향을 공유해서 서로 독립이 아닌데도 **신뢰구간이 좁게 나옵니다.**
> 자릿수가 그럴듯해서 "차이가 의미 있다"는 결론이 조용히 뒤집힙니다.
>
> 그리고 시간으로 자르는 것은 지금 실사용자 기록이 한 주에만 몰려 있어서,
> 자르는 선이 **시간에 따른 변화가 아니라 가입 시기 차이**를 자릅니다.
> 검사는 통과하지만 그 검사가 보장하는 게 없습니다.
> 주의 문구 없이 대표 숫자로 쓰면 틀린 결론이 리포트에 그대로 남습니다.

## C-5 — IPS · 0.5일

**무엇을**

`app/services/eval/ope.py` 를 새로 만듭니다.
IPS는 과거 기록으로 "다르게 추천했으면 어땠을까"를 되짚는 계산인데,
**결론부터 말하면 지금은 못 씁니다.**
이 작업의 목적은 **못 쓴다는 것을 숫자로 돌려주는 것**입니다.

돌려줄 것: 추정값, 실제로 쓸 수 있는 표본 수, 가중치가 얼마나 흩어졌나,
잘라낸 건수와 비중, 신뢰구간 폭, 그리고 **쓸 수 있나 없나.**

쓸 수 있다고 판정하는 기준은 **실제로 쓸 수 있는 표본 1,800건 이상**입니다.
이건 "클릭률 10%에서 2%p 차이를 알아보려면"이라는 조건에서 계산해 나온 값입니다 —

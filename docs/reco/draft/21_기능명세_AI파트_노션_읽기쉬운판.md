# AI 파트가 만들 기능

> 작성자: 박재우 · 작성일: 2026-09-03

우리는 **냉장고에 있는 재료로 만들 수 있는 요리**를 추천하는 시스템을 만들고 있습니다.
그중 AI 파트가 맡은 기능을 **화면 순서대로** 정리했습니다. 기능은 모두 14개입니다.

괄호 안 글자(`MAIN-000` 같은 것)는 기능 코드입니다.

| 어디 | 무엇 |
|---|---|
| 메인화면 | 오늘의 추천 (MAIN-000) |
| 레시피 | 보유 재료 기반 추천 (RECIPE-001) · 레시피 상세 정보 (RECIPE-021) |
| 온보딩 | 취향 측정 (MAIN-021) |
| 팬트리 | 보유 재료 관리 (PANTRY-020) |
| 데이터 | 재료 이름 정리 (DATA-006) · 레시피 특성 만들기 (DATA-007) · 검수 도구 (DATA-022) |
| 공통 | 추천 기록 (COMMON-020) · 사용자 행동 수집 (COMMON-021) · 추천 API (COMMON-022) |
| 평가 | 추천 품질 평가 (EVAL-002) |
| 대시보드 | 추천 디버거 (VIEW-020) · 데이터 품질 화면 (VIEW-021) |

## 메인화면

### 오늘의 추천 (MAIN-000)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 미리 계산해 두기 | 하루에 한 번, 사용자마다 추천 목록을 미리 계산해 둡니다. 화면은 계산해 둔 결과를 가져다 보여주기만 합니다.<br>계산할 때 **그 사람이 그때 무슨 재료를 갖고 있었는지도 같이 저장**합니다. 나중에 열어봤을 때 지금 가진 재료와 다르면 '오래된 추천' 이라고 표시합니다 — 새벽에 "두부가 상하기 전에" 로 계산해 뒀는데 낮에 두부를 다 쓴 경우가 있습니다. |
| 추천 사유 문구 | 추천한 항목마다 "왜 이것인가" 를 한 문장으로 붙입니다. 미리 계산할 때 같이 만듭니다.<br>그 문구가 **어디서 나왔는지**(생성모델 · 정해진 틀 · 대체 문구)도 같이 저장합니다. 어느 쪽이 더 나은지 나중에 비교하려면 구분이 있어야 합니다. |
| 목록 돌려주기 | 상위 20개를 돌려줍니다(기본값). 항목마다 부족한 재료 · 조리시간 · 난이도를 같이 줍니다. |
| **지금 어디까지 됐나** | 결과를 담을 표는 준비 끝났습니다. 하지만 **조회 API 와 계산 배치는 아직 없습니다** — 3주 계획 밖입니다.<br>기간 안에 못 만들면 프론트에 알립니다. **화면이 이 기능이 있다는 전제로 그려지면 안 됩니다.** |

## 레시피

### 보유 재료 기반 추천 (RECIPE-001)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 후보 고르기 | 갖고 있는 재료로 만들 수 있는 레시피를 찾습니다. 재료가 몇 개까지 부족해도 봐줄지는 요청할 때 정합니다(기본 2개). |
| 알레르기 제외 | 사용자의 알레르기 재료가 들어간 레시피는 결과에서 **뺍니다.** 양념·고명까지 레시피의 모든 재료를 봅니다.<br>알레르기 그룹을 고르면 그 그룹 재료 전부로 넓힙니다. 재료 하나만 적어도 같은 그룹 전체로 퍼집니다.<br>**점수를 깎는 게 아니라 아예 뺍니다.** |
| 점수 매기기 | 항목별 점수를 비중대로 더해 순위를 정합니다.<br>재료 충족도 24% · 맛 선호 16% · 소비기한 임박 15% · 선호·기피 재료 11% · 함께 쓰는 재료 10% · 인기도 10% · 부족 재료 수 5% · 요리 계열 4% · 조리시간 3% · 제철 2% (설계상 합 100%)<br>이 중 **요리 계열과 제철은 아직 데이터가 없어 계산되지 않습니다.** 그래서 오늘 실제로 도는 것은 나머지 8개, 합쳐서 94% 입니다. 값이 있는 항목만으로 다시 나눠 100% 로 맞춥니다. 데이터가 들어오면 비중을 다시 정할 필요 없이 그대로 켜집니다. |
| 점수 깎기 | 최근에 보여준 레시피, 최근에 만든 레시피, 기피 재료가 든 레시피는 점수를 깎습니다. |
| 목록 다양하게 | 비슷한 레시피가 연달아 나오지 않게 조정합니다. 상위 후보 중 일부는 탐색용으로 섞어 넣습니다.<br>탐색용 항목은 목록 **여기저기에 흩어 놓습니다.** 점수 순서대로 두면 늘 비슷한 자리에 오게 되고, 그러면 "위에 있어서 눌린 것" 과 "좋아서 눌린 것" 을 나중에 구분할 수 없습니다. |
| 돌려주는 것 | 레시피 정보 · 부족한 재료 목록 · 점수 · 순위 · 추천 사유. 여기에 **요청 번호**를 같이 줍니다(나중에 사용자 행동을 모을 때 씁니다). |
| 하나도 없을 때 | 조건에 맞는 게 0건이면 부족 재료 허용 개수를 늘려 다시 찾습니다. 그래도 없으면 인기 레시피로 채웁니다. |

| 세부 기능 | 무엇을 하나 |
|---|---|
| 기본 정보 | 레시피명 · 재료 목록 · 조리 순서 · 조리시간 · 난이도 · 인분 |
| 원본 출처 | 원본 페이지 링크를 같이 줍니다 |

## 온보딩

### 취향 측정 (MAIN-021)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 보여줄 레시피 목록 | 대표 레시피 20종을 프론트에 줍니다. 맛이 **최대한 서로 다르게** 고릅니다. |
| 응답 저장 · 맛 취향 만들기 | 사용자가 고른 레시피 3개로 맛 취향 값을 만듭니다. 매움 · 짠맛 · 단맛 세 가지 척도 응답도 반영합니다.<br>**고른 레시피 번호와 척도 응답을 원본 그대로 보관합니다.** 맛 취향 값은 고른 레시피들의 평균이라, 결과만 저장해두면 기준 레시피의 맛 값이 바뀔 때 다시 계산할 수 없습니다. 원본이 없으면 사용자를 처음부터 다시 모아야 합니다. |
| 알레르기 등록 | 알레르기 그룹 10종에서 고르고, 재료명을 직접 적을 수도 있습니다. 등록한 값은 추천에서 빼는 조건으로 씁니다.<br>**알레르기로 등록한 항목은 반드시 '차단' 등급으로 저장합니다.** 등급을 안 정하면 같은 그룹으로 퍼지지 않아서 본인이 적은 재료만 걸러집니다 — 아몬드만 등록했는데 호두와 잣이 그대로 추천되는 식입니다. |
| 기피 재료 등록 | 재료명 3개까지 받습니다. 점수를 깎는 데 씁니다 — 알레르기와 달리 **빼지는 않습니다.** |
| 가구원 수 등록 | 1~10 (11 이상은 거부). 선택 항목이라 안 받아도 나머지는 저장됩니다. |

## 팬트리

### 보유 재료 관리 (PANTRY-020)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 재료 등록·삭제 | 재료명 · 수량 · 단위 · 구매일 · 소비기한 |
| 소비기한 추정 | 소비기한을 안 넣으면 구매일에 재료별로 먹을 수 있는 일수를 더해 추정합니다.<br>**기준은 앱에 등록한 날이 아니라 산 날입니다** — 사고 사흘 뒤에 등록해도 사흘을 손해보지 않습니다.<br>사용자가 직접 넣은 값이 추정보다 우선입니다. 구매일이 미래일 수는 없습니다. |
| 다 먹었나 · 버렸나 | 지울 때 다 먹어서인지 버려서인지 고르게 합니다. 답을 안 해도 됩니다.<br>그 사유는 항목이 목록에서 사라진 뒤에도 남깁니다 — 행을 지워버리면 **무엇을 얼마나 버렸는지 다시는 셀 수 없습니다.** |
| 소비기한 임박 반영 | 곧 기한이 되는 재료가 든 레시피를 추천에서 밀어줍니다.<br>기준은 파는 쪽 기한이 아니라 **먹을 수 있는 기한(소비기한)** 입니다.<br>임박했는지는 **한국 시간 기준 오늘 날짜**로 판단합니다. 시간대가 어긋나면 자정부터 오전 9시 사이에 하루 전 날짜로 계산됩니다. |

## 데이터

### 재료 이름 정리 (DATA-006)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 표기 정리 | 재료 원문에서 수량 · 단위 · 덧붙은 표현을 떼어냅니다 |
| 사전에 연결 | 정리한 표기를 재료 사전 항목에 연결합니다. **정확히 같은 것 → 다른 이름 → 규칙** 순으로 봅니다 |
| 못 붙인 것 처리 | 사전에 없는 표현은 사람이 볼 목록에 쌓아둡니다. **임의로 만들어 넣지 않습니다.** |
| 도구·비식재료 빼기 | 도구 · 용기 · 소모품 표현은 재료에서 뺍니다 |
| 역할 판정 | 레시피마다 주재료와 양념을 나눕니다. 기본 양념은 항상 갖고 있는 것으로 칩니다 |

### 레시피 특성 만들기 (DATA-007)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 재료 목록 구성 | 레시피마다 주재료 목록과 전체 재료 목록을 만듭니다 |
| 맛 특성 수치화 | 재료 구성으로 그 레시피의 맛 특징을 숫자로 냅니다 |
| 비슷한 것끼리 묶기 | 비슷한 레시피를 묶어 목록 다양화에 씁니다 |
| 추천 대상 판정 | 재료 정보가 없는 레시피는 추천 대상에서 뺍니다 |
| 시험용 데이터 격리 | 시험·검증하려고 만든 가짜 특성에는 표식을 달아, 실제 추천 조회에서 자동으로 빠지게 합니다. 쓰려면 조회할 때 따로 요청해야 합니다(기본은 제외) |

### 검수 도구 (DATA-022)

| 세부 기능 | 무엇을 하나 |
|---|---|

| 검수 결과 반영 | 사람이 확정한 결과를 사전에 넣고 다시 정리합니다 |

## 공통

### 추천 기록 (COMMON-020)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 추천 이력 저장 | 추천 한 건마다 어떤 조건으로 요청했는지 · 점수 근거 · 보여준 목록을 저장합니다.<br>**저장이 실패해도 추천 응답까지 실패하지는 않습니다.** |
| 기록 실패 세기 | 실패한 건수를 세어 대시보드에 보여줍니다 |

### 사용자 행동 수집 (COMMON-021)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 이벤트 수집 | 노출 · 클릭 · 저장 · 저장취소 · 조리완료 · 평점 · 관심없음 · 검색<br>**요청 번호와 몇 번째 자리였는지**를 같이 받습니다.<br>접속 번호 앞에 사용자 구분 글자를 붙여서 받습니다 — 실사용자 · 게스트 · 개발/디버거. 개발하며 만든 기록이 섞인 채로 쌓이면 나중에 지표에서 걸러낼 수 없습니다. |
| 노출 기록 | 추천 목록에 담긴 항목을 '보여준 것' 으로 기록합니다.<br>무엇을 근거로 '보여줬다' 고 판정했는지도 나눠 저장합니다 — 서버가 내보낸 목록인지, 화면에 실제로 보인 것인지, 앱이 보고한 것인지. 구분이 있어야 나중에 방식을 바꿔도 옛 데이터와 섞이지 않습니다. |

### 추천 API (COMMON-022)

| 세부 기능 | 무엇을 하나 |
|---|---|
| 추천 요청 | 사용자 ID · **세션 식별자** · 몇 개 받을지 · 재료가 몇 개까지 부족해도 되는지 · 조리시간 상한.<br>세션 식별자를 안 보내면 게스트로 기록되고, 나중에 되돌릴 수 없습니다. |
| 행동 전송 | 이벤트를 한 건씩 보냅니다 |
| 온보딩 저장 | 온보딩 응답을 사용자당 한 번 저장합니다 — 고른 레시피 · 맛 척도 세 가지 · 알레르기(그룹과 재료) · 기피 재료 · 가구원 수.<br>만들어진 맛 취향 값과 차단되는 재료가 몇 개인지를 돌려줍니다. 척도 범위를 벗어난 값은 거부합니다. |
| 보유 재료 조회·수정 | 조회, 그리고 한꺼번에 수정. 수정할 때 없어진 재료에 대해 다 먹었는지 버렸는지도 같이 받습니다 |
| 재료·레시피 검색 | 이름 자동완성 |
| 추천 근거 조회 | 요청 번호로 그 추천 한 건의 점수 근거와 단계마다 후보가 몇 개였는지를 봅니다. 디버거 화면이 씁니다 |
| 헬스체크 | 서비스가 살아 있는지 확인 |

| 세부 기능 | 무엇을 하나 |

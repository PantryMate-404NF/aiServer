# 트랙 A — 데이터

> 작성자: 박재우 · 작성일: 2026-09-03

우리는 **냉장고에 있는 재료로 만들 수 있는 요리**를 추천하는 시스템을 만들고 있습니다.
그중 A가 맡은 일은 **레시피 4만 6천 건의 재료를 정리해서, 추천이 실제로 돌아가게 만드는 것**입니다.

지금 실제 데이터로 나오는 추천은 **0건**입니다. 이유가 여기 있습니다.
레시피마다 "이 요리에 꼭 필요한 재료가 무엇인가"를 정리해 둔 표가 **통째로 비어 있어서**,
추천 엔진이 읽을 것이 없습니다. B가 만드는 점수 계산도 **비중의 81%가 A가 채울 값에 묶여** 있습니다.

**3주 뒤 이런 모습이면 성공입니다.**

- 레시피 4만 6천 건의 특성이 실제 데이터로 채워져서, 추천 후보 조회가 가짜가 아닌 진짜 결과를 돌려준다
- 맛 점수가 "무작위로 고르는 것보다 낫다"는 것이 숫자로 증명된다
- 그 전부가 `make feature-test` 한 줄로 매번 다시 확인된다 — 조용한 유실이 네 번째로 일어나지 않게

> 공통 규칙(환경 만들기, 서로 부딪히지 않는 법)은 [03_작업분담_공통.md](03_작업분담_공통.md) 를 먼저 읽으세요.

## 지금 어디까지 와 있나

데이터 자체는 이미 들어와 있습니다.

```
레시피         46,353건
재료 목록     451,862줄   ← 아직 사람이 쓴 문장 그대로다
후기          62만 건
```

문제는 **정리된 것이 하나도 없다**는 점입니다.

| 무엇 | 지금 상태 |
|---|---|
| 레시피별 재료 정리 결과 | 비어 있음 |
| 레시피 특성 (필수 재료·맛·인기도) | 비어 있음 |
| 재료가 몇 개 레시피에 나오는지 세어 둔 값 | 536종 **전부 0** |
| 재료 이름을 알아본 비율 | 80.8% — 나머지 20%는 버려지고 있음 |
| 레시피 상태 표시 | 46,353건 전부 "아직 정리 안 됨" |

A-1(재료 사전을 DB에서 읽어오는 부분 고치기)만 **9월 2일에 끝났습니다.**
남은 작업은 다 합쳐 **8일 남짓**입니다.

## 내가 만든 것을 누가 쓰나

| 무엇을 만드나 | 누가 쓰나 | 왜 필요한가 |
|---|---|---|
| **레시피 특성 표** (`recipe_feature`) 4만 6천 행 | B·C | 추천이 실제로 읽는 **유일한** 표 |
| **맛 6축의 전체 평균** (`feature_stats`) | B | 맛 점수를 재는 기준점 |
| **레시피별 재료 표** (`recipe_ingredient`) 약 35만 행 | C | 화면의 '부족한 재료' 표시, 재료로 레시피 거꾸로 찾기 |
| **배치 실행 기록** (`batch_run`) | C | 관측 화면이 그리는 원천 |
| **견본 파일 30건** (`app/services/normalize/fixtures/feature_golden.json`) | B·C | 데이터베이스 없이도 테스트를 돌릴 수 있게 |
| **`make feature-test`** | B·C | 표 구조를 건드린 사람이 돌려야 하는 검사 |

### B에게 꼭 말할 것

**1. 맛의 평균값을 문서에 적지 마세요.** 표본이 조금만 달라져도 15~20% 움직이는 값입니다.
적어두면 B가 코드에 그대로 베껴 넣을 위험이 있고, 그러면 기준이 어긋난 채 **에러 없이** 돕니다.
B는 `feature_stats` 의 **가장 최근 행에서 읽습니다.**

**2. 평균은 레시피 쪽과 사용자 취향 쪽에서 똑같이 뺍니다.** 한쪽만 빼면 서로 다른 자를 대고
재는 셈이 되어 역시 에러 없이 틀립니다. 그리고 **어떤 평균을 썼는지 추천 기록에 같이
남겨야** 합니다 — 안 남기면 평균을 새로 계산하는 순간 **과거 점수를 다시 계산할 수 없습니다.**

**3. 요리 종류(한식·중식)로 점수를 매기는 건 불가능합니다.** 원본에 그런 분류가 아예 없습니다.
비중표는 **그대로 둡니다.** 이 항목의 값만 "없음"으로 내보내면, 점수를 낼 때
없는 항목은 위아래에서 **함께 빠집니다**(나눗셈). 그래서 몫을 다른 데로 옮길
필요가 없습니다 — 옮기면 오히려 나중에 점수를 되돌려 계산할 수 없게 됩니다.

### C에게 말할 것

재료 표에 `match_method` 가 `fuzzy` 나 `embed` 인 행이 보이면 **규약 위반이니 신고**해 주세요.
"비슷해 보이니까 이거겠지" 로 자동 확정한 재료는 들어가면 안 됩니다.

나중에 C가 검수 화면을 만들면 A는 지금의 TSV 시트 대신 검수 큐 테이블에 직접 넣도록 바꿉니다.
그전까지는 **TSV 파일이 인터페이스**입니다.

있어서 "어느 쪽 id 냐"를 못 정하고 에러가 났습니다. `i.id`, `i.name` 처럼 어느 표인지

> **'돼지고기' 자리에 '닭고기'를 넣은 채 에러 없이 계속 돕니다.**

## A-2 — 재료 정리 프로그램 만들기

**기간** 1일 · **먼저** A-1

**무엇을**

`app/services/normalize/batch.py` 를 만듭니다. 사람이 쓴 재료 문장을 읽어서 → 다듬고 → 사전의
재료와 짝지어 주고 → 역할(필수·양념·선택)을 판정해서 → 정리된 재료 표에 넣습니다.

이미 있는 `coverage.py` 를 본으로 삼되, 입력이 파일이 아니라 데이터베이스입니다.
옵션은 세 개: `--limit N`(몇 건만) / `--truncate`(싹 지우고 다시) / `--dry-run`(쓰지 않고 확인만).

저장은 레시피 2,000건 단위로 끊어서 합니다. 이때 **한 번에 보낼 개수를 반드시 명시**하세요.
데이터를 한꺼번에 밀어 넣는 함수의 기본 묶음 크기 때문에 **후기 62만 건이 2만 9천 건으로
줄어든 적**이 있습니다. 에러는 안 났습니다.

**🔴 중단된 곳부터 이어서 하는 기능은 만들지 않습니다.**
전량이 **9분**이면 끝나기 때문입니다(2,000건에 22.6초 → 45만 줄 약 525초).
이어붙이기 로직의 버그가 그 9분보다 비쌉니다. 대신 ① 2,000건마다 진행 상황을 찍고
② `--truncate` 로 언제든 처음부터 다시 돌립니다.

**완료 기준**

```
.venv/bin/python -m app.services.normalize.batch --limit 2000 --truncate
```

이걸 **두 번** 돌린 뒤 `SELECT count(*) FROM recipe_ingredient` 가 **두 번 같은 수**여야 합니다.
그리고 `--dry-run` 은 데이터베이스를 건드리지 않아야 합니다(개수 변화 없음).

**막히면**

A-1이 늦어지면 파일에서 사전을 읽는 방식으로 `--dry-run` 경로만 먼저 만들고,
**쓰기는 붙이지 마세요.**

> ⚠️ **조용히 틀리는 방식**
>
> 정리된 재료 표는 (레시피, 재료) 조합이 열쇠라서, **한 레시피에 같은 재료가 두 번 나오면
> 한 줄로 접힙니다.** 실제로 2,941개 레시피 중 **577건(19.6%)** 에서 이런 충돌이 있었고,
> 그중 3건은 역할이 서로 달랐습니다.
>
> "먼저 온 것을 남긴다"로 처리하면, '간장'이 재료칸(→필수)과 양념칸(→양념)에 둘 다 있을 때
> **적힌 순서에 따라 결과가 달라집니다.** 에러 없이, 돌릴 때마다 다르게.
> 파이썬에서 먼저 **역할 우선순위(필수 > 양념 > 고명 > 선택)로 합친 다음** 넣어야 합니다.

## A-3 — 45만 줄 전량 정리 1회차

**기간** 0.5일 · **먼저** A-2

**무엇을**

`make normalize-batch` 타깃을 Makefile에 추가하고 451,862줄 전량을 돌립니다.
돌린 뒤 확인용 조회문 묶음을 `app/services/normalize/batch_verify.sql` 로 남깁니다 —
행 수, 어떤 방식으로 재료를 알아봤는지 분포, 역할 분포, 레시피당 재료 개수 분포.

**완료 기준**

15분 안에 끝나야 하고, 다음이 전부 맞아야 합니다.

- 정리된 재료 행 수가 **34만~37만 사이** (예상치 46,353 × 7.65 = 354,600)
- 재료를 알아본 방식이 `exact`·`alias`·`rule` **세 가지만** 존재. `fuzzy`·`embed` 는 0건
- 역할은 **필수·양념·선택 세 가지만** 나오고 **고명은 0건이어야 정상**입니다. 고명 판정이
  꺼져 있고, 원문 재료칸 이름이 451,862줄 전부 '기본재료'라 규칙이 돌 일이 없습니다.
  **🔴 0이 아니면 뭔가 켜진 것이므로 실패로 봅니다.**

```sql
SELECT count(*) FROM recipe_ingredient WHERE role='garnish';   -- 0 이어야 함
```

**막히면**

`--limit 10000` 으로 일부만 넣고 A-4를 먼저 진행하세요.
단, **일부만 넣었다는 사실을 배치 기록에 남겨서** 나중에 착각하지 않게 하세요.

> ⚠️ **조용히 틀리는 방식**
>
> **행 수만 보고 넘어가는 것.** 35만이라는 숫자는 **알아본 재료만** 센 것입니다.
> 못 알아본 **8만 7천 건은 표에 아예 안 들어가서** 결과가 오히려 '깔끔하게' 보입니다 —
> 20%를 버렸다는 사실이 **어떤 숫자에도 나타나지 않습니다.**
> A-4에서 "못 알아본 재료 수"를 채워야만 이걸 되짚어 볼 수 있습니다.

## A-14 — 재료별 등장 횟수 채우기  🔴

**기간** 0.25일 · **먼저** A-3

**무엇을**

재료마다 "몇 개 레시피에 나오는가"를 세어 두는 칸이 **536종 전부 0**입니다.
그런데 **B의 작업 지시서가 A를 선행으로 지목**하고 있습니다. B가 "이 두 재료는 같이
잘 쓰인다"를 계산할 때 흔한 재료의 비중을 낮추는 데 이 값이 필요합니다.

정리가 끝나면 한 문장이면 됩니다.

```sql
UPDATE ingredient i SET freq_count = c.n
FROM (SELECT ingredient_id, count(DISTINCT recipe_id) n
      FROM recipe_ingredient GROUP BY 1) c
WHERE c.ingredient_id = i.id;
```

**완료 기준**

```sql
SELECT count(*) FILTER (WHERE freq_count > 0), count(*) FROM ingredient;
```

앞 값이 **400 이상**. 그리고 가장 많이 나온 재료 5종이 상식과 맞는지 **눈으로 확인**하세요
(소금·간장·설탕 같은 것이 위에 와야 합니다).

**막히면**

**지금 0이라는 사실을 B에게 알리세요.** B가 모르면 "흔한 재료와 귀한 재료를 구분한다"는
계산이 조용히 망가진 채로 돕니다.

> ⚠️ **조용히 틀리는 방식**
>
> 이 값이 0이면 계산식이 0으로 나누기가 되거나, 방어 코드가 있으면 **모든 재료의 가중치가
> 똑같아집니다.** 예외도 안 나고 점수도 정상 범위입니다.
> **"소금과 트러플을 구분한다"는 의도만 소리 없이 사라집니다.**

## A-4 — 레시피 특성 만들기

**기간** 1일 · **먼저** A-3

> ✅ **이미 정해진 것** ([결정사항](05_작업분담_결정사항.md))
> 필수 재료가 0개인 레시피(7.2%) 중에서, **못 알아본 재료의 비율이 30%를 넘으면
> 정리 실패로 보고 추천에서 뺍니다.** 30%라는 기준은 임시값이고, 실제 분포를 보고
> 조정하면 됩니다 — 특성 표를 다시 만들면 되므로 **되돌릴 수 있습니다.**
> 🔴 품질 보고할 때 **정상과 실패를 반드시 따로 세세요.**

**무엇을**

`app/services/normalize/feature_build.py` 를 만듭니다. 정리된 재료 표 + 재료 사전 + 레시피를 읽어서
**레시피 특성 표**를 채웁니다.

**🔴 "물·쌀은 필수 재료가 아니다"를 두 겹으로 겁니다.**
역할 판정 단계가 이미 이런 기본 재료 39종을 양념 쪽으로 보냅니다. 그런데 39종 중
**24종만 양념 목록과 겹치고, 15종은 '기본 재료' 표시로만 걸러집니다** — 쌀·밀가루·전분·참깨와
물의 온갖 표기(생수·수돗물·끓는물·얼음 등 11가지).
그래서 조회문에서도 `role='essential' AND NOT i.is_staple` 로 **한 번 더** 겁니다.
앞 단계만 믿으면 검수나 수동 수정이 역할을 바꿨을 때 **물과 쌀이 필수 재료에 들어갑니다.**

채우는 것:

- **필수 재료 목록** — 역할이 필수이면서 기본 재료가 아닌 것
- **전체 재료 목록** — 전부. 🔴 단 **조리도구는 뺍니다** (도마 2,259회·냄비 등, 파싱된 것의 5.8%).
  알레르기 차단은 이 목록으로 판단하는데, 거기에 냄비가 섞이면 안 됩니다
- **분류 목록** — 재료가 속한 갈래
- **필수 재료 수 / 전체 재료 수 / 못 알아본 재료 수** ← 마지막 것을 꼭 채우세요
- 조리 시간, 난이도 그대로 복사
- 레시피 상태를 '아직 정리 안 됨' → '정리됨' 으로 (지금 46,353건 전부 전자입니다)

**완료 기준**

`make feature-build` 후 조회 6줄이 전부 통과.

1. 특성 표가 **46,353행**
2. 필수 재료 목록에 기본 재료(물·쌀 등)가 들어간 레시피가 **0건**

   ```sql
   SELECT count(*) FROM recipe_feature rf
   WHERE EXISTS(SELECT 1 FROM ingredient i
                WHERE i.is_staple AND i.id = ANY(rf.essential_ids));
   ```
3. 전체 재료 수 = 실제 목록 길이 (전 행 일치)
4. 필수 재료 수 ≤ 전체 재료 수 (전 행)
5. 못 알아본 재료 수의 합이 **0보다 큼** (0이면 안 채운 것입니다)
6. 레시피당 평균 필수 재료 수가 **2.7~3.3** (실측 2.99, 중앙값 3)

**막히면**

A-3에서 일부만 넣었다면 그것으로 만들고 나중에 전량을 다시 돌리세요.
이 프로그램은 **몇 번을 돌려도 같은 결과**라 다시 돌리는 비용이 없습니다.

> ⚠️ **조용히 틀리는 방식**
>

## A-6 — 인기도 점수

> 실제로 저장된 행 수(624,422)를 쓰면 후기를 파싱하는 규칙이 바뀔 때마다 인기도가 흔들립니다.
> 계산은 **로그를 씌운 뒤 순위 ÷ 전체 개수.**
> 🔴 백분위 함수(`percent_rank`)가 아니라 **줄 번호(`row_number`)** 를 씁니다 —
> 동점이 8,470건이나 몰려 있어서 백분위를 쓰면 구간이 비고, 후보를 500개로 자르는 지점이
> 돌릴 때마다 달라집니다. 그러면 **같은 요청의 점수를 다시 만들어 낼 수 없게 됩니다.**

**무엇을**

후기 개수의 실제 분포(46,353건)를 먼저 보세요.

```
최소 0 · 최대 1,079 · 평균 13.54 · 중앙값 4 · 상위10% 25 · 상위1% 181
후기가 0건인 레시피는 단 1개
```

**꼬리가 극단적입니다**(중앙값 4인데 최대 1,079). 최소~최대로 늘려 펴면 상위 1%가 나머지
전부를 0.02 근처로 눌러버려서 인기도가 사실상 **있다/없다 두 값**이 됩니다. 그래서
**로그를 씌운 뒤 순위(순위 ÷ 전체)** 를 씁니다 — 0~1에 고르게 퍼지는 것이 보장됩니다.

**🔴 품질 점수는 만들 재료가 없습니다.** 평점 평균 0건, 평점 개수 0건, 조회수 0건 —
크롤에 평점이 **아예 없습니다.** B의 비중표에서도 이 항목은 0이므로 **0으로 두고 그 이유를
컬럼 설명과 배치 로그에 남깁니다.** 후기 개수로 억지로 만들면 인기도와 사실상 같은
**가짜 축이 하나 느는 것뿐**입니다.

**완료 기준**

```sql
SELECT min(popularity_score), max(popularity_score),
       corr(popularity_score, ln(1+r.review_count))
FROM recipe_feature f JOIN recipe r USING(recipe_id);
```

최솟값 ≈ 0, 최댓값 ≈ 1, **상관계수 0.92 이상.**

🔴 여기서 **0.99를 요구하면 어떤 구현도 통과 못 합니다.** 실측이 이렇습니다.

```
percent_rank 0.9264 · cume_dist 0.9347 · row_number 0.9242 · 최소최대 0.6532
```

순위 방식은 원래 값을 **등간격으로 펴기 때문에** 로그값과의 직선 상관이 1이 될 수 없습니다
(순위끼리 비교하면 0.99를 넘습니다).

그리고 10구간 히스토그램이 각 구간 **4,600±500** 이어야 합니다 — 순위니까 고르게 나옵니다.
품질 점수는 `SELECT count(*) FROM recipe_feature WHERE quality_score <> 0` 이 **0**.

**막히면**

없습니다 — 후기 개수만 있으면 되므로 A-4와 나란히 진행할 수 있습니다.

> ⚠️ **조용히 틀리는 방식**
>
> **후기 개수가 두 개 있습니다.** 하나는 크롤 원문에 적힌 개수(627,610 기준),
> 다른 하나는 실제로 저장된 624,422건(본문이 빈 것 제외).
> **어느 쪽으로 계산했는지 안 적어두면 나중에 아무도 재현하지 못합니다** —
> 두 값 다 그럴듯해서 틀린 걸 알아챌 수가 없습니다.
>
> 두 번째: **순위는 레시피가 늘면 전부 바뀝니다.** 크롤을 추가하면 과거 점수를
> 다시 만들 수 없게 되므로, **계산 시점의 레시피 개수를 배치 기록에 남기세요.**

파일이 있고, `.venv/bin/python -m app.services.normalize.fixtures.check` 가
30건 전부 현재 표의 칸 구성과 일치하는지, 그리고 필수 재료 0개인 경우가 5건 들어 있는지
확인해 줍니다. B에게 **파일 경로와 불러오는 예시 3줄**을 전달하세요.

**막히면**

없습니다.

> ⚠️ **조용히 틀리는 방식**
>
> **정상 케이스 30건만 넣는 것.**
> B의 점수 계산기가 이런 것들을 만나면 —
>
> ```
> 필수 재료 0개      7.2%
> 맛 값이 전부 0     0.3%
> 조리 시간 없음     4.47%
> ```
>
> 에러가 나는 게 아니라 **말도 안 되는 값이나 '만점'을 조용히 내놓습니다.**
> 견본에 이런 경계 사례가 없으면 그 버그는 **실데이터에서만** 나타나고,
> 그때는 원인이 A인지 B인지 아무도 모릅니다.

## A-10 — 검수 시트 발주

**기간** 0.5일 · **먼저** 없음 (A-3과 나란히)

> ✅ **이미 정해진 것** ([결정사항](05_작업분담_결정사항.md))
> 검수 후보를 담는 형식과 **시트를 만드는 프로그램은 C가 만듭니다.**
> **A는 못 알아본 재료 목록만 넘깁니다.**

**무엇을**

이게 **재료 인식률을 올리는 유일한 길**입니다. 실측을 보세요.

```
못 알아본 표현        24,701종
그 표현들의 등장       86,846건
```

전부 볼 필요는 없습니다. **상위 300종이 못 알아본 것의 44.8%를 덮습니다.**

```
상위 300종 →  인식률 80.8% → 89.4%
상위 500종 →  인식률 80.8% → 90.6%
```

목표치가 85%이므로 **300종만 봐도 넘습니다.** 한 건 판정에 15초로 잡으면 **75분**입니다.

지금 `scripts/reco/bench/out/review_sheet.tsv` 에 2,000행이 있지만 **결정 칸이 0건 기입** —
검수가 아직 시작도 안 됐습니다. 상위 4종은 사전에서 빠진 게 확실하니 미리 표시해 두세요.

```
밥 2,738 · 깨소금 2,419 · 매실액 1,723 · 참치액 962
```

`make review-sheet TOP=300` 으로 다시 뽑아서 담당자에게 넘깁니다.

**완료 기준**

시트가 **300행 + 안내 헤더**로 다시 만들어지고, **상위 20종은 후보가 3개씩 다 채워져** 있을 것
(빈 후보가 있으면 "15초에 한 건" 이 깨집니다). 넘겼다는 사실을 `docs/reco/design/08_CHANGELOG.md` 에 기록.
**칸을 채우는 건 사람 몫이므로 A의 완료 조건에는 넣지 않습니다.**

**막히면**

**사람이 시트를 안 채우면 기다리지 않습니다.**
상위 **50종만 직접 판정**해서 `seeds/ingredient_alias.csv` · `seeds/ingredient.csv` 에 넣으세요.
50종이면 못 알아본 것의 약 24%라 인식률이 80.8% → **85.4%** 가 되어 **혼자서도 목표를 넘깁니다.**
애매한 것(참치액이 새 재료인지 액젓의 다른 이름인지 같은 것)만 남겨두면 됩니다.

> ⚠️ **조용히 틀리는 방식**
>
> **시트를 채웠는데 `make seed` 를 안 돌려서 데이터베이스 사전이 그대로인 것.**
> 재정리가 **옛 사전으로** 돌아서 인식률이 안 오릅니다 — 에러가 아니라
> **"검수했는데 별로 안 올랐네"** 로 보입니다.
> A-11의 한 줄 명령이 이걸 구조적으로 막습니다.

## A-11 — 재정리 한 줄 명령 — `make renormalize`

**기간** 0.5일 · **먼저** A-4, A-10

**무엇을**

검수 결과가 실제 추천까지 반영되는 길을 **한 줄로 고정**합니다.

```
검수 반영 → 시드 검증 → DB 반영 → 재료 정리(전량) → 특성 만들기 → 맛 평균 재계산 → 검사
```

각 단계 전에 이전 값을 저장해 두고, **마지막에 전/후 인식률을 나란히 출력**합니다.

길 자체는 이미 설계돼 있습니다 — 시드 파일이 원본이고, 검수 반영기가 결과를
'다른 이름'·'재료 아님'·'새 재료' 세 갈래로 나눠줍니다.
**A는 그걸 끊기지 않게 잇기만 하면 됩니다.**

**완료 기준**

`make renormalize` 가 한 번에 완주하고 마지막에 이런 식으로 찍습니다.

```
mention 0.808 → 0.894
```

**인식률이 떨어지면 실패로 끝내세요** (검수가 잘못됐다는 뜻입니다).
그리고 아무것도 안 채운 시트로 돌리면 인식률 그대로 + 정상 종료여야 합니다.

**막히면**

없습니다.

> ⚠️ **조용히 틀리는 방식**
>
> **재료 표만 다시 만들고 특성 표를 다시 안 만드는 것.**
> 추천이 읽는 건 **특성 표 하나뿐**이라, 화면은 **옛날 값으로 멀쩡히 돕니다.**
> 두 표가 어긋났다는 사실은 **어떤 조회로도 알 수 없습니다.**
> 그래서 재정리를 두 명령으로 쪼개지 않고 **하나로 묶습니다 — 사람이 반만 실행할 수 없게.**

## A-12 — 비슷한 레시피 묶기

**기간** 1일 · **먼저** A-4 (필수 재료 목록이 필요)

**무엇을**

**"이건 나중으로 미뤄도 되나?"에 대한 답: 안 됩니다.** 근거가 둘입니다.

**① 원래 계획대로는 아예 불가능합니다.** 레시피 내용을 숫자로 바꾸는 코드가 저장소
어디에도 없고 필요한 도구도 안 깔려 있습니다. 그 모델을 새로 돌리는 건 3주 안에 안 들어갑니다.

**② 대신 쓸 만한 분류축도 죽어 있습니다.** 요리 종류·주재료 분류 칸이 실측 **0건**이고,
원문 태그는 46,353건에 **고유 태그가 45,529종** — 레시피마다 하나뿐인 검색 키워드
('미소라면', '챠슈라멘')라 분류로 쓸 수 없습니다. **25.8%(11,956건)는 태그가 아예 없습니다.**

→ 이걸 안 하면 **추천 결과에 다양성을 주는 장치가 하나도 없게 됩니다.**

**그래서 싼 버전으로 합니다.** 라이브러리 없이 30줄이면 됩니다.

```
필수 재료 목록(536종 있음/없음) → 흔한 재료 비중 낮추기 → 48차원으로 압축
   ⊕ 평균 뺀 맛 6축
→ 50개 묶음으로 나누기, 시드 고정
```

묶음 방식에 `v1-tfidf-svd48` 같은 **이름표를 붙여** 나중에 제대로 된 판과 구분되게 합니다.

**완료 기준**

```sql
SELECT count(*) FROM recipe_feature WHERE cluster_id IS NULL;   -- 0
SELECT max(c)::real/46353 FROM
  (SELECT count(*) c FROM recipe_feature GROUP BY cluster_id) t;  -- 0.15 미만
```

- 묶음이 안 배정된 레시피 0건
- 한 묶음이 전체의 **15%를 넘지 않을 것** (넘으면 쏠린 겁니다)
- 빈 묶음 0개 (서로 다른 묶음이 정확히 50개)
- **같은 시드로 두 번 돌려서 배정이 100% 일치**
- **🔴 묶음 10개를 골라 제목 5개씩 눈으로 보고, 그 결과를 출력에 포함**

**막히면**

A-4가 늦으면 정리된 재료 표만으로 시제품을 만드세요(있음/없음 표는 거기서 바로 만들 수 있습니다).
정 안 되면 묶음을 비워두고 **B에게 알리세요** — 조회 쪽에 비었을 때의 대안이 이미 있어서
깨지지는 않습니다. 다만 **다양성이 0이 된다는 사실을 명시적으로 넘기세요.**

> ⚠️ **조용히 틀리는 방식**
>
> **묶음이 '재료 개수'로 갈리는 것.**
> 길이를 맞추는 처리를 빼면 **재료 12개짜리 레시피끼리 한 묶음**이 됩니다.
> 그런데 균형 지표(최대 비중 15% 미만, 빈 묶음 0)는 **오히려 좋아 보이고**
> 다양성 지표도 올라갑니다 — **지표가 전부 초록인데 의미는 없습니다.**
> **묶음별 대표 제목을 눈으로 보는 것이 유일한 방어입니다.**
>
> 두 번째: **이름표를 안 남기고 다시 묶는 것.**
> 과거 기록의 묶음 번호가 다른 것을 가리키게 되어, **B가 쌓아온 학습이 조용히 오염됩니다.**

## 만들지 않는 것과 그 이유

B와 C가 "왜 여기가 비어 있지?" 하고 묻게 될 것들입니다. **미룬 게 아니라 재료가 없습니다.**

| 무엇 | 왜 못 만드나 |
|---|---|
| 레시피 내용을 숫자로 바꾼 값 | 그걸 만드는 코드가 저장소에 없고, 필요한 도구도 안 깔려 있음 |
| 요리 종류·요리 형태 분류 | **원본에 분류축 자체가 없음** — 태그는 45,529종으로 사실상 레시피마다 하나뿐 |
| 계절 정보 | 월별 데이터 원천이 없음 |
| 영양 정보 | 원본에 없음 |
| 품질 점수 | **평점이 0건** — 크롤에 평점이 아예 안 들어 있음 |

B는 이 다섯 개를 "없음"으로 받고 **점수 비중은 그대로 둡니다.**

**A가 실제로 공급하는 것**은 이렇습니다 — 재료 충족도, 맛 유사도, 재료 궁합,
인기도, 부족한 재료 수, 조리 시간 적합도, 유통기한 임박 재료 활용.

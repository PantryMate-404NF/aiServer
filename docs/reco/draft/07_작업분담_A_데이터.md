## A-4 — recipe_feature 빌더 — 배열 · n_* (essential 규칙 확정)

> ✅ **결정됨 ([D-10](05_작업분담_결정사항.md)).** 필수재료 0개(7.2%)는
> `n_unmatched / (n_total + n_unmatched) > 0.3` 이면 **정규화 실패로 보고 제외**한다.
> 임계값 0.3 은 임시값 — 실제 분포를 보고 조정한다(소급 가능).
> 🔴 품질 보고 시 **정상과 실패를 따로 센다.**

**기간** 1일

**무엇을**

app/services/normalize/feature_build.py. recipe_ingredient + ingredient + recipe 를 읽어 recipe_feature 를 채운다.

🔴 is_staple 39종 규칙 — 확인 결과: P4 가 이미 R3_is_staple 로 staple 을 SEASONING 에 보낸다. 그런데 39종 중 24종만 is_seasoning 과 겹치고(간장·소금·설탕류), **15종은 is_staple 로만 걸린다**: 쌀·밀가루·전분·참깨·물·생수·정수물·수돗물·찬물·냉수·뜨거운물·온수·끓는물·미지근한물·얼음. 그래서 **두 겹으로 건다** — SQL 에서도 `role='essential' AND NOT i.is_staple`. P4 만 믿으면 검수 alias 나 manual override 가 role 을 바꿨을 때 물·쌀이 essential_ids 에 들어간다.

- essential_ids: role='essential' AND NOT is_staple
- all_ids: 전부. 🔴 단 is_non_ingredient(도마 ×2,259 · 냄비 등, 실측 파싱분의 5.8%)는 제외 — 알러지 하드컷(`all_ids && allergy_ids`)의 분모에 조리도구가 섞이면 안 된다
- category_ids: DISTINCT ingredient.category_id
- n_essential / n_total / **n_unmatched**(P3 미매칭 수, 반드시 채운다) / cook_minutes · difficulty 복사
- recipe.status 를 'raw' → 'normalized' 로 (지금 46,353건 전부 'raw')

**완료 기준**

make feature-build 후 SQL 6줄이 전부 통과: ① count(*)=46,353 ② `SELECT count(*) FROM recipe_feature rf WHERE EXISTS(SELECT 1 FROM ingredient i WHERE i.is_staple AND i.id = ANY(rf.essential_ids))` = **0** ③ n_total = cardinality(all_ids) 전행 일치 ④ n_essential ≤ n_total 전행 ⑤ sum(n_unmatched) > 0 (0이면 안 채운 것) ⑥ avg(n_essential) 이 2.7~3.3 (실측 2.99 · 중앙값 3).

**선행** A-3

**막히면** A-3 부분 적재분으로 빌더를 만들고 전량은 나중에 다시 돌린다 — 빌더는 멱등이라 비용이 없다.

> ⚠️ **조용히 틀리는 방식**
>
> **n_essential=0 이 7.2%(약 3,340건)** 다(실측). retrieve_candidates 는 이걸 `CASE WHEN n_essential=0 THEN 1.0` 로 coverage 만점을 주고, `cardinality(essential_ids)=0` 전용 인덱스로 항상 후보에 넣는다. 여기엔 정상(간장계란밥)과 **정규화 실패**가 섞여 있는데 구분할 방법이 없다 — Top-20 이 전부 이것으로 채워져도 에러가 안 난다. n_unmatched/(n_total+n_unmatched) 로 갈라 두 숫자를 따로 보고해야 한다. 그리고 n_total=0 인 90건(0.2%)은 ⓪ 게이트가 잡지만, 12개 중 11개를 놓친 레시피는 통과한다 — 스키마 주석이 정확히 경고한 상황이다.

## A-6 — popularity_score · quality_score — 분포를 보고 정하기

> ✅ **결정됨 ([D-9](05_작업분담_결정사항.md)).** 인기도는 **`recipe.review_count`**
> (크롤 원문 개수 627,605) 로 계산한다. 실적재 행수(624,422)를 쓰면 후기 파싱
> 규칙이 바뀔 때마다 인기도가 흔들린다. `log1p` 후 **순위 / N**. 🔴 `percent_rank` 가 아니라
> `row_number() OVER (ORDER BY ln(1+review_count), id)` 다 — `percent_rank` 는
> 동점 블록이 8,470건이라 3분위가 비고, 후보 500컷이 비결정적이 되어
> **propensity 재현이 깨진다.**

**기간** 0.5일

**무엇을**

실측 review_count 분포(46,353건): min 0 · max 1,079 · 평균 13.54 · p50 **4** · p90 25 · p99 181 · 0건인 레시피 단 1개.
→ 꼬리가 극단적이다(p50 4 vs max 1,079). min-max 정규화를 쓰면 상위 1%가 나머지 전부를 0.02 근처로 눌러 버려 popularity 가 사실상 이진 피처가 된다. **log1p 후 백분위 순위(rank/N)** 를 쓴다 — 0~1 균등이 보장되고 f_popularity(w=0.10)가 순위를 실제로 만든다.

🔴 quality_score 는 **재료가 없다.** 실측: rating_avg NOT NULL 0건 · rating_count>0 0건 · view_count>0 0건. 크롤에 평점이 아예 없다. DEFAULT_WEIGHTS 에서 f_quality 는 w=0.0 이므로 **0 으로 두고 그 이유를 컬럼 COMMENT 와 배치 로그에 남긴다.** 후기 개수로 만들면 popularity 와 상관계수 1.0 인 가짜 축이 하나 늘 뿐이다.

**완료 기준**

psql 한 줄: `SELECT min(popularity_score), max(popularity_score), corr(popularity_score, ln(1+r.review_count)) FROM recipe_feature f JOIN recipe r USING(recipe_id)` → min≈0 · max≈1 · **Pearson corr ≥ 0.92**.
🔴 0.99 를 요구하면 어떤 구현도 통과 못 한다 — 실측 percent_rank 0.9264 ·
cume_dist 0.9347 · row_number 0.9242 · min-max 0.6532. 백분위 순위는 원값을
등간격으로 펴므로 로그값과의 **선형** 상관이 1 이 될 수 없다. 순위상관을 보려면
`corr` 대신 순위끼리 재야 하고 그때는 0.99 를 넘는다. 그리고 10분위 히스토그램이 각 구간 4,600±500 (백분위 순위이므로 균등해야 한다). quality_score 는 `SELECT count(*) FROM recipe_feature WHERE quality_score <> 0` = 0.

**선행** A-4

**막히면** 없음 — recipe.review_count 만 있으면 되므로 A-4 와 병행 가능.

> ⚠️ **조용히 틀리는 방식**
>
> **두 개의 review_count 가 있다.** recipe.review_count 는 로더가 `len(d["reviews"])` 로 넣은 원문 개수(627,610 기준)이고, recipe_review 실적재는 624,422 건이다(파싱 99.14%, 본문 빈 것 제외). 어느 쪽으로 정규화했는지 안 적으면 나중에 아무도 재현 못 한다 — 값은 둘 다 그럴듯해서 틀린 걸 알아채지 못한다. 그리고 백분위 순위는 **코퍼스가 늘면 전부 바뀐다.** 크롤을 추가하면 과거 점수가 재현 불가가 되므로 popularity 계산 시점의 n_recipes 를 batch_run.params 에 남긴다.

① content_emb 를 만드는 코드가 저장소 어디에도 없다 — sentence-transformers·sklearn 미설치(numpy 2.5.2 만 있음), ko-SBERT 배치는 3주에 안 들어간다. 그래서 설계대로의 k-means 는 **불가능**하다.
② 대체 다양성 축인 분류축도 죽어 있다 — recipe.dish_type/cuisine/main_ing_cat 실측 NOT NULL **0건**이고, raw_json.categories 는 46,353건에 고유 태그 45,529종(사실상 레시피당 유일한 SEO 키워드: '미소라면','챠슈라멘')이라 분류축이 아니다. 25.8%(11,956건)는 태그가 아예 없다.
→ cluster_id 가 없으면 ③ 재랭킹에 다양성 축이 **하나도** 없다. scripts/reco/bench/kmeans_worth_it 이 비교 대상으로 삼은 '분류축 캡' 폴백 자체가 존재하지 않는다.

그래서 **싼 버전으로 한다**: essential_ids 멀티핫(536차) → TF-IDF → numpy SVD 48차 ⊕ 중심화 flavor_vec(6) → Lloyd K=50, 고정 시드. sklearn 없이 30줄. cluster_version='v1-tfidf-svd48' 로 기록해 나중에 content_emb 판과 구분되게 한다.

**완료 기준**

psql: `SELECT count(*) FROM recipe_feature WHERE cluster_id IS NULL` = 0. `SELECT max(c)::real/46353 FROM (SELECT count(*) c FROM recipe_feature GROUP BY cluster_id) t` < 0.15 (한 클러스터가 15% 넘으면 편중). 빈 클러스터 0개(count(DISTINCT cluster_id)=50). 같은 시드로 두 번 돌려 배정 100% 일치. **그리고 클러스터 10개를 골라 제목 5개씩 눈으로 본다** — 출력에 포함.

**선행** A-4 (essential_ids 필요)

**막히면** A-4 가 늦으면 recipe_ingredient 만으로 프로토타입(멀티핫은 recipe_ingredient 에서 바로 만든다). 정 안 되면 cluster_id NULL 로 두고 B 에 통보 — retrieval.py 가 이미 NULL→균등탐색 폴백을 하므로 깨지지는 않는다. 다만 ③ 의 다양성이 0 이 된다는 사실을 명시적으로 넘긴다.

> ⚠️ **조용히 틀리는 방식**
>
> 클러스터가 **'재료 개수'로 갈리는 것.** TF-IDF 의 L2 정규화를 빼면 재료 12개짜리 레시피끼리 한 클러스터가 된다. 균형 지표(최대 비중 <15%, 빈 클러스터 0)는 오히려 좋아 보이고 ILD 도 올라간다 — 다양성 지표가 전부 초록인데 의미는 없다. 클러스터별 대표 제목을 눈으로 보는 것이 유일한 방어다. 두 번째: cluster_version 을 안 남기고 재클러스터링하면 과거 로그의 cluster_id 가 다른 것을 가리키게 되어 Thompson belief 가 조용히 오염된다.


## A-14 — 🔴 `ingredient.freq_count` 채우기

**기간** 0.25일

**무엇을**

`ingredient.freq_count` 가 **536종 전량 0** 이다. 그런데 **B 지시서가 A 를 선행으로
지목한다** — `f_cooccur`(w=0.10)의 IDF 분모와 `00` 문서의 MMR IDF 가 둘 다 여기 묶여 있다.

정규화가 끝나면 한 문장이면 된다.

```sql
UPDATE ingredient i SET freq_count = c.n
FROM (SELECT ingredient_id, count(DISTINCT recipe_id) n
      FROM recipe_ingredient GROUP BY 1) c
WHERE c.ingredient_id = i.id;
```

**완료 기준**

`SELECT count(*) FILTER (WHERE freq_count > 0), count(*) FROM ingredient`
→ 앞 값이 400 이상. 그리고 상위 5종이 상식과 맞는가 눈으로 확인
(소금·간장·설탕 류가 위에 와야 한다).

**선행** A-3 (정규화 결과가 있어야 센다)

**막히면** B 에게 **지금 0 이라는 사실을 알린다.** B 가 모르면 가중 자카드가
그냥 자카드로 조용히 퇴화한 채 돈다.

> ⚠️ **조용히 틀리는 방식**
>
> IDF 는 `log(N / freq_count)` 인데 `freq_count = 0` 이면 0 나눗셈이거나
> (가드가 있으면) IDF 가 상수가 된다. 후자면 **모든 재료의 가중치가 같아져**
> 가중 자카드가 그냥 자카드가 된다 — 예외도 안 나고 점수도 정상 범위다.
> "흔한 재료(소금)와 희귀한 재료(트러플)를 구분한다"는 설계 의도만 사라진다.

# 재료 이미지 URL 인수인계

**정하는 것**: 받은 DB 덤프의 `ingredients.image_url` 148건을 채워 원본을 고쳐 돌려드립니다. 어디를 고쳤는지, 출처와 라이선스 표시 의무가 무엇인지, 사람이 무엇을 확인해야 하는지를 정합니다

**적용 대상**: 백엔드(복원과 적재), 프론트(표시와 저작자 표기)

**버전**: 2.1.0 · **최종 수정**: 2026-09-29 · **작성자**: 유재현

---

## 1. 무엇을 드리는가

요청하신 것은 "레시피에는 이미지 주소가 있는데 재료에는 없으니 채워 달라" 였습니다. **148건 전부 채웠습니다.**

**드리는 것은 받은 덤프 그 자체입니다.** 별도 파일이 아니라 **보내 주신 덤프의 `image_url` 칸을 직접 고쳐** 돌려드립니다. 받으시면 평소 하시던 복원 절차를 그대로 밟으시면 되고, 저희 쪽 파일을 따로 합치실 일이 없습니다.

이미지의 목적은 **사용자가 레시피를 볼 때 "양파" 를 알아볼 수 있는 참고 이미지**입니다(2026-09-29 유재현). 상품 사진이 아니어도 되고, 그 재료를 알아볼 수 있으면 충분합니다. 아래 고른 기준이 그것입니다.

함께 드리는 참고 파일이 셋 있습니다. 덤프와 달리 이것들은 적재 대상이 아닙니다.

| 파일 | 무엇 |
|---|---|
| `licenses.csv` | 148건의 라이선스와 저작자. **표시 의무가 있어 프론트에 이 파일이 필요합니다**(4절) |
| `report.md` | 수집 결과 요약과 사람이 확인할 목록 |
| `preview.html` | **브라우저로 열어 148칸을 눈으로 확인하는 페이지.** 테두리가 있는 칸이 확인 대상입니다 |

## 2. 정확히 무엇을 고쳤는가

**두 자리를 고쳤습니다. 같은 값입니다.**

| 고친 파일 | 어디 | 건수 |
|---|---|---|
| `csv/ingredients.csv` | `image_url` 칸 | 148 |
| `pantry_recipe_domain_dump.sql` | `COPY public.ingredients (...)` 블록의 네 번째 값 | 148 |

**둘 다 고친 이유**는 보내 주신 README 3절이 `.sql` 로 복원하라고 적고 있기 때문입니다. CSV 만 고치면 복원한 DB 의 `image_url` 이 그대로 비어 있습니다 — 에러가 나지 않고 화면만 비어 다들 늦게 알아챕니다.

**칸을 새로 만들지는 않았습니다.** `ingredients` 표에는 `image_url character varying(500)` 이 이미 있었고 값만 `\N` 이었습니다. 그래서 DDL 은 한 글자도 건드리지 않았습니다. 기존 스키마 그대로 복원됩니다.

**`image_url` 말고는 아무것도 바뀌지 않았습니다.** 확인한 것은 다음과 같습니다.

- 행 수 148건 그대로, 행 순서 그대로, 칸 이름 그대로입니다. 백업본과 전 행을 대조해 `image_url` 밖에 바뀐 칸이 없음을 확인했습니다.
- 다른 네 표(`recipes` · `recipe_ingredients` · `recipe_steps` · `recipe_scraps`)의 CSV 는 파일을 열지도 않았습니다. SQL 안의 네 COPY 블록도 값 개수와 종료 표시를 대조해 그대로임을 확인했습니다.
- 서식을 지켰습니다 — LF 줄바꿈, BOM 없는 UTF-8, 따옴표 규칙 동일. 쓰기 전에 **아무것도 바꾸지 않고 다시 쓴 결과가 원본과 바이트까지 같은지** 먼저 확인하고, 다르면 쓰지 않도록 했습니다.
- 주소는 가장 긴 것이 240자라 `varchar(500)` 에 들어갑니다. 탭 · 줄바꿈 · 쉼표 · 따옴표가 든 주소는 0건이라 어느 서식도 깨지지 않습니다.

커진 만큼이 채운 주소입니다. CSV 는 11,074 → 26,886 바이트, SQL 은 37,596,497 → 37,612,013 바이트입니다.

**받은 원본 그대로의 사본**은 저희 쪽 `data/backup/pantry_recipe_domain_dump_원본_20260929/` 에 있습니다. 되돌리셔야 하면 말씀해 주십시오.

**CSV 편집기에서 주소를 클릭하면 열리지 않습니다. 데이터 문제가 아닙니다.** 편집기가 주소를 알아볼 때 쉼표를 주소의 일부로 보아 **뒤 칸까지 붙여서** 부릅니다. 찹쌀가루(id 105)로 예를 들면 이렇습니다.

| 부른 주소 | 결과 |
|---|---|
| `.../0/04/%EC%B0%B9%EC%8C%80.JPG` (저장된 값) | 200 · `image/jpeg` · 72,634바이트 |
| `.../0/04/%EC%B0%B9%EC%8C%80.JPG,ROOM_TEMP,365,180,2026-09-20` | 404 |

뒤에 붙은 것은 `default_storage_type` 부터 `created_at` 까지의 칸입니다. 주소를 확인하실 때는 칸 값만 복사해 주소창에 붙여 넣으시고, **148칸을 한눈에 보시려면 `preview.html` 을 브라우저로 여십시오.** 주소창에 한글 파일명이 보이는 것도 정상입니다 — 저장된 값은 퍼센트 인코딩되어 있고(한글이 그대로 든 주소 0건), 브라우저가 보기 좋게 되돌려 보여 주는 것뿐입니다.

전달 직전에 **148건 전부 다시 불러 확인했습니다**(2026-09-29). 148건 모두 200 이고 `image/*` 로 응답합니다.

이미 복원해 두신 DB 에 값만 넣으실 거라면 CSV 로 이렇게 하셔도 같습니다.

```sql
-- ingredient_id 로 맞춰 image_url 만 갱신합니다
UPDATE ingredients SET image_url = :image_url WHERE ingredient_id = :ingredient_id;
```

## 3. 어디서 가져왔는가 — 만개의레시피가 아닙니다

**레시피와 같은 곳에서 가져오지 못했습니다.** 레시피의 `thumbnail_url` 은 만개의레시피 CDN(`recipe1.ezmember.co.kr`)인데, **그 사이트에는 재료 페이지가 없습니다**(2026-09-29 확인). 거기 있는 것은 요리 사진뿐이라, "마늘" 로 검색해 나온 썸네일을 쓰면 마늘이 아니라 마늘장아찌 사진이 들어갑니다. 에러는 나지 않고 화면만 틀리므로 쓰지 않았습니다.

**오아시스마켓 상품 사진도 쓰지 않았습니다.** 저장소에 이미 있습니다 — `products` 표에 `ingredient_id` 매핑과 오아시스 CDN 썸네일 4,771건이 들어 있고(`pentry-db-package_v2`), 그것으로 148건 가운데 137건을 채울 수 있었습니다. 쓰지 않기로 한 것은 **2026-09-29 유재현의 결정**입니다 — 필요한 것이 상품이 아니라 "그 재료를 알아볼 수 있는 참고 이미지" 라서 상품 데이터에 묶이지 않는 편이 낫다는 판단입니다. 뒤에 이 문서를 보고 "오아시스 데이터를 못 찾아서 위키미디어를 썼구나" 로 읽지 않으시도록 적어 둡니다.

대신 **위키미디어**에서 가져왔습니다. 한국어 위키백과 문서의 대표 이미지를 받아, 그 원본이 있는 위키미디어 공용의 주소(`upload.wikimedia.org` · `thumb.wikimedia.org`)를 넣었습니다. 고른 이유는 셋입니다.

- **자유 라이선스**라 제품에 실을 수 있습니다. 상용 이미지를 긁어 쓰면 나중에 내려야 합니다.
- 주소가 안정적이고 키가 필요 없습니다.
- 폭 960px 썸네일이라 원본(수 MB)을 그대로 부르지 않습니다.

## 4. 반드시 지켜야 하는 것 — 저작자 표시

**대부분의 이미지에 표시 의무가 있습니다.** 148건 가운데 표시 없이 쓸 수 있는 것은 44건뿐이고, 나머지 **104건은 저작자와 라이선스를 적어야 합니다.** 적지 않으면 라이선스 위반입니다.

| 라이선스 | 건수 | 표시 의무 |
|---|---|---|
| CC BY-SA (1.0~4.0, kr · fi 포함) | 80 | 있음 |
| Public domain · CC0 · Copyrighted free use | 44 | 없음 |
| CC BY (1.0~4.0) | 20 | 있음 |
| GFDL 1.2 | 3 | 있음 |
| KOGL Type 1 | 1 | 있음 |

`licenses.csv` 에 재료마다 `license` · `artist` · `credit_url` 이 있습니다.

**다만 열두 건은 저작자 칸이 비어 있습니다** — 공용 쪽 파일 설명에 저작자가 적혀 있지 않은 것들입니다(양파 · 당근 · 마요네즈 · 오이 · 멸치 · 표고버섯 · 식빵 · 베이킹파우더 · 햄 · 바지락 · 바나나 · 굴). 표시 의무는 그대로이므로, 그 열둘은 `credit_url`(공용 파일 페이지)을 대신 걸어 주시면 됩니다. 화면 어디에 적을지는 프론트가 정하시면 되고, 흔한 방법은 이미지 상세나 설정의 "이미지 출처" 목록에 한 번에 적는 것입니다. 재료 칸마다 적을 필요는 없습니다.

**직접 내려받아 우리 서버에 두실 생각이면** 라이선스는 그대로 따라갑니다(표시 의무도 그대로). CC BY-SA 는 2차 저작물에 같은 조건을 요구하므로, 이미지를 자르거나 합성하실 계획이면 그 조건을 먼저 보셔야 합니다.

## 5. 문서가 없어 같은 갈래로 대신한 셋

백과 문서가 그 재료를 직접 다루지 않아, **알아볼 수 있으면 된다**는 기준으로 같은 갈래의 사진을 넣었습니다. 정확한 상품 사진이 필요해지면 이 셋부터 바꾸십시오.

| 재료 | 무엇을 넣었나 | 왜 |
|---|---|---|
| 올리고당 | 옥수수시럽 | 백과 문서가 화학(소당류)이라 분자 구조식뿐입니다. 같은 선반의 액상 감미료입니다 |
| 허브솔트 | 허브를 섞은 양념 소금 | 상표를 섞은 양념이라 백과 문서가 없습니다 |
| 물엿 | 엿기름 물엿 | "엿" 문서의 대표 이미지가 엿 막대(고체)였습니다. 물엿은 액체입니다 |

## 6. 사람이 한 번 봐 주실 것

기계는 문서가 그 재료를 가리키는지 모릅니다. 아래 둘만 확인해 주시면 됩니다.

**(1) 이름과 다른 문서에서 가져온 것 — `report.md` 의 마지막 표(58건).** 대부분은 표준 표기 차이라 문제가 없습니다(요거트 → 요구르트, 소고기 → 쇠고기, 팽이버섯 → 팽나무버섯). 저희가 이미 고친 것도 있습니다 — 카레는 문서 대표 이미지가 **고료카쿠 타워(건물)** 였고, 이스트는 **효모의 현미경 사진**, 달걀은 **계란프라이**, 토마토소스는 **스파게티 접시**, 마늘은 1793년 식물 삽화였습니다. 전부 손으로 고른 사진으로 바꿨습니다.

**(2) 같은 이미지를 쓰는 재료 — 6묶음 13건.** 뜻이 겹쳐 같은 사진이 들어갔습니다. 화면에서 구분이 필요하면 알려 주십시오.

## 7. 다시 만드는 법

두 단계입니다. 재료가 늘면 그대로 다시 돌리면 됩니다.

```bash
# 1) 주소를 모읍니다 → data/ingredient_images/{ingredients,licenses}.csv, report.md, preview.html
PYTHONUTF8=1 uv run python scripts/crawl_ingredient_images.py

# 2) 덤프 원본에 써 넣습니다. --write 가 없으면 무엇을 고칠지만 알려 주고 쓰지 않습니다
PYTHONUTF8=1 uv run python scripts/apply_ingredient_images_to_dump.py
PYTHONUTF8=1 uv run python scripts/apply_ingredient_images_to_dump.py --write
```

1단계가 하는 일은 넷입니다.

1. 재료명(동의어가 있으면 그쪽) → 영어 문서 → 검색 순으로 문서를 찾고, 문서로는 맞는 사진이 안 나오는 것은 **손으로 고른 파일 표**를 씁니다(스크립트 위쪽의 `COMMONS_FILES`).
2. 받은 주소마다 **HEAD 로 실제 이미지인지 확인**합니다. 확인에 실패하면 채우지 않습니다.
3. 라이선스와 저작자를 함께 받아 적습니다.
4. 못 찾은 것은 빈 칸으로 두고 사유를 보고서에 적습니다.

상대 서버에는 배치 조회(한 번에 50건)와 호출 간격(1초)으로 요청합니다. `robots.txt` 는 확인했습니다.

2단계는 쓰기 전에 무변경 왕복이 바이트까지 같은지 보고, 쓴 뒤에는 백업본과 전 행을 대조합니다. 어느 쪽이든 어긋나면 쓰지 않고 멈춥니다.

## 8. 저희가 판단하지 않은 것

- **`recipe_ingredients` 에도 이미지 주소를 둘지**는 정하지 않았습니다. 지금은 `ingredients` 한 곳에만 있고, 레시피 화면에서는 `ingredient_id` 로 조인해 쓰시면 됩니다. 179,603행에 주소를 복사해 두면 조인이 없어지는 대신 표가 커지고 값이 두 곳으로 갈라집니다. 그쪽이 낫다고 보시면 말씀해 주십시오. 그 표는 칸이 실제로 새로 생기는 것이라 DDL 도 함께 바뀝니다.
- **이미지를 우리 서버에 옮길지**는 정하지 않았습니다. 지금 값은 위키미디어를 직접 가리킵니다. 외부 주소라 그쪽이 파일을 지우면 깨지고, 트래픽도 그쪽으로 갑니다. 안정성이 필요하면 받아서 우리 저장소에 두는 편이 낫고 그때도 라이선스는 따라갑니다.
- **화면에 맞는 크기**는 960px 하나로만 드렸습니다. 작은 이미지가 필요하시면 아래를 보십시오.

주소는 두 가지가 섞여 있습니다.

| 모양 | 건수 | 크기를 바꿀 수 있나 |
|---|---|---|
| `.../thumb/…/960px-이름.jpg` (썸네일) | 97 | 됩니다. `960px` 을 **120 · 250 · 330 · 500 · 1280** 중 하나로 바꿉니다 |
| `.../commons/…/이름.jpg` (원본) | 51 | 안 됩니다. 원본이 이미 960px 이하라 썸네일이 만들어지지 않은 것들입니다 |

**임의의 숫자는 400 으로 거부됩니다**(2026-09-29 확인 — 320 · 400 · 640 · 800 전부 거부, 허용 목록만 됩니다). 목록용으로는 250px 이나 330px 을 쓰시고, 원본 주소 51건은 그대로 두시면 됩니다. 크기를 통일해야 하면 받아서 우리 쪽에서 줄이는 편이 확실합니다.
